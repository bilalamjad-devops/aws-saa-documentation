4. Question

Category: CSAA – Design Secure Architectures

A travel photo-sharing website is using Amazon S3 to serve high-quality photos to visitors. After a few days, it was discovered that other travel websites are linking to and using these photos. This has resulted in financial losses for the business. The team initially applied PutBucketPolicy with referrer restrictions, but found that referrer headers can be spoofed, rendering this approach insufficient.

What is the MOST effective method to mitigate this issue?

- Block the IP addresses of the offending websites using NACL.
- Use Amazon CloudFront distributions for your photos.
- Configure your S3 bucket to remove public read access and use pre-signed URLs with expiry dates.
- Move the high-quality photos to Amazon WorkDocs to serve them privately.

This is a classic **AWS exam trap** because it mixes **hotlinking**, **CloudFront**, and **S3 Presigned URLs**.

---

# Step 1: Simplify the Question

The company has this architecture:

```text
Visitors
     │
     ▼
   S3 Bucket
   (Public Photos)
```

People can access photos normally.

But another website is doing this:

```html
<img src="https://mybucket.s3.amazonaws.com/photo1.jpg">
```

They are **not downloading the photo and uploading it again**.

Instead, they are using **your S3 URL**.

When visitors open their website:

```
Their Website
      │
      ▼
Your S3 Bucket
```

Your S3 bucket pays the bandwidth cost.

This is called **hotlinking**.

---

# Step 2: What did they already try?

They used:

**Bucket Policy with Referer restriction**

Example:

```
Only allow:

www.mytravel.com
```

Problem:

HTTP Referer header can be faked (spoofed).

So AWS says this is **not secure enough**.

---

# Step 3: What are they asking?

They're asking:

> "What's the MOST effective solution?"

Notice they are **not asking for faster content delivery**.

They are asking:

> How do we stop unauthorized websites from using our photos?

---

# Option A

### Block IP addresses

❌ Bad idea

Today:

```
Website A

IP:
1.1.1.1
```

Tomorrow:

```
2.2.2.2
```

Attackers can change IPs.

Not scalable.

---

# Option B

### Use CloudFront

Many students choose this.

But CloudFront **by itself** only does:

* caching
* CDN
* global delivery

It **does not stop people from embedding your images**.

If CloudFront is public:

```
CloudFront URL

Everyone can still access it.
```

CloudFront only becomes secure if you add:

* Signed URLs
* Signed Cookies
* OAC

The question doesn't mention any of those.

So CloudFront alone isn't the answer.

---

# Option C ✅

Remove public access.

Keep objects private.

Generate **Presigned URLs**.

Example:

Instead of:

```
https://bucket.s3.amazonaws.com/photo.jpg
```

Generate:

```
https://bucket.s3.amazonaws.com/photo.jpg
?X-Amz-Signature=...
&Expires=3600
```

After 1 hour:

```
URL expires

No access
```

Now another website cannot permanently hotlink your image because:

* URL expires
* Bucket is private
* Only your application generates valid URLs

Exactly what the company wants.

---

# Option D

Move to WorkDocs

❌ Completely unrelated.

WorkDocs is like Google Drive or SharePoint.

Not for serving website images.

---

# Why not CloudFront?

This is the important exam lesson.

CloudFront **does not automatically provide security**.

CloudFront provides:

* CDN
* caching
* edge locations

To make CloudFront secure, you'd also need:

* Signed URLs
* Signed Cookies
* OAC

Since none of these are mentioned, CloudFront alone doesn't solve the problem.

# Exam Tip

If you see:

> Public S3 objects are being abused

Think:

✅ Make S3 private

✅ Presigned URL

---

If you see:

> CloudFront serves private content

Think:

✅ Signed URL

✅ Signed Cookies

✅ OAC

---

# Summary

| Requirement                                    | Best Solution                       |
| ---------------------------------------------- | ----------------------------------- |
| Temporary access to a private S3 object        | **S3 Presigned URL**                |
| Prevent public S3 hotlinking                   | **Private bucket + Presigned URLs** |
| Private content through CloudFront             | **CloudFront Signed URL/Cookies**   |
| Prevent direct S3 access when using CloudFront | **Origin Access Control (OAC)**     |
| Speed up global content delivery               | **CloudFront**                      |

### 🔑 Memory Trick

* **S3 Presigned URL** → "I want to share **one private S3 object temporarily**."
* **CloudFront Signed URL/Cookies** → "I want to protect **content served through CloudFront**."
* **OAC** → "I want **CloudFront to be the only service that can read from S3**."
