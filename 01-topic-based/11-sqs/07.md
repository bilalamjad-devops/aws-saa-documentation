7. Question

Category: CSAA – Design High-Performing Architectures

A company has a web-based ticketing service that utilizes Amazon SQS and a fleet of EC2 instances. The EC2 instances that consume messages from the SQS queue are configured to poll the queue as often as possible to keep end-to-end throughput as high as possible. The Solutions Architect noticed that polling the queue in tight loops is using unnecessary CPU cycles, resulting in increased operational costs due to empty responses.

In this scenario, what should the Solutions Architect do to make the system more cost-effective?

- `Configure Amazon SQS to use long polling by setting the ReceiveMessageWaitTimeSeconds to a number greater than zero.`
- Configure Amazon SQS to use long polling by setting the ReceiveMessageWaitTimeSeconds to zero.
- Configure Amazon SQS to use short polling by setting the ReceiveMessageWaitTimeSeconds to a number greater than zero.
- Configure Amazon SQS to use short polling by setting the ReceiveMessageWaitTimeSeconds to zero.

You have:

```text
Producer
     ↓
   SQS Queue
     ↓
EC2 Workers
```

The EC2 instances keep asking SQS:

> "Any messages?"

SQS replies:

> "No."

One second later...

> "Any messages?"

Again...

> "No."

Again...

> "No."

Again...

> "No."

This constant checking wastes:

* CPU
* API calls
* Money

The question says:

> **Empty responses are increasing costs.**

That is your clue.

---

# Short Polling (Default) ❌

Short polling is impatient.

```text
EC2
↓

Any message?

↓

No

↓

Ask again immediately
```

Imagine checking your mailbox every second.

Most of the time:

> Nothing there.

Waste of effort.

---

# Long Polling ✅

Long polling is smarter.

Instead of replying immediately:

```text
EC2
↓

Any message?

↓

(wait...)

(wait...)

(wait...)

Message arrives

↓

Return message
```

SQS waits for a message.

Much fewer empty responses.

Much cheaper.

---

# What is ReceiveMessageWaitTimeSeconds?

This parameter decides:

### 0 seconds

```text
Short Polling
```

Immediate response.

---

### Greater than 0

Example:

```text
20 seconds
```

SQS waits up to 20 seconds.

If a message arrives after 5 seconds:

Return immediately.

If nothing arrives:

Return after 20 seconds.

---

# Why is Long Polling cheaper?

Without Long Polling:

```text
Every second

↓

ReceiveMessage

↓

Empty
```

Thousands of useless API calls.

---

With Long Polling:

```text
ReceiveMessage

↓

Wait

↓

Message arrives

↓

Return
```

Much fewer requests.

Lower AWS bill.

---

# Why are the other answers wrong?

### Long Polling + WaitTime = 0 ❌

0 means:

Short Polling.

---

### Short Polling + WaitTime > 0 ❌

Impossible.

Greater than 0 automatically means Long Polling.

---

### Short Polling + WaitTime = 0 ❌

That's exactly the current problem.

---

---

### Long Polling

Restaurant says:

# Quick Cheat Sheet

| Requirement                         | Answer          |
| ----------------------------------- | --------------- |
| Reduce empty responses              | ✅ Long Polling  |
| Lower SQS cost                      | ✅ Long Polling  |
| Reduce CPU usage                    | ✅ Long Polling  |
| Default polling                     | ✅ Short Polling |
| `ReceiveMessageWaitTimeSeconds = 0` | ✅ Short Polling |
| `ReceiveMessageWaitTimeSeconds > 0` | ✅ Long Polling  |

### One-line memory rule

> **Empty responses + high polling cost = Enable Long Polling (`ReceiveMessageWaitTimeSeconds > 0`).**

# Amazon SQS (Simple Queue Service)

## What is SQS?

Think of a restaurant.

Customer places order → Kitchen is busy.

Instead of shouting directly to the chef, the cashier puts the order on a **queue**.

```
Producer
   |
   v
+---------+
|   SQS   |
+---------+
   |
   v
Consumer
```

Producer = sends message

Consumer = processes message

The queue stores messages until workers are ready.

This is called **decoupling**.

---

# Why use SQS?

Without SQS

```
Web App ----> Worker
```

If worker crashes

❌ Request fails.

---

With SQS

```
Web App
   |
   v
 SQS Queue
   |
   v
 Worker
```

Worker crashes?

No problem.

Message waits in queue.

Another worker processes it later.

---

# Long Polling vs Short Polling

This appears A LOT.

## Short Polling (default)

Worker keeps asking:

```
Any message?

No

Any message?

No

Any message?

No
```

Many empty responses.

Higher cost.

Default:

```
ReceiveMessageWaitTimeSeconds = 0
```

---

## Long Polling

Worker asks:

```
Any message?

(wait...)

(wait...)

Yes!
```

AWS waits before replying.

Benefits

✅ fewer API calls

✅ fewer empty responses

✅ lower cost

Setting

```
ReceiveMessageWaitTimeSeconds > 0
```

---

Exam trick

Need

* reduce empty responses
* reduce cost
* reduce CPU

Answer

**Long Polling**

---

# Visibility Timeout

Very important.

Example

Queue contains

```
Message A
```

Worker1 receives it.

AWS hides it temporarily.

```
Queue

(Message A invisible)
```

No other worker can process it.

Worker processes.

If successful

```
Delete Message
```

Finished.

---

What if worker crashes?

After timeout

```
Visibility Timeout expires
```

Message becomes visible again.

Worker2 processes it.

---

Remember

Visibility Timeout

≠ delete

It only hides.

Delete happens only after successful processing.

---

# Dead Letter Queue (DLQ)

Suppose message keeps failing.

```
Try 1

Fail

Try 2

Fail

Try 3

Fail
```

Instead of retrying forever

Move message

↓

DLQ

Used to investigate bad messages.

---

# Fanout (SNS + SQS)

One message

Many consumers

```
      SNS
       |
   -----------
   |    |    |
 Queue Queue Queue
```

Every queue receives a copy.

---

Example

Order placed

↓

SNS

↓

Accounting Queue

↓

Shipping Queue

↓

Analytics Queue

Everyone gets the message.

---

# Message Filtering

Suppose messages

```
Car Insurance

Life Insurance

Health Insurance
```

Without filtering

Every queue receives everything.

Bad.

---

With SNS Filter Policy

```
SNS

      |

-------------------------

|          |           |

CarQ     LifeQ     HealthQ
```

Each queue receives only its own messages.

Exam keyword

> Filter Policy

Answer

SNS

---

# Priority Queue?

SQS has NO priority.

You cannot say

```
VIP = High Priority
```

Instead

Create

```
Premium Queue

Free Queue
```

Workers

```
Poll Premium

If empty

↓

Poll Free
```

---

# FIFO Queue

Normal queue

Order isn't guaranteed.

FIFO queue

```
1

2

3

4
```

Always same order.

FIFO also removes duplicates.

Exam keywords

* ordering
* deduplication

Answer

FIFO

---

# Standard Queue

Default queue.

Unlimited throughput.

At least once delivery.

Possible duplicate.

Best for almost everything.

---

# SNS vs SQS

Easy table.

| SNS           | SQS             |
| ------------- | --------------- |
| Push          | Poll            |
| Broadcast     | Queue           |
| One → Many    | One queue       |
| Notifications | Buffer messages |
| Fanout        | Decoupling      |

Remember

SNS = announce

SQS = store
