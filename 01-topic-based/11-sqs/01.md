1. Question

Category: CSAA – Design High-Performing Architectures

A company has a web-based ticketing service that utilizes Amazon SQS and a fleet of EC2 instances. The EC2 instances that consume messages from the SQS queue are configured to poll the queue as often as possible to keep end-to-end throughput as high as possible. The Solutions Architect noticed that polling the queue in tight loops is using unnecessary CPU cycles, resulting in increased operational costs due to empty responses.

In this scenario, what should the Solutions Architect do to make the system more cost-effective?

- `Configure Amazon SQS to use long polling by setting the ReceiveMessageWaitTimeSeconds to a number greater than zero.`
- Configure Amazon SQS to use long polling by setting the ReceiveMessageWaitTimeSeconds to zero.
- Configure Amazon SQS to use short polling by setting the ReceiveMessageWaitTimeSeconds to a number greater than zero.
- Configure Amazon SQS to use short polling by setting the ReceiveMessageWaitTimeSeconds to zero.

---


Excellent! This is **the most common SQS question** in the SAA exam.

---

# Step 1: Understand the scenario

You have:

```text
Producer
     ↓
   SQS Queue
     ↓
EC2 Workers
```

The EC2 instances keep asking SQS:

> "Any messages?"

SQS replies:

> "No."

One second later...

> "Any messages?"

Again...

> "No."

Again...

> "No."

Again...

> "No."

This constant checking wastes:

* CPU
* API calls
* Money

The question says:

> **Empty responses are increasing costs.**

That is your clue.

---

# Short Polling (Default) ❌

Short polling is impatient.

```text
EC2
↓

Any message?

↓

No

↓

Ask again immediately
```

Imagine checking your mailbox every second.

Most of the time:

> Nothing there.

Waste of effort.

---

# Long Polling ✅

Long polling is smarter.

Instead of replying immediately:

```text
EC2
↓

Any message?

↓

(wait...)

(wait...)

(wait...)

Message arrives

↓

Return message
```

SQS waits for a message.

Much fewer empty responses.

Much cheaper.

---

# What is ReceiveMessageWaitTimeSeconds?

This parameter decides:

### 0 seconds

```text
Short Polling
```

Immediate response.

---

### Greater than 0

Example:

```text
20 seconds
```

SQS waits up to 20 seconds.

If a message arrives after 5 seconds:

Return immediately.

If nothing arrives:

Return after 20 seconds.

---

# Why is Long Polling cheaper?

Without Long Polling:

```text
Every second

↓

ReceiveMessage

↓

Empty
```

Thousands of useless API calls.

---

With Long Polling:

```text
ReceiveMessage

↓

Wait

↓

Message arrives

↓

Return
```

Much fewer requests.

Lower AWS bill.

---

# Why are the other answers wrong?

### Long Polling + WaitTime = 0 ❌

0 means:

Short Polling.

---

### Short Polling + WaitTime > 0 ❌

Impossible.

Greater than 0 automatically means Long Polling.

---

### Short Polling + WaitTime = 0 ❌

That's exactly the current problem.

---

# Easy Memory Trick

Imagine ordering food.

### Short Polling

Every minute you ask:

> Is my pizza ready?

No.

One minute later...

Is it ready?

No.

Annoying.

---

### Long Polling

Restaurant says:

> Sit down.
>
> We'll call you when it's ready.

Much smarter.

---

# Exam Keywords

If you see:

* Empty responses
* Too many API calls
* Polling frequently
* Reduce cost
* CPU waste

Immediately think:

✅ **Long Polling**

---

# Quick Cheat Sheet

| Requirement                         | Answer          |
| ----------------------------------- | --------------- |
| Reduce empty responses              | ✅ Long Polling  |
| Lower SQS cost                      | ✅ Long Polling  |
| Reduce CPU usage                    | ✅ Long Polling  |
| Default polling                     | ✅ Short Polling |
| `ReceiveMessageWaitTimeSeconds = 0` | ✅ Short Polling |
| `ReceiveMessageWaitTimeSeconds > 0` | ✅ Long Polling  |

### One-line memory rule

> **Empty responses + high polling cost = Enable Long Polling (`ReceiveMessageWaitTimeSeconds > 0`).**

1. Question

Category: CSAA – Design High-Performing Architectures

A company is using Amazon S3 to store frequently accessed data. When an object is created or deleted, the S3 bucket will send an event notification to the Amazon SQS queue. A solutions architect needs to create a solution that will notify the development and operations team about the created or deleted objects.

Which of the following would satisfy this requirement?

- Create a new Amazon SNS FIFO topic for the other team. Grant S3 permission to send the notification to the second SNS topic.
- Set up another SQS queue for the other team. Grant S3 permission to send a notification to the second SQS queue.
- Set up an Amazon SNS topic and configure two SQS queues to poll the SNS topic. Grant S3 permission to send notifications to SNS and update the bucket to use the new SNS topic.
- `Create an Amazon SNS topic and configure two SQS queues to subscribe to the topic. Grant S3 permission to send notifications to SNS and update the bucket to use the new SNS topic.`

This is one of the **most important SNS + SQS architecture questions** in SAA. Once you understand this pattern, you'll answer many questions easily.

---

# Step 1: Current Architecture

Right now:

```text
S3
 │
 │ Object Created
 │ Object Deleted
 ▼
SQS Queue
```

Only **one queue** receives the notification.

---

# New Requirement

Now both teams should receive every notification.

```
Development Team

Operations Team
```

Question:

> How can both teams receive the same event?

---

# Can S3 send to two SQS queues?

❌ No.

This is the key AWS limitation.

Think:

```
S3

↓

ONE destination only
```

An S3 event notification can target **one destination**:

* one SNS topic ✅
* OR one SQS queue ✅
* OR one Lambda ✅

Not multiple SQS queues directly.

---

# What is SNS?

SNS stands for:

**Simple Notification Service**

Think of it as a **broadcast speaker**.

```
S3

↓

SNS

↓↓↓

Everyone hears it
```

SNS duplicates the message.

---

# Fan-Out Pattern

This is called **Fan-Out**.

```
          S3
           │
           ▼
         SNS Topic
        /         \
       ▼           ▼
   SQS Queue   SQS Queue
   (Dev Team)  (Ops Team)
```

SNS receives **one message** and creates copies.

Everyone gets the same notification.

---

# Why not two SQS queues directly?

Suppose you try this:

```
S3

├── Queue A

└── Queue B
```

AWS doesn't allow this.

S3 supports only one event destination.

---

# What does "Subscribe" mean?

People often confuse this.

SQS **doesn't poll SNS**.

Instead:

```
Queue

↓

Subscribes

↓

SNS
```

Think YouTube.

You subscribe to a channel.

The channel pushes videos to you.

You don't keep checking every second.

Same idea.

---

# Why are the other answers wrong?

## Option 1

> Create another SNS FIFO topic

❌ Wrong

S3 still cannot send events to multiple topics.

Also FIFO is unnecessary.

---

## Option 2

> Create another SQS queue

❌ Wrong

Again:

S3 → only one destination.

Cannot notify two queues directly.

---

## Option 3

> Two SQS queues poll SNS

❌ Wrong

SNS is **push**, not **pull**.

Nobody polls SNS.

SNS pushes messages to subscribers.

---

## Option 4 ✅

```
S3

↓

SNS

↓

Queue 1

Queue 2
```

Perfect.

This is exactly what SNS was designed for.

---

# Memory Trick

Imagine your school principal.

Without SNS:

```
Principal

↓

One student
```

Only one student hears.

---

With SNS:

```
Principal

↓

School Speaker

↓

Every classroom hears
```

SNS is the school speaker.

---

# Exam Keywords

Whenever you see:

* Send to multiple consumers
* Multiple applications
* Multiple teams
* Fan-out
* Broadcast
* Publish once
* Multiple subscribers

Think immediately:

✅ **SNS**

If you see:

* Reliable processing
* Buffering
* Queue
* Workers

Think:

✅ **SQS**

If you see both together:

```
Producer

↓

SNS

↓

SQS

↓

Consumers
```

That's the classic **SNS Fan-Out architecture**.

---

# Quick Cheat Sheet

| Requirement                   | AWS Service             |
| ----------------------------- | ----------------------- |
| One producer → One consumer   | SQS                     |
| One producer → Many consumers | SNS                     |
| Broadcast message             | SNS                     |
| Buffer work                   | SQS                     |
| S3 notify multiple systems    | S3 → SNS → Multiple SQS |
| Can SQS poll SNS?             | ❌ No                    |
| Can SQS subscribe to SNS?     | ✅ Yes                   |

## One-line exam rule

> **One sender → many receivers = SNS Fan-Out.**
> **One sender → one worker = SQS.**
