

1. Question

Category: CSAA – Design High-Performing Architectures

A company is using Amazon S3 to store frequently accessed data. When an object is created or deleted, the S3 bucket will send an event notification to the Amazon SQS queue. A solutions architect needs to create a solution that will notify the development and operations team about the created or deleted objects.

Which of the following would satisfy this requirement?

- Create a new Amazon SNS FIFO topic for the other team. Grant S3 permission to send the notification to the second SNS topic.
- Set up another SQS queue for the other team. Grant S3 permission to send a notification to the second SQS queue.
- Set up an Amazon SNS topic and configure two SQS queues to poll the SNS topic. Grant S3 permission to send notifications to SNS and update the bucket to use the new SNS topic.
- `Create an Amazon SNS topic and configure two SQS queues to subscribe to the topic. Grant S3 permission to send notifications to SNS and update the bucket to use the new SNS topic.`

This is one of the **most important SNS + SQS architecture questions** in SAA. Once you understand this pattern, you'll answer many questions easily.

---

# Step 1: Current Architecture

Right now:

```text
S3
 │
 │ Object Created
 │ Object Deleted
 ▼
SQS Queue
```

Only **one queue** receives the notification.

---

# New Requirement

Now both teams should receive every notification.

```
Development Team

Operations Team
```

Question:

> How can both teams receive the same event?

---

# Can S3 send to two SQS queues?

❌ No.

This is the key AWS limitation.

Think:

```
S3

↓

ONE destination only
```

An S3 event notification can target **one destination**:

* one SNS topic ✅
* OR one SQS queue ✅
* OR one Lambda ✅

Not multiple SQS queues directly.

---

# What is SNS?

SNS stands for:

**Simple Notification Service**

Think of it as a **broadcast speaker**.

```
S3

↓

SNS

↓↓↓

Everyone hears it
```

SNS duplicates the message.

---

# Fan-Out Pattern

This is called **Fan-Out**.

```
          S3
           │
           ▼
         SNS Topic
        /         \
       ▼           ▼
   SQS Queue   SQS Queue
   (Dev Team)  (Ops Team)
```

SNS receives **one message** and creates copies.

Everyone gets the same notification.

---

# Why not two SQS queues directly?

Suppose you try this:

```
S3

├── Queue A

└── Queue B
```

AWS doesn't allow this.

S3 supports only one event destination.

---

# What does "Subscribe" mean?

People often confuse this.

SQS **doesn't poll SNS**.

Instead:

```
Queue

↓

Subscribes

↓

SNS
```

Think YouTube.

You subscribe to a channel.

The channel pushes videos to you.

You don't keep checking every second.

Same idea.

---

# Why are the other answers wrong?

## Option 1

> Create another SNS FIFO topic

❌ Wrong

S3 still cannot send events to multiple topics.

Also FIFO is unnecessary.

---

## Option 2

> Create another SQS queue

❌ Wrong

Again:

S3 → only one destination.

Cannot notify two queues directly.

---

## Option 3

> Two SQS queues poll SNS

❌ Wrong

SNS is **push**, not **pull**.

Nobody polls SNS.

SNS pushes messages to subscribers.

---

## Option 4 ✅

```
S3

↓

SNS

↓

Queue 1

Queue 2
```

Perfect.

This is exactly what SNS was designed for.

---

# Memory Trick

Imagine your school principal.

Without SNS:

```
Principal

↓

One student
```

Only one student hears.

---

With SNS:

```
Principal

↓

School Speaker

↓

Every classroom hears
```

SNS is the school speaker.

# Exam Keywords

Whenever you see:

* Send to multiple consumers
* Multiple applications
* Multiple teams
* Fan-out
* Broadcast
* Publish once
* Multiple subscribers

Think immediately:

✅ **SNS**

If you see:

* Reliable processing
* Buffering
* Queue
* Workers

Think:

✅ **SQS**

If you see both together:

```
Producer

↓

SNS

↓

SQS

↓

Consumers
```

That's the classic **SNS Fan-Out architecture**.

---

# Quick Cheat Sheet

| Requirement                   | AWS Service             |
| ----------------------------- | ----------------------- |
| One producer → One consumer   | SQS                     |
| One producer → Many consumers | SNS                     |
| Broadcast message             | SNS                     |
| Buffer work                   | SQS                     |
| S3 notify multiple systems    | S3 → SNS → Multiple SQS |
| Can SQS poll SNS?             | ❌ No                    |
| Can SQS subscribe to SNS?     | ✅ Yes                   |

## One-line exam rule

> **One sender → many receivers = SNS Fan-Out.**
> **One sender → one worker = SQS.**
