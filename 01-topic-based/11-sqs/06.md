6. Question

Category: CSAA – Design Resilient Architectures

An investment bank has a distributed batch processing application that is hosted in an AWS Auto Scaling group of Amazon EC2 Spot instances with an Amazon SQS queue. The SQS queue is currently configured to use short polling to retrieve messages, and the components are configured to use client-side buffering so that the calls made from the client will be buffered first and then sent as a batch request to SQS.

What is a period of time during which the SQS queue prevents other consuming components from receiving and processing a message?

- Receiving Timeout
- `Visibility Timeout`
- Component Timeout
- Processing Timeout

This question is actually the **same concept** as Question 4. AWS asks it in a different way to see if you really understand **Visibility Timeout**.

---

# The Question

It asks:

> **What is the period of time during which SQS prevents other consumers from receiving and processing the same message?**

The answer is simply:

✅ **Visibility Timeout**

---

# Let's understand it with one example

Suppose your SQS queue has one message.

```text
SQS Queue

Order #100
```

There are two EC2 workers.

```text
         SQS Queue
             │
      ┌──────┴──────┐
      ▼             ▼
    EC2-A         EC2-B
```

---

## Step 1: EC2-A receives the message

```text
SQS Queue

Order #100

↓

EC2-A receives it
```

Does SQS delete it immediately?

❌ No.

Instead, it **hides** the message.

---

## Step 2: Visibility Timeout starts

```text
Queue

Order #100

↓

Invisible (30 seconds by default)
```

Now EC2-B cannot see it.

```text
EC2-A  ✅ Processing

EC2-B  ❌ Cannot receive it
```

This hidden period is called:

> **Visibility Timeout**

---

## Step 3A: Everything succeeds

EC2-A finishes processing.

```text
EC2-A

↓

DeleteMessage()

↓

Message removed forever
```

Done.

---

## Step 3B: EC2 crashes

Suppose EC2-A crashes.

```text
EC2-A

↓

Crash ❌

↓

Never calls DeleteMessage()
```

After the timeout expires:

```text
30 seconds later

↓

Message becomes visible again

↓

EC2-B receives it
```

Nothing is lost.

---

# Why does AWS do this?

Imagine there was **no Visibility Timeout**.

```
Queue

↓

EC2-A receives message

↓

EC2-B also receives same message

↓

Both process it
```

Result:

* Customer charged twice ❌
* Email sent twice ❌
* Order shipped twice ❌

Visibility Timeout prevents this.

---

# Exam Memory Trick

Imagine a restaurant.

One waiter picks up an order ticket.

```
Kitchen Board

Burger Order
```

The ticket is temporarily removed from the board.

Other waiters cannot take it.

If the waiter delivers the food:

```
Ticket thrown away
```

If the waiter disappears:

```
Ticket returned to board

↓

Another waiter picks it up
```

That ticket being hidden is exactly **Visibility Timeout**.

---

# Wrong Answers

### ❌ Receiving Timeout

There is no SQS feature called Receiving Timeout.

The similar setting is **ReceiveMessageWaitTimeSeconds**, which controls **Long Polling**, not message locking.

---

### ❌ Processing Timeout

Sounds logical.

But AWS doesn't use this name.

---

### ❌ Component Timeout

Not an SQS feature.

---

# Quick Comparison

| Feature                     | Purpose                                                    |
| --------------------------- | ---------------------------------------------------------- |
| **Visibility Timeout**      | Hide message while one consumer is processing it           |
| **Long Polling**            | Wait for messages instead of constantly checking the queue |
| **DeleteMessage**           | Permanently remove message after successful processing     |
| **Dead Letter Queue (DLQ)** | Store messages that repeatedly fail processing             |

---

# One-line exam rule

Whenever you read:

* "Prevent another consumer from processing the same message"
* "Worker is processing the message"
* "Hide message temporarily"

Immediately think:

> ✅ **Visibility Timeout**
