4. Question

Category: CSAA – Design High-Performing Architectures

An e-commerce application is using a fanout messaging pattern for its order management system. For every order, it sends an Amazon SNS message to an SNS topic, and the message is replicated and pushed to multiple Amazon SQS queues for parallel asynchronous processing. A Spot EC2 instance retrieves the message from each SQS queue and processes the message. There was an incident that while an EC2 instance is currently processing a message, the instance was abruptly terminated, and the processing was not completed in time.

In this scenario, what happens to the SQS message?

- The message is deleted and becomes duplicated in the SQS when the EC2 instance comes online.
- `When the message visibility timeout expires, the message becomes available for processing by other EC2 instances`
- The message will be sent to a Dead Letter Queue in AWS DataSync.
- The message will automatically be assigned to the same EC2 instance when it comes back online within or after the visibility timeout.

This is one of the **highest-yield SQS questions** for the SAA exam. The key is understanding **Visibility Timeout**.

---

# Step 1: What happens when a consumer reads an SQS message?

Suppose your queue contains one message.

```
SQS Queue

Order #1001
```

EC2 Worker reads it.

**Question:** Does SQS delete it immediately?

**No!**

Instead, SQS hides it.

```
Invisible for 30 seconds (default)
```

This hiding period is called **Visibility Timeout**.

---

# Step 2: Why hide it?

Imagine there are two EC2 instances.

```
Queue

Order #1001

      ↓

EC2-A
EC2-B
```

EC2-A starts processing.

If the message stayed visible...

EC2-B would also process it.

That means:

```
Customer charged twice ❌
Order shipped twice ❌
```

So SQS hides the message from everyone else.

---

# Step 3: Normal flow

```
Queue
   │
   ▼
EC2 receives message
   │
Visibility Timeout starts
   │
EC2 processes
   │
EC2 calls DeleteMessage
   │
Message removed forever
```

Everything is successful.

---

# Step 4: What happened in the question?

The question says:

> Spot EC2 was terminated while processing.

So this happens:

```
Queue

Order

↓

EC2 starts processing

↓

Visibility Timeout starts

↓

EC2 TERMINATED ❌

↓

No DeleteMessage
```

Notice something.

The worker never deleted the message.

Therefore SQS thinks:

> "Maybe the worker crashed."

So it waits until the visibility timeout ends.

---

# Step 5: After timeout expires

Suppose timeout = 30 seconds.

```
0 sec
↓

EC2 receives message

↓

Invisible

↓

EC2 crashes

↓

30 seconds pass

↓

Message becomes visible again
```

Now another EC2 instance can read it.

```
EC2-B

↓

Processes successfully

↓

Deletes message
```

Nothing is lost.

---

# Therefore the correct answer is

✅ **When the message visibility timeout expires, the message becomes available for processing by other EC2 instances.**

This is exactly how SQS provides reliability.

---

# Why are the others wrong?

### ❌ Message is deleted

No.

Only the **consumer** deletes the message.

SQS never deletes it automatically after it is received.

---

### ❌ Automatically assigned back to same EC2

No.

SQS has no idea which EC2 processed it.

Any available consumer can receive it after the timeout expires.

---

### ❌ Sent to Dead Letter Queue

Not immediately.

DLQ is only used after the message exceeds the configured **maximum receive count**.

Example:

```
Receive #1 → Fail

Receive #2 → Fail

Receive #3 → Fail

Receive #4 → Fail

Receive #5 → Fail

↓

Move to DLQ
```

A single EC2 crash is **not enough**.

Also, **AWS DataSync has nothing to do with DLQs**.

---

# Easy memory trick

Think of SQS like borrowing a library book.

```
Take book

↓

Library marks it as unavailable
(Visibility Timeout)

↓

Return book
(DeleteMessage)

OR

Never return it

↓

Loan expires

↓

Someone else can borrow it
```

That's exactly how SQS works.

---

# SQS exam cheat sheet

| Event                            | Result                              |
| -------------------------------- | ----------------------------------- |
| Consumer receives message        | Message becomes invisible           |
| Consumer finishes successfully   | Calls `DeleteMessage`               |
| Consumer crashes                 | Message is **not deleted**          |
| Visibility Timeout expires       | Message becomes visible again       |
| Message keeps failing repeatedly | Sent to **Dead Letter Queue (DLQ)** |

---

## 📌 SAA Exam Rule

Whenever you see:

* Spot Instance terminated
* Lambda failed
* EC2 crashed
* Consumer died
* Processing interrupted

Think immediately:

> **Visibility Timeout expires → another consumer processes the message.** ✅

This is one of the most frequently tested SQS concepts on the AWS Solutions Architect Associate exam.
