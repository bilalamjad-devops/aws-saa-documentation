19. Question

A content management system (CMS) is hosted on a fleet of auto-scaled, On-Demand Amazon EC2 instances that use Amazon Aurora as its database. Currently, the system stores the file documents that users upload in one of the attached Amazon EBS volumes. The system’s performance has been observed to be slow, and the manager has instructed the team to improve the architecture.

In this scenario, which solution should be implemented to achieve a scalable, highly available, POSIX-compliant shared file system?

- Create an Amazon S3 bucket and use this as the storage for the CMS
- `Use Amazon EFS to provide a shared file system for concurrent access to data`
- Upgrade your existing EBS volumes to Provisioned IOPS SSD volumes
- Leverage Amazon ElastiCache to cache frequently accessed data and reduce latency

### Keywords Scan 🔍

1. **"POSIX-compliant shared file system"**
* **Trigger:** Standard POSIX file system capabilities + concurrent shared access across multiple Linux EC2 instances $\rightarrow$ **Amazon EFS** (Elastic File System).


2. **"fleet of auto-scaled Amazon EC2 instances ... store file documents in attached EBS"**
* **Trigger:** Single EBS volume multiple instances par attach nahi ho sakta (EFS Multi-Attach/concurrent read-write shared file system access enable karta hai).



---

### Correct Answer

**Use Amazon EFS to provide a shared file system for concurrent access to data**

---

### Roman Urdu Explanation 💡

* **Amazon EFS (Elastic File System):** Yeh ek fully managed, highly available shared file storage hai jo **POSIX-compliant** hai aur hazaron Auto-scaling EC2 instances ko ek saath concurrent read/write access deta hai.
* **EBS Volume Issue:** Single EBS volume multiple auto-scaling EC2 instances ke saath file share nahi kar sakta (Multi-Attach restrictions ke sath).
* **Amazon S3:** S3 Object Storage hai, **POSIX file system nahi** (is mein standard filesystem operations jaise file locking, appending, atomic renames natively nahi hote).

---

### Elimination Rules ❌

* **Amazon S3:** Object storage hai, POSIX-compliant file system requirement ko fulfill nahi karta.
* **Provisioned IOPS SSD (EBS):** EBS volume block storage hota hai aur auto-scaling fleet ke liye shared network file system ki tarah act nahi karta.
* **Amazon ElastiCache:** Yeh in-memory data store/cache (Redis/Memcached) hai, document file system nahi.

**POSIX (Portable Operating System Interface)** ek standard set of rules (standards) hai jo IEEE ne banaya tha taaki different operating systems (jaise Linux, Unix, macOS) aapas mein compatible ho sakein.

Jab hum AWS mein kisi storage service ke liye kehte hain ke woh **POSIX-compliant** hai, toh iska matlab yeh hota hai:

---

### Key Features of POSIX File System

1. **Standard File Permissions:**
* Files aur folders par Linux waali standard permissions chalti hain (`read`, `write`, `execute` — `chmod` / `chown` commands).


2. **Standard File Operations:**
* Applications bina kisi extra API ya SDK ke direct standard OS commands se files read/write, rename, delete, ya append kar sakti hain (jaise `open()`, `read()`, `write()`, `close()`).


3. **File Locking & Hierarchy:**
* Folder tree structure (`/mnt/efs/data/...`) maintain hota hai aur multiple process/instances ek hi file par simultaneous access/locking handle kar sakte hain.



---

### AWS Comparison: EFS vs S3

* **Amazon EFS (POSIX-Compliant):** Local hard disk ya shared network folder (NFS) ki tarah act karta hai. Existing Linux applications ko bina kisi code change ke EFS mount karke use kiya ja sakta hai.
* **Amazon S3 (Not POSIX):** Yeh **Object Storage** hai. S3 mein folders actual folders nahi hotay (sirf key prefixes hotay hain). Is mein file append ya direct OS commands nahi chalte, balki AWS API/SDK (`PutObject`, `GetObject`) se interaction hota hai.
