13. Question

Category: CSAA – Design Resilient Architectures

A company has recently migrated its microservices-based application to Amazon Elastic Kubernetes Service (Amazon EKS). As part of the migration, the company must ensure that all sensitive configuration data and credentials, such as database passwords and API keys, are stored securely and encrypted within the Amazon EKS cluster’s etcd key-value store.

What is the most suitable solution to meet the company’s requirements?

- Use AWS Secrets Manager with a new AWS KMS key to securely manage and store sensitive data within the EKS cluster's etcd key-value store.
- Enable default Amazon EBS volume encryption for the account with a new AWS KMS key to ensure encryption of sensitive data within the Amazon EKS cluster.
- Use Amazon EKS default options and the Amazon Elastic Block Store (Amazon EBS) Container Storage Interface (CSI) driver as an add-on to securely store sensitive data within the Amazon EKS cluster.
- `Enable secret encryption with a new AWS KMS key on an existing Amazon EKS cluster to encrypt sensitive data stored in the EKS cluster's etcd key-value store.`

Exactly. Your understanding of the question is basically correct: **the key word is encryption of Kubernetes Secrets stored in EKS's `etcd`**.

Let's build this from zero, because you haven't used KMS/Secrets Manager yet.

### 1. First, what is `etcd`?

Think of `etcd` as the **database/storage behind Kubernetes**.

Kubernetes stores things like:

* Pods
* Deployments
* Services
* Configurations
* Kubernetes Secrets

So conceptually:

```text
EKS Cluster
   │
   └── Kubernetes control plane
          │
          └── etcd
               ├── Pod information
               ├── Deployment information
               ├── Configurations
               └── Kubernetes Secrets
                    ├── DB password
                    ├── API key
                    └── credentials
```

The question specifically says:

> sensitive configuration data and credentials ... stored within the EKS cluster's **etcd key-value store**

So AWS is telling you exactly **where the sensitive data is stored**.

---

### 2. What is the problem?

Suppose Kubernetes has a Secret:

```text
DB_PASSWORD = MySuperPassword123
```

That Kubernetes Secret ultimately gets stored in `etcd`.

The requirement is:

> **Encrypt these Secrets before they are stored in etcd.**

So we need **EKS secret encryption using AWS KMS**.

---

### 3. What is KMS?

Very simply:

**AWS KMS = AWS service for managing encryption keys.**

Think:

```text
KMS
 │
 └── Encryption Key
        ↓
      encrypt
        ↓
   Sensitive data
```

For this question:

```text
Kubernetes Secret
       ↓
     KMS key
       ↓
   encrypted Secret
       ↓
      etcd
```

So if someone somehow gets access to the underlying `etcd` data, they don't simply see the Secret in plaintext.

---

### 4. What does the correct answer actually say?

> **Enable secret encryption with a new AWS KMS key on an existing EKS cluster**

That's the important phrase.

**EKS + Secret encryption + KMS = encrypt Kubernetes Secrets in etcd.**

---

### 5. Don't confuse this with AWS Secrets Manager

This is where the question is tricky.

**AWS Secrets Manager** is a separate AWS service for storing secrets such as:

```text
DB username
DB password
API keys
tokens
```

You can absolutely use Secrets Manager with EKS in real-world architectures.

But the question isn't asking:

> "Where should I store my application secrets?"

It specifically asks:

> "How do I encrypt sensitive data stored in the EKS cluster's `etcd`?"

Therefore:

**KMS + EKS secret encryption** is the direct answer.

---

### 6. Why the other options don't work

| Option                          | Why?                                                                                   |
| ------------------------------- | -------------------------------------------------------------------------------------- |
| **EKS Secret Encryption + KMS** | ✅ Encrypts Kubernetes Secrets stored in etcd                                           |
| Secrets Manager                 | ❌ Separate secret-management service; doesn't enable etcd encryption                   |
| EBS encryption                  | ❌ Encrypts EBS volumes, not Kubernetes Secrets in etcd                                 |
| EBS CSI driver                  | ❌ Provides EBS storage to Kubernetes applications; unrelated to etcd Secret encryption |

### SAA memory trick

When you see:

> **EKS + Kubernetes Secrets + etcd + encryption**

immediately think:

**→ EKS Secret Encryption → AWS KMS key**

And one important distinction:

> **KMS = manages encryption keys.**

> **Secrets Manager = manages application secrets.**

> **EBS encryption = protects EBS storage.**

You'll encounter these three concepts repeatedly in SAA questions.
