26. Question

Category: CSAA – Design High-Performing Architectures

A content management system (CMS) is hosted on a fleet of auto-scaled, On-Demand Amazon EC2 instances that use Amazon Aurora as its database. Currently, the system stores the file documents that users upload in one of the attached Amazon EBS volumes. The system’s performance has been observed to be slow, and the manager has instructed the team to improve the architecture.

In this scenario, which solution should be implemented to achieve a scalable, highly available, POSIX-compliant shared file system?

- Upgrade your existing EBS volumes to Provisioned IOPS SSD volumes
- `Use Amazon EFS to provide a shared file system for concurrent access to data`
- Create an Amazon S3 bucket and use this as the storage for the CMS
- Leverage Amazon ElastiCache to cache frequently accessed data and reduce latency

Yes — your thinking is **mostly correct**, but there is one important correction:

> **EFS is primarily for Linux-based workloads. For Windows, use Amazon FSx for Windows File Server, not EFS.**

### What is happening in this question?

You have **multiple EC2 instances**:

```text
              ┌── EC2 #1
              │
Users → ALB → ├── EC2 #2
              │
              └── EC2 #3
                    │
                    ↓
              Shared files
```

The CMS allows users to upload documents.

The problem is that the documents are currently stored on an **EBS volume** attached to an EC2 instance.

The requirement says:

> **scalable + highly available + POSIX-compliant + shared file system**

That combination strongly points to:

### ✅ Amazon EFS

```text
              ┌── EC2 #1 ──┐
              │            │
Users → ALB ──┼── EC2 #2 ──┼──→ EFS
              │            │
              └── EC2 #3 ──┘
```

All EC2 instances can access the **same EFS file system concurrently**.

For example:

```text
EFS
│
├── document1.pdf
├── document2.pdf
├── image1.jpg
└── report.docx
```

EC2 #1, #2, and #3 can all access those files.

---

## The important EBS vs EFS vs S3 distinction

Think of these three like this:

| Service | Think of it as                  | Multiple EC2 access          |
| ------- | ------------------------------- | ---------------------------- |
| **EBS** | Hard disk attached to EC2       | Usually one EC2              |
| **EFS** | Shared Linux network filesystem | ✅ Multiple EC2               |
| **S3**  | Internet-scale object storage   | ✅ But not a POSIX filesystem |

So if the question says:

> **"shared file system"**

think:

### EFS → Linux

And if it says:

> **"Windows shared file system"**

think:

### FSx for Windows File Server

---

### Why not S3?

S3 is excellent for storing files/objects:

```text
S3
├── PDF
├── JPG
├── CSV
└── ZIP
```

But S3 doesn't behave like a normal Linux filesystem with POSIX semantics.

A CMS may expect operations like:

```text
/open file
/read file
/write file
/modify file
/file permissions
```

That's where EFS fits much better.

---

### One more important correction to your sentence

You said:

> "EFS to store data from multiple sources in one place"

I'd phrase the exam concept as:

> **Multiple EC2 instances need concurrent access to the same shared filesystem → EFS.**

It isn't really about "multiple sources"; it's about **multiple compute instances accessing the same files**.

### 🧠 Exam shortcut

Memorize this:

**EBS → block storage → EC2**

**EFS → shared POSIX filesystem → Linux → multiple EC2**

**FSx for Windows → shared Windows filesystem**

**S3 → object storage → massive scalable storage**

That distinction will solve a lot of SAA questions.
