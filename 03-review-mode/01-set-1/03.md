3. Question

Category: CSAA – Design High-Performing Architectures

A company is using a combination of Amazon API Gateway and AWS Lambda for the web services of an online web portal that is accessed by hundreds of thousands of clients each day. The company will be announcing a new revolutionary product, and it is expected that the web portal will receive a massive number of visitors from all around the globe.

How can the back-end systems and applications, beyond the subnet-level filtering of network ACLs, be protected from traffic spikes?

- API Gateway will automatically scale and handle massive traffic spikes so you do not have to do anything.
- Configure API Gateway for Multi-AZ deployment and provision a read replica
- `Use throttling limits in API Gateway`
- Manually upgrade the Amazon EC2 instances being used by API Gateway

Yes — your understanding of API Gateway needs **one small correction**. The key is to separate **what API Gateway does** from **what it connects to**.

## First: What is API Gateway?

Think of API Gateway as the **front door for APIs**.

A client might send:

```text
User / Mobile App / Website
          ↓
    API Gateway
          ↓
      Lambda
          ↓
   DynamoDB / RDS / S3
```

But API Gateway is **not limited to S3, EC2, or DynamoDB**.

It can front many kinds of backends, including:

* Lambda
* EC2 applications
* ECS/EKS applications
* HTTP services
* AWS services such as S3
* Other APIs

So in this question:

```text
Hundreds of thousands of users
            ↓
       API Gateway
            ↓
          Lambda
            ↓
       Backend systems
```

---

# What is the question actually asking?

The important sentence is:

> "The web portal will receive a massive number of visitors."

Imagine normally:

```text
1,000 requests/sec
```

Then the new product launches:

```text
100,000 requests/sec
```

If all 100,000 requests are immediately allowed through:

```text
100,000 requests
       ↓
 API Gateway
       ↓
   Lambda
       ↓
 Backend
       💥💥💥
```

The backend could become overloaded.

The question asks:

> **How can we protect the backend from traffic spikes?**

The answer is:

### ✅ API Gateway throttling

You tell API Gateway something like:

```text
Maximum normal rate = 1,000 requests/sec
Burst = 2,000 requests
```

Then:

```text
              API Gateway
                   │
       ┌───────────┴───────────┐
       │                       │
 Within limit             Too many
       │                       │
       ↓                       ↓
   Lambda                    429
       │
    Backend
```

The excess requests receive:

**HTTP 429 — Too Many Requests**

This prevents the sudden traffic spike from overwhelming your downstream systems.

---

# 🔥 The key SAA concept

Think of **throttling as a traffic gate**.

Without throttling:

```text
Internet
  ↓
💥💥💥💥💥
API Gateway
  ↓
💥💥💥💥💥
Lambda / Backend
```

With throttling:

```text
Internet
  ↓
💥💥💥💥💥
API Gateway
  ↓
🚦 THROTTLING
  ↓
Only acceptable traffic
  ↓
Lambda / Backend
```

So:

> **API Gateway protects downstream applications by controlling how many requests are allowed through.**

---

## Why the other options are wrong

### ❌ "API Gateway automatically scales, so do nothing"

API Gateway **does scale**, but that doesn't mean you should allow unlimited traffic to your backend.

The requirement specifically says:

> **protect the back-end systems from traffic spikes**

Throttling is the mechanism designed for this.

---

### ❌ Multi-AZ + read replica

This is mixing up database concepts.

You might remember:

**RDS:**

```text
Multi-AZ → high availability
Read Replica → read scaling
```

API Gateway doesn't have:

```text
API Gateway Multi-AZ
API Gateway Read Replica
```

AWS manages its infrastructure for you.

---

### ❌ Manually upgrade EC2

API Gateway isn't an EC2 instance that you manage.

You don't do:

```text
API Gateway EC2
    ↓
upgrade t3.medium → t3.large
```

There is no underlying API Gateway EC2 instance that you manually resize.

---

# One very important distinction

You'll see these concepts repeatedly in SAA:

| Problem                                        | Think of                                                                                     |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Too many requests hitting backend              | **API Gateway throttling**                                                                   |
| Sudden workload that can wait                  | **SQS buffering**                                                                            |
| Need to distribute traffic                     | **Load Balancer**                                                                            |
| Need to cache API responses                    | **API Gateway caching / CloudFront**                                                         |
| Need global edge delivery                      | **CloudFront**                                                                               |
| Lambda is getting too many concurrent requests | **Reserved/Provisioned concurrency, throttling, or queue-based design depending on problem** |

### For this exact question:

**Massive traffic spike → protect backend → API Gateway throttling.** ✅

And your original understanding isn't wrong; just expand it from:

> "API Gateway is used for S3/EC2/DynamoDB"

to:

> **"API Gateway is an API front door that can connect clients to many different backends, including Lambda, AWS services, and HTTP applications."**

**Throttling = putting a limit on how much traffic is allowed through.** 🚦

Think of it like a **toll gate** on a highway.

Suppose your backend can safely handle **1,000 requests/second**.

Without throttling:

```text
Users
 ↓
10,000 requests/sec
 ↓
API Gateway
 ↓
Lambda
 ↓
💥 Backend overloaded
```

With throttling:

```text
Users
 ↓
10,000 requests/sec
 ↓
API Gateway
 🚦 Throttle: 1,000/sec
 ↓
1,000 requests → Lambda
 ↓
Backend
```

The requests above the configured limit are rejected with:

**HTTP 429 — Too Many Requests**

### Why do we use it?

Because sometimes **protecting the backend is more important than accepting every request immediately**.

For example:

> Product launch → suddenly 100,000 users → API Gateway throttles requests → backend doesn't get overwhelmed.

### Easy SAA memory trick

**Throttling = "Slow down / limit the traffic."**

* **API Gateway throttling** → limits incoming API requests.
* **Lambda concurrency limit** → limits how many Lambda executions run simultaneously.
* **DynamoDB throttling** → happens when requests exceed the table's available capacity.

So whenever you see:

> **"Traffic spike is overwhelming the backend"**

Think:

**🚦 Throttling**.
