8. Question

Category: CSAA – Design High-Performing Architectures

An online learning company hosts its Microsoft .NET e-Learning application on a Windows Server in its on-premises data center. The application uses an Oracle Database Standard Edition as its backend database.

The company wants a high-performing solution to migrate this workload to the AWS cloud to take advantage of the cloud’s high availability. The migration process should minimize development changes, and the environment should be easier to manage.

Which of the following options should be implemented to meet the company requirements? (Select TWO.)

- Use AWS Transform MGN to migrate the on-premises Oracle database server to a new Amazon EC2 instance.
- Refactor the application to .NET Core and run it as a serverless container service using Amazon Elastic Kubernetes Service (Amazon EKS) with AWS Fargate.
- `Rehost the on-premises .NET application to an AWS Elastic Beanstalk Multi-AZ environment which runs in multiple Availability Zones.`
- Provision and replatform the application to Amazon Elastic Container Service (Amazon ECS) with Amazon EC2 worker nodes. Use the Windows Server Amazon Machine Image (AMI) and deploy the .NET application using to the ECS cluster via the ECS Anywhere service.
- `Perform a homogeneous migration by moving the Oracle database to Amazon RDS for Oracle in a Multi-AZ deployment using AWS Database Migration Service (AWS DMS).`

Yes — and **that is exactly why this question feels confusing**. You don't need to have used Elastic Beanstalk yet. Let's add it to your mental model from zero.

## First: What is Elastic Beanstalk?

Think of **Elastic Beanstalk as a simplified application deployment service**.

Suppose you have a normal application:

```text
.NET Application
```

Normally, you might have to do:

```text
EC2
↓
Install Windows
↓
Install IIS
↓
Configure application
↓
Configure Load Balancer
↓
Configure Auto Scaling
↓
Configure monitoring
```

With **Elastic Beanstalk**, you basically tell AWS:

> "Here is my application. Run it for me."

Elastic Beanstalk handles much of the underlying infrastructure for you.

```text
Your .NET Application
        ↓
Elastic Beanstalk
        ↓
EC2 + Load Balancer + Auto Scaling + Health Monitoring
```

So **Elastic Beanstalk is not a database** and it's not a replacement for EC2.

It is more like a **management layer for deploying applications**.

---

# Now let's reread Question 8

The company currently has:

```text
ON-PREMISES

Windows Server
      ↓
.NET Application
      ↓
Oracle Database
```

They want:

> "Move this to AWS."

And they give us two big requirements:

### Requirement 1 — High availability

They don't want everything sitting on one server/AZ.

### Requirement 2 — Minimal development changes

They don't want to rewrite the application.

### Requirement 3 — Easier management

They don't want to manually manage lots of servers.

---

# Part 1: .NET application

We ask:

> "How can I move the existing .NET application to AWS with minimal code changes and less management?"

**Elastic Beanstalk** is a good answer.

So:

```text
ON-PREMISES                    AWS

.NET Application   ─────→   Elastic Beanstalk
                                ↓
                         EC2 instances
                         Load Balancer
                         Auto Scaling
                         Multi-AZ
```

You are basically saying:

> "AWS, take care of much of the infrastructure. I'll focus on my application."

That's why the answer says:

> **Rehost the on-premises .NET application to an AWS Elastic Beanstalk Multi-AZ environment.**

---

# Part 2: Oracle database

Now separately ask:

> "What do we do with Oracle?"

They already have:

```text
Oracle
```

The easiest migration is:

```text
Oracle → Oracle
```

rather than:

```text
Oracle → PostgreSQL
```

Because changing database engines could require application changes.

So use:

**Amazon RDS for Oracle**

And because they want high availability:

**RDS Multi-AZ**

And to move the database:

**AWS DMS**

Therefore:

```text
On-premises Oracle
       │
       │ AWS DMS
       ↓
RDS for Oracle
       │
    Multi-AZ
```

---

# So the entire question is actually very simple

The question is asking:

> **"I have an old .NET application + Oracle database on-premises. I want to move both to AWS, don't want much code modification, want high availability, and want AWS to manage as much as possible. What should I choose?"**

Answer:

### Application

**Elastic Beanstalk Multi-AZ**

### Database

**RDS for Oracle Multi-AZ + DMS**

---

## Put this in your mental map

You already know:

```text
EC2 = virtual server

RDS = managed relational database

Aurora = AWS relational database compatible with
         MySQL/PostgreSQL

DynamoDB = NoSQL database

DMS = migrate/replicate databases
```

Now add:

```text
Elastic Beanstalk
        ↓
Deploy/manage applications
        ↓
AWS handles much of the underlying infrastructure
        ↓
Can use EC2, Load Balancer, Auto Scaling, etc.
```

### Very important distinction

Don't think:

> "Elastic Beanstalk = another type of EC2."

Think:

> **"Elastic Beanstalk = an easier way to deploy and manage my application, while AWS manages much of the infrastructure underneath."**

---

### And don't worry about not having used it

For SAA, you don't need hands-on experience with every AWS service before understanding the question.

You mainly need to recognize the **job of the service**:

* **EC2** → server
* **Elastic Beanstalk** → application deployment/management
* **RDS** → managed relational DB
* **DMS** → database migration
* **S3** → object storage
* **Lambda** → serverless code
* **EKS** → Kubernetes
* **ECS** → containers

Once you recognize those roles, these questions become much easier.
