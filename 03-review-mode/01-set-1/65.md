65. Question

Category: CSAA – Design High-Performing Architectures

A company wishes to query data that resides in multiple AWS accounts from a central data lake. Each account has its own Amazon S3 bucket that stores data unique to its business function. Access to the data lake must be granted based on user roles.

Which solution will minimize overhead and costs while meeting the required access patterns?

- Use Amazon Data Firehose to consolidate data from multiple accounts into a single account.
- Use AWS Control Tower to centrally manage each account's S3 buckets.
- Create a scheduled AWS Lambda function using Amazon EventBridge for transferring data from multiple accounts to the S3 buckets of the central account.
- `Use AWS Lake Formation to consolidate data from multiple accounts into a single account.`

Exactly. Your understanding of **Control Tower** is correct. Q65 is mainly teaching you to recognize **Lake Formation as the service for centrally managing data access across accounts**, not as a general AWS-account-management service.

## 1. What is the question actually saying?

Imagine a company has 3 AWS accounts:

```text
Account A → S3 bucket → Sales data
Account B → S3 bucket → HR data
Account C → S3 bucket → Finance data
```

Now the company wants:

> "I want people to query all this data from one central data lake, and access should depend on their roles."

For example:

```text
Data Analyst
   ↓
Central Data Lake
   ↓
Can query Sales + Finance

HR employee
   ↓
Central Data Lake
   ↓
Can query HR only
```

And they want to do this with **low management overhead and cost**.

That's where **AWS Lake Formation** comes in.

---

# 2. What is a Data Lake?

A **data lake** is basically:

> **A central place where an organization stores lots of data so it can be analyzed.**

Think:

```text
                     DATA LAKE
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       Sales           HR             Finance
        data           data             data
```

The data can come from:

* S3
* databases
* applications
* different AWS accounts
* different business departments

The important idea is:

> **Centralize data for analytics.**

---

# 3. What is AWS Lake Formation?

AWS Lake Formation helps you **build, secure, and manage a data lake**.

The important exam point is:

> **Lake Formation lets you centrally control who can access which datasets.**

And access can be granular.

For example:

```text
Analyst
  ↓
Sales table
  ✅ allowed

HR table
  ❌ denied
```

Even more granular:

```text
Employee table

Name       Salary       Department
 ↓           ↓              ↓
 ✅          ❌             ✅
```

Lake Formation can control access at levels such as:

* databases
* tables
* columns

So it's more than simply:

> "Can you access this S3 bucket?"

---

# 4. Why S3 appears in Lake Formation

Don't think that Lake Formation replaces S3.

Think:

```text
Lake Formation
       ↓
   controls/
   manages
       ↓
      S3
       ↓
    actual data
```

**S3 = storage**

**Lake Formation = data lake management + governance + permissions**

A very useful distinction:

| Service            | Main job                      |
| ------------------ | ----------------------------- |
| **S3**             | Store objects/data            |
| **Lake Formation** | Build/govern/secure data lake |
| **Glue**           | Data catalog + ETL            |
| **Athena**         | Query data using SQL          |
| **Redshift**       | Data warehouse/analytics      |

---

# 5. What does "multiple AWS accounts" mean here?

The company has:

```text
AWS Account 1
 └── S3 → Sales

AWS Account 2
 └── S3 → HR

AWS Account 3
 └── S3 → Finance
```

Instead of building complicated custom pipelines to copy everything everywhere, Lake Formation can help establish centralized data access/governance across accounts.

The question specifically says:

> **"minimize overhead and costs"**

That's the clue to avoid building your own Lambda/EventBridge transfer architecture.

---

# 6. What is Data Firehose?

You asked about **Data Firehose**.

Amazon Data Firehose is a service for:

> **continuously delivering streaming data to destinations.**

For example:

```text
Application
     ↓
Streaming data
     ↓
Data Firehose
     ↓
S3
```

Imagine an application generating:

```text
10,000 events/sec
```

Firehose can continuously deliver that data to destinations such as S3.

### Don't think:

> "Firehose = move any data between AWS accounts."

That's not its primary purpose.

For Q65, using Firehose in every account would create unnecessary architecture and overhead.

---

# 7. What is Control Tower?

You are correct:

> **AWS Control Tower = manage/govern multiple AWS accounts.** ✅

Think:

```text
                 AWS Organization
                       │
              AWS Control Tower
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
      Account A     Account B    Account C
```

Control Tower helps establish and govern a **multi-account AWS environment**.

Things like:

* account provisioning
* governance
* guardrails
* standardized account setup
* compliance controls

So:

> **Control Tower = manage the AWS accounts**

Not:

> **Control Tower = manage/query the company's data lake**

That's why Control Tower is wrong in Q65.

---

# 8. Lambda + EventBridge option

The question suggests:

```text
Account A
    ↓
Lambda
    ↓
EventBridge
    ↓
Central S3

Account B
    ↓
Lambda
    ↓
EventBridge
    ↓
Central S3
```

Could you build something like this?

**Technically, yes.**

But look at the question:

> **"minimize overhead and costs"**

Now you're responsible for:

* Lambda functions
* permissions
* cross-account access
* EventBridge configuration
* data transfers
* error handling
* retries
* monitoring
* maintenance

That's a lot of custom infrastructure.

If AWS provides a service designed specifically for **data lake governance**, use it.

→ **Lake Formation**.

---

# 9. The most important distinction

You now have several AWS services that can sound similar.

Memorize them like this:

| Service               | Think                                         |
| --------------------- | --------------------------------------------- |
| **AWS Organizations** | 🏢 Manage multiple AWS accounts               |
| **Control Tower**     | 🏗️ Set up + govern multi-account environment |
| **RAM**               | 🤝 Share AWS resources across accounts        |
| **Lake Formation**    | 🗄️ Build/govern/secure data lake             |
| **Glue**              | 📚 Data catalog + ETL                         |
| **Firehose**          | 🚰 Stream/continuously deliver data           |
| **Lambda**            | ⚙️ Run code                                   |
| **EventBridge**       | 📅 Event-driven automation                    |
| **S3**                | 🪣 Store objects                              |
| **Athena**            | 🔎 Query S3 data using SQL                    |
| **Redshift**          | 🏭 Data warehouse                             |

---

# 10. Why the answer is Lake Formation

The question contains three big clues:

### Clue 1

> **"central data lake"**

→ **Lake Formation**

### Clue 2

> **"data from multiple AWS accounts"**

→ Lake Formation supports centralized data sharing/governance.

### Clue 3

> **"Access ... based on user roles"**

→ Lake Formation provides granular data permissions.

Therefore:

**AWS Lake Formation** ✅

> **Firehose moves *streaming data*.**
