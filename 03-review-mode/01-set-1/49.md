49. Question

Category: CSAA – Design Resilient Architectures

An online shopping platform is hosted on an Auto Scaling group of Amazon EC2 Spot instances and utilizes Amazon Aurora PostgreSQL as its database. It is required to optimize database workloads in the cluster by directing the production traffic to high-capacity instances and routing the reporting queries from the internal staff to the low-capacity instances.

Which is the most suitable configuration for the application as well as the Aurora database cluster to achieve this requirement?

- Configure your application to use the reader endpoint for both production traffic and reporting queries, which will enable your Aurora database to automatically perform load-balancing among all the Aurora Replicas.
- Do nothing since by default, Aurora will automatically direct the production traffic to your high-capacity instances and the reporting queries to your low-capacity instances.
- In your application, use the instance endpoint of your Aurora database to handle the incoming production traffic and use the cluster endpoint to handle reporting queries.
- `Create a custom endpoint in Aurora based on the specified criteria for the production traffic and another custom endpoint to handle the reporting queries.`

Yes. This question is mainly testing **Aurora endpoints**. Don't memorize the long explanation. First understand the architecture.

## 1. What is RDS?

**Amazon RDS = managed relational database service.**

You can run databases such as:

* MySQL
* PostgreSQL
* MariaDB
* Oracle
* SQL Server
* Aurora

AWS manages things like provisioning, backups, patching, etc.

Think:

> **RDS = AWS manages my relational database server for me.**

---

## 2. What is Aurora?

**Amazon Aurora is AWS's cloud-optimized relational database engine.**

It is compatible with:

* MySQL
* PostgreSQL

Aurora is different from a normal RDS database because it is designed around a **cluster**.

Simple picture:

```text
                 Aurora Cluster
                      |
          ┌───────────┴───────────┐
          ↓                       ↓
      Primary                 Replicas
     (Writer)              (Readers)
          ↓                       ↓
       Writes                 Reads
```

For this question, think:

> **Aurora = database cluster with a writer + read replicas.**

---

# 3. Understand the question first

The company has:

```text
Production users
       ↓
   Production
    queries
       ↓
HIGH-CAPACITY Aurora instances
```

And:

```text
Internal employees
       ↓
 Reporting queries
       ↓
LOW-CAPACITY Aurora instances
```

Why?

Because you **don't want reporting queries to consume the powerful database instances needed by production users.**

So:

```text
Production traffic
       ↓
High-capacity instances
       ↓
"Give me powerful DBs"

Reporting traffic
       ↓
Low-capacity instances
       ↓
"Give me cheaper/smaller DBs"
```

The question is asking:

> **How can we tell Aurora which group of instances should receive each type of traffic?**

Answer:

**Custom endpoints.**

---

# 4. Aurora endpoints

This is the important part.

### Cluster endpoint

Also called the **writer endpoint**.

```text
Application
     ↓
Cluster endpoint
     ↓
Primary / Writer
```

Used when you need:

* INSERT
* UPDATE
* DELETE
* DDL
* write operations

Think:

> **Cluster endpoint = "Take me to the current writer."**

---

### Reader endpoint

```text
Application
     ↓
Reader endpoint
     ↓
Replica 1
Replica 2
Replica 3
```

It distributes **read traffic** across Aurora Replicas.

Think:

> **Reader endpoint = "Give me any available reader."**

For example:

```text
SELECT * FROM products;
```

Aurora can load-balance that read across replicas.

---

### Instance endpoint

This points to **one specific DB instance**.

```text
Application
      ↓
Instance endpoint
      ↓
Aurora Replica #2
```

You're saying:

> "I specifically want THIS database instance."

Useful when you need to connect to or diagnose a particular instance.

---

# 5. Custom endpoint ⭐

This is what the question is testing.

You can create a group of Aurora instances and give that group an endpoint.

For example:

```text
Aurora Cluster

High-capacity:
┌────────────┐
│ Replica 1  │
│ Large      │
└────────────┘

┌────────────┐
│ Replica 2  │
│ Large      │
└────────────┘

          ↓
   Custom Endpoint
   "production"
```

And:

```text
Low-capacity:
┌────────────┐
│ Replica 3  │
│ Small      │
└────────────┘

┌────────────┐
│ Replica 4  │
│ Small      │
└────────────┘

          ↓
   Custom Endpoint
   "reporting"
```

Now:

```text
Production application
        ↓
Production custom endpoint
        ↓
High-capacity instances


Internal reporting
        ↓
Reporting custom endpoint
        ↓
Low-capacity instances
```

That's exactly what the question wants.

---

# 6. Why isn't Reader Endpoint enough?

Reader endpoint means:

> "Send my read request to the Aurora readers."

But it doesn't mean:

> "Send production users to large readers and employees to small readers."

It can distribute across the available reader instances.

The question wants **specific groups based on capacity**.

Therefore:

**Custom endpoints.**

---

## 🧠 Your notes

Write this:

> **Aurora Cluster:** Primary writer + Aurora Replicas for reads.

> **Cluster/Writer Endpoint:** Connects to the current primary/writer. Used for read/write operations.

> **Reader Endpoint:** Load-balances read traffic across Aurora Replicas.

> **Instance Endpoint:** Connects to one specific Aurora DB instance.

> **Custom Endpoint:** Connects/load-balances across a **specific subset of Aurora instances** based on criteria such as instance class/capacity.

### Exam shortcut:

**Need normal reads → Reader endpoint**

**Need current writer → Cluster endpoint**

**Need one specific DB → Instance endpoint**

**Need different groups of DB instances → Custom endpoint** ⭐

Yes — **exactly**, with one small correction:

The question is not asking to redirect users to different **applications**. It is asking the application to send **different types of database traffic** to different Aurora instances.

Think of it like this:

```text
                    Application
                         |
             ┌───────────┴───────────┐
             |                       |
       Production traffic       Reporting traffic
       (important users)        (internal staff)
             |                       |
             ▼                       ▼
     Custom Endpoint A        Custom Endpoint B
             |                       |
             ▼                       ▼
     High-capacity Aurora     Low-capacity Aurora
          instances                instances
```

### The key clue

> **production traffic → high-capacity instances**

> **reporting queries → low-capacity instances**

So Aurora needs to know:

* "Production request? → send to this group."
* "Reporting request? → send to that group."

That's exactly what **Aurora Custom Endpoints** are for.

### Don't confuse this with `Reader Endpoint`

Reader endpoint means:

> "I have read-only queries. Send them across my Aurora Replicas."

But it doesn't let you say:

> "Send production reads to the powerful replicas and reporting reads to the weaker replicas."

For that, use **custom endpoints**.

### Exam shortcut 🧠

When you see:

**"different types of traffic → different groups of Aurora instances"**

Think:

> **Custom Endpoint**

When you see:

**"read requests → distribute among Aurora Replicas"**

Think:

> **Reader Endpoint**

So your understanding is correct: **different request types should go to different endpoints**, and those endpoints point to the appropriate group of Aurora instances.
