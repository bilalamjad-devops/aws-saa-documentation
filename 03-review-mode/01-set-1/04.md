4. Question

Category: CSAA – Design Secure Architectures

A software development company is using serverless computing with AWS Lambda to build and run applications without having to set up or manage servers. The company has a Lambda function that connects to a MongoDB Atlas, which is a popular Database as a Service (DBaaS) platform, and also uses a third-party API to fetch certain data for its application. One of the developers was instructed to create the environment variables for the MongoDB database hostname, username, and password, as well as the API credentials that will be used by the Lambda function for DEV, SIT, UAT, and PROD environments.

Considering that the Lambda function is storing sensitive database and API credentials, how can this information be secured to prevent other developers on the team, or anyone, from seeing these credentials in plain text? Select the best option that provides maximum security.

- There is no need to do anything because, by default, Lambda already encrypts the environment variables using the AWS Key Management Service.
- Enable SSL encryption that leverages on AWS CloudHSM to store and encrypt the sensitive information.
- `Create a new AWS KMS key and use it to enable encryption helpers that leverage on AWS Key Management Service to store and encrypt the sensitive information.`
- Lambda does not provide encryption for the environment variables. Deploy your code to an Amazon EC2 instance instead.

Yes — this question is really asking about **how to hide secrets from other developers who have access to the Lambda console**.

Let's simplify the whole scenario.

### 1. What does the Lambda function need?

Your Lambda needs credentials like:

```text
MongoDB hostname = mongodb.example.com
MongoDB username = admin
MongoDB password = MySecretPassword123

API key = abc123...
API secret = xyz789...
```

These are **secrets**.

The developer wants to put them into **Lambda environment variables**.

---

### 2. The important problem

Lambda **does encrypt environment variables at rest by default** using AWS KMS.

But imagine another developer has permission to view the Lambda function in the AWS Console.

They may be able to see the environment-variable values through the Lambda console.

So the question is essentially saying:

> **"How do I encrypt these secrets AND prevent other developers with Lambda access from seeing the plaintext values?"**

That's the key.

---

### 3. Why isn't the default Lambda encryption enough?

Think of two levels:

**Normal/default encryption:**

```text
Lambda Environment Variables
        ↓
AWS-managed/default KMS key
        ↓
Encrypted at rest 🔒
```

Good for protecting the data when stored.

But someone with sufficient Lambda permissions may still be able to see the environment variables through the console.

---

### 4. What does the correct answer do?

You create **your own KMS key** and enable Lambda's **encryption helpers**.

```text
Your secrets
     ↓
Your KMS key
     ↓
Encrypted environment variable
     ↓
Lambda
```

The important benefit is that **you control the KMS key permissions**.

For example:

```text
Developer
   ↓
Can view Lambda
   ↓
❌ Cannot use KMS key
   ↓
Cannot decrypt secret
```

But:

```text
Lambda execution role
   ↓
Has permission to use KMS key
   ↓
✅ Can decrypt secret
```

So the secret is protected even from developers who can access the Lambda configuration.

---

### 5. Don't confuse KMS with CloudHSM

This option:

> Enable SSL encryption that leverages AWS CloudHSM

is wrong.

**SSL/TLS = encryption in transit**

For example:

```text
Lambda ─────🔒─────> MongoDB
```

It protects the network connection.

But the question is primarily concerned with **protecting stored credentials** and controlling who can decrypt them.

That's where **KMS** comes in.

---

### 6. One important real-world point

For an actual production architecture, I would generally prefer:

**AWS Secrets Manager** for MongoDB/API credentials rather than putting the actual passwords directly in Lambda environment variables.

For SAA questions, however, when the question specifically talks about **Lambda environment-variable encryption helpers + KMS**, the expected answer is:

> ✅ **Create your own AWS KMS key and use Lambda encryption helpers.**

### 🧠 SAA memory trick

Remember these three:

| Situation                               | Think               |
| --------------------------------------- | ------------------- |
| Encrypt data at rest                    | **KMS**             |
| Encrypt data in transit                 | **TLS/SSL**         |
| Store application passwords/API secrets | **Secrets Manager** |

And for this exact question:

**"Lambda environment variables + prevent developers from seeing plaintext" → customer-managed KMS key + encryption helpers.**
