# Q51 — What is this question trying to teach?

The question is testing:

> **RDS Multi-AZ vs Read Replica**

The important problem is:

**“What happens if my RDS database's Availability Zone goes down?”**

The answer is:

👉 **Multi-AZ**

Think:

**Database failure / AZ failure → Multi-AZ**

---

# 1. What is RDS?

**Amazon RDS = managed relational database service.**

Instead of installing/managing MySQL, PostgreSQL, Oracle, etc. yourself on EC2, AWS manages much of it for you.

Example:

```text
Your application
       ↓
      RDS
       ↓
    MySQL
```

---

# 2. What is Multi-AZ?

Suppose your primary database is here:

```text
AZ-A
┌──────────────┐
│ RDS Primary  │
└──────────────┘
```

With Multi-AZ, AWS maintains a **standby** in another AZ:

```text
AZ-A                    AZ-B
┌──────────────┐       ┌──────────────┐
│ RDS Primary  │ ───→  │ RDS Standby  │
└──────────────┘       └──────────────┘
       synchronous replication
```

If AZ-A fails:

```text
AZ-A ❌

AZ-B
┌──────────────┐
│ RDS Standby  │
│ becomes      │
│ primary      │
└──────────────┘
```

AWS performs the failover automatically.

### Key idea:

**Multi-AZ = High Availability**

---

# 3. What is a Read Replica?

A Read Replica is primarily for **scaling read traffic**.

Example:

```text
             ┌── Read Replica
             │
Application ─┤
             │
             └── Read Replica

             ↑
          Primary
```

The primary handles writes.

The replicas handle additional reads.

The replication is generally **asynchronous**.

So:

**Read Replica = Read scaling**

not primarily:

**Read Replica = automatic HA**

---

# 4. The easiest way to distinguish them

| Feature                   | Multi-AZ              | Read Replica                    |
| ------------------------- | --------------------- | ------------------------------- |
| Main purpose              | **High availability** | **Read scaling**                |
| Standby?                  | ✅ Yes                 | ❌ No, replica for reads         |
| Replication               | **Synchronous**       | Generally asynchronous          |
| Automatic failover        | ✅ Yes                 | ❌ Not automatic in the same way |
| Different AZ              | ✅ Yes                 | Can be                          |
| Helps read-heavy workload | Not its main purpose  | ✅ Yes                           |

---

# 5. Apply this to Q51

The key sentence is:

> **“repeated outages in the Availability Zone”**

That's the clue.

They don't have a performance problem.

They don't need more read capacity.

They have:

**AZ failure → database unavailable**

Therefore:

👉 **Multi-AZ**

### Exam shortcut

Whenever you see:

* AZ failure
* database must remain available
* automatic failover
* standby
* synchronous replication

Think:

> 🧠 **RDS Multi-AZ**

## What about the other answers?

### Snapshot

```text
RDS → Snapshot
```

Snapshot = **backup**

It doesn't keep your application running during an AZ failure.

Think:

> **Snapshot = recover later**

---

### Increase instance size

```text
db.t3 → db.m5 → db.r5
```

This gives more:

* CPU
* RAM
* performance

But the database is still in the same AZ.

So:

> **Bigger database ≠ protection from AZ failure**

---

### Read Replica

Useful when the problem is:

> "Too many read requests."

Not:

> "My AZ keeps going down."

So:

> **Read Replica = scale reads**
