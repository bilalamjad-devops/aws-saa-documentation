14. Question

Category: CSAA – Design High-Performing Architectures

A popular social media website uses a Amazon CloudFront web distribution to serve static content to millions of users around the globe. Recently, the website has received a number of complaints about long login times. Additionally, there are instances where users encounter HTTP 504 errors. The manager has instructed the team to significantly reduce login time and further optimize the system.

Which of the following options should be used together to set up a cost-effective solution that improves the application’s performance? (Select TWO.)

- Deploy your application to multiple AWS regions to accommodate your users around the world. Set up a Route 53 record with latency routing policy to route incoming traffic to the region that provides the best latency to the user.
- Establish multiple Amazon VPCs in different AWS regions and configure a transit VPC to interconnect all of your resources. To handle the requests faster, set up AWS Lambda functions in each region with the AWS Serverless Application Model (SAM) service.
- `Customize the content that the CloudFront web distribution delivers to your users using Lambda@Edge, which allows your AWS Lambda functions to execute the authentication process in AWS locations closer to the users.`
- `Implement an origin failover by creating an origin group that includes two origins. Assign one as the primary origin and the other as secondary, which enables CloudFront to automatically switch to if the primary origin encounters specific HTTP status code failure responses.`

- Configure your origin to add a Cache-Control max-age directive to your objects, and specify the longest practical value for max-age to increase the cache hit ratio of your CloudFront distribution.


Yes — your understanding is **mostly right**, but there is one important distinction: **CloudFront is serving the static content, but the login/authentication process is dynamic logic.**

### First, picture the architecture

Normally:

**User → CloudFront Edge Location → S3 / Application Origin**

CloudFront is excellent for static files such as:

* HTML
* CSS
* JavaScript
* images
* videos

So if your website is in S3, CloudFront puts copies of those static files closer to users around the world.

But **login is different**. Login usually requires some processing/authentication.

For example:

```text
User in Pakistan
       ↓
CloudFront Edge
       ↓
Authentication logic
       ↓
Backend
       ↓
Database / Identity system
```

### Why Lambda@Edge?

Suppose your user is in Pakistan, but your authentication logic is running in an AWS Region far away.

The request might travel:

```text
Pakistan user
      ↓
CloudFront Edge in nearby location
      ↓
far-away AWS Region
      ↓
authentication
      ↓
response
```

That adds latency.

With **Lambda@Edge**, you can execute certain Lambda logic at CloudFront's edge locations, closer to the user:

```text
Pakistan user
      ↓
CloudFront Edge
      ↓
Lambda@Edge
      ↓
authentication logic
```

So the purpose is **not to make S3 faster**.

It is to move suitable **request/response processing closer to the user**.

---

## But what about the 504?

That's a separate problem.

A **504 Gateway Timeout** generally means CloudFront waited for a response from the origin but didn't get one in time.

So the question has **two problems**:

### Problem 1 — Login is slow

Use:

**Lambda@Edge**

Run suitable authentication/request-processing logic closer to users.

### Problem 2 — Sometimes origin gives 504

Use:

**CloudFront Origin Failover**

You create:

```text
                ┌── Primary Origin
CloudFront ─────┤
                └── Secondary Origin
```

If the primary origin fails with configured error codes, CloudFront can send the request to the secondary origin.

So:

```text
User
 ↓
CloudFront
 ↓
Primary Origin ❌
 ↓
Secondary Origin ✅
```

This improves availability and helps with the 504 problem.

---

### One important correction to your thinking

You said:

> "we have static website in S3?"

**Possibly, but the question doesn't say that.**

It only says CloudFront is being used to serve static content.

The application can look something like:

```text
                  CloudFront
                 /          \
          Static content    Dynamic/login
               ↓                 ↓
              S3          Application/Backend
```

CloudFront can handle both static content and requests that ultimately go to an application origin.

### Exam shortcut 🧠

Remember this pair:

| Problem                              | Think of                       |
| ------------------------------------ | ------------------------------ |
| Need logic closer to global users    | **Lambda@Edge**                |
| Origin sometimes fails               | **CloudFront Origin Failover** |
| Static content slow                  | **CloudFront caching**         |
| Need application in multiple regions | **Multi-Region + Route 53**    |

And **Lambda@Edge ≠ making S3 copies**. CloudFront already handles the caching/distribution of static content. Lambda@Edge is for **running code at CloudFront edge locations**.
