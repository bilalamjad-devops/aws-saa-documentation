9. Question

Category: CSAA – Design High-Performing Architectures

A retail company receives raw .csv data files into its Amazon S3 bucket from multiple sources on an hourly basis, with an average file size of 2 GB. The bucket is managed using S3 Access Grants for fine‑grained access control.

An automated process must be implemented to convert these .csv files into the more efficient Apache Parquet format and store the converted files in another S3 bucket. Additionally, the conversion process must be automatically initiated each time a new file is uploaded into the S3 bucket.

Which of the following options must be implemented to meet these requirements with the LEAST operational overhead?



- `Utilize an AWS Glue extract, transform, and load (ETL) job to process and convert the .csv files to Apache Parquet format and then store the output files into the target S3 bucket. Configure an Amazon EventBridge rule to trigger the Glue job on S3 Object Created events.`
- Create an ETL (Extract, Transform, Load) job and a Data Catalog table in AWS Glue. Configure the Glue crawler to run on a schedule to check for new files in the S3 bucket every hour and convert them to Parquet format.
- Use an AWS Lambda function triggered by an S3 Object Created event to convert the .csv files to Parquet format. Use the AWS Transfer Family with SFTP service to move the output files to the target S3 bucket.
- Set up an Apache Spark job running in an Amazon EC2 instance and create an Amazon EventBridge rule to monitor S3 Object Created events in the S3 bucket. Configure AWS Lambda to invoke the Spark job for every new .csv file added via a Function URL.

## But why Parquet?

This is the important concept.

**CSV is a simple text-based format.**

**Parquet is a data-storage format designed for analytics.**

Imagine you have a huge CSV:

```text
id,name,city,age,salary
1,Bilal,Islamabad,25,100000
2,Ali,Lahore,30,120000
3,Ahmed,Karachi,28,90000
...
millions of rows
```

If an analytics system only wants:

> "Give me the salary of everyone."

With CSV, the system generally has to read through the rows and parse the text.

Parquet stores data in a **columnar format**.

Conceptually:

```text
CSV:

id | name | city | age | salary
--------------------------------
1  | Bilal| ISB  | 25  | 100000
2  | Ali  | LHR  | 30  | 120000
3  | Ahmed| KHI  | 28  | 90000
```

Parquet is organized more like:

```text
ID column       → 1, 2, 3...
NAME column     → Bilal, Ali, Ahmed...
CITY column     → ISB, LHR, KHI...
AGE column      → 25, 30, 28...
SALARY column   → 100000, 120000, 90000...
```

So if an analytics query only needs `salary`, it can efficiently read the relevant column instead of processing all the other columns.

It also supports **compression**, so large datasets can often take less storage and be processed more efficiently.

# What service does the actual conversion?

The key phrase is:

> **"convert .csv files to Apache Parquet"**

That's a **data transformation / ETL** job.

So immediately think:

> **AWS Glue**

Glue is a **serverless ETL service**.

It can read:

```text
S3 CSV
```

transform it:

```text
CSV → Parquet
```

and write:

```text
S3 Parquet
```

So:

```text
S3 bucket A
   │
   │ CSV
   ↓
AWS Glue ETL
   │
   │ Parquet
   ↓
S3 bucket B
```

---

# But how does Glue know when a new file arrives?

The question says:

> "automatically initiated each time a new file is uploaded"

That means **event-driven**.

Something happens:

```text
S3 Object Created
```

and we want AWS to react immediately.

That's where **Amazon EventBridge** comes in.

So:

```text
New CSV uploaded to S3
          ↓
   S3 Object Created
          ↓
      EventBridge
          ↓
      Glue ETL Job
          ↓
      CSV → Parquet
          ↓
       S3 bucket
```

That's the correct architecture.

---

# Why not Lambda?

This is the important part.

You might think:

> "S3 can trigger Lambda, so why not Lambda?"

For a **small file**, Lambda could potentially work.

But the question tells you:

> **average file size = 2 GB**

That's a clue.

Lambda has resource and execution limitations, so using Lambda to perform large data transformations is not the ideal solution.

AWS Glue is designed specifically for **data processing and ETL workloads**.

Think:

| Requirement                          | Think                   |
| ------------------------------------ | ----------------------- |
| Small event-driven code              | Lambda                  |
| Large data transformation / ETL      | **Glue**                |
| CSV → Parquet                        | **Glue**                |
| Data processing                      | **Glue**                |
| S3 file uploaded → trigger something | EventBridge / S3 events |

---

# Why not Glue Crawler?

This is another important distinction.

The wrong option says:

> Run a Glue crawler every hour to check for new files and convert them.

A **Glue Crawler does NOT perform the CSV → Parquet transformation.**

Its job is mainly to:

> **discover data/schema and populate the Glue Data Catalog.**

Think:

```text
Glue Crawler
      ↓
"What columns and schema does this data have?"
      ↓
Glue Data Catalog
```

Whereas:

```text
Glue ETL Job
      ↓
"Transform this data."
      ↓
CSV → Parquet
```

So don't confuse:

**Crawler = discover/catalog**

**ETL Job = transform/process**

---

# Why EventBridge instead of a schedule?

The requirement says:

> "each time a new file is uploaded"

That's an **event**, not a schedule.

Bad approach:

```text
Every hour
   ↓
Check S3
   ↓
Is there a new file?
   ↓
Process it
```

Better:

```text
File uploaded
     ↓
Event occurs
     ↓
EventBridge
     ↓
Glue
```

The second approach is more immediate and avoids unnecessary checking.

# What about S3 Access Grants?

Don't let that distract you.

The question mentions:

> "The bucket is managed using S3 Access Grants..."

That's mainly about **who can access the S3 data**.

It isn't the main problem you're solving.

The actual problem is:

> **Process 2-GB CSV files automatically and convert them to Parquet.**

So focus on:

**Glue + EventBridge.**

# The four options in simple language

### Option 1 — ✅ Correct

```text
S3
 ↓
EventBridge
 ↓
Glue ETL
 ↓
Parquet
 ↓
S3
```

Exactly what we want.

---

### Option 2 — ❌

```text
Glue Crawler
 ↓
check every hour
```

Crawler discovers schema/data.

It isn't the transformation engine.

And scheduled checking isn't as good as triggering when the file actually arrives.

---

### Option 3 — ❌

```text
S3
 ↓
Lambda
 ↓
CSV → Parquet
 ↓
Transfer Family
 ↓
S3
```

Too complicated.

Also, **Transfer Family is unnecessary**. It's primarily for managed file-transfer protocols such as SFTP/FTPS/FTP.

We're already inside AWS/S3. We don't need SFTP just to move the transformed object between S3 buckets.

And 2-GB files make Lambda a poor choice for this transformation.

---

### Option 4 — ❌

```text
S3
 ↓
EventBridge
 ↓
Lambda
 ↓
EC2 Spark
```

This can theoretically be engineered, but look at the complexity:

* EC2
* Spark
* Lambda
* EventBridge
* infrastructure management

The question explicitly says:

> **LEAST operational overhead**

Why build and maintain Spark infrastructure when **Glue already provides managed ETL**?
