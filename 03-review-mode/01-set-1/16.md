16. Question

Category: CSAA – Design Cost-Optimized Architectures

A company is using AWS Fargate to run a batch job whenever an object is uploaded to an Amazon S3 bucket. The minimum ECS task count is initially set to 1 to save on costs and should only be increased based on new objects uploaded to the S3 bucket.

Which is the most suitable option to implement with the LEAST amount of effort?

- `Set up an Amazon EventBridge (Amazon CloudWatch Events) rule to detect S3 object PUT operations and set the target to the ECS cluster to run a new ECS task.`
- Set up an alarm in CloudWatch to monitor S3 object-level operations recorded on CloudTrail. Set two alarm actions to update the ECS task count to scale-out/scale-in depending on the S3 event.

- Set up an Amazon EventBridge (Amazon CloudWatch Events) rule to detect S3 object PUT operations and set the target to a Lambda function that will run the StartTask API command.
- Set up an alarm in Amazon CloudWatch to monitor S3 object-level operations that are recorded on CloudTrail. Create an Amazon EventBridge (Amazon CloudWatch Events) rule that triggers the ECS cluster when new CloudTrail events are detected.

Exactly — your understanding is basically correct. The confusing part is **what "batch job" means** and how **S3 → EventBridge → Fargate** connects.

Let's build it from zero.

## 1. First, your ECS/Fargate understanding

Think:

* **ECS** = AWS service for running/managing containers.
* **Fargate** = compute engine that runs those ECS containers **without you managing EC2 servers**.
* **EKS** = AWS-managed Kubernetes.
* **EC2** = you manage the servers yourself.

So:

```text
ECS + Fargate
     ↓
Run Docker containers
     ↓
No EC2 server management
```

And yes, **Fargate is serverless compute for containers**.

---

# 2. What is a "batch job"?

A batch job is basically:

> **Do some work, then finish.**

For example, imagine the company receives files:

```text
S3 Bucket
│
├── invoice1.csv
├── invoice2.csv
├── invoice3.csv
└── invoice4.csv
```

Whenever a new file arrives, the company wants to process it.

Maybe the processing means:

```text
CSV file
   ↓
Container
   ↓
Read file
   ↓
Process data
   ↓
Generate result
   ↓
Upload result to S3
   ↓
Container finishes
```

That container's execution is the **batch job**.

It isn't necessarily a web application that runs forever.

---

# 3. What does the question want?

The company says:

> "Whenever an object is uploaded to S3, run my batch job."

So the desired architecture is:

```text
             NEW FILE
                ↓
          Amazon S3 Bucket
                ↓
           EventBridge
                ↓
          ECS Task / Fargate
                ↓
          Process the file
                ↓
              DONE
```

That's the whole question.

---

# 4. Why EventBridge?

EventBridge basically says:

> **"When X happens, do Y."**

Here:

**X = S3 object uploaded**

**Y = Start an ECS task**

So:

```text
S3 PUT event
     ↓
EventBridge
     ↓
Run ECS task
```

This is much cleaner than writing your own Lambda.

---

# 5. Why not Lambda?

You *could* do:

```text
S3
 ↓
EventBridge
 ↓
Lambda
 ↓
Start ECS task
```

But ask yourself:

> Why do I need Lambda in the middle?

EventBridge can directly target ECS.

Therefore:

```text
S3
 ↓
EventBridge
 ↓
ECS/Fargate
```

is simpler.

And the question specifically says:

> **LEAST amount of effort**

Therefore, remove unnecessary components.

---

# 6. What does "minimum ECS task count = 1" mean?

This part can be confusing.

Suppose initially:

```text
ECS Service
Desired count = 1
```

So there is one task running.

Then:

```text
file1 uploaded
     ↓
EventBridge
     ↓
start another ECS task
```

Then:

```text
file2 uploaded
     ↓
EventBridge
     ↓
start another ECS task
```

etc.

The important idea is:

> **An S3 upload event causes a new ECS task to run.**

The question isn't asking you to build complicated CPU-based auto scaling.

It's asking for **event-driven execution**.

---

# 7. Very important exam pattern

You should recognize this pattern:

### "When something happens → do something"

Think:

### **EventBridge**

Examples:

```text
S3 object created
      ↓
EventBridge
      ↓
Lambda
```

or

```text
S3 object created
      ↓
EventBridge
      ↓
ECS task
```

or

```text
EC2 state changes
      ↓
EventBridge
      ↓
SNS
```

EventBridge is the **event router**.

---

## 8. Why the other options are unnecessarily complicated

### Option 1 — EventBridge → ECS ✅

```text
S3
 ↓
EventBridge
 ↓
ECS/Fargate
```

Simple. Correct.

---

### Option 2 — CloudWatch Alarm + CloudTrail ❌

```text
S3
 ↓
CloudTrail
 ↓
CloudWatch
 ↓
Alarm
 ↓
scaling
```

Too many components.

You already have the event directly available to EventBridge.

---

### Option 3 — EventBridge → Lambda → ECS ❌

```text
S3
 ↓
EventBridge
 ↓
Lambda
 ↓
ECS
```

This can work, but Lambda is unnecessary.

If EventBridge can directly start the ECS task:

> **Why introduce Lambda?**

---

### Option 4 — CloudTrail + CloudWatch + EventBridge ❌

Again, unnecessarily complicated.

---

# 9. One correction to your thinking

You said:

> "ECS is to run containers"

**Yes.**

And:

> "Fargate is serverless"

**Yes.**

But don't think:

> "Fargate = batch jobs only."

No.

Fargate can run many types of container workloads:

```text
ECS + Fargate
│
├── Web application
├── API
├── Microservice
├── Background worker
└── Batch job
```

The question happens to use Fargate for a **batch job** because the container needs to run when an S3 event occurs and then finish.
