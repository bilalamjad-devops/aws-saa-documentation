45. Question

Category: CSAA – Design Cost-Optimized Architectures

A company hosted a web application in an Auto Scaling group of EC2 instances. The IT manager is concerned about the over-provisioning of the resources that can cause higher operating costs. A Solutions Architect has been instructed to create a cost-effective solution without affecting the performance of the application.

Which dynamic scaling policy should be used to satisfy this requirement?

- `Use target tracking scaling.`
- Use scheduled scaling.
- Use simple scaling.
- Use suspend and resume scaling.

Yes. Keep this one simple for SAA. The main thing is to recognize **what triggers the scaling**.

### 1. Target Tracking Scaling ⭐

**What is it?**

You tell Auto Scaling:

> "Keep this metric around this target."

Example:

```text
Target CPU = 50%

CPU > 50% → add EC2 instances
CPU < 50% → remove EC2 instances
```

It continuously adjusts capacity based on demand.

**Why use it?**

* Avoid over-provisioning
* Automatically add/remove instances
* Good for changing/unpredictable workloads
* Helps control cost while maintaining performance

**Exam clue:**

> "Maintain CPU around 50%"
> "Avoid over-provisioning"
> "Automatically adjust capacity based on demand"

➡️ **Target Tracking**

---

### 2. Scheduled Scaling

You already **know when demand will happen**.

Example:

```text
8:00 AM → scale from 2 → 10 instances
5:00 PM → scale from 10 → 2 instances
```

**Why?**

Because the workload is predictable.

Example:

> Office application is heavily used every day from 9 AM–5 PM.

➡️ **Scheduled Scaling**

**Exam clue:**

> predictable traffic
> known schedule
> every morning
> every weekend
> business hours

➡️ **Scheduled Scaling**

---

### 3. Simple Scaling

This is an older/basic scaling approach based on a **CloudWatch alarm**.

Example:

```text
CPU > 70%
      ↓
CloudWatch Alarm
      ↓
Add 2 instances
      ↓
Cooldown
```

The important exam point:

> After a scaling action, simple scaling waits for the **cooldown period** before another scaling action.

So it is less responsive than modern approaches such as target tracking/step scaling.

**Exam clue:**

If the question specifically talks about **CloudWatch alarm + cooldown + add/remove fixed number of instances**, think:

➡️ **Simple Scaling**

---

### 4. Suspend and Resume Scaling

This is **not really a scaling strategy for handling normal demand**.

It means:

> "Temporarily stop one or more Auto Scaling processes."

For example, during maintenance:

```text
Normal scaling
      ↓
Suspend scaling
      ↓
Perform maintenance/troubleshooting
      ↓
Resume scaling
```

You temporarily pause activities such as launching or terminating instances.

**Exam clue:**

> temporarily pause scaling
> maintenance
> troubleshooting
> stop scaling activities

➡️ **Suspend/Resume**

---

# 🧠 SAA Cheat Sheet

| Policy              | Think                                  |
| ------------------- | -------------------------------------- |
| **Target Tracking** | 🎯 "Keep metric around X"              |
| **Scheduled**       | 🕐 "I know when traffic will happen"   |
| **Simple**          | 🚨 "Alarm → scaling action → cooldown" |
| **Suspend/Resume**  | ⏸️ "Temporarily stop scaling"          |

### Your Question #45

The problem says:

> **over-provisioning → higher cost → adjust resources according to demand**

There is no predictable schedule.

So:

**🎯 Target Tracking Scaling** ✅

The easiest mental model is:

> **Target Tracking = "Give me just enough EC2 capacity to maintain my target."**
