40. Question

Category: CSAA – Design Secure Architectures

A travel photo-sharing website is using Amazon S3 to serve high-quality photos to visitors. After a few days, it was discovered that other travel websites are linking to and using these photos. This has resulted in financial losses for the business. The team initially applied PutBucketPolicy with referrer restrictions, but found that referrer headers can be spoofed, rendering this approach insufficient.

What is the MOST effective method to mitigate this issue?

- `Configure your S3 bucket to remove public read access and use pre-signed URLs with expiry dates.`
- Move the high-quality photos to Amazon WorkDocs to serve them privately.
- Use Amazon CloudFront distributions for your photos.
- Block the IP addresses of the offending websites using NACL.

### Question 40 — simple concept

The problem is **hotlinking**:

```text
Your S3
  ↓
Your website → Photo
  ↓
Other website → Photo ❌
```

Other websites are directly using your public S3 photos, so **you pay for requests/data transfer**.

The key clue is:

> **Referrer headers can be spoofed**

So don't rely on `Referer` restrictions.

### Best solution

**Make S3 private + use pre-signed URLs.** ✅

```text
User
 ↓
Your application
 ↓
Generate temporary pre-signed URL
 ↓
S3 private object
```

The URL works only for a limited time.

Example conceptually:

```text
photo.jpg
     ↓
Pre-signed URL
     ↓
Valid for 10 minutes
```

After 10 minutes → ❌ access denied.

### Why the other answers?

**CloudFront** → speeds up delivery; by itself, it doesn't solve unauthorized sharing.

**NACL** → IP blocking is weak because attackers/websites can change IPs.

**WorkDocs** → wrong service for serving website images.

### 🧠 Remember

> **Private S3 + temporary controlled access → Pre-signed URL**

And one important distinction:

**Pre-signed URL ≠ permanent public URL.**

Anyone who gets the pre-signed URL can use it **until it expires**, so your application should generate URLs with an appropriate short expiry.
