35. Question

Category: CSAA – Design High-Performing Architectures

A startup is using Amazon RDS to store data from a web application. Most of the time, the application has low user activity but it receives bursts of traffic within seconds whenever there is a new product announcement. The Solutions Architect needs to create a solution that will allow users around the globe to access the data using an API.

What should the Solutions Architect do meet the above requirement?

- Create an API using Amazon API Gateway and use an Auto Scaling group of Amazon EC2 instances to handle the bursts of traffic in seconds.
- Create an API using Amazon API Gateway and use Amazon Elastic Beanstalk with Auto Scaling to handle the bursts of traffic in seconds.
- Create an API using Amazon API Gateway and use the Amazon ECS cluster with Service Auto Scaling to handle the bursts of traffic in seconds.
- `Create an API using Amazon API Gateway and use AWS Lambda to handle the bursts of traffic in seconds.`

Yes. This question is mainly testing **one concept: sudden burst traffic + very low traffic most of the time → serverless Lambda**.

Let's build it from your current knowledge.

## 1. What is the situation?

Imagine your startup has a web application:

```text
Normal time
100 users
↓
Very little traffic

New product announced
↓
10,000 users arrive within seconds
```

The important phrase is:

> **"bursts of traffic within seconds"**

And another important phrase:

> **"Most of the time, low user activity"**

So we need something that:

1. Doesn't require servers sitting around doing nothing.
2. Can scale **very quickly** when thousands of requests arrive.

---

# 2. What does API Gateway do?

You already saw API Gateway in Question 31.

Think of it as the **front door/API endpoint**.

```text
User
  ↓
API Gateway
  ↓
Backend
  ↓
RDS
```

For example:

```text
GET /products
POST /orders
GET /users
```

API Gateway receives these API requests and sends them to the backend.

But **API Gateway itself isn't the main compute solution here.**

The question is:

> What should handle the sudden burst?

# 3. Why Lambda?

The architecture becomes:

```text
                  ┌── Lambda instance
                  │
Users → API Gateway → Lambda → RDS
                  │
                  ├── Lambda instance
                  │
                  └── Lambda instance
```

Suppose 10 requests arrive:

```text
10 requests
    ↓
Lambda
    ↓
Lambda can run multiple instances concurrently
```

Then suddenly:

```text
10,000 requests
       ↓
Lambda
       ↓
More concurrent Lambda execution capacity
```

You don't manually launch EC2 instances.

AWS manages the scaling.

---

# 4. Compare this with EC2 Auto Scaling

This is the key SAA point.

### EC2 Auto Scaling

Suppose you currently have:

```text
2 EC2 instances
```

Then product announcement happens:

```text
10,000 requests
       ↓
ASG detects increased demand
       ↓
Launch additional EC2
       ↓
Wait for instances to start
       ↓
Application becomes ready
```

Launching and initializing EC2 capacity takes time.

The question specifically says:

> **burst within seconds**

Therefore, traditional EC2 Auto Scaling isn't the best fit.

---

# 5. What about ECS?

Same basic problem.

```text
Traffic increases
       ↓
ECS Service Auto Scaling
       ↓
Need additional task capacity
       ↓
Scale out
```

It can scale, but Lambda is much more suitable when you need **very fast, serverless scaling for request-driven workloads**.

---

# 6. What about Elastic Beanstalk?

Elastic Beanstalk makes deploying applications easier.

Remember your previous question:

> Elastic Beanstalk = AWS manages much of the infrastructure for your application.

But underneath, it still uses resources such as EC2.

So:

```text
Elastic Beanstalk
       ↓
EC2
       ↓
Auto Scaling
```

Again, scaling additional EC2 capacity isn't as quick as Lambda's ability to create concurrent executions.

Look at the requirements:

| Requirement                  | Best fit             |

| Users need an API            | **API Gateway**      |
| Traffic normally low         | **Lambda**           |
| Sudden burst within seconds  | **Lambda**           |
| Don't want to manage servers | **Lambda**           |
| Global users                 | API Gateway + Lambda |
| Database already exists      | **RDS**              |

So:

```text
Users worldwide
       ↓
API Gateway
       ↓
AWS Lambda
       ↓
Amazon RDS
```

Exactly — you're thinking about the architecture correctly. The missing piece is that **API Gateway throttling and Lambda scaling solve two different problems**.

### Think of the flow

```text
Users
  ↓
API Gateway
  ↓
Lambda
  ↓
RDS
```

Each component has a different job:

* **API Gateway** → receives API requests, authentication, throttling, routing, etc.
* **Lambda** → runs the application's business logic.
* **RDS** → stores the application's data.

### Your question: "If API Gateway limits requests, why Lambda?"

Because **throttling doesn't process the request**.

Suppose API Gateway allows 1,000 requests/second:

```text
10,000 users
     ↓
API Gateway
     ↓
Only 1,000/sec allowed
     ↓
Lambda
     ↓
RDS
```

API Gateway is basically saying:

> "I will control how many requests are allowed through."

But **something still has to execute those requests**.

That's Lambda's job.

---

### Example: product announcement

A user calls:

```text
GET /products/123
```

API Gateway receives it.

Then what?

It needs something to actually do:

```text
1. Receive product ID
2. Validate request
3. Query RDS
4. Process the result
5. Return response
```

That application logic can run in **Lambda**.

```text
User
 ↓
API Gateway
 ↓
Lambda
 ├── validate request
 ├── query RDS
 ├── process result
 └── return response
```

RDS **cannot normally act as your application/API logic**. It's primarily your database.

---

### The important distinction

Think of it like a restaurant:

```text
API Gateway = receptionist
Lambda      = waiter/chef
RDS         = storage/database
```

The receptionist can say:

> "Only 100 customers at a time."

That's **throttling**.

But someone still needs to prepare the customer's order.

That's **Lambda**.

---

### And why Lambda specifically?

Because the question says:

> **Low activity most of the time + huge burst within seconds**

With EC2:

```text
Traffic ↑
   ↓
ASG notices
   ↓
Launch EC2
   ↓
Wait for capacity
```

With Lambda:

```text
Traffic ↑
   ↓
Lambda creates/increases concurrent executions
   ↓
Process requests
```

So the exam is really testing:

> **API Gateway controls and exposes the API; Lambda provides the compute that processes the API requests.**

And **throttling is not a replacement for compute**. It is a mechanism to protect/control the system.

One final nuance: API Gateway throttling can actually make the situation **more controlled**, but if you need to handle a large burst *within seconds*, you still need a backend capable of scaling quickly. That's why **API Gateway + Lambda** is the best answer here.

```text

     │ maximum allowed request rate
```

### API Gateway throttling

Controls **how many requests are allowed through**.

### Lambda scaling

Controls **how much compute capacity is available to process those requests**.

For example:

```text
      ↓
```
