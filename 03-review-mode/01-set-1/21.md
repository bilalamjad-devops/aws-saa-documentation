21. Question

Category: CSAA – Design Secure Architectures

A company has a web application that uses Amazon CloudFront to distribute its images, videos, and other static content stored in its Amazon S3 bucket to users around the world. The company has recently introduced a new member-only access feature for some of its high-quality media files. There is a requirement to provide access to multiple private media files only to paying subscribers without having to change the current URLs.

Which of the following is the most suitable solution to implement to satisfy this requirement?


- `Use Signed Cookies to control who can access the private files in your CloudFront distribution by modifying your application to determine whether a user should have access to your content. For members, send the required Set-Cookie headers to the viewer which will unlock the content only to them.`
- Create a Signed URL with a custom policy which only allows the members to see the private files.
- Configure your CloudFront distribution to use Field-Level Encryption to protect your private data and only allow access to members.
- Configure your CloudFront distribution to use Match Viewer as its Origin Protocol Policy which will automatically match the user request. This will allow access to the private content if the request is a paying member and deny it if it is not a member.

Yes — **your understanding is basically correct**, with one important refinement.

### What the question is saying

Imagine your S3 bucket has:

```text
S3
├── public-image.jpg
├── public-video.mp4
├── premium-video-1.mp4
├── premium-video-2.mp4
└── premium-video-3.mp4
```

CloudFront sits in front of S3:

```text
User → CloudFront → S3
```

Everyone can access the normal/public content.

Now the company says:

> "Only paying members should be able to access the premium files."

And there is an important requirement:

> **Don't change the current URLs.**

---

### Signed URL vs Signed Cookie

This is the key exam concept.

#### 1. Signed URL

A signed URL looks conceptually like:

```text
https://example.com/premium-video-1.mp4?signature=...
```

The authorization information is attached to the **URL itself**.

This is good when you want to give someone access to **one particular file**.

For example:

```text
User → signed URL → premium-video-1.mp4
```

---

#### 2. Signed Cookie

With a signed cookie, the URL can remain:

```text
https://example.com/premium-video-1.mp4
```

The authorization information is stored in the **browser's cookie**.

So:

```text
User logs in
      ↓
Application checks: "Is this person a paying member?"
      ↓
Yes
      ↓
CloudFront signed cookie is given to browser
      ↓
Browser requests premium files normally
      ↓
CloudFront checks the cookie
      ↓
Access allowed
```

That's why **signed cookies are the best answer here**.

### Your "don't login again and again" idea

You're thinking in the right direction, but don't confuse **normal login/session cookies** with **CloudFront signed cookies**.

The signed cookie specifically gives CloudFront authorization to access protected content.

For example, a subscriber might have:

```text
https://example.com/video1.mp4
https://example.com/video2.mp4
https://example.com/video3.mp4
```

The URLs don't need to change.

The browser sends the CloudFront signed cookie with the requests, and CloudFront checks it.

---

### The exam shortcut 🧠

Remember:

| Requirement                            | Choose            |
| -------------------------------------- | ----------------- |
| Protect **one specific file**          | **Signed URL**    |
| Protect **multiple files**             | **Signed Cookie** |
| **Don't change existing URLs**         | **Signed Cookie** |
| Member/subscriber area with many files | **Signed Cookie** |

So this question practically gives you the answer with:

> **multiple private media files + don't change current URLs**

→ **CloudFront Signed Cookies** ✅

And yes, your mental model of **S3 → CloudFront → users worldwide** is correct.
