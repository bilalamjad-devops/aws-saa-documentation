64. Question

Category: CSAA – Design Resilient Architectures

An organization requires a persistent block storage volume to support its mission-critical workloads. The backup data will be stored in an object storage service and, after 30 days, transitioned to an archival storage service for long-term retention. The team has already configured an Amazon EBS snapshot retention rule for point-in-time recovery.

What should be done to meet the above requirement?

- Attach an instance store volume in your Amazon EC2 instance. Use Amazon S3 to store your backup data and configure a lifecycle policy to transition your objects to S3 One Zone-IA.
- Attach an instance store volume in your existing Amazon EC2 instance. Use Amazon S3 to store your backup data and configure a lifecycle policy to transition your objects to S3 Glacier Flexible Retrieval.
- Attach an EBS volume to your Amazon EC2 instance. Use Amazon S3 to store your backup data and configure a lifecycle policy to transition your objects to S3 One Zone-IA.
- `Attach an EBS volume to your Amazon EC2 instance. Use Amazon S3 to store your backup data and configure a lifecycle policy to transition your objects to S3 Glacier Flexible Retrieval.`

Yes. This question is basically testing whether you can **separate three different storage requirements** instead of getting distracted by the EBS snapshot sentence.

### What is the question asking?

It wants **3 layers**:

1. **Mission-critical workload needs persistent block storage** → **EBS**
2. **Backup needs object storage** → **S3**
3. **Backup older than 30 days needs archival storage** → **S3 Glacier Flexible Retrieval**

So the mental picture is:

**EC2 → EBS → workload**

and separately:

**Backup → S3 → after 30 days → Glacier Flexible Retrieval**

### 1. Why EBS?

The phrase **"persistent block storage volume"** is the biggest clue.

* **EBS** = persistent **block storage**
* Attached to EC2
* Good for databases, OS disks, applications, etc.
* Data survives an EC2 stop/start.

Don't confuse it with **Instance Store**:

| Storage            | Type           | Persistent? | Typical use                     |
| ------------------ | -------------- | ----------- | ------------------------------- |
| **EBS**            | Block          | ✅ Yes       | Important/mission-critical data |
| **Instance Store** | Block          | ❌ No        | Temporary/cache/scratch data    |
| **S3**             | Object         | ✅ Yes       | Backup, files, objects          |
| **Glacier**        | Object/archive | ✅ Yes       | Long-term archive               |

---

### 2. Why S3 for backup?

The question explicitly says:

> "backup data will be stored in an **object storage service**"

That's basically screaming **S3**.

S3 is **object storage**.

Then S3 Lifecycle can automatically move objects between storage classes.

---

### 3. Why Glacier after 30 days?

The important words are:

> **"after 30 days, transitioned to an archival storage service for long-term retention."**

That's your clue for:

**S3 → Glacier**

Here, the answer uses **S3 Glacier Flexible Retrieval**.

So:

**Day 0:** Backup → S3
**Day 30:** S3 Lifecycle → Glacier Flexible Retrieval
**Long term:** Glacier

---

## The tricky part: EBS snapshots

The question deliberately tells you:

> "The team has already configured an Amazon EBS snapshot retention rule"

Don't think:

**EBS Snapshot → S3 → Glacier**

That's the trap.

Although EBS snapshots are stored in AWS-managed infrastructure backed by S3, **you don't manage those snapshot objects using your normal S3 Lifecycle rules**.

So if the question specifically asks you to create:

**backup → S3 → after 30 days → Glacier**

you need to create/use **your own S3 backup objects**.

---

## Why not One Zone-IA?

This is another clue.

**One Zone-IA** means:

> "I don't access this data frequently, but I still want it readily available."

It's **infrequent-access storage**, not your main archival choice.

Think:

| Requirement                             | Think                |
| --------------------------------------- | -------------------- |
| Frequently accessed                     | S3 Standard          |
| Infrequently accessed                   | S3 Standard-IA       |
| Cheap, single-AZ infrequent storage     | S3 One Zone-IA       |
| Archive                                 | **S3 Glacier**       |
| Very long-term, rarely accessed archive | Glacier Deep Archive |

No — **that's exactly the trap in this question.** ❌

An **EBS snapshot is stored in AWS-managed S3 infrastructure**, but you **cannot take that EBS snapshot and use an S3 Lifecycle rule to move it to S3 Glacier**.

Think of it like this:

```text
EBS Volume
    ↓
EBS Snapshot
    ↓
AWS manages snapshot storage
    ❌ You don't control it with normal S3 Lifecycle
```

Whereas if **you create your own backup data as S3 objects**:

```text
EBS / Application
      ↓
Your backup
      ↓
S3
      ↓ 30 days
S3 Glacier Flexible Retrieval
```

### The exam shortcut

| Situation                   | Can you lifecycle to Glacier?  |
| --------------------------- | ------------------------------ |
| **EBS snapshot**            | ❌ Not with normal S3 Lifecycle |
| **Your own S3 object**      | ✅ Yes                          |
| EBS snapshot retention rule | Manages **snapshots**          |
| S3 Lifecycle rule           | Manages **S3 objects**         |

So when the question says **"EBS snapshot retention rule is already configured"**, don't think *"great, now move the snapshot to Glacier."*

It's actually telling you:

> **The snapshot part is already handled; now choose the appropriate storage for the separate backup requirement.**

That is why the answer is **EBS + S3 + S3 Glacier Flexible Retrieval**.
