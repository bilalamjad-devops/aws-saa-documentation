17. Question

Category: CSAA – Design High-Performing Architectures

An e-commerce company runs a highly scalable web application that depends on an Amazon Aurora database. As the number of users increases, the read replica faces difficulties keeping up with the increasing read traffic, causing performance bottlenecks during peak periods.

Which of the following will resolve the issue with the most cost-effective solution?

- Increase the size of the Aurora DB cluster.
- Set up a read replica that can operate across different regions.
- Implement read scaling with Aurora Global Database.
- `Use automatic scaling for the Aurora read replica using Aurora Auto Scaling.`

Yes — your thinking is basically correct. The key is to distinguish **read traffic** from **write traffic**, and then understand what Aurora Auto Scaling actually scales.

### First, your mental model

You already know:

* **RDS** → managed relational database.
* **Aurora** → AWS's high-performance relational database engine, available with MySQL/PostgreSQL compatibility.
* **DynamoDB** → NoSQL.
* **Aurora can have read replicas.**
* **Read replica = another database instance used mainly for SELECT/read requests.**

Now imagine:

```text
                Customers
                    |
                    v
              Web Application
                    |
             +------+------+
             |             |
          WRITE          READ
             |             |
             v             v
        Aurora Writer   Aurora Reader
                         Reader 1
                         Reader 2
```

Suppose your application has:

* 10,000 writes/day
* 1,000,000 reads/day

The **reads** can become the bottleneck.

For example:

```text
SELECT * FROM products;
SELECT * FROM orders;
SELECT * FROM users;
```

These are read operations.

---

## So what is happening in Question 17?

The question says:

> "the read replica faces difficulties keeping up with the increasing read traffic"

In simple words:

**Customers are doing more and more READ operations, and the existing read replica cannot handle all those reads efficiently.**

Think:

```text
Customers
   |
   | 100,000 READ requests
   v
Read Replica
   |
   | "Too much work!"
   v
Performance bottleneck
```

The solution is to automatically add/remove **read replicas** depending on demand.

### Aurora Auto Scaling

It can automatically adjust the number of Aurora Replicas based on workload.

For example:

**Normal traffic**

```text
Aurora Writer
     |
     +--- Reader 1
```

Peak traffic:

```text
Aurora Writer
     |
     +--- Reader 1
     +--- Reader 2
     +--- Reader 3
     +--- Reader 4
```

When traffic decreases, unnecessary replicas can be removed.

So:

> **More read traffic → more Aurora Replicas**

> **Less read traffic → fewer Aurora Replicas**

That's why the correct answer is:

**Use automatic scaling for the Aurora read replica using Aurora Auto Scaling.**

---

### Very important distinction

Don't think:

> "Aurora Auto Scaling makes the database itself bigger."

Instead think:

> **Aurora Auto Scaling adds/removes Aurora read replicas.**

That's the important SAA exam concept.

### Your options

| Option                    | What it does                                 | Problem                             |
| ------------------------- | -------------------------------------------- | ----------------------------------- |
| Increase DB cluster size  | Makes existing database capacity larger      | Costs more continuously             |
| Cross-region read replica | Adds readers in another Region               | Not needed here                     |
| Aurora Global Database    | Multi-Region architecture                    | Not needed; problem is read scaling |
| **Aurora Auto Scaling**   | **Automatically adds/removes read replicas** | ✅ Best                              |

---

## One correction to your mental model

You said:

> "customers face difficulty when they face read data from db?"

**Yes, but technically the customer isn't necessarily "having difficulty reading."**

The **database is having difficulty processing the huge number of read requests**.

For example:

```text
100 customers
    ↓
100 read requests
    ↓
Reader handles easily ✅
```

But:

```text
100,000 customers
       ↓
100,000 read requests
       ↓
One reader
       ↓
CPU/connections become overloaded ❌
```

Aurora Auto Scaling helps:

```text
100,000 customers
       ↓
Read traffic
       ↓
+-------------------------+
| Aurora Auto Scaling     |
+-------------------------+
       ↓
Reader 1
Reader 2
Reader 3
Reader 4
```

The reads can then be distributed among the available Aurora Replicas.

### Remember this for SAA

**Aurora Reader/Replica → handles READS**

**Aurora Writer → handles WRITES**

**Aurora Auto Scaling → automatically adds/removes READ REPLICAS**

**Aurora Global Database → primarily Multi-Region / global applications + DR + local reads**

And one important correction from your earlier understanding: **Aurora Auto Scaling is not the same thing as "Aurora v2 can scale."** The exam may use "Aurora Auto Scaling" specifically to mean **automatic scaling of Aurora Replicas for read capacity**.

Yes — you're building the right mental model, but there are **2 important corrections**.

## 1. First: Aurora Serverless v2

Your understanding:

> Aurora v2 is serverless, so it is good for auto scaling.

Almost correct, but be careful with the terminology.

**Aurora Serverless v2** is a deployment/capacity option for Aurora that can automatically adjust **compute capacity** based on workload.

So:

```text
Low workload
   ↓
small compute capacity
   ↓
High workload
   ↓
larger compute capacity
```

But **Aurora Serverless v2 is NOT the same thing as Aurora Auto Scaling.**

For SAA, keep these separate:

* **Aurora Serverless v2** → automatically adjusts database **compute capacity**
* **Aurora Auto Scaling** → automatically adds/removes **Aurora Replicas** for read traffic

---

# 2. Your Multi-AZ understanding needs one correction

You said:

> primary in one AZ, standby/backup in another AZ

That's broadly right for **RDS Multi-AZ**.

But you said:

> it is async means data duplicates not at the spot

❌ This is the important correction.

For **RDS Multi-AZ**, replication to the standby is **synchronous**.

Think:

```text
                RDS
                 |
        +--------+--------+
        |                 |
      AZ-A              AZ-B
        |                 |
     PRIMARY            STANDBY
        |                 |
        +----SYNC--------+
```

A write is synchronously replicated to the standby.

If the primary fails:

```text
PRIMARY ❌
   ↓
STANDBY
   ↓
becomes PRIMARY
```

The standby is **not normally used to serve read traffic**.

That's very important.

---

# 3. Then where do we put READ REPLICAS?

This is where things become much easier if you visualize the architecture.

### RDS Multi-AZ

```text
AZ-A                  AZ-B

PRIMARY  ----------->  STANDBY
   ↑                     ↑
 Writes              Failover
```

The standby is primarily for **high availability/failover**.

---

### Read Replica

A read replica is different:

```text
AZ-A                  AZ-B

PRIMARY  ----------->  READ REPLICA
   |                       |
 Writes                  READS
                           ↑
                      Customers
```

The read replica is there to **handle read traffic**.

Historically/typically, RDS read replicas use **asynchronous replication**.

So:

```text
Primary
   |
   | async replication
   ↓
Read Replica
```

There can be a small replication lag.

---

# 4. Can the Read Replica be in another AZ?

**Yes.**

For example:

```text
Region: us-east-1

AZ-A
 └── RDS Primary

AZ-B
 └── RDS Read Replica

AZ-C
 └── RDS Read Replica
```

And your application can send read requests to the replicas.

```text
                    Application
                  /      |      \
                 /       |       \
              WRITE     READ    READ
                |         |       |
                ↓         ↓       ↓
             Primary   Replica1 Replica2
```

---

# 5. Now understand the difference between Standby and Read Replica

This is **very important for SAA**.

|                               | Multi-AZ Standby                | Read Replica                    |
| ----------------------------- | ------------------------------- | ------------------------------- |
| Main purpose                  | **High availability**           | **Read scaling**                |
| Normally serves reads?        | ❌ No                            | ✅ Yes                           |
| Replication                   | **Synchronous**                 | **Asynchronous**                |
| Used for automatic failover?  | ✅ Yes                           | ❌ Not normally                  |
| Can help read-heavy workload? | ❌                               | ✅                               |
| Can be in another AZ?         | Yes                             | Yes                             |
| Can be cross-region?          | Depends on service/architecture | ✅ Yes for supported RDS engines |

### Easy memory trick:

> **Standby = "Save me if primary dies."**

> **Read Replica = "Help me because too many people are reading."**

---

# 6. And Aurora makes this even more interesting

Aurora has a slightly different architecture.

You can have:

```text
             Aurora Cluster
                  |
        +---------+---------+
        |                   |
      Writer              Readers
        |              /     |     \
        |          Reader1 Reader2 Reader3
        |
   Applications
```

Aurora Replicas can serve read traffic.

If your application suddenly gets huge read traffic:

```text
Normal:

Writer
  |
  +--- Reader 1


Peak:

Writer
  |
  +--- Reader 1
  +--- Reader 2
  +--- Reader 3
  +--- Reader 4
```

**Aurora Auto Scaling** can automatically adjust the number of Aurora Replicas.

That's exactly what Question 17 was testing.
