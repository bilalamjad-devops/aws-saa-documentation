56. Question

Category: CSAA – Design Secure Architectures

A company hosted an e-commerce website on an Auto Scaling group of Amazon EC2 instances behind an Application Load Balancer. The Solutions Architect noticed that the website is receiving a high number of illegitimate external requests from multiple systems with frequently changing IP addresses. To address the performance issues, the Solutions Architect must implement a solution that would block these requests while having minimal impact on legitimate traffic.

Which of the following options fulfills this requirement?

- Create a regular rule in AWS WAF and associate the web ACL to an Application Load Balancer.
- Create a private connection using AWS PrivateLink to block the offending requests.
- Create a custom network ACL and associate it with the subnet of the Application Load Balancer to block the offending requests.
- `Create a rate-based rule in AWS WAF and associate the web ACL to an Application Load Balancer.`

Exactly. You already know the important part: **AWS WAF protects web applications**, including things like SQL injection, XSS, malicious HTTP requests, etc.

Question 56 is teaching you one **specific WAF feature: rate-based rules**.

## 1. What is the question actually saying?

The website is:

```text
Internet
   ↓
Application Load Balancer
   ↓
EC2 Auto Scaling Group
```

The problem is:

> A huge number of **illegitimate requests** are hitting the website.

And there are **many IP addresses**, which keep changing.

The architect wants:

> Block excessive/malicious requests **without blocking legitimate users**.

The important clue is:

### "high number of requests"

That should make you think:

> **WAF rate-based rule**

---

# 2. Regular WAF rule vs Rate-based WAF rule

Think of WAF as a security guard checking HTTP requests.

### Regular WAF rule

It asks:

> "Does this request match a bad pattern?"

For example:

```text
Request
   ↓
Does it contain SQL injection?
   ↓
YES → BLOCK
NO  → ALLOW
```

You can make rules for things like:

* SQL injection
* XSS
* specific IP addresses
* countries
* HTTP headers
* URI paths
* malicious patterns

So a **regular rule** is basically:

> **"Does this request match my condition?"**

---

# 3. Rate-based rule

A rate-based rule asks a different question:

> **"How many requests is this IP sending?"**

For example, suppose you configure:

```text
Maximum = 1,000 requests / 5 minutes / IP
```

Then:

```text
Normal user
IP A
↓
100 requests / 5 min
↓
ALLOW


Attacker
IP B
↓
50,000 requests / 5 min
↓
RATE LIMIT EXCEEDED
↓
BLOCK
```

So the rate-based rule is excellent when the problem is:

> **Too many requests from the same source/IP.**

---

# 4. Why does the question mention frequently changing IPs?

This is the tricky part.

You might think:

> "I'll create a NACL and block the attacker's IP."

But the question says:

> **frequently changing IP addresses**

So:

```text
Attacker IP 1 → block
Attacker IP 2 → block
Attacker IP 3 → block
Attacker IP 4 → block
...
```

That's not a good scalable solution.

Instead, WAF can dynamically monitor request rates.

```text
IP A → 50 requests → okay
IP B → 200 requests → okay
IP C → 100,000 requests → BLOCK
```

So you're not manually maintaining a list of bad IP addresses.

---

# 5. WAF sits in the right place

The architecture becomes:

```text
                    Internet
                       ↓
                    AWS WAF
                       ↓
             Application Load Balancer
                       ↓
                EC2 Auto Scaling
                       ↓
                   Application
```

WAF checks the incoming web requests **before they reach your application servers**.

And WAF can be associated with an **ALB**.

---

# 6. What is AWS PrivateLink?

This is unrelated to the problem.

**PrivateLink = private connectivity.**

Think:

```text
VPC A
  ↓
AWS PrivateLink
  ↓
VPC B / AWS service
```

It allows private communication between VPCs/services.

It is **not**:

> "Check HTTP requests and block attackers."

So when you see:

> PrivateLink

think:

**private network connectivity**, not web security.

---

# 7. Why NACL isn't the best answer

You already learned:

> **NACL = subnet-level, stateless firewall**

It can do things like:

```text
DENY 1.2.3.4
ALLOW 5.6.7.8
```

But it doesn't understand:

> "This IP has sent 50,000 HTTP requests in 5 minutes."

That's exactly the kind of thing WAF rate-based rules are designed for.

---

# 🧠 The important SAA distinction

Memorize this:

| Requirement                                | Think                   |
| ------------------------------------------ | ----------------------- |
| SQL injection                              | **WAF**                 |
| XSS                                        | **WAF**                 |
| HTTP request filtering                     | **WAF**                 |
| Block requests based on HTTP conditions    | **WAF regular rule**    |
| Too many requests from an IP               | **WAF rate-based rule** |
| Subnet-level network filtering             | **NACL**                |
| Instance-level filtering                   | **Security Group**      |
| DDoS protection                            | **AWS Shield**          |
| Private connectivity between VPCs/services | **PrivateLink**         |

### And the question's clue:

> **"high number of illegitimate external requests"**

→ WAF

> **"frequently changing IP addresses"**

→ Don't manually block IPs with NACL

> **"minimal impact on legitimate traffic"**

→ Don't simply block everyone; use **rate-based rule**

### Final mental shortcut:

**WAF regular rule:**

> "Is this request bad?"

**WAF rate-based rule:**

> "Is this source sending TOO MANY requests?"

That's the main lesson of Question 56.
