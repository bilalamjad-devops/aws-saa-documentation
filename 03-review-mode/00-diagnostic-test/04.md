4. Question

Category: CSAA – Design High-Performing Architectures

A company is refactoring an application’s architecture to leverage an AWS Lambda function and Amazon API Gateway. The application receives 5 KB JSON blobs, processes it, and stores the result to an Amazon Aurora database. The application only needs to acknowledge when it has accepted a request, not when it has processed it.

Initially, the application failed to meet acceptance criteria due to numerous throttling errors during data processing. To resolve this issue, the company had to raise the default number of Lambda concurrent executions several times.

How can a solutions architect improve the scalability of the infrastructure to reduce throttling errors?

- Rewrite the Lambda function code into 2 functions – one function to receive the information and another function to persist the information into the database. Use Amazon Simple Notification Service (Amazon SNS) to signal available work to the second Lambda function.
- `Rewrite the Lambda function code into 2 functions – one function to receive the information and another function to persist the information into the database. Use Amazon Simple Queue Service (Amazon SQS) to signal available work to the second Lambda function.`
- Migrate the data store from Aurora to Amazon DynamoDB. Set up a DynamoDB Accelerator (DAX) cluster between the application and the DynamoDB database. Configure the read capacity units (RCUs) of the DynamoDB table to match the expected read throughput. Configure the application to route DynamoDB requests to the DAX cluster using the DAX client SDK.
- Rewrite the Lambda function code into a Go application that runs on an Amazon EC2 instance. Use native Go drivers for database connection.

Yes — this question is mainly testing **Lambda + SQS decoupling**, and the wording makes it look more complicated than it is.

## 1. First understand the problem

The application receives a request:

**5 KB JSON → API Gateway → Lambda → Aurora**

The important sentence is:

> **"The application only needs to acknowledge when it has accepted a request, not when it has processed it."**

This is the biggest clue.

It means the user does **NOT** need to wait for Aurora processing.

So instead of:

```text
User
 ↓
API Gateway
 ↓
Lambda
 ↓
Aurora
 ↓
Response to User
```

we can do:

```text
User
 ↓
API Gateway
 ↓
Lambda #1
 ↓
SQS
 ↓
Lambda #2
 ↓
Aurora
```

Now Lambda #1 can quickly say:

> "I received your request."

And the actual processing happens **later, asynchronously**.

---

# 2. Why are they getting throttling errors?

Suppose suddenly **10,000 requests** arrive.

Without SQS:

```text
10,000 requests
       ↓
10,000 Lambda executions trying to process
       ↓
Aurora
```

Lambda concurrency can become very high.

Eventually Lambda hits its concurrency limit:

> **THROTTLED**

The company tried increasing the Lambda concurrency limit several times.

But that's not necessarily the best architectural solution.

The better question is:

> **How can we absorb traffic spikes instead of forcing Lambda to process everything immediately?**

Answer:

## SQS = buffer

---

# 3. What SQS changes

With SQS:

```text
                ┌──────────────┐
User ──> API ──>│ Lambda #1    │
                └──────┬───────┘
                       ↓
                ┌──────────────┐
                │     SQS      │
                │   QUEUE      │
                └──────┬───────┘
                       ↓
                Lambda #2
                       ↓
                    Aurora
```

Imagine 10,000 requests arrive.

Lambda #1 doesn't need to process all 10,000.

It simply puts messages into SQS:

```text
SQS:
[request 1]
[request 2]
[request 3]
...
[request 10000]
```

Then Lambda #2 processes them as capacity becomes available.

So SQS acts as a **shock absorber/buffer**.

---

# 4. Why does this reduce throttling?

Imagine Aurora can comfortably handle processing at:

**100 requests/second**

But suddenly you receive:

**5,000 requests/second**

Without a queue:

```text
5000/sec
   ↓
Lambda
   ↓
Aurora
```

You're forcing the system to deal with the spike immediately.

With SQS:

```text
5000/sec
   ↓
Lambda #1
   ↓
SQS
   ↓
100/sec
   ↓
Lambda #2
   ↓
Aurora
```

The excess work waits in the queue.

This is called **decoupling**.

### Remember:

> **SQS doesn't make the work disappear. It separates the arrival rate from the processing rate.**

---

# 5. Why SQS and not SNS?

This is an extremely important SAA distinction.

### SQS

Think:

> **"I have work that needs to be processed."**

```text
Producer → SQS → Consumer
```

The message stays in the queue until a consumer processes it.

Excellent for:

* buffering
* asynchronous processing
* decoupling
* handling traffic spikes
* work queues

---

### SNS

Think:

> **"Something happened; tell multiple subscribers."**

```text
                 → Lambda
Publisher → SNS → SQS
                 → Email
                 → HTTP
```

SNS is primarily **pub/sub and fanout**.

For example:

> "An order was placed."

You might want:

* Lambda → update inventory
* SQS → billing
* Email → notification

That's SNS territory.

---

# 6. The clue that tells you SQS

This question gives you **three huge clues**:

### Clue 1

> "only needs to acknowledge when it has accepted a request"

Means:

**Asynchronous processing**

---

### Clue 2

> "numerous throttling errors"

Means:

**Too much work arriving at Lambda at once**

---

### Clue 3

> "process it later"

SQS is excellent for:

**buffering work between producer and consumer.**

Therefore:

**Lambda → SQS → Lambda**

---

# 7. Why not the other answers?

### ❌ Lambda → SNS → Lambda

SNS is designed for **publish/subscribe and fanout**.

Here, we have a **work queue**.

We don't want:

> "Tell everyone about this message."

We want:

> "Hold this work until a worker can process it."

That's SQS.

---

### ❌ DynamoDB + DAX

This is attacking the wrong problem.

The problem isn't:

> "DynamoDB reads are slow."

The problem is:

> **Too many Lambda executions/concurrency.**

Also, the application already uses Aurora and the question doesn't indicate that Aurora is the bottleneck.

---

### ❌ Move Lambda to EC2

That doesn't solve the architectural problem.

You'd simply replace:

```text
Lambda throttling
```

with the responsibility of managing:

```text
EC2 capacity
scaling
patching
availability
etc.
```

And the question wants a scalable, cost-effective architecture.

---

# 8. One very important exam concept

You should memorize this pattern:

### Synchronous

```text
Client
  ↓
API Gateway
  ↓
Lambda
  ↓
Database
  ↓
Response
```

Client waits for processing.

---

### Asynchronous

```text
Client
  ↓
API Gateway
  ↓
Lambda
  ↓
SQS
  ↓
Lambda
  ↓
Database
```

Client gets:

> **"Request accepted."**

Then processing happens later.

---

# 9. SQS vs SNS — memorize this

| Requirement                           | Choose  |
| ------------------------------------- | ------- |
| Queue work                            | **SQS** |
| Buffer traffic spikes                 | **SQS** |
| Decouple producer/consumer            | **SQS** |
| Process messages asynchronously       | **SQS** |
| One message → one worker processes it | **SQS** |
| Publish/subscribe                     | **SNS** |
| One message → multiple subscribers    | **SNS** |
| Fanout                                | **SNS** |
| Notifications                         | **SNS** |

And an extremely common architecture is:

```text
Producer
   ↓
SNS
   ↓
 ┌───────┬───────┬───────┐
 ↓       ↓       ↓
SQS     Lambda   Email
```

SNS can **fan out** to multiple destinations, including SQS.

---

## 🧠 Your mental model for this question

Don't think:

> "Lambda is throttling → increase Lambda concurrency."

Think:

> **"Requests are arriving faster than processing → put a queue between receiving and processing."**

Then:

**Queue = SQS**

So the answer becomes obvious:

> **Lambda #1 → SQS → Lambda #2 → Aurora**

This is one of the most important SAA architecture patterns: **decouple the producer from the consumer using SQS to absorb spikes and enable asynchronous processing.**
