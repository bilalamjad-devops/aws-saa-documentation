3. Question

Category: CSAA – Design Secure Architectures

A company needs to limit the visibility and discoverability of workloads across AWS accounts with differing administrative requirements. Using AWS Organizations, a solutions architect and accounts stakeholders grouped accounts into organizational units (OU).

A solution is required that will monitor changes to the OU hierarchy and allow stakeholders to subscribe to related alerts.

Which option meets these requirements with the LEAST administrative overhead?

- Use AWS CloudFormation stacksets to create resources across Organizations. Initiate the drift detection operation on a stack to identify changes.
- Use AWS Control Tower to provision the AWS accounts. Set up AWS Config aggregated rules.
- `Use AWS Control Tower to provision the AWS accounts. Enable account drift notifications.`
- Use AWS Service Catalog to create accounts in Organizations. Configure an AWS CloudTrail organization trail to consolidate changes across accounts.

This one is testing a **very specific AWS Control Tower concept**, so don't overthink it.

### What is the question actually asking?

You already have:

**AWS Organizations → multiple AWS accounts → OUs**

Now management wants:

> "If someone changes the OU/account structure, detect it and let stakeholders subscribe to alerts."

And the key phrase is:

**"LEAST administrative overhead"**

So we're looking for an AWS service that already has this capability rather than building our own monitoring.

### Why Control Tower?

Think of **AWS Control Tower = management/governance layer on top of AWS Organizations**.

It helps manage a multi-account AWS environment and provides governance features.

For this question:

> **Control Tower + account drift notifications**

is the most direct solution because Control Tower already understands the organization/account structure and can notify stakeholders about relevant drift.

### The important distinction

Don't confuse these:

| Service                            | Think of it as                                            |
| ---------------------------------- | --------------------------------------------------------- |
| **AWS Organizations**              | Manage accounts + OUs                                     |
| **AWS Control Tower**              | Govern/manage a multi-account environment                 |
| **AWS Config**                     | "Is this resource configured correctly?"                  |
| **CloudTrail**                     | "Who did what API action?"                                |
| **CloudFormation Drift Detection** | "Did someone change my CloudFormation-managed resources?" |
| **Service Catalog**                | Publish/provision approved products                       |

So if the question says:

> **Monitor OU/account hierarchy changes + notifications + least overhead**

👉 **Control Tower account drift notifications**

---

### Why the other answers are wrong

**CloudFormation StackSets + drift detection ❌**

CloudFormation drift asks:

> "Did someone change a resource that CloudFormation manages?"

It isn't designed specifically to monitor your **Organizations OU hierarchy**.

---

**Control Tower + AWS Config aggregated rules ❌**

AWS Config is excellent for:

> "Are my EC2/S3/IAM/etc. resources compliant?"

But this question is about **changes to the Organizations structure**, not resource configuration compliance.

---

**Service Catalog + CloudTrail organization trail ❌**

CloudTrail can absolutely record Organizations API calls.

But you'd then need additional logic to:

1. identify OU-related events
2. filter them
3. generate meaningful alerts
4. notify stakeholders

That's **more operational overhead**.

---

### 🧠 Exam shortcut

When you see:

> **AWS Organizations + OUs + multi-account governance + least administrative overhead**

Immediately think:

**AWS Control Tower**

And when you see:

> **resource configuration compliance**

think:

**AWS Config**

When you see:

> **who performed an API action / audit trail**

think:

**CloudTrail**

When you see:

> **CloudFormation-managed resource changed manually**

think:

**CloudFormation Drift Detection**

---

### One correction to keep in mind

The wording in these Tutorials Dojo explanations can sometimes make Control Tower sound like it is simply "an OU monitoring service." It isn't. **Control Tower is primarily a multi-account governance/orchestration service**, and the exam is testing that its built-in governance/drift capabilities can satisfy this requirement with less custom work.

So your mental model should be:

**Organizations = structure**
**Control Tower = govern that structure**
**Config = resource compliance**
**CloudTrail = API activity/audit**

That distinction is much more valuable for SAA than memorizing this particular answer.
