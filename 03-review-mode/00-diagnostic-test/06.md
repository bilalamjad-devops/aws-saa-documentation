6. Question

Category: CSAA – Design Cost-Optimized Architectures

A company runs an internal application on AWS which uses Amazon EC2 instances for compute and Amazon RDS for PostgreSQL for its data store. Considering the application only runs during working hours on weekdays, a solution is required to optimize costs with minimal operational overhead.

Which solution would satisfy these requirements?

- Purchase reserved instance subscriptions for EC2 and RDS
- Purchase a compute savings plan for EC2 and RDS.

- `Deploy the AWS CloudFormation template of the Instance Scheduler on AWS. Set up the start and stop schedules of the EC2 instance and RDS DB instance.`
- Create an Amazon CloudWatch alarm that triggers an AWS Lambda function when CPU utilization falls below an idle threshold. In the function, implement logic for stopping both the EC2 instance and the RDS database.


Yes — this question is mainly testing **“when should I use discounts vs when should I stop resources?”**

### The key clue

> **“only runs during working hours on weekdays”**

That means the workload is **predictable but not 24/7**.

For example:

* Monday–Friday: 9 AM → 5 PM
* Saturday–Sunday: OFF
* Nights: OFF

So instead of paying for 24/7 capacity, **stop EC2 and RDS when they aren't needed**.

### Why Instance Scheduler is correct

**Instance Scheduler on AWS** lets you define a schedule such as:

```text
Monday–Friday
  9:00 AM  → Start EC2 + RDS
  5:00 PM  → Stop EC2 + RDS

Saturday–Sunday
  → Keep stopped
```

So you're only paying for the resources while they're actually needed.

And importantly, **Instance Scheduler is an AWS-provided CloudFormation solution/template**, not a normal AWS service like EC2 or RDS.

---

## Why the other answers are wrong

### 1. Reserved Instances ❌

Reserved Instances are useful when you know:

> "I need this capacity consistently for a long period."

Example:

```text
EC2 → running 24/7 for 1 or 3 years
RDS → running 24/7 for 1 or 3 years
```

You get a discount in exchange for the commitment.

But here:

```text
Weekday working hours → needed
Nights/weekends       → NOT needed
```

So don't commit to capacity that you're not using most of the time.

---

### 2. Compute Savings Plan ❌

Same basic problem.

Savings Plans are good when you have **consistent compute spending**.

Also remember:

> **Compute Savings Plans do NOT cover RDS DB instances.**

So this answer is particularly bad because the application uses both **EC2 + RDS**.

---

### 3. CloudWatch + Lambda based on CPU ❌

This sounds clever, but it's the wrong trigger.

Imagine it's Tuesday at 2 PM and the application temporarily has:

```text
CPU = 5%
```

That doesn't mean:

> "The company isn't working anymore. Shut everything down."

The application could simply be idle for a few minutes.

The requirement already tells us **exactly when the resources are needed**, so use a **schedule**, not CPU utilization.

---

# 🔑 Your SAA mental model

Keep this table in your notes:

| Situation                                   | Think of                               |
| ------------------------------------------- | -------------------------------------- |
| Need capacity 24/7 for years                | **Reserved Instances / Savings Plans** |
| EC2 workload is interruptible               | **Spot Instances**                     |
| Need capacity in a specific AZ              | **Capacity Reservation**               |
| Resources needed only during specific hours | **Instance Scheduler**                 |
| Unpredictable load + automatically adjust   | **Auto Scaling / Target Tracking**     |

### One more important distinction

**Cost optimization doesn't always mean "get a discount."**

Sometimes the best optimization is:

> **Don't run the resource when you don't need it.**

That's exactly what Question 6 is testing.

### Instance Scheduler is NOT an EC2 feature

**Instance Scheduler on AWS** is an AWS-provided **solution implemented through CloudFormation**. You deploy that solution, and it then manages the start/stop schedules for your EC2 and RDS resources.

So in the TutorialsDojo question, they specifically say:

> "Deploy the AWS CloudFormation template of Instance Scheduler on AWS."

That's why that answer is correct.

### But can you use Terraform?

**Yes, you can use Terraform to automate the same idea**, but you shouldn't think of that as "using the Instance Scheduler feature of EC2."

You could build your own scheduling architecture with Terraform, for example:

```text
Terraform
   │
   ├── EventBridge Scheduler
   │       │
   │       └── Start/Stop
   │
   ├── IAM permissions
   │
   └── Lambda / automation
          │
          ├── EC2
          └── RDS
```

Or you can deploy/manage AWS's Instance Scheduler solution through infrastructure-as-code, depending on the solution's current supported deployment approach.

### For the SAA exam, remember this

Don't get stuck on **CloudFormation vs Terraform**.

The exam is testing:

> **Resources needed only at predictable times → schedule start/stop → Instance Scheduler.**

Whereas:

> **Resources needed continuously → Reserved Instances/Savings Plans**

> **Workload can be interrupted → Spot**

> **Need guaranteed capacity in a specific AZ → Capacity Reservation**

So if you see:

**"EC2 + RDS only needed during business hours"**

your brain should immediately go:

**👉 Instance Scheduler → start/stop on a schedule.**
