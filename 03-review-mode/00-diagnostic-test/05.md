5. Question

Category: CSAA – Design High-Performing Architectures

A company operates a three-tier application with all its components hosted on AWS, except for the data layer. This data layer consists of a MySQL-compatible database located on-premises, connected to AWS through a Site-to-Site VPN. The database’s memory consumption ranges from 2 to 16 GiB.

On the other hand, the application experiences unpredictable traffic patterns, including spikes and periods of zero activity, which translates to irregular load on the database. The company wants to replace the on-premises database with a managed service that can automatically adapt to varying demands through serverless capacity scaling.

Which option will meet these requirements?

- Set up an Amazon Aurora database with a memory-optimized DB instance class type.
- Set up an Amazon RDS for the MySQL database with 4 gigabytes of memory.
- Set up an Amazon DynamoDB table with auto-scaling enabled. Configure the table with a minimum of 2 and a maximum of 16 capacity units.
- `Configure an Amazon Aurora Serverless v2 database with a minimum capacity of 1 and a maximum of 8 Aurora capacity units (ACUs).`

Yes — **you correctly understand the first part**, but there is an important distinction in what this question is asking.

The company **does have an on-premises MySQL-compatible database**, and they want to **replace it with a managed AWS database**.

But the question is **not asking "How do we migrate the database?"**

It is asking:

> **"Once we replace it, which AWS database service should we use?"**

That's why the answer is **Aurora Serverless v2**, not a migration service.

---

## 1. What is happening in the scenario?

Current architecture:

```text
AWS
┌──────────────────────────────┐
│  Web tier                    │
│  Application tier            │
└──────────────┬───────────────┘
               │
            VPN
               │
               ↓
      ┌─────────────────┐
      │ On-Premises     │
      │ MySQL Database  │
      └─────────────────┘
```

The company wants to get rid of that on-premises database.

So the desired architecture is approximately:

```text
AWS
┌──────────────────────────────┐
│ Web + Application            │
│                              │
│              ↓               │
│       Aurora Serverless v2   │
└──────────────────────────────┘
```

The question is:

**What database should replace MySQL?**

---

# 2. Why Aurora Serverless v2?

Look at the requirements one by one.

### Requirement #1 — MySQL-compatible

The existing database is:

> MySQL-compatible

Aurora supports:

> **MySQL-compatible**

✅ Aurora fits.

---

### Requirement #2 — unpredictable traffic

The application has:

```text
high traffic
   ↓
low traffic
   ↓
zero traffic
   ↓
high traffic
```

So you don't want to permanently provision a large database.

---

### Requirement #3 — automatically scale capacity

This is the biggest clue:

> **"serverless capacity scaling"**

Aurora Serverless v2 can automatically adjust database capacity.

Therefore:

**Aurora Serverless v2 = MySQL-compatible + automatically adjusts capacity**

---

# 3. The 2–16 GiB clue

This is the clever part of the question.

They tell you:

> Database memory consumption ranges from **2 to 16 GiB**.

Aurora Serverless v2 uses:

> **ACU (Aurora Capacity Unit)**

For the purposes of this question:

**1 ACU ≈ 2 GiB memory**

Therefore:

```text
2 GiB  → 1 ACU
16 GiB → 8 ACU
```

So configure:

```text
Minimum = 1 ACU
Maximum = 8 ACUs
```

That's exactly why this answer is correct.

---

# 4. Why not normal Aurora?

This option:

> Set up an Amazon Aurora database with a memory-optimized DB instance class.

Aurora itself is a managed relational database.

But normal/provisioned Aurora works roughly like:

```text
Choose instance
       ↓
db.r...
       ↓
Fixed CPU/memory
```

If you choose a large instance to handle the spike:

```text
Peak demand
    ↓
large instance
```

During zero traffic:

```text
Zero traffic
    ↓
large instance still running
    ↓
$$$$
```

That's over-provisioning.

Aurora **Serverless v2** instead allows capacity to adjust:

```text
Low demand
   ↓
~1 ACU

High demand
   ↓
up to ~8 ACU
```

---

# 5. Why not RDS MySQL?

This one is very important for the exam.

RDS MySQL:

```text
Choose instance
       ↓
Fixed capacity
```

For example:

> 4 GiB instance

It doesn't automatically change its compute capacity continuously based on workload the way Aurora Serverless v2 does.

So:

```text
Traffic = 0
     ↓
4 GiB instance still running
```

Not ideal.

---

# 6. Why not DynamoDB?

DynamoDB is serverless and can scale.

So initially you might think:

> "Serverless + auto scaling = DynamoDB!"

But the existing application uses:

> **MySQL-compatible database**

DynamoDB is:

> **NoSQL**

That means changing:

```text
MySQL
 ↓
DynamoDB
```

could require substantial application redesign.

Therefore:

**MySQL-compatible → Aurora**

**NoSQL → DynamoDB**

---

# 7. Your migration question is still VERY important

You said:

> "they have on-premises DB, they want to move, they should use other service to migrate database right?"

### YES. Absolutely.

If the question were:

> **"How should we migrate the existing on-premises MySQL database to AWS Aurora with minimal downtime?"**

Then we'd start thinking about:

### AWS Database Migration Service (DMS)

For example:

```text
On-premises MySQL
       │
       │ AWS DMS
       ↓
Aurora MySQL
```

DMS is about **moving/replicating the data**.

But this question isn't asking:

> "How do we move the data?"

It's asking:

> **"Which AWS database should we choose to replace the existing database?"**

So:

**Database selection → Aurora Serverless v2**

**Database migration → potentially AWS DMS**

These are two separate questions.

---

# 8. Very important SAA distinction

Think of these as two stages:

### Stage 1 — Choose the destination

Current:

```text
On-prem MySQL
```

Requirement:

```text
MySQL-compatible
+
serverless
+
automatically scales
+
unpredictable workload
```

Answer:

**Aurora Serverless v2**

---

### Stage 2 — Move the data

Once you've chosen Aurora:

```text
On-prem MySQL
       │
       │ DMS
       ↓
Aurora Serverless v2
```

DMS may be used for the migration.

**The question only asks Stage 1.**

---

When you see:

> **MySQL/PostgreSQL + unpredictable workload + serverless database + automatic capacity scaling**

Immediately think:

### **Aurora Serverless v2**

When you see:

> **Need to migrate/replicate on-premises database → AWS**

Think:

### **AWS DMS**

When you see:

> **NoSQL + massive scale + serverless**

Think:

### **DynamoDB**

And one correction to keep in your notes: **Aurora Serverless v2 is the compute-scaling feature here; Aurora itself is the relational/MySQL-compatible database.** That's the distinction this question is testing.

### For your SAA exam, think like this:

| Database                        | Can automatically scale capacity? | Type                                     |
| ------------------------------- | --------------------------------- | ---------------------------------------- |
| **Aurora Serverless v2**        | ✅ Yes                             | Relational / MySQL/PostgreSQL compatible |
| **DynamoDB**                    | ✅ Yes                             | NoSQL                                    |
| **Normal Aurora (provisioned)** | ❌ Not automatically for compute   | Relational                               |
| **RDS MySQL**                   | ❌ Not automatically for compute   | Relational                               |
| **RDS PostgreSQL**              | ❌ Not automatically for compute   | Relational                               |

### The key mental model

**Need SQL/relational + automatic scaling → Aurora Serverless v2**

**Need NoSQL + automatic scaling → DynamoDB**

So don't memorize simply:

> "Aurora v2 and DynamoDB scale, everything else doesn't."

Instead memorize:

> **Serverless database requirement → identify the database type first.**

```text
Need relational/SQL?
        │
        └── Yes → Aurora Serverless v2

Need NoSQL?
        │
        └── Yes → DynamoDB
```

And remember your previous question:

**On-prem MySQL → Aurora Serverless v2** = choosing the destination.

**On-prem MySQL → AWS DMS → Aurora** = migrating the data.

That's a very important SAA distinction.
