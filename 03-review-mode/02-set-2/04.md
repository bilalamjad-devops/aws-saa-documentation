4. Question

Category: CSAA – Design High-Performing Architectures

A software company has resources hosted in AWS and on-premises servers. You have been requested to create a decoupled architecture for applications which make use of both resources.

Which of the following options are valid? (Select TWO.)

- Use RDS to utilize both on-premises servers and EC2 instances for your decoupled application
- `Use SWF to utilize both on-premises servers and EC2 instances for your decoupled application`
- Use DynamoDB to utilize both on-premises servers and EC2 instances for your decoupled application
- `Use SQS to utilize both on-premises servers and EC2 instances for your decoupled application`
- Use VPC peering to connect both on-premises servers and EC2 instances for your decoupled application

Yes. This question is mainly teaching you **decoupling**, and then testing which AWS services are actually designed to do it.

## 1. What is the question saying?

The company has:

```text
On-premises servers
        +
AWS EC2
```

And the applications on both sides need to communicate.

But they **don't want the applications to depend directly on each other**.

Instead of:

```text
On-prem app ─────────→ EC2 app
             direct connection
```

they want:

```text
On-prem app ──→ Queue ──→ EC2 app
                 ↑
                SQS
```

Now the two applications are **decoupled**.

### Why is this useful?

Suppose the EC2 application is temporarily unavailable.

With direct communication:

```text
On-prem → EC2 ❌
```

The request may fail.

With SQS:

```text
On-prem → SQS → EC2
```

The message can wait in SQS until the EC2 application is ready.

That's the basic idea of **decoupling**.

---

# 2. Can SQS be used with on-premises applications?

### YES. ✅

This is an important point.

SQS is an **AWS managed service**, but the application producing or consuming messages does **not have to be running on EC2**.

For example:

```text
On-prem application
        ↓
      SQS
        ↓
EC2 application
```

Your on-premises application can communicate with SQS using AWS APIs/SDKs and appropriate AWS credentials/network connectivity.

Similarly:

```text
EC2 application
        ↓
      SQS
        ↓
On-prem application
```

can also work.

So remember:

> **SQS can decouple AWS resources, on-premises applications, or a combination of both.**

---

# 3. What is SWF?

This is the older/less commonly encountered service in modern AWS questions.

**SWF = Amazon Simple Workflow Service.**

Its purpose is to **coordinate long-running workflows across distributed applications**.

Imagine an order:

```text
Order received
      ↓
Payment
      ↓
Inventory
      ↓
Shipping
      ↓
Email customer
```

You have multiple separate components.

SWF can help coordinate:

> "Payment completed → now run inventory → then shipping → then notification."

So:

### SQS

**Message queue**

```text
Producer → SQS → Consumer
```

Think:

> **"Store this message until another component processes it."**

### SWF

**Workflow orchestration**

```text
Step 1 → Step 2 → Step 3 → Step 4
```

Think:

> **"Coordinate these distributed steps in the correct workflow."**

---

# 4. Why aren't RDS and DynamoDB answers?

Because they're databases.

```text
RDS       → relational database
DynamoDB  → NoSQL database
```

They aren't primarily designed to decouple application components.

For SAA, when you see:

> **"Decouple applications/components/microservices"**

your first thought should be:

**SQS**

And depending on the question:

**SNS / EventBridge / other messaging/event services** can also be relevant.

---

# 5. Why isn't VPC Peering correct?

This is a different concept.

VPC Peering is about:

> **connecting two VPCs privately.**

It isn't a messaging/decoupling service.

Also, you don't use VPC Peering to connect an on-premises network directly to a VPC.

For on-premises ↔ AWS connectivity, you'd think about things such as:

* Site-to-Site VPN
* Direct Connect

But **those solve connectivity**, not application decoupling.

---

# 🧠 The big distinction

This question actually tests **two different concepts**:

### Connectivity

> "How do my on-premises servers communicate with AWS?"

Think:

**VPN / Direct Connect**

### Decoupling

> "How do my applications communicate without being tightly dependent on each other?"

Think:

**SQS / SWF**

Don't mix these two.

### 🔥 One-line memory

**SQS = "Here is a message; process it when you're ready."**

**SWF = "Here are several workflow steps; coordinate them."**

And yes, **SQS absolutely can sit between an on-premises application and an AWS application.**

29-August-2026

**Yes, for a very simple mental model, you can think of SWF as somewhat similar to Terraform's `depends_on` — but don't treat them as the same thing.**

### Your analogy

Terraform:

```text
A
│
└── depends_on → B
                 │
                 ▼
                C
```

Meaning:

> **First A must happen, then B, then C.**

SWF:

```text
Step 1
   ↓
Step 2
   ↓
Step 3
   ↓
Step 4
```

Meaning:

> **Coordinate a multi-step workflow and keep track of what has happened.**

### But the important difference

| Terraform `depends_on`                     | SWF                                        |
| ------------------------------------------ | ------------------------------------------ |
| Controls **infrastructure creation order** | Controls **application/business workflow** |
| "Create A before B"                        | "Do payment before shipping"               |
| Infrastructure as Code                     | Workflow orchestration                     |
| Usually seconds/minutes                    | Can coordinate long-running workflows      |
| Doesn't manage business tasks              | Tracks tasks and workflow state            |

### 🎯 For your SAA exam

When you see:

> **"This must happen → then this → then this, across multiple distributed components"**

Think:

**SWF / Step Functions → workflow orchestration**

When you see:

> **"Application A needs to send work to Application B without depending on B being immediately available"**

Think:

**SQS → decoupling/message queue**

So your shortcut is:

> **`depends_on` = infrastructure order**
> **SWF = application workflow order**
> **SQS = application message waiting line**
