7. Question

Category: CSAA – Design Resilient Architectures

A company runs a messaging application in the ap-northeast-1 and ap-southeast-2 region. A Solutions Architect needs to create a routing policy wherein a larger portion of traffic from the Philippines and North India will be routed to the resource in the ap-northeast-1 region.

Which Route 53 routing policy should the Solutions Architect use?

- `Geoproximity Routing`
- Latency Routing
- Geolocation Routing
- Weighted Routing

Yes — this question is testing **Route 53 routing policies**, not ALB. The key is to understand **what decides where the user goes**.

### First: What is Route 53 doing?

Think:

**User → Route 53 → decides which AWS resource/region → user connects there**

For example:

```text
                    Route 53
                       |
             ---------------------
             |                   |
        Tokyo (Japan)       Sydney (Australia)
       ap-northeast-1        ap-southeast-2
```

Route 53 decides whether the user should go to Tokyo or Sydney.

It does **not** mean Route 53 itself processes the application traffic. It mainly answers the DNS question:

> "For `app.example.com`, which destination should I give this user?"

---

# The 4 policies you need to know

## 1. 🌍 Geoproximity Routing

This is the important one for **Question 7**.

It routes users based on **geographic proximity** to your resources.

But the special feature is:

### **BIAS**

You can make the geographic coverage of a resource **larger or smaller**.

Imagine:

```text
                 India
                   ↓
              Philippines
                   ↓
              Tokyo 🇯🇵
```

Normally, Tokyo might receive users from its nearby geographic area.

But with **bias**, you can say:

> "I want Tokyo to cover a larger geographic area."

So more users from **North India + Philippines** can be routed to Tokyo.

### Exam keyword:

**Geoproximity + "larger/smaller geographic area" + "bias" = Geoproximity**

---

# 2. 📍 Geolocation Routing

This sounds very similar, so this is where exams try to confuse you.

Geolocation asks:

> **"WHERE is the user coming from?"**

Then you explicitly decide what resource that location should use.

Example:

```text
India       → Tokyo
Japan       → Tokyo
Australia   → Sydney
USA         → Virginia
```

You can make rules based on:

* Country
* Continent
* Sometimes more specific geographic locations

But you **cannot use a bias to expand/shrink the geographic coverage**.

### Exam keyword:

**"Users from a particular country/continent should go to X" = Geolocation**

---

# 3. ⚡ Latency Routing

Latency asks:

> **"Which AWS Region gives this user the lowest network latency?"**

Example:

```text
User in India
      |
      ↓
Route 53 tests available regions
      |
      ├── Tokyo
      └── Sydney
             ↓
       lowest latency
             ↓
          selected
```

You don't manually say:

> India → Tokyo

Instead, Route 53 determines which region provides the **lowest latency**.

### Exam keyword:

**"lowest latency / fastest response" = Latency Routing**

---

# 4. ⚖️ Weighted Routing

Weighted routing asks:

> **"What percentage of traffic should go to each resource?"**

Example:

```text
             Route 53
                |
        ----------------
        |              |
      90%             10%
        |              |
      App A          App B
```

Very useful for:

### Canary deployment

```text
90% → old version
10% → new version
```

Or:

```text
70% → Region A
30% → Region B
```

### Exam keyword:

**"percentage / proportion / 80-20 / 90-10 traffic" = Weighted**

---

# Now Question 7

The question says:

> We have Tokyo and Sydney.

And wants:

> **A larger portion of traffic from Philippines and North India should go to Tokyo.**

The critical phrase is:

### **"larger portion of geographic area"**

They aren't simply saying:

> "India users should go to Tokyo."

They want to **expand Tokyo's geographic coverage**.

That's exactly what **Geoproximity + Bias** provides.

Therefore:

**✅ Geoproximity Routing**

---

# Don't confuse these 4

| Policy           | Think                              | Example                            |
| ---------------- | ---------------------------------- | ---------------------------------- |
| **Geoproximity** | 📍 Geographic proximity + **BIAS** | Make Tokyo cover a larger area     |
| **Geolocation**  | 🌎 Where is the user?              | India → Tokyo, Australia → Sydney  |
| **Latency**      | ⚡ Which is fastest?                | Send user to lowest-latency Region |
| **Weighted**     | ⚖️ Percentage                      | 90% → A, 10% → B                   |

### 🔥 Your exam shortcut

| If question says...                         | Pick             |
| ------------------------------------------- | ---------------- |
| **Bias / expand or shrink geographic area** | **Geoproximity** |
| **Country/continent/location-based rule**   | **Geolocation**  |
| **Lowest latency / best performance**       | **Latency**      |
| **Percentage / proportion / traffic split** | **Weighted**     |

---

## And NO — this isn't done using ALB

This is an important distinction.

You can have:

```text
                    Route 53
                       |
             ---------------------
             |                   |
            ALB                 ALB
             |                   |
        Tokyo EC2            Sydney EC2
```

**Route 53** decides **which destination/ALB** the user should resolve to.

Then the **ALB** distributes the request among EC2 instances **inside that region**.

So:

**Route 53 = Which destination/region?**
**ALB = Which EC2 instance inside that destination?**

That's the mental model I want you to remember for the exam.
