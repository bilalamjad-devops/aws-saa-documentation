15. Question

Category: CSAA – Design Resilient Architectures

A music publishing company is building a multitier web application that requires a key-value store with provisioned capacity mode that will save the document models. Each model is composed of band ID, album ID, song ID, composer ID, lyrics, and other data. The web tier will be hosted in an Amazon ECS cluster with AWS Fargate launch type.

Which of the following is the MOST suitable setup for the database tier?

- `Launch an Amazon DynamoDB table.`
- Launch an Amazon Aurora Serverless database.
- Use Amazon WorkDocs to store the document models.
- Launch an Amazon RDS database with Read Replicas.

Absolutely. This one is actually **very easy once you identify the keywords**. The question is testing whether you can distinguish **DynamoDB vs RDS/Aurora vs WorkDocs**.

## 1. First, what is the question saying?

The company has data like:

```text
Band ID
Album ID
Song ID
Composer ID
Lyrics
Other information
```

And the question explicitly says:

> **"requires a key-value store"**

and

> **"document models"**

and

> **"provisioned capacity mode"**

These are huge clues pointing to **DynamoDB**.

So the architecture is basically:

```text
Users
   ↓
ECS + Fargate
   ↓
DynamoDB
```

✅ **Answer: DynamoDB**

---

# 2. What is a key-value store?

Think of a simple dictionary:

```text
Key              Value
-------------------------------
song-001     →   song information
song-002     →   song information
song-003     →   song information
```

For example:

```text
Key: song-001

Value:
{
  band_id: 10,
  album_id: 25,
  song_id: 001,
  composer_id: 55,
  lyrics: "...",
}
```

This is exactly the kind of thing **DynamoDB** is designed for.

DynamoDB supports:

* **Key-value data**
* **Document data**

So the question practically tells you the answer.

---

# 3. Why not RDS?

Amazon RDS is primarily a **relational database**.

Think:

```text
RDS
 ↓
Tables
 ↓
Rows + Columns
 ↓
SQL
```

Example:

```text
Songs table

song_id | band_id | album_id | composer_id
--------|---------|----------|------------
001     | 10      | 25       | 55
002     | 10      | 25       | 56
```

That's relational.

But the question says:

> **key-value store + document models**

That's DynamoDB territory.

So:

**RDS → relational**

**DynamoDB → key-value/document**

---

# 4. What about Aurora Serverless?

This one sounds attractive because of the word **Serverless**.

But don't get distracted.

Aurora is still a **relational database**.

```text
Aurora
   ↓
Relational database
   ↓
SQL
```

Aurora Serverless means:

> AWS manages/scales the database capacity for you.

It does **NOT** mean:

> "Aurora becomes a NoSQL key-value database."

So:

```text
Aurora Serverless
      ↓
Relational ❌ for this requirement
```

---

# 5. What is Amazon WorkDocs?

WorkDocs is basically a **document collaboration/storage service**.

Think:

```text
WorkDocs
   ↓
Files / documents
   ↓
Share / collaborate / edit
```

It's not a database.

The question says:

> "document models"

Don't confuse **document model** with **document files**.

### Document model

Something like:

```json
{
  "song_id": "001",
  "band_id": "10",
  "album_id": "25",
  "lyrics": "..."
}
```

That's a **database data model**.

DynamoDB supports this.

### Document file

Something like:

```text
song-lyrics.docx
contract.pdf
report.doc
```

That's the kind of thing WorkDocs deals with.

---

# 6. What does "Provisioned Capacity Mode" mean?

This is another DynamoDB clue.

DynamoDB has capacity modes, including:

### Provisioned

You tell DynamoDB approximately how much capacity you need:

```text
Read capacity: 100
Write capacity: 50
```

### On-demand

AWS automatically handles capacity based on requests.

For this question, they specifically say:

> **provisioned capacity mode**

DynamoDB supports this.

---

# 7. And what does ECS Fargate have to do with it?

Honestly, **not much for choosing the database**.

They're giving you the architecture:

```text
Web/Application tier
        ↓
ECS
 + Fargate
        ↓
Database tier
```

Fargate is simply the **serverless compute engine for containers**.

The database requirement is what determines the answer:

> **Key-value + document → DynamoDB**

---

# 🧠 Exam shortcut

When you see:

**"Key-value store"**

👉 **DynamoDB**

When you see:

**"Document database / document model"**

👉 **DynamoDB**

When you see:

**"Relational / SQL"**

👉 **RDS / Aurora**

When you see:

**"Collaborate/edit/share documents"**

👉 **WorkDocs**

---

> **The application needs a key-value/document database → DynamoDB.**

Don't overthink the ECS/Fargate part. **The database requirement is the giveaway.**
