34. Question

Category: CSAA – Design Cost-Optimized Architectures

A company has a serverless application made up of AWS Amplify, Amazon API Gateway and a Lambda function. The application is connected to an Amazon RDS MySQL database instance inside a private subnet. A Lambda Function URL is also implemented as the dedicated HTTPS endpoint for the function, which has the following value:

https://12june1898pil1pinas.lambda-url.us-west-2.on.aws/

There are times during peak loads when the database throws a “too many connections” error preventing the users from accessing the application.

Which solution could the company take to resolve the issue?

- Increase the concurrency limit of the Lambda function
- Increase the memory allocation of the Lambda function
- `Provision an RDS Proxy between the Lambda function and RDS database instance`
- Increase the rate limit of API Gateway

Absolutely — this question is mainly testing **one very important serverless architecture problem: Lambda can scale much faster than a traditional RDS database can handle connections.**

Let’s break it down in our usual way.

---

# 🎯 1. What is the question really asking?

Ignore all the complicated wording.

The architecture is basically:

```text
Users
  ↓
AWS Amplify
  ↓
API Gateway
  ↓
Lambda
  ↓
RDS MySQL
```

During normal traffic:

```text
Lambda → RDS
Lambda → RDS
Lambda → RDS
```

Everything works.

But during **peak traffic**, Lambda automatically scales:

```text
             ┌→ Lambda → DB connection
             ├→ Lambda → DB connection
Users → API → ├→ Lambda → DB connection
             ├→ Lambda → DB connection
             ├→ Lambda → DB connection
             └→ Lambda → DB connection
```

Suddenly you might have hundreds/thousands of Lambda executions trying to establish database connections.

RDS says:

> ❌ "I can only handle X number of connections, and they're all being used."

So you get:

**Too many connections**

### The key question is:

> **How can we prevent thousands of Lambda connections from overwhelming RDS?**

Answer:

> **RDS Proxy**

---

# 🧠 2. First understand the core problem

You need to understand one difference:

### Lambda is highly scalable

Lambda can rapidly create many concurrent executions.

For example:

```text
100 requests
     ↓
100 Lambda executions
     ↓
100 DB connections
```

Then:

```text
10,000 requests
     ↓
10,000 Lambda executions
     ↓
Potentially thousands of DB connections 😱
```

But your RDS database doesn't necessarily scale its **connections** at the same speed.

So we have a mismatch:

```text
Lambda
"Give me more!"
      ↓
      ↓
      ↓
RDS
"Slow down! I have limited connections!"
```

---

# 🧠 3. What exactly is RDS Proxy?

Think of RDS Proxy as a **middleman / connection manager**.

Without RDS Proxy:

```text
Lambda 1 ───────→ RDS
Lambda 2 ───────→ RDS
Lambda 3 ───────→ RDS
Lambda 4 ───────→ RDS
Lambda 5 ───────→ RDS
...
Lambda 1000 ────→ RDS
```

Potentially a huge number of database connections.

With RDS Proxy:

```text
Lambda 1 ──┐
Lambda 2 ──┤
Lambda 3 ──┤
Lambda 4 ──┤
Lambda 5 ──┤
            ↓
       RDS Proxy
       ┌───────────┐
       │ Connection│
       │   Pool    │
       └─────┬─────┘
             ↓
            RDS
```

The Proxy maintains a **pool of reusable database connections**.

Instead of every Lambda execution creating its own database connection to RDS, the proxy manages and reuses connections.

### Think of it like a restaurant:

Without proxy:

```text
100 customers
→ 100 separate tables
→ restaurant gets overwhelmed
```

With proxy:

```text
100 customers
→ waiter manages tables
→ available tables are reused
→ restaurant handles traffic much better
```

The **waiter = RDS Proxy**.

---

# 🔥 4. Why is this especially important with Lambda?

This is a very important SAA pattern.

Traditional application:

```text
EC2 application
       ↓
     RDS
```

Maybe you have 5 EC2 servers.

You can control how many database connections those servers create.

But Lambda is different:

```text
Request
 ↓
Lambda instance

Request
 ↓
Another Lambda instance

Request
 ↓
Another Lambda instance

Request
 ↓
Another Lambda instance
```

Lambda can scale horizontally very quickly.

Therefore:

> **Serverless application + relational database + connection exhaustion = think RDS Proxy**

This is one of your important SAA patterns.

---

# 🔍 5. Now let's examine every option

## Option 1 — Increase Lambda concurrency limit ❌

> Increase the concurrency limit of the Lambda function

First understand what **concurrency** means.

Concurrency = how many Lambda executions can happen simultaneously.

For example:

```text
Concurrency = 100

At maximum:

Lambda #1
Lambda #2
...
Lambda #100
```

Now suppose RDS is already suffering:

```text
RDS supports ~100 connections

Lambda
 ↓
100 concurrent executions
 ↓
100 DB connections
 ↓
💥 Too many connections
```

If you increase Lambda concurrency:

```text
Concurrency = 1000

Lambda
 ↓
1000 concurrent executions
 ↓
Potentially 1000 DB connections
 ↓
💥💥 Even worse
```

So increasing Lambda concurrency can actually **make the database problem worse**.

### Remember:

> Lambda concurrency controls **how many Lambda executions can run simultaneously**, not how many database connections RDS can handle.

❌ Not the solution.

---

# Option 2 — Increase Lambda memory ❌

> Increase the memory allocation of the Lambda function

Lambda memory affects the resources available to the Lambda execution.

For example:

```text
128 MB
256 MB
512 MB
1 GB
...
```

More memory can provide more CPU and make the function execute faster.

But our problem isn't:

> "Lambda is running too slowly."

Our problem is:

> **RDS is receiving too many database connections.**

So:

```text
More Lambda memory
        ↓
Lambda may run faster
        ↓
But RDS still has connection limits
```

It doesn't solve the fundamental problem.

❌ Not the best answer.

---

# Option 3 — RDS Proxy ✅

> Provision an RDS Proxy between the Lambda function and RDS database instance

This directly addresses the problem.

Architecture becomes:

```text
Users
  ↓
Amplify
  ↓
API Gateway
  ↓
Lambda
  ↓
RDS Proxy
  ↓
RDS MySQL
```

The proxy:

* maintains connection pools
* reuses database connections
* manages connections between Lambda and RDS
* helps Lambda handle large numbers of concurrent connections
* reduces the connection-management burden on RDS

Therefore:

### ✅ Correct answer

---

# Option 4 — Increase API Gateway rate limit ❌

API Gateway rate limiting controls how many requests can reach your API over a period of time.

For example:

```text
Users
 ↓
API Gateway
 ↓
Rate limit
 ↓
Lambda
```

If you increase the rate limit, you're basically saying:

> "Allow even more requests through."

But our problem is already:

```text
Too many requests
       ↓
Too many Lambda executions
       ↓
Too many DB connections
       ↓
RDS 💥
```

Increasing the API Gateway rate limit could therefore make things worse.

❌ Not the solution.

---

# 🧩 6. The entire architecture

### Without RDS Proxy

```text
                    ┌→ Lambda ──→ DB connection ─┐
                    ├→ Lambda ──→ DB connection ─┤
Users → API Gateway ├→ Lambda ──→ DB connection ─┤
                    ├→ Lambda ──→ DB connection ─┤
                    └→ Lambda ──→ DB connection ─┘
                                                   ↓
                                              RDS MySQL
                                                   ↓
                                            "Too many connections"
```

### With RDS Proxy

```text
                    ┌→ Lambda ──┐
                    ├→ Lambda ──┤
Users → API Gateway ├→ Lambda ──┤
                    ├→ Lambda ──┤
                    └→ Lambda ──┘
                         ↓
                    RDS Proxy
                         ↓
                 Connection Pool
                         ↓
                     RDS MySQL
```

That's the entire concept.
