54. Question

Category: CSAA – Design Resilient Architectures

A company hosts its web application on a set of Amazon EC2 instances in an Auto Scaling group behind an Application Load Balancer (ALB). The application has an embedded NoSQL database. As the application receives more traffic, the application becomes overloaded mainly due to database requests. The management wants to ensure that the database is eventually consistent and highly available.

Which of the following options can meet the company requirements with the least operational overhead?

- Change the ALB with a Network Load Balancer (NLB) to handle more traffic and integrate AWS Global Accelerator to ensure high availability. Configure replication of the NoSQL database on the set of EC2 instances to spread the database load.
- `Configure the Auto Scaling group to spread the EC2 instances across three Availability Zones. Use the AWS Database Migration Service (AWS DMS) with a replication server and an ongoing replication task to migrate the embedded NoSQL database to Amazon DynamoDB.`
- Change the ALB with a Network Load Balancer (NLB) to handle more traffic. Use the AWS Glue DynamoDB export connector to export data from Amazon DynamoDB to Amazon S3 for analytics periodically, and continue running the application’s NoSQL database on the EC2 instances.
- Configure the Auto Scaling group to spread the EC2 instances across three Availability Zones. Configure replication of the NoSQL database on the set of EC2 instances to spread the database load.


### 🎯 What is being tested?

**Embedded NoSQL database on EC2 → scalability + high availability + low operational overhead.**

### ✅ Correct answer

**ASG across 3 AZs + AWS DMS → Amazon DynamoDB with ongoing replication (CDC).**

### Why?

* **EC2 ASG across AZs** → application becomes highly available.
* **DynamoDB** → fully managed NoSQL, automatically scalable and highly available.
* **DMS** → migrates the existing embedded NoSQL data and can continuously replicate changes.
* Much less operational work than manually replicating the database across EC2 instances.

### ❌ Key eliminations

* **NLB + Global Accelerator** → doesn't solve the embedded database problem.
* **Manual DB replication on EC2** → high operational overhead.
* **Glue → S3** → analytics/export use case, not solving the application's database availability.

🔥 **Exam shortcut:**
**Database overloaded + embedded in EC2 + want low management → migrate to managed database service.**
For **NoSQL → DynamoDB**, DMS can perform the migration and ongoing replication.

## 1. What Is Being Tested Here? (Core Exam Concepts)

Is question mein AWS 3 major architectural principles test kar raha hai:

1. **Decoupling State / Database from EC2 Instances:**
* EC2 instances ke andar database "embed" (chala kar) rakhna ek anti-pattern hai. Jab web traffic badhta hai, toh compute aur database dono aapas mein resource contention (CPU/RAM fight) karte hain.
* Proper cloud design yeh kehta hai ke DB ko EC2 se alag (decouple) karke kisi **Fully Managed Database Service** par shift kiya jaye.


2. **NoSQL Managed Service & Eventual Consistency:**
* Embedded NoSQL database ko AWS ki fully managed NoSQL service $\rightarrow$ **Amazon DynamoDB** par migrate karna chahiye. DynamoDB naturally **eventually consistent** and **highly available** hota hai without any manual cluster patching or scaling.


3. **High Availability across 3 AZs + Low Operational Overhead:**
* Web tier (EC2 instances) ko **3 Availability Zones (AZs)** par spread karne se application level High Availability milti hai.
* Embedded DB ko manual custom replication se manage karne mein bohot zyada overhead hota hai. **AWS DMS** ka use karke embedded NoSQL DB se DynamoDB tak live migration karna low operational overhead deta hai.



---

## 2. Core AWS Technical Rules

* **Embedded DB on EC2 $\rightarrow$ Always Migrate to Managed Service:** Whenever a question mentions an "embedded database on EC2 causing bottlenecks/overload", the correct solution ALWAYS involves migrating off EC2 to RDS, Aurora, or DynamoDB.
* **DynamoDB Characteristics:** Fully managed, serverless, NoSQL database with built-in multi-AZ replication, high throughput, and eventual consistency options.
* **AWS DMS for NoSQL:** DMS supports migrating NoSQL data stores (like MongoDB/embedded documents) directly into **Amazon DynamoDB**.

---

## 3. Correct Option Explanation

#### ✅ **Configure the Auto Scaling group to spread the EC2 instances across three Availability Zones. Use the AWS Database Migration Service (AWS DMS) with a replication server and an ongoing replication task to migrate the embedded NoSQL database to Amazon DynamoDB.**

* **Why it works:**
1. **Spreading across 3 AZs:** Web tier fault tolerant ho jaata hai.
2. **Migrating to DynamoDB via DMS:** Embedded DB ka load EC2 se khatam ho jata hai. DynamoDB auto-scale karta hai aur manual database server maintenance ka overhead zero kar deta hai.



---

## 4. Incorrect Options Breakdown (Exam Elimination Technique)

| Option | Why It Fails the Exam Requirement |
| --- | --- |
| **Configure replication of the NoSQL database on the set of EC2 instances...** | Manual database replication setup on EC2 creates **massive operational overhead** (patching, sync errors, disk scaling). It leaves the DB coupled to EC2. |
| **Change ALB with NLB... AWS Global Accelerator...** | Bottleneck database request ka tha, load balancer ka nahi. Global Accelerator multi-region apps ke liye hota hai; single-region bottleneck ke liye nahi. |
| **Use AWS Glue DynamoDB export connector...** | Glue DynamoDB export analytics (S3) ke liye hota hai. Yeh EC2 par chalne wale embedded DB ke bottleneck ko solve nahi karta. |

---

## 5. Exam Decision Matrix (Cheat Sheet)

* **Embedded/Local DB on EC2 causing overload:** $\rightarrow$ **Decouple and migrate to AWS Managed DB (RDS / DynamoDB)**
* **NoSQL Database Managed Replacement:** $\rightarrow$ **Amazon DynamoDB**
* **Migrate DB with ongoing changes & minimal management:** $\rightarrow$ **AWS DMS (Replication Task)**
* **High Availability for EC2 Auto Scaling Group:** $\rightarrow$ **Spread instances across $\ge 2$ or 3 Availability Zones**
