27. Question

Category: CSAA – Design Resilient Architectures

A company has a dynamic web app written in MEAN stack that is going to be launched in the next month. There is a probability that the traffic will be quite high in the first couple of weeks. In the event of a load failure, how can you set up DNS failover to a static website?

- Add more servers in case the application fails.
- Enable failover to an application hosted in an on-premises data center.
- Duplicate the exact application architecture in another region and configure DNS weight-based routing.
- `Use Route 53 with the failover option to a static S3 website bucket or CloudFront distribution.`

Yes — this question is basically testing **Route 53 Failover Routing + S3/CloudFront as a cheap backup website**.

You already understand the basic Route 53 idea, so let's build from there.

## What is the question saying?

Imagine your main application is:

```text
Users
   ↓
Route 53
   ↓
Main MEAN application
   ↓
EC2 / containers / database
```

The company expects **very high traffic** when the application launches.

They are worried:

> "What if our main application goes down?"

They don't necessarily want to build an entire second copy of the application because that would be expensive.

Instead, they want:

> **If the main application fails → show users a simple static website.**

For example:

```text
Normal situation

User
 ↓
Route 53
 ↓
Main application ✅
 ↓
"Welcome to our website"
```

If the application crashes:

```text
User
 ↓
Route 53
 ↓
Main application ❌
 ↓
S3 / CloudFront static website ✅
 ↓
"Sorry, we're temporarily unavailable."
```

That's the entire idea.

---

# Why S3?

A static website doesn't need a server.

For example, you could have:

```text
index.html
style.css
logo.png
```

stored in **Amazon S3**.

S3 is extremely cheap compared with running another fleet of EC2 instances.

So instead of:

```text
Primary application
        +
Second complete application
        ↓
Expensive
```

you can have:

```text
Primary application
        +
Cheap static backup in S3
        ↓
Cost-effective
```

---

# Where does Route 53 Failover come in?

You create two Route 53 records:

### Primary

```text
example.com
     ↓
Primary application
```

with a health check.

### Secondary

```text
example.com
     ↓
S3 static website / CloudFront
```

with **Failover routing**.

Then:

```text
                 Route 53
                    │
              Health Check
                    │
             Is primary healthy?
              /              \
            YES               NO
             ↓                 ↓
      Main application    S3/CloudFront
          PRIMARY            SECONDARY
```

That's why the answer says:

> **Use Route 53 with the failover option to a static S3 website bucket or CloudFront distribution.**

---

# Why NOT Weighted Routing?

This is an important distinction because you just learned weighted routing.

### Weighted

Means:

> "Send some traffic to A and some traffic to B."

For example:

```text
Route 53
   ├── 90% → Application A
   └── 10% → Application B
```

That's useful for things like:

* testing a new version
* gradual deployment
* distributing traffic

But that's **not what this question wants**.

The question says:

> **Only use the backup when the primary fails.**

That's **Failover**, not Weighted.

```text
Failover:

Primary ✅ → Primary

Primary ❌ → Secondary
```

---

# Why not "add more servers"?

Because adding more servers is about **scaling**, not necessarily **failover**.

If your application is overloaded:

```text
Traffic increases
      ↓
ASG launches more EC2 instances
      ↓
Application handles more traffic
```

That's scaling.

But the question specifically asks:

> What if the application **fails**?

That's a different problem.

---

# Why not duplicate the whole application in another Region?

You could do this:

```text
Region A
  ↓
Complete application


Region B
  ↓
Complete application
```

and then use Route 53.

That gives you a much stronger DR architecture, but the question is asking for a **cost-effective failover to a static website**.

Running a complete second MEAN application just as a backup is unnecessarily expensive for this requirement.

---

# 🧠 The key concept

You should now have these three Route 53 routing policies clearly separated:

### Failover

**"Primary or backup?"**

```text
Primary ✅ → Primary

Primary ❌ → Backup
```

### Weighted

**"How much traffic goes where?"**

```text
90% → A
10% → B
```

### Latency

**"Which endpoint gives the user the lowest latency?"**

```text
Pakistan user → Mumbai
US user       → Virginia
```

---

## One-line exam trick

When you see:

> **"If primary fails, automatically send users to backup/DR"**

Think:

### 🚨 Route 53 **Failover Routing**

When you see:

> **"90% traffic here, 10% there"**

Think:

### ⚖️ Route 53 **Weighted Routing**

When you see:

> **"Send users to the Region with lowest latency"**

Think:

### 🌎 Route 53 **Latency-based Routing**

And Question 27 is simply:

**Primary MEAN app → fails → Route 53 automatically sends users to cheap static S3/CloudFront backup.**
