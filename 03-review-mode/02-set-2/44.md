44. Question

Category: CSAA – Design Resilient Architectures

An e-commerce company is receiving a large volume of sales data files in .csv format from its external partners on a daily basis. These data files are then stored in an Amazon S3 Bucket for processing and reporting purposes.

The company wants to create an automated solution to convert these .csv files into Apache Parquet format and store the output of the processed files in a new S3 bucket called “tutorialsdojo-data-transformed”. This new solution is meant to enhance the company’s data processing and analytics workloads while keeping its operating costs low.

Which of the following options must be implemented to meet these requirements with the LEAST operational overhead?


- `Use AWS Glue crawler to automatically discover the raw data file in S3 as well as check its corresponding schema. Create a scheduled ETL job in AWS Glue that will convert .csv files to Apache Parquet format and store the output of the processed files in the “tutorialsdojo-data-transformed” bucket.`
- Utilize an AWS Batch job definition with Bash syntax to convert the .csv files to the Apache Parquet format. Configure the job definition to run automatically whenever a new .csv file is uploaded to the source bucket.
- Use Amazon S3 event notifications to trigger an AWS Lambda function that converts .csv files to Apache Parquet format using Apache Spark on an Amazon EMR cluster. Save the processed files to the “tutorialsdojo-data-transformed” bucket.
- Integrate Amazon EMR File System (EMRFS) with the source S3 bucket to automatically discover the new data files. Use an Amazon EMR Serverless with Apache Spark to convert the .csv files to the Apache Parquet format and then store the output in the “tutorialsdojo-data-transformed” bucket.

Absolutely — let’s do **Q44** in the same style.

# Q44 — AWS Glue vs Batch vs Lambda/EMR vs EMR Serverless

## 🎯 1. What is the question really asking?

Ignore the complicated wording.

The company has:

* Lots of `.csv` files arriving in **S3**
* Needs to convert them to **Apache Parquet**
* Put converted files into another **S3 bucket**
* Wants **low operational overhead**
* Wants to keep costs low

So the core requirement is:

> **S3 CSV → transform → S3 Parquet, with the least management.**

The big clue is:

### 🔥 **CSV → Parquet = ETL/data transformation**

And AWS has a service specifically designed for this:

> **AWS Glue = managed/serverless ETL service**

# 🧠 3. What exactly is Apache Parquet?

This is important because you'll see it in SAA/data questions.

CSV is basically:

```text
name,age,country
Bilal,25,Pakistan
Ali,30,USA
John,28,UK
```

Parquet stores data in a **columnar** format.

Conceptually:

```text
CSV:
Row → name + age + country
Row → name + age + country
Row → name + age + country


Parquet:
name column → Bilal, Ali, John
age column  → 25, 30, 28
country     → Pakistan, USA, UK
```

This makes Parquet particularly efficient for **analytics**, because analytical queries often need only certain columns.

It also supports efficient compression and encoding.

### Exam shortcut:

> **CSV → Parquet → analytics/data processing → AWS Glue**

# 🔍 4. Let's examine every option

## ✅ Option 1 — CORRECT

> Use AWS Glue crawler + scheduled Glue ETL job.

This is the intended answer.

### What happens?

First:

```text
S3 CSV
   ↓
Glue Crawler
   ↓
Data Catalog
```

The crawler examines the data and determines things such as:

* file format
* schema
* columns
* partitions

Then:

```text
S3 CSV
   ↓
Glue ETL
   ↓
Parquet
   ↓
S3 transformed bucket
```

### Why Glue?

Because Glue is a **fully managed ETL service**.

You don't need to manage:

* EC2 servers
* clusters
* operating systems
* cluster scaling
* Hadoop infrastructure

That's exactly what **least operational overhead** is pointing toward.

---

# ❌ Option 2 — AWS Batch

The option says:

```text
S3 CSV
   ↓
AWS Batch
   ↓
CSV → Parquet
```

AWS Batch is designed for running **batch computing jobs**, commonly using containers.

Think:

> "I have lots of compute jobs that need to run."

For example:

```text
1000 scientific calculations
1000 video-processing jobs
large computational workloads
```

AWS Batch manages job queues and compute environments.

But here the actual requirement is:

> **Data ETL / data transformation**

AWS Glue is purpose-built for that.

So using Batch would introduce unnecessary infrastructure/configuration.

### Exam thinking:

```text
ETL/data transformation → Glue
General batch compute → Batch
```

Therefore ❌.

---

# ❌ Option 3 — Lambda + EMR

This one looks attractive because it says:

```text
S3
 ↓
S3 Event Notification
 ↓
Lambda
 ↓
EMR + Spark
 ↓
S3
```

But look at what we're doing.

We're introducing:

* Lambda
* EMR
* Spark
* EMR cluster management

That's a lot of moving parts.

The question specifically says:

> **LEAST operational overhead**

Why build/manage an EMR environment when Glue can perform the ETL?

### Another important point

**Lambda isn't inherently bad here.**

S3 → Lambda is perfectly valid for many lightweight transformations.

But this option specifically says:

> Lambda triggers an **EMR cluster using Apache Spark**

That's unnecessarily complex for the requirement.

So ❌.

---

# ❌ Option 4 — EMRFS + EMR Serverless

This is the trickiest option.

It sounds excellent because:

> "EMR Serverless"

sounds like:

> "serverless = low management"

And that's partly true.

### What is EMR Serverless?

EMR Serverless allows you to run frameworks such as:

* Apache Spark
* Hive

without managing the underlying cluster infrastructure yourself.

So:

```text
EMR Serverless
       ↓
Apache Spark
       ↓
CSV → Parquet
```

is technically a reasonable architecture.

### So why isn't it the answer?

Because of **EMRFS**.

EMRFS is not a mechanism for:

> "Watch S3 and discover whenever a new file arrives."

EMRFS is an EMR implementation for accessing data in S3.

Think:

```text
EMR
 │
 └── EMRFS
       │
       └── Read/write S3 data
```

It isn't an S3 event-discovery mechanism.

For discovering new S3 files, you would use things like:

```text
S3 Event Notifications
```

or

```text
AWS Glue
```

Also, Glue is more directly aligned with this **ETL + catalog + schema + Parquet** requirement.

Therefore ❌.

# 🧩 5. The important services in this question

Let's make sure these names don't blur together.

| Service               | What does it actually do?                  | Role here                                                |
| --------------------- | ------------------------------------------ | -------------------------------------------------------- |
| **S3**                | Object storage                             | Stores CSV + Parquet                                     |
| **AWS Glue**          | Managed ETL/data integration               | ⭐ Main transformation service                            |
| **Glue Crawler**      | Discovers data/schema and creates metadata | Understands CSV structure                                |
| **Glue Data Catalog** | Central metadata catalog                   | Stores table/schema information                          |
| **AWS Batch**         | Runs batch computing jobs                  | Not necessary here                                       |
| **Lambda**            | Serverless code execution                  | Could process small workloads, but not needed here       |
| **EMR**               | Big-data processing platform               | Overkill here                                            |
| **EMR Serverless**    | Serverless Spark/Hive execution            | Possible, but not the intended least-overhead ETL choice |
| **EMRFS**             | EMR mechanism for accessing S3             | Not an S3 file-arrival detector                          |
| **Apache Spark**      | Distributed data-processing engine         | Glue can use Spark underneath                            |
| **Parquet**           | Columnar data format                       | Efficient analytics/storage                              |
