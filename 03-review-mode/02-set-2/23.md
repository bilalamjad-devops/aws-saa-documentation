23. Question

Category: CSAA – Design Secure Architectures

A GraphQL API hosted is hosted in an Amazon EKS cluster with AWS Fargate launch type and deployed using AWS SAM. The API is connected to an Amazon DynamoDB table with DynamoDB Accelerator (DAX) as its data store. Both resources are hosted in the us-east-1 region.

The AWS IAM authenticator for Kubernetes is integrated into the EKS cluster for role-based access control (RBAC) and cluster authentication. A solutions architect must improve network security by preventing database calls from traversing the public internet. An automated cross-account backup for the DynamoDB table is also required for long-term retention.

Which of the following should the solutions architect implement to meet the requirement?

- Create a DynamoDB interface endpoint. Associate the endpoint to the appropriate route table. Enable Point-in-Time Recovery (PITR) to restore the DynamoDB table to a particular point in time on the same or a different AWS account.
- Create a DynamoDB interface endpoint. Set up a stateless rule using AWS Network Firewall to control all outbound traffic to only use the dynamodb.us-east-1.amazonaws.com endpoint. Integrate the DynamoDB table with Amazon Timestream to allow point-in-time recovery from a different AWS account.
- `Create a DynamoDB gateway endpoint. Associate the endpoint to the appropriate route table. Use AWS Backup to automatically copy the on-demand DynamoDB backups to another AWS account for disaster recovery.`
- Create a DynamoDB gateway endpoint. Set up a Network Access Control List (NACL) rule that allows outbound traffic to the dynamodb.us-east-1.amazonaws.com gateway endpoint. Use the built-in on-demand DynamoDB backups for cross-account backup and recovery.

Absolutely. This question looks complicated because it throws **EKS + Fargate + SAM + GraphQL + DynamoDB + DAX + IAM + RBAC** at you, but **most of those details are distractions**.

The question is actually testing only **2 things**:

1. How to access **DynamoDB privately from a VPC**
2. How to make **cross-account DynamoDB backups**

The answer is:

> **DynamoDB Gateway Endpoint + AWS Backup** ✅

Let's break it down.

---

# 1. First, ignore most of the story

The question says:

> EKS with Fargate, GraphQL, SAM, DAX, IAM authenticator, RBAC...

Don't get distracted.

The actual requirements are:

### Requirement 1

> Database calls must NOT go through the public Internet.

### Requirement 2

> DynamoDB backups must automatically be copied to another AWS account.

That's it.

Now match each requirement to an AWS service.

---

# 2. Requirement #1: Private access to DynamoDB

Normally, your application might communicate with DynamoDB through:

```text
EKS/Fargate
     ↓
Internet
     ↓
DynamoDB
```

But the company says:

> ❌ We don't want traffic going through the public Internet.

AWS provides **VPC endpoints** for this.

For DynamoDB:

# DynamoDB Gateway Endpoint ✅

Architecture:

```text
EKS / Fargate
     ↓
   VPC
     ↓
DynamoDB Gateway Endpoint
     ↓
DynamoDB
```

The traffic stays on the AWS network instead of needing an Internet Gateway/NAT for DynamoDB access.

---

# 3. Remember this VERY important exam rule

You previously learned:

> **VPC Gateway Endpoint = S3 + DynamoDB**

Correct.

So:

```text
Gateway Endpoint
     │
     ├── S3
     └── DynamoDB
```

For this question:

> DynamoDB → **Gateway Endpoint** ✅

---

# 4. Why not Interface Endpoint?

This is an important distinction.

AWS has two major types:

### Gateway Endpoint

Used for:

```text
S3
DynamoDB
```

### Interface Endpoint

Used for many other AWS services through **PrivateLink**.

For example, conceptually:

```text
VPC
 ↓
Interface Endpoint
 ↓
AWS service
```

But for **DynamoDB**, the exam's intended answer here is:

> **Gateway Endpoint**

So don't choose interface endpoint when you see:

> DynamoDB + private VPC access

Think:

**DynamoDB → Gateway Endpoint**

---

# 5. What does "associate endpoint with route table" mean?

This part sounds complicated but it's simple.

Your VPC has a route table:

```text
Route Table

DynamoDB prefix list
       ↓
vpce-123456
```

Meaning:

> "When traffic is destined for DynamoDB, send it through this gateway endpoint."

So:

```text
Fargate
   ↓
Route Table
   ↓
DynamoDB Gateway Endpoint
   ↓
DynamoDB
```

You don't need to memorize the internal routing mechanics deeply for SAA.

Just remember:

> **Gateway endpoint → associated with route table**

---

# 6. Requirement #2: Cross-account backup

Now the second requirement:

> "Automatically copy DynamoDB backups to another AWS account."

There are two things in the answers:

### DynamoDB built-in backups

and

### AWS Backup

This is where the question wants you to distinguish them.

---

# 7. DynamoDB on-demand backup

DynamoDB itself can create backups.

For example:

```text
DynamoDB Table
      ↓
On-demand backup
```

Useful for backup/recovery.

But the question specifically says:

> **another AWS account**

The question tells you that native DynamoDB on-demand backups don't provide the required cross-account copy.

Therefore:

❌ Native DynamoDB backup

---

# 8. AWS Backup

AWS Backup is designed to centrally manage backups.

Think:

```text
DynamoDB
   ↓
AWS Backup
   ↓
Backup
   ↓
Another AWS Account
```

Therefore:

> **Cross-account backup → AWS Backup** ✅

This is the second half of the correct answer.

---

# 9. Put the two requirements together

The question says:

### Requirement 1:

Private DynamoDB access.

→ **DynamoDB Gateway Endpoint**

### Requirement 2:

Cross-account backup.

→ **AWS Backup**

Therefore:

# ✅ Gateway Endpoint + AWS Backup

---

# 10. Now let's destroy the wrong options

## Option A

> Create a DynamoDB interface endpoint + PITR

There are two problems.

### Problem 1: Interface endpoint

For this question, DynamoDB should use:

**Gateway Endpoint**.

### Problem 2: PITR

PITR = **Point-in-Time Recovery**.

Think:

> "I accidentally deleted/changed something. Let me restore the DynamoDB table to how it looked at an earlier point."

For example:

```text
Monday 10 AM
       ↓
Monday 11 AM
       ↓
Monday 12 PM ← restore here
```

PITR is about **restoring to a point in time**.

It is NOT the solution for:

> "Copy backups to another AWS account."

So:

❌ Interface endpoint
❌ PITR for cross-account backup requirement

---

# 11. Option B

> Interface endpoint + Network Firewall + Timestream

This is basically a collection of unnecessary services.

### Network Firewall

You don't need to introduce Network Firewall simply to privately access DynamoDB.

The **VPC endpoint** solves the private connectivity requirement.

### Timestream

Timestream is a **time-series database**.

Think:

```text
IoT sensors
   ↓
Temperature
CPU metrics
Device readings
   ↓
Timestream
```

It has nothing to do with DynamoDB cross-account backup.

So:

❌ Interface Endpoint
❌ Network Firewall
❌ Timestream

---

# 12. Option D

> Gateway endpoint + NACL + native DynamoDB backup

The first part is good:

**Gateway endpoint** ✅

But:

> Native DynamoDB backup for cross-account recovery

❌

That's the problem.

Use:

> **AWS Backup**

instead.

---

# 13. The most important concepts from this question

You can put this tiny table in your notes:

| Requirement                                  | Service                       |
| -------------------------------------------- | ----------------------------- |
| Private access to DynamoDB from VPC          | **DynamoDB Gateway Endpoint** |
| Private access to S3 from VPC                | **S3 Gateway Endpoint**       |

---

# 14. One thing about DAX

The question mentions **DAX**, but don't let it confuse you.

DAX = **DynamoDB Accelerator**.

Think:

```text
Application
     ↓
    DAX
     ↓
DynamoDB
```

DAX is an **in-memory cache for DynamoDB**.

Its purpose is mainly:

> Make DynamoDB reads faster.

It is **not**:

* a backup service
* a VPC endpoint
* a replacement for DynamoDB
* a cross-account backup solution

So in this question, DAX is basically background information.
