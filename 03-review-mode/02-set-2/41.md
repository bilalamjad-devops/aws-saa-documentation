41. Question

Category: CSAA – Design Cost-Optimized Architectures

A company is building an internal application that allows users to upload images. Each upload request must be sent to Amazon Kinesis Data Streams for processing before the pictures are stored in an Amazon S3 bucket.

The application should immediately return a success message to the user after the upload, while the downstream processing is handled asynchronously. The processing typically takes about 5 minutes to complete.

Which solution will enable asynchronous processing from Kinesis to S3 in the most cost-effective way?

- Use a combination of AWS Lambda and Step Functions to orchestrate service components and asynchronously process the requests.
- Send data from Kinesis Data Streams to Amazon Data Firehose and configure it to deliver directly to S3.
- Use a combination of Amazon SQS to queue the requests and then asynchronously process them using On-Demand Amazon EC2 Instances.
- `Use Kinesis Data Streams with AWS Lambda consumers to asynchronously process records and write them to S3.`

Absolutely. This question is actually a **very good Kinesis question**, because it combines **Kinesis Data Streams, Lambda, Firehose, SQS, and Step Functions**. Let's build the concepts rather than memorize the answer.

# 🎯 1. What is the question really asking?

Strip away the complicated wording.

The requirements are:

1. User uploads an image.
2. The upload **must go into Kinesis Data Streams**.
3. User should get **success immediately**.
4. Processing takes about **5 minutes**.
5. Processing should happen **asynchronously**.
6. After processing, save the image/result to **S3**.
7. They want the **most cost-effective** solution.

The important requirement is:

> **Kinesis Data Streams → asynchronous processing → S3**

So our first mental picture should be:

```text
User
  ↓
Application
  ↓
Kinesis Data Streams
  ↓
??? processing
  ↓
S3
```

The question is asking:

> **What should we put after Kinesis to process the records asynchronously?**

Answer:

### ✅ Lambda consumer

```text
User
  ↓
Application
  ↓
Kinesis Data Streams
  ↓
Lambda
  ↓
S3
```

---

# 🧠 2. Why is it asynchronous?

This is the most important concept.

Imagine the user uploads an image:

```text
User
  ↓
Upload image
  ↓
Kinesis
```

Once the application successfully puts the record into Kinesis, it can immediately tell the user:

```text
✅ Upload received successfully
```

It does **NOT** wait for the 5-minute processing.

Meanwhile:

```text
Kinesis
   ↓
Lambda
   ↓
process image
   ↓
S3
```

So we have two separate timelines:

```text
USER SIDE

Upload
  ↓
Kinesis
  ↓
"Success!" ✅
  ↓
User continues


PROCESSING SIDE

Kinesis
  ↓
Lambda
  ↓
5-minute processing
  ↓
S3
```

That's **asynchronous processing**.

---

# 🧠 3. Why does Lambda work with Kinesis?

This is something you should understand very well for SAA.

Lambda can act as a **consumer of Kinesis Data Streams**.

Architecture:

```text
             Kinesis Data Streams
                     │
                     │ records
                     ↓
              Lambda Consumer
                     │
                     ↓
              Process records
                     │
                     ↓
                    S3
```

Lambda doesn't just magically "listen" to Kinesis.

AWS creates an **event source mapping**.

Conceptually:

```text
Kinesis
   ↓
Lambda event source mapping
   ↓
Poll records
   ↓
Batch records
   ↓
Invoke Lambda
   ↓
Process
```

AWS manages the polling, batching, checkpointing and retries for the Lambda/Kinesis integration.

That's why you don't need to build your own polling application.

---

# 🔥 4. Why is this cost-effective?

Because you don't need to keep EC2 servers running.

With EC2:

```text
Kinesis
   ↓
EC2
   ↓
process
   ↓
S3
```

You have to manage:

* EC2 instances
* operating system
* patching
* scaling
* capacity
* availability

With Lambda:

```text
Kinesis
   ↓
Lambda
   ↓
S3
```

Lambda automatically runs when records need processing.

So for this type of workload:

> **Kinesis + Lambda = serverless stream processing**

Very attractive from a cost/operations perspective.

# 🔍 5. Now let's understand EVERY answer option

## Option 1 — Lambda + Step Functions ❌

> Use Lambda and Step Functions to orchestrate service components.

First, what is **Step Functions**?

Think of Step Functions as a **workflow/orchestration engine**.

For example:

```text
Step 1
  ↓
Lambda
  ↓
Step 2
  ↓
Approval
  ↓
Step 3
  ↓
SNS
```

It is useful when you have a **multi-step workflow**.

For example:

```text
Receive image
     ↓
Resize image
     ↓
Check image
     ↓
Store image
     ↓
Send notification
```

You might use Step Functions if you need sophisticated orchestration.

But this question doesn't need that.

We simply have:

```text
Kinesis
  ↓
Lambda
  ↓
S3
```

Adding Step Functions would add another service and additional orchestration cost/complexity without solving a problem.

Therefore:

❌ **Wrong**

### Exam lesson:

> **Simple event processing → Lambda**

> **Complex multi-step workflow → Step Functions**

---

# Option 2 — Kinesis Data Streams → Firehose → S3 ❌

This one is **very tempting**.

Because you already learned:

> **Kinesis Data Firehose = deliver streaming data**

And that's true.

Firehose is excellent for:

```text
Streaming data
     ↓
Firehose
     ↓
S3
```

For example:

```text
Application
    ↓
Kinesis
    ↓
Firehose
    ↓
S3
```

Firehose's main job is:

> **Deliver streaming data to a destination.**

It can buffer records and deliver them to S3, Redshift, OpenSearch, etc.

### So why isn't it the answer?

Because the question isn't simply saying:

> "Move Kinesis data to S3."

It says:

> **Processing typically takes about 5 minutes.**

The requirement is for **application processing logic** before storing the result.

Lambda as a Kinesis consumer gives you direct control over that processing:

```text
Kinesis
   ↓
Lambda
   ↓
5-minute processing
   ↓
S3
```

Firehose is primarily a **delivery mechanism**, not a general-purpose application worker.

It can invoke Lambda for transformations, but that is a different pattern and isn't the best fit for this question's processing requirement.

Therefore:

❌ **Wrong**

### 🔥 Remember:

```text
Kinesis Data Firehose
        ↓
"DELIVER this streaming data"
```

while:

```text
Kinesis Data Streams + Lambda
        ↓
"PROCESS these streaming records"
```

# Option 3 — SQS + On-Demand EC2 ❌

This one is wrong for **two reasons**.

### Reason #1: The question explicitly requires Kinesis

It says:

> Each upload request **must be sent to Kinesis Data Streams**.

But this option says:

```text
Application
   ↓
SQS
   ↓
EC2
```

Kinesis has disappeared! 😄

So immediately:

❌ Doesn't satisfy the requirement.

### Reason #2: EC2 is unnecessary

You would have:

```text
SQS
 ↓
EC2
 ↓
Process
```

Now you have to manage EC2 infrastructure.

The question specifically wants a **cost-effective asynchronous architecture**.

Lambda is much more natural:

```text
Kinesis
 ↓
Lambda
 ↓
S3
```

Therefore:

❌ **Wrong**

# Option 4 — Kinesis Data Streams + Lambda consumers → S3 ✅

This is exactly what the question describes.

```text
                  ┌───────────────┐
User → Application → Kinesis Data │
                  │    Streams    │
                  └───────┬───────┘
                          ↓
                    Lambda Consumer
                          ↓
                    Process image
                          ↓
                         S3
```

The application can return:

```text
"Upload successful" ✅
```

as soon as the record is successfully placed in Kinesis.

Lambda processes the record asynchronously.

And after processing:

```text
Lambda → S3
```

### ✅ Correct.

# 🆚 7. Kinesis Data Streams vs Firehose

This distinction is **very important for your SAA exam**.

| Feature                              | Kinesis Data Streams                    | Kinesis Data Firehose                  |
| ------------------------------------ | --------------------------------------- | -------------------------------------- |
| Main purpose                         | **Real-time data streaming/processing** | **Deliver streaming data**             |
| Can Lambda consume it?               | ✅ Yes                                   | Lambda can be used for transformations |
| Stores streaming records temporarily | ✅ Yes                                   | Buffers before delivery                |
| Main mental model                    | **Collect/process**                     | **Deliver**                            |
| Example                              | Real-time application processing        | Send logs/events to S3                 |
| Requires you to manage shards?       | Yes                                     | No                                     |
| Great for direct S3 delivery?        | Possible via consumers                  | **Yes, that's a primary use case**     |

### Simple memory trick:

> **Streams = I want to process the stream.**

> **Firehose = I want to deliver the stream somewhere.**

---

# 🆚 8. Kinesis vs SQS

Another important exam distinction.

### SQS

Think:

> **"Here is a job. Someone process it."**

```text
Producer
   ↓
SQS
   ↓
Worker
```

Example:

```text
Order placed
   ↓
SQS
   ↓
Process order
```

### Kinesis Data Streams

Think:

> **"Here is a continuous stream of events."**

```text
Events
 ↓
Kinesis Data Streams
 ↓
Consumers
```

Example:

```text
Website clicks
       ↓
Kinesis
       ↓
Real-time analytics
```

In this question, the requirement **explicitly says Kinesis**, so don't replace it with SQS.

# 🧩 9. Why does the 5-minute detail matter?

This is a clue.

The question isn't simply:

> "Store Kinesis data in S3."

It's saying:

> Processing takes about **5 minutes**.

So you need an actual processing component.

```text
Kinesis
   ↓
Lambda
   ↓
5-minute processing
   ↓
S3
```

That's why the direct Kinesis → Firehose → S3 option isn't the intended answer.
