6. Question

Category: CSAA – Design Secure Architectures

An Intelligence Agency developed a missile tracking application that is hosted on both development and production AWS accounts. The Intelligence agency’s junior developer only has access to the development account. The developer has received security clearance to access the agency’s production account, but the access is only temporary, and only write access to Amazon EC2 and Amazon S3 is allowed.

Which of the following allows the developer to issue short-lived access tokens that act as temporary security credentials, leveraging AWS Identity and Access Management (IAM) roles, to allow access to AWS resources?

- All of the given options are correct.
- Use AWS IAM Identity Center
- `Use AWS Security Token Service (STS)`
- Use Amazon Cognito to issue JSON Web Tokens (JWT)

Yes — this question is mainly testing **three different identity/authentication services that can sound similar**. Let's separate them clearly.

## 1. First, what is the question asking?

The developer:

* normally has access only to **Dev account**
* temporarily needs access to **Production**
* needs only specific permissions: **write to EC2 and S3**
* access should be **temporary**, not permanent

So the key words are:

> **temporary access + IAM role + temporary AWS credentials**

That points directly to **AWS STS**.

```text
Dev user
   ↓
AssumeRole
   ↓
AWS STS
   ↓
Temporary credentials
   ↓
Production IAM Role
   ↓
EC2 + S3
```

---

# 2. What is AWS IAM Identity Center?

Think of **IAM Identity Center = workforce SSO/login system**.

Imagine a company has 1,000 employees.

Instead of creating separate IAM users for everyone:

```text
Employee
   ↓
Company login
   ↓
IAM Identity Center
   ↓
AWS Account / Applications
```

It lets employees use their organizational identity to access AWS accounts and applications.

For example:

```text
Bilal
  ↓
Company username/password
  ↓
IAM Identity Center
  ↓
AWS Console
  ├── Dev account
  ├── Test account
  └── Prod account
```

You can centrally control:

> "This employee can access Dev."

> "This employee can access Prod."

> "This employee can access Prod with Administrator permissions."

So:

### IAM Identity Center

**Think:**

> 🔑 **Who can log in and which AWS accounts/apps can they access?**

It is primarily about **workforce access / SSO / centralized access management**.

---

# 3. What is AWS Cognito?

Cognito is more about **customers/users of your application**, not your company's AWS administrators.

Imagine you build:

```text
myshoppingapp.com
```

Customers need to:

```text
Sign Up
   ↓
Login
   ↓
Get authenticated
   ↓
Use the application
```

Cognito can manage those application users.

For example:

```text
Customer
   ↓
Cognito
   ↓
JWT token
   ↓
Your web/mobile application
```

So:

### Cognito

**Think:**

> 👤 **Users logging into my application**

Examples:

* Mobile app users
* Website customers
* Application authentication
* User registration/login

---

# 4. What is a JWT?

JWT = **JSON Web Token**.

It's basically a token containing claims about an authenticated user/session.

Conceptually:

```text
User
 ↓
Login
 ↓
Cognito
 ↓
JWT
 ↓
Application
```

The application can use the JWT to understand things like:

> "This user has successfully authenticated."

Don't confuse:

**JWT** ❌ with **AWS temporary security credentials**.

They are different things.

---

# 5. STS is different

STS = **Security Token Service**.

Its important job for SAA:

> **Give temporary AWS security credentials.**

Example:

```text
Developer
   ↓
AssumeRole
   ↓
STS
   ↓
Temporary credentials
   ↓
Prod IAM Role
   ↓
S3 / EC2
```

Those credentials are temporary and can have limited permissions.

That's exactly what Question 6 describes.

---

# 🔥 The easiest comparison

| Service                 | Think                         | Main purpose                                |
| ----------------------- | ----------------------------- | ------------------------------------------- |
| **STS**                 | 🎟️ Temporary AWS credentials | Temporary access / AssumeRole               |
| **IAM Identity Center** | 🔑 Company SSO                | Workforce access to AWS accounts/apps       |
| **Cognito**             | 👤 App users                  | Customer/user authentication                |
| **JWT**                 | 🪪 Digital token              | Carries authentication/authorization claims |
| **IAM Role**            | 🎭 Permission identity        | Defines what actions are allowed            |

### Exam shortcut

If you see:

**"temporary AWS credentials"**
→ **STS**

**"AssumeRole"**
→ **STS**

**"temporary cross-account access"**
→ **STS + IAM Role**

**"employees/workforce SSO into AWS accounts"**
→ **IAM Identity Center**

**"customers/users logging into web/mobile application"**
→ **Cognito**

**"JWT"**
→ **Cognito/application authentication**

---

### One very important distinction

Don't memorize:

> "Identity Center doesn't generate tokens."

That's too simplistic.

For **this exam question**, the important distinction is that **STS is the service specifically being asked for when the requirement is temporary AWS security credentials obtained by assuming an IAM role**.

So when you see:

> **"short-lived access tokens that act as temporary security credentials"**

🚨 **STS immediately.**

Exactly — **“Login with Google” and Cognito are not competing ideas.** Cognito can actually be the service that sits between your app and Google.

Think of it like this:

```text
                 ┌── Google
User → Cognito ──┤
                 ├── Apple
                 └── Facebook
                    ↓
                  Your App
```

### What happens?

Suppose you build a mobile app.

User clicks:

> **Continue with Google**

The flow can be:

```text
User
 ↓
Your App
 ↓
Amazon Cognito
 ↓
Google
 ↓
User logs in with Google
 ↓
Google confirms identity
 ↓
Cognito
 ↓
Tokens
 ↓
Your App
```

So **Google is the Identity Provider (IdP)**, while **Cognito acts as the identity/authentication service for your application** and can federate with external providers.

---

### Then why use Cognito?

Because you don't want to build all this yourself:

* User registration/login
* Password management
* MFA
* Token handling
* Social login integration
* User pools
* Federation with Google, Apple, etc.

Cognito provides that infrastructure.

### 🧠 Very simple exam distinction

| Situation                                         | Think                          |
| ------------------------------------------------- | ------------------------------ |
| User wants to log into **your application**       | **Cognito**                    |
| User clicks **Login with Google**                 | **Google = Identity Provider** |
| Cognito connects your app to Google               | **Federation**                 |
| Temporary credentials to access **AWS resources** | **STS**                        |
| Employees SSO into **AWS accounts**               | **IAM Identity Center**        |

So your understanding should be:

> **Cognito = authentication system for application users.**
> **Google = an external identity provider that Cognito can use for "Login with Google."**

And this is why **Cognito + Google** makes perfect sense.
