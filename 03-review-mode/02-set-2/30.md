30. Question

Category: CSAA – Design Resilient Architectures

A company is running a dashboard application on a Spot EC2 instance inside a private subnet. The dashboard is reachable via a domain name that maps to the private IPv4 address of the instance’s network interface. A solutions architect needs to increase network availability by allowing the traffic flow to resume in another instance if the primary instance is terminated.

Which solution accomplishes these requirements?


- Set up AWS Transfer for FTPS service in Implicit FTPS mode to automatically disable the source/destination checks on the instance’s primary elastic network interface and reassociate it to another instance.
- `Create a secondary elastic network interface and point its private IPv4 address to the application’s domain name. Attach the new network interface to the primary instance. If the instance goes down, move the secondary network interface to another instance.`
- Attach an elastic IP address to the instance’s primary network interface and point its IP address to the application’s domain name. Automatically move the EIP to a secondary instance if the primary instance becomes unavailable using the AWS Transit Gateway.
- Use the AWS Network Firewall to detach the instance’s primary elastic network interface and move it to a new instance upon failure.

Yes — this question is teaching a **very specific EC2 networking/high-availability technique: Elastic Network Interfaces (ENIs)**.

The important part is that this application is **private**, and the company wants to keep the **same private IP** even if the Spot instance dies.

---

## 1. First understand the situation

They currently have:

```text
Private DNS
    │
    ▼
Private IP
    │
    ▼
Spot EC2
```

The problem:

```text
Spot EC2 TERMINATED ❌
       │
       ▼
Private IP is gone with that instance
       │
       ▼
Dashboard unavailable
```

They want:

```text
Primary EC2
     │
     │ failure
     ▼
Secondary EC2
     │
     ▼
Same private IP
     │
     ▼
Traffic resumes
```

The key question is:

> **How can we move the network identity from one EC2 to another?**

Answer: **a secondary ENI.**

---

# 2. What is an ENI?

You already know EC2 has networking.

Think of an **ENI (Elastic Network Interface)** as a **virtual network card**.

It has things such as:

* Private IP address
* MAC address
* Security groups
* Network connectivity

For example:

```text
ENI
├── Private IP: 10.0.1.50
├── MAC address
└── Security Groups
```

And you can attach an ENI to an EC2 instance.

---

# 3. Why is the SECONDARY ENI important?

Suppose we create:

```text
Secondary ENI
Private IP = 10.0.1.50
```

Then attach it to our primary EC2:

```text
             Primary EC2
                 │
       ┌─────────┴─────────┐
       │                   │
 Primary ENI          Secondary ENI
 10.0.1.10              10.0.1.50
                         ▲
                         │
                    DNS points here
```

Now the domain points to:

```text
dashboard.company.internal
          ↓
       10.0.1.50
```

The important thing is that **10.0.1.50 belongs to the secondary ENI**, not permanently to the EC2 instance.

---

# 4. What happens when the Spot instance dies?

The Spot instance gets terminated:

```text
Primary EC2 ❌
```

But the **secondary ENI survives**.

So we can attach that ENI to a replacement EC2:

```text
Before:

Secondary ENI
10.0.1.50
     │
     ▼
Primary EC2 ❌


After:

Secondary ENI
10.0.1.50
     │
     ▼
Replacement EC2 ✅
```

DNS still says:

```text
dashboard.company.internal
        ↓
    10.0.1.50
```

And **10.0.1.50 hasn't changed**.

Therefore traffic starts flowing to the replacement instance.

That's the entire trick.

---

# 5. Why doesn't DNS need to change?

This is one of the **most important points in this question**.

Without ENI:

```text
DNS → 10.0.1.50 → EC2 #1 ❌

New EC2 → 10.0.1.72

Now you would need to change DNS.
```

With secondary ENI:

```text
DNS → 10.0.1.50
          │
          ▼
      Secondary ENI
          │
          ▼
      EC2 #1 ❌

Move ENI

DNS → 10.0.1.50
          │
          ▼
      Secondary ENI
          │
          ▼
      EC2 #2 ✅
```

**Same IP. Same ENI. No DNS change.**

That's why this answer is so good.

---

# Option 1 — AWS Transfer for FTPS ❌

This one is basically nonsense for the requirement.

**AWS Transfer Family** is for transferring files using protocols such as:

* SFTP
* FTPS
* FTP

The question isn't asking for file transfer.

It also cannot magically detach the primary ENI and move it between instances.

### Important EC2 concept

An EC2 instance's **primary network interface cannot be detached**.

A **secondary ENI can be detached and attached elsewhere**.

So remember:

```text
Primary ENI   → cannot detach
Secondary ENI → can detach/attach
```

---

# Option 2 — Secondary ENI ✅

This is the correct answer.

```text
                 DNS
                  │
                  ▼
             10.0.1.50
                  │
                  ▼
          Secondary ENI
                  │
          ┌───────┴───────┐
          │               │
       EC2 #1          EC2 #2
       Primary          Standby
```

Normal situation:

```text
ENI → EC2 #1
```

Failure:

```text
EC2 #1 ❌

ENI → EC2 #2 ✅
```

The ENI carries the network identity with it.

### Why this is especially useful here

The application is using a **private IP**.

So we don't need a public Elastic IP.

And because the ENI retains its networking information, we don't need to change DNS.

**This is the key lesson.**

---

# Option 3 — Elastic IP + Transit Gateway ❌

This option tries to sound sophisticated 😂 but contains two problems.

### Problem 1: This is a private application

The question says:

> private subnet

So an **Elastic IP isn't necessary**.

EIP is a **public IPv4 address**.

Think:

```text
Private application
       ↓
Private IP
       ↓
No EIP needed
```

### Problem 2: Transit Gateway doesn't do this

You learned VPC networking already.

**Transit Gateway** is basically a central networking hub:

```text
VPC A ──┐
VPC B ──┼── Transit Gateway
VPC C ──┘
On-prem ─┘
```

It connects networks.

It does **not** automatically say:

> "EC2 #1 died, let me move this EIP to EC2 #2."

So this option is wrong.

---

# Option 4 — Network Firewall ❌

You just learned Network Firewall in Q28.

But here it has nothing to do with this problem.

Network Firewall:

```text
Traffic
   ↓
Firewall
   ↓
Allow / Block
```

It is for **traffic filtering/security**.

It doesn't manage EC2 failover by moving ENIs.

Also, again:

> **You cannot detach the primary ENI from an EC2 instance.**

So this option is wrong twice.

---

# The BIG SAA lesson from Q30

You should add this to your mental toolbox:

### If the question says:

> "I need to move the same private IP/network identity from a failed EC2 instance to another EC2 instance"

Think:

## **Secondary ENI**

```text
              DNS
               │
               ▼
          Private IP
               │
               ▼
        Secondary ENI
               │
       ┌───────┴───────┐
       ▼               ▼
    EC2 #1           EC2 #2
   Primary            Standby
```

When EC2 #1 fails:

```text
Secondary ENI
      │
      └──────────► EC2 #2
```

No DNS change.

---

### One correction to keep in your head

Don't confuse **ENI failover** with **Elastic IP failover**.

| Requirement                                       | Think                        |
| ------------------------------------------------- | ---------------------------- |
| Move **private IP/network identity** between EC2s | **Secondary ENI**            |
| Move a **public IPv4 address** between EC2s       | **Elastic IP reassociation** |
| Connect multiple VPCs/networks                    | **Transit Gateway**          |
| Filter network traffic                            | **Network Firewall**         |
| Protect HTTP/HTTPS application                    | **WAF**                      |

So Q30's keyword is:

> **Private IP + EC2 failure + move network identity to another instance = Secondary ENI.**
