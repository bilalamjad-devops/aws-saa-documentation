14. Question

Category: CSAA – Design Resilient Architectures

A company plans to migrate all of their applications to AWS. The Solutions Architect suggested to store all the data to EBS volumes. The Chief Technical Officer is worried that EBS volumes are not appropriate for the existing workloads due to compliance requirements, downtime scenarios, and IOPS performance.

Which of the following are valid points in proving that EBS is the best service to use for migration? (Select TWO.)

- `An EBS volume is off-instance storage that can persist independently from the life of an instance.`
- EBS volumes can be attached to any EC2 Instance in any Availability Zone.
- Amazon EBS provides the ability to create snapshots (backups) of any EBS volume and write a copy of the data in the volume to Amazon RDS, where it is stored redundantly in multiple Availability Zones
- `EBS volumes support live configuration changes while in production which means that you can modify the volume type, volume size, and IOPS capacity without service interruptions.`
- When you create an EBS volume in an Availability Zone, it is automatically replicated on a separate AWS region to prevent data loss due to a failure of any single hardware component.

Yes. This question is mainly testing **what EBS actually provides and what it does NOT provide**. Let's ignore the complicated wording first.

## 🧠 First understand the scenario

The company wants to migrate applications to AWS and the CTO is worried:

* Will EBS data survive if EC2 is terminated?
* Can EBS handle high IOPS?
* Can we change EBS configuration without downtime?
* Is EBS replicated across regions?

The question asks:

> **Which TWO statements prove that EBS is suitable?**

The correct answers are:

✅ **1. EBS is off-instance storage and can persist independently of EC2.**

✅ **4. EBS supports live configuration changes.**

---

# 1️⃣ "EBS can persist independently from the instance"

This is very important.

Imagine:

```text
EC2 Instance
     │
     │ attached
     ▼
EBS Volume
```

You have:

```text
EC2 = Application/server
EBS = Disk/storage
```

If the EC2 instance is terminated, the EBS volume **can remain** depending on its `DeleteOnTermination` setting.

So:

```text
EC2 ❌ terminated

EBS ✅ still exists
```

That's what this statement means:

> **EBS is off-instance storage that can persist independently from the life of an instance.**

This is one reason EBS is useful for databases, application data, etc.

---

# 2️⃣ "EBS can attach to any EC2 instance in any AZ"

❌ **WRONG**

This is a classic exam trap.

An EBS volume belongs to **one Availability Zone**.

For example:

```text
Region
│
├── AZ-A
│    └── EBS-1
│
└── AZ-B
     └── EC2-2
```

You **cannot** normally do:

```text
EBS-1 (AZ-A)
      ↓
EC2-2 (AZ-B)
```

Instead:

```text
EBS-1 (AZ-A)
      ↓
EC2-1 (AZ-A) ✅
```

### Remember:

> **EBS and EC2 must be in the same AZ.**

---

# 3️⃣ EBS snapshot → RDS

❌ **Wrong**

This option is trying to trick you.

It says:

> EBS snapshot → Amazon RDS

No.

EBS snapshots are stored in **Amazon S3** behind the scenes.

Think:

```text
EBS Volume
     ↓
EBS Snapshot
     ↓
Amazon S3
```

Not:

```text
EBS → RDS ❌
```

Also remember:

**EBS snapshot is not the same thing as an EBS volume.**

Snapshot = backup/copy.

---

# 4️⃣ Live configuration changes

✅ **CORRECT**

This is the second correct answer.

EBS allows you to modify things while the system is running, such as:

* volume size
* volume type
* IOPS capacity

For example:

```text
Before:

EBS
100 GB
gp3
3,000 IOPS

        ↓ modify

After:

EBS
200 GB
gp3
6,000 IOPS
```

You don't necessarily need to stop your application just to make these changes.

That's why the statement says:

> **"live configuration changes while in production"**

This is useful when your workload grows.

---

# 5️⃣ "EBS automatically replicates to another AWS Region"

❌ **WRONG**

This is another exam trap.

EBS automatically replicates data **within the same Availability Zone** to protect against hardware failure.

It does **NOT** automatically replicate your EBS volume to another Region.

Think:

```text
Region
│
├── AZ-A
│    └── EBS
│        ├── copy
│        └── copy
│
└── AZ-B
```

Not:

```text
Region 1
   ↓ automatic replication ❌
Region 2
```

If you want cross-region protection, you can **copy EBS snapshots to another Region**.

---

# 🎯 The two answers

### ✅ Answer 1

> **An EBS volume is off-instance storage that can persist independently from the life of an instance.**

Meaning:

**EC2 can die → EBS can survive.**

---

### ✅ Answer 2

> **EBS volumes support live configuration changes while in production.**

Meaning:

**You can modify size/type/IOPS without necessarily taking the application offline.**

---

| ------------------------------------------ | -------- |
| Persistent block storage                   | ✅        |
| Used with EC2                              | ✅        |
| Survives EC2 termination if configured     | ✅        |
| EBS + EC2 must be same AZ                  | ✅        |
| Automatically replicated within AZ         | ✅        |

### One sentence for your exam:

> **EBS = persistent block storage for EC2, AZ-scoped, replicated within the AZ, snapshot-backed, and can be modified while in use.**

That's the main lesson from Q14.
