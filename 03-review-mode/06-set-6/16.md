16. Question

Category: CSAA – Design Secure Architectures

An application is loading hundreds of JSON documents into an Amazon S3 bucket every hour which is registered in AWS Lake Formation as a data catalog. The Data Analytics team uses Amazon Athena to run analyses on these data, but due to the volume, most queries take a long time to complete.

What change should be made to improve the query performance while ensuring data security?


- `Transform the JSON data into Apache Parquet format. Ensure that the user has an lakeformation:GetDataAccess IAM permission for underlying data access control.`
- Convert the JSON documents into CSV format. Provide fine-grained named resource access control to specific databases or tables in AWS Lake Formation.
- Compress the data into GZIP format before storing it in the S3 bucket. Apply an IAM policy with aws:SourceArn and aws:SourceAccount global condition context keys in Lake Formation that prevents cross-service confused deputy problems and other security issues.
- Apply minification on the data and implement the Lake Formation tag-based access control (LF-TBAC) authorization strategy to ensure security.

Is question ka correct answer **Transform the JSON data into Apache Parquet format. Ensure that the user has an lakeformation:GetDataAccess IAM permission for underlying data access control.** hai.

---

### Scenario Breakdown & Key Requirements

1. **Performance Problem:** S3 bucket mein har ghante hundreds of **JSON documents** aa rahe hain. Amazon Athena par queries chalane mein **boht time (long time)** lag raha hai.
2. **Data Catalog & Security:** S3 bucket **AWS Lake Formation** mein registered hai as a data catalog. Queries ko fast bhi banana hai aur **data security / access control** ko bhi ensure karna hai.

---

### Correct Option Explanation

#### ✅ **Convert JSON to Parquet + Lake Formation Permissions**

* **Apache Parquet (Columnar Format):** JSON (jo text/row format mein hota hai) ki jagah **Apache Parquet** ek columnar storage format hai. Columnar formats mein Athena ko poora document scan nahi karna padta, sirf wahi columns read karne padte hain jo query mein mangwaye gaye hon. Is se query performance 10x-100x fast ho jati hai aur scanned data kam hone se **cost bhi significantly reduce** hoti hai.
* **Lake Formation Security:** Lake Formation ke zariye underlying S3 data ko security-wise control karne ke liye user ke pas `lakeformation:GetDataAccess` IAM permission honi chahiye taake Lake Formation temporary credentials generate karke user ko authorized data fetch karne de.

---

### Incorrect Options Breakdown (Elimination)

* ❌ **CSV Format:** CSV bhi uncompressed, row-based text format hai jo Athena queries ki performance improve nahi karta.
* ❌ **GZIP Compression only + Confused Deputy keys:** Sirf GZIP karne se row-based JSON columnar nahi banta. Iske ilawa `aws:SourceArn` cross-service confused deputy protection ke liye hota hai, Lake Formation ke normal user query authorization ke liye nahi.
* ❌ **Minification + LF-TBAC:** Minification (spaces/newlines hatana) JSON ke scan size mein boht chota farq lati hai. Parquet jitna dramatic performance boost nahi de sakti.

---

### SAA-C03 Athena Performance Optimization Rule 💡

> **Athena Query Optimization Rule:**
> * Athena performance aur cost optimize karne ke liye best practice **Columnar Formats (Apache Parquet ya Apache ORC)** me transform karna aur **Partitioning** istemal karna hai.
