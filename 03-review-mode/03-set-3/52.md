52. Question

Category: CSAA – Design High-Performing Architectures

A company currently has an Augment Reality (AR) mobile game that has a serverless backend. It is using a DynamoDB table which was launched using the AWS CLI to store all the user data and information gathered from the players and a Lambda function to pull the data from DynamoDB. The game is being used by millions of users each day to read and store data.

How would you design the application to improve its overall performance and make it more scalable while keeping the costs low? (Select TWO

- Configure CloudFront with DynamoDB as the origin; cache frequently accessed data on the client device using ElastiCache.
- `Enable DynamoDB Accelerator (DAX) and ensure that the Auto Scaling is enabled and increase the maximum provisioned read and write capacity.`
- Since Auto Scaling is enabled by default, the provisioned read and write capacity will adjust automatically. Also enable DynamoDB Accelerator (DAX) to improve the performance from milliseconds to microseconds.
- Use AWS IAM Identity Center to authenticate users and have them directly access DynamoDB using single sign-on. Manually set the provisioned read and write capacity to a higher RCU and WCU.
- `Use API Gateway in conjunction with Lambda and turn on the caching on frequently accessed data and enable DynamoDB global replication.`

## 1. Requirements Breakdown

1. **Workload:** AR mobile game jise millions of active daily users read/write operations ke liye access kar rahe hain.
2. **Current Architecture:** DynamoDB Table (AWS CLI se launch hui) + AWS Lambda.
3. **Goal:** Performance ko improve karna (**microseconds read response time**), high scalability achieve karna, aur cost control mein rakhna.

---

## 2. Core Technical Concepts

1. **DynamoDB Accelerator (DAX):**
* DynamoDB ke aage **fully managed in-memory cache** hai jo read performance ko **milliseconds se microseconds** tak accelerate kar deta hai. High-read workloads (jaise mobile games) ke liye ultimate performance boost hai.


2. **DynamoDB Provisioned Capacity & Auto Scaling:**
* Jab DynamoDB Table AWS CLI se default parameters ke sath launch ki jati hai, toh **Auto Scaling by default enable nahi hoti**.
* Scaling ke liye Auto Scaling ko **explicitly enable** karna padta hai aur maximum RCU/WCU limits set karni padti hain taake traffic spikes (millions of users) ke waqt application crash na ho.


3. **API Gateway Caching:**
* Lambda aur DynamoDB ke aage **Amazon API Gateway** lagane se frequently accessed requests API Gateway cache memory se hi return ho jati hain, jis se Lambda execution costs aur DynamoDB read load drastically kam ho jata hai.



---

## 3. Correct Options Explanation (Select TWO)

#### ✅ **Enable DynamoDB Accelerator (DAX) and ensure that the Auto Scaling is enabled and increase the maximum provisioned read and write capacity.**

* **Why it works:** DAX reads ko microsecond latency deta hai. CLI se bani table par Auto Scaling explicitly turn on karni padti hai taake high game traffic par application automatically scale ho sake.

#### ✅ **Use API Gateway in conjunction with Lambda and turn on the caching on frequently accessed data and enable DynamoDB global replication.**

* **Why it works:** API Gateway caching backend Lambda aur DynamoDB par repetitive read hits ko rok kar latency drop karti hai aur execution cost bachati hai. Global replication multi-region scalability provide karti hai.

---

## 4. Incorrect Options Breakdown (Elimination Strategy)

| Option | Why It Fails the Exam Requirement |
| --- | --- |
| **CloudFront with DynamoDB origin... ElastiCache on mobile** | **Technical Misconception:** CloudFront ka origin DynamoDB nahi ban sakta (ALB/S3/Custom HTTP ho sakta hai). ElastiCache mobile client device par install nahi ho sakta; woh AWS server-side in-memory cache hai. |
| **Since Auto Scaling is enabled by default...** | **False Premise:** AWS CLI se table create karte waqt Auto Scaling **by default enabled nahi hoti**. |
| **IAM Identity Center for players... Manually set RCU/WCU** | **Bad Architecture:** Millions of public mobile game users ke liye IAM Identity Center SSO use nahi hota (Cognito use hota hai). Manual RCU/WCU setting scalability block karti hai aur costs barha sakti hai. |

---

## 5. Exam Decision Matrix (DynamoDB Performance Cheat Sheet)

* **Microsecond read latency for DynamoDB:** $\rightarrow$ **DynamoDB Accelerator (DAX)**
* **DynamoDB Table created via AWS CLI:** $\rightarrow$ **Must explicitly configure Auto Scaling**
* **Cache API responses in front of Lambda:** $\rightarrow$ **Amazon API Gateway Caching**

### 🎯 What is being tested?

**DynamoDB performance + scalability + low cost.**

### ✅ Correct answers

**1. Enable DynamoDB Accelerator (DAX) and ensure Auto Scaling is enabled, increasing maximum provisioned RCU/WCU.**

* **DAX** → caches frequently accessed DynamoDB data → **microsecond latency**.
* **Auto Scaling** → adjusts capacity based on demand.

**2. Use API Gateway + Lambda, enable caching, and enable DynamoDB global replication.**

* **API Gateway caching** → reduces repeated backend requests.
* **Global Tables** → improves access for users across different regions.

### ⚠️ Important exam clue

One option says:

> "Since Auto Scaling is enabled by default..."

❌ **False.** DynamoDB Auto Scaling is **not enabled by default** for tables created through the AWS CLI.

### 🔥 Exam shortcut

**DynamoDB + millions of users + performance → DAX + Auto Scaling**

**API Gateway + Lambda + caching → reduce repeated requests**

Also remember:

**DAX = DynamoDB cache → milliseconds → microseconds.**
