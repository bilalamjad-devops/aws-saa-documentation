20. Question

Category: CSAA – Design High-Performing Architectures

An e-commerce application is using a fanout messaging pattern for its order management system. For every order, it sends an Amazon SNS message to an SNS topic, and the message is replicated and pushed to multiple Amazon SQS queues for parallel asynchronous processing. A Spot EC2 instance retrieves the message from each SQS queue and processes the message. There was an incident that while an EC2 instance is currently processing a message, the instance was abruptly terminated, and the processing was not completed in time.

In this scenario, what happens to the SQS message?

- The message is deleted and becomes duplicated in the SQS when the EC2 instance comes online.
- The message will automatically be assigned to the same EC2 instance when it comes back online within or after the visibility timeout.
- `When the message visibility timeout expires, the message becomes available for processing by other EC2 instances`
- The message will be sent to a Dead Letter Queue in AWS DataSync.

Is question mein **Amazon SQS Visibility Timeout** aur **EC2 Spot Instance Termination** ka core messaging concept test ho raha hai.

Aayein rules aur issue ko step-by-step analyze karte hain:

---

### 1. Scenario Breakdown

1. **Architecture:** Fanout pattern setup hai: `SNS Topic` $\rightarrow$ `Multiple SQS Queues` $\rightarrow$ `Spot EC2 Instances` (asynchronous parallel processing).
2. **Incident:** Spot EC2 instance ek SQS message ko process kar raha tha ke achanak instance **terminate** (band) ho gaya aur task complete nahi ho saka.
3. **Question:** Is interruption ke baad SQS queue mein mojood us message ka kya hoga?

---

### 2. SQS Visibility Timeout Kaise Kaam Karta Hai?

Jab koi consumer (EC2 instance) SQS queue se message read (receive) karta hai:

```
[ SQS Queue ] ──► (EC2 Receives Message) ──► [ Message Becomes Hidden / Invisible ]
                                                        │
                                                        ▼
                                              (Visibility Timeout Clock Starts)
                                                        │
                       ┌────────────────────────────────┴────────────────────────────────┐
                       ▼                                                                 ▼
      [ EC2 Completes Task & Calls DeleteMessage ]                    [ EC2 Interrupted / Crashes / Times Out ]
                       │                                                                 │
                       ▼                                                                 ▼
      (Message Permanently Removed)                                   (Visibility Timeout Expires ⏱️)
                                                                                         │
                                                                                         ▼
                                                                      (Message Re-appears in Queue for Others)

```

1. **In-Flight / Invisible State:** Message queue se delete nahi hota, balki ek specific duration ke liye baaki consumers se **hide (invisible)** ho jata hai. Is time period ko **Visibility Timeout** kehte hain.
2. **Normal Success Flow:** Processing complete hone par EC2 instance `DeleteMessage` API call karke SQS se message delete karta hai.
3. **Failure / Termination Flow:** Agar EC2 instance message complete karne se pehle crash ya terminate ho jaye, toh `DeleteMessage` call nahi ho pata. Jaise hi **Visibility Timeout expire** hota hai, SQS us message ko dobara **visible (available)** kar deta hai taake doosra working EC2 instance use wapas pick karke process kar sake.

---

### 3. Correct Option Explanation

#### ✅ **When the message visibility timeout expires, the message becomes available for processing by other EC2 instances**

* **Why it works:** SQS guarantee karta hai ke jab tak message explicitly delete na ho ya visibility timeout khatam na ho, message safely queue mein rehta hai aur timeout expire hote hi doosre instances ke liye duplicate work se bachate hue wapas pool mein aa jata hai.

---

### 4. Incorrect Options Breakdown (Elimination Strategy)

* ❌ **Option 1 (Message deleted & duplicated):** SQS message ko automatically delete nahi karta jab tak consumer `DeleteMessage` na bheje.
* ❌ **Option 2 (Assigned to same instance):** SQS stateless hai; SQS ko yeh nahi pata hota ke pehle kis specific instance ne message pick kiya tha. Any available worker can pick it.
* ❌ **Option 4 (DLQ in AWS DataSync):** DataSync file migration tool hai, queuing service nahi. Dead Letter Queue (DLQ) SQS ke andar hi config hota hai (baad mein *MaxReceiveCount* exceed hone par message DLQ mein jata hai, direct 1st failure par nahi).
