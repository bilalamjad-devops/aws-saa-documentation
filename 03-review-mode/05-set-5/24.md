24. Question

Category: CSAA – Design High-Performing Architectures

A Solutions Architect joined a large tech company with an existing Amazon VPC. When reviewing the Auto Scaling events, the Architect noticed that their web application is scaling up and down multiple times within the hour.

What design change could the Architect make to optimize cost while preserving elasticity?

- Increase the base number of Auto Scaling instances for the Auto Scaling group
- Upgrade the instance type in the launch template.
- Add provisioned IOPS to the instances
- `Change the cooldown period of the Auto Scaling group and set the CloudWatch metric to a higher threshold`

Is question mein **Auto Scaling Flapping (Rapid Scale-Up & Scale-Down)** aur **Cost Optimization** ka scenario test ho raha hai.

---

### Scenario Breakdown

Jab koi application ek hi ghante mein baar baar scale-up aur scale-down ho rahi ho (jise **flapping** kehte hain), toh is se extra costs aur system instability paida hoti hai:

1. **Scale-up:** Naye instances launch hote hain (jis par minimum billing cycle/hourly cost apply ho sakti hai).
2. **Rapid Scale-down:** Jaise hi load thoda kam hota hai, instances terminate ho jate hain.
3. **Repeat:** Traffic ka chota sa spike aate hi dubara scale-up shuru ho jata hai.

---

### Correct Option Explanation

#### ✅ **Change the cooldown period of the Auto Scaling group and set the CloudWatch metric to a higher threshold**

* **Why it works:**
* **Cooldown Period:** Auto Scaling ko instructed rakhta hai ke naya instance launch ya terminate karne ke baad ek specific time limit (e.g., 300 seconds) tak wait kare taake previous scaling action ka asar stabilize ho sake. Is se unnecessary rapid scale-up/down (flapping) ruk jati hai.
* **Higher Threshold:** Metric (e.g., CPU Utilization) ki scaling limit thodi upar set karne se choti-moti temporary spikes par bewaja naye instances launch nahi hotay, jis se cost control mein rehti hai aur elasticity bhi preserve rehti hai.



---

### Incorrect Options Breakdown (Elimination)

* ❌ **Increase base number of instances:** Base instances barhane se hamesha ke liye fixed cost barh jayegi, jo cost preservation ke khilaf hai.
* ❌ **Upgrade instance type:** Larger instances use karne se idle cost barh sakti hai, jabki masala scaling logic/cooldown ka hai.
* ❌ **Add Provisioned IOPS:** EBS IOPS ka Auto Scaling threshold ya flapping se koi talaluq nahi hai.
