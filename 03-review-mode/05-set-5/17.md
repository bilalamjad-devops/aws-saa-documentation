17. Question

Category: CSAA – Design High-Performing Architectures

A company plans to design a highly available architecture in AWS. They have two target groups with three EC2 instances each, which are added to an Application Load Balancer. In the security group of the EC2 instance, you have verified that port 80 for HTTP is allowed. However, the instances are still showing out of service from the load balancer.

What could be the root cause of this issue?

- The instances are using the wrong AMI.
- `The health check configuration is not properly defined.`
- The wrong subnet was used in your VPC
- The wrong instance type was used for the EC2 instance.

Is question mein **Application Load Balancer (ALB) Health Checks** aur **EC2 Instance Status** ka real-world troubleshooting scenario test ho raha hai.

Aayein rules aur issue ko step-by-step analyze karte hain:

---

### 1. Scenario Breakdown

1. **Architecture:** High Availability setup hai jismein 2 Target Groups hain, har Target Group mein 3 EC2 instances hain jo **Application Load Balancer (ALB)** ke peeche lage hain.
2. **Security Group Check:** EC2 Security Group mein **Port 80 (HTTP)** inbound traffic already **Allowed** hai (network access ka issue nahi hai).
3. **Problem:** Is ke bawajood ALB Target Group mein instances ka status **"Out of Service" (Unhealthy)** show ho raha hai.

---

### 2. Technical Evaluation

```
[ Client Request ] ──► [ ALB Listener (Port 80) ] 
                              │
                    (Periodic Health Checks)
                              │
                              ▼
               [ Target Group Health Check Path ]
             (Default: "/" or Custom URL, Port 80)
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
            [ Status: 200 OK ]   [ Status: 404 / Timeout / Wrong Path ]
               (In Service)               (Out of Service)

```

1. **ALB Health Checks Kaise Kaam Karte Hain?**
* ALB periodic basis par Target Group ke instances par health check request bhejta hai (e.g., `HTTP GET /` ya `HTTP GET /health`).
* Agar health check path galat configure ho (e.g., path `/index.html` set hai jo instance par exist nahi karta), toh EC2 instance **404 Not Found** response dega.
* ALB is 404 response ko failure samjhega aur instance ko **"Out of Service"** mark kar dega — chahe Security Group mein Port 80 allowed hi kyun na ho!


2. **Option Elimination:**
* **Wrong AMI / Wrong Instance Type:** Instances run kar rahe hain aur SG verified hai; AMI ya Instance type badalne se ALB Target Group health check pass nahi hoga.
* **Wrong Subnet:** Subnet routing masla hota toh initial network connect hi na hota, lekin ALB targets ko reach karke health status report kar raha hai.



---

### 3. Correct Option Explanation

#### ✅ **The health check configuration is not properly defined.**

* **Why it works:** Health check path, port, protocol, ya success response codes (e.g., 200 OK vs 404/500) agar app ke actual endpoint se match na karein, toh ALB working instances ko bhi "Out of Service" mark kar deta hai.

---

### 4. Cheat Sheet for ALB Troubleshooting (SAA-C03)

* **Target 'Out of Service' + Security Group OK:** $\rightarrow$ Check **Health Check Path / Port / Response Code**.
* **Target 'Out of Service' + Connection Timeout:** $\rightarrow$ Check **EC2 Security Group / Network ACLs** (Port 80/443 inbound missing).
* **HTTP 502 Bad Gateway:** $\rightarrow$ Application server on EC2 crashed / not listening on the target port.
* **HTTP 504 Gateway Timeout:** $\rightarrow$ Application response timeout / Database connection issue behind EC2.
