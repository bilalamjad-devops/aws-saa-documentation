46. Question

Category: CSAA – Design High-Performing Architectures

A company plans to develop a custom messaging service that will be used to train an AI for an automatic response feature. The service is expected to receive thousands of messages per day, all of which will be processed by an Amazon EMR cluster. It is crucial that none of the messages are lost, no duplicates are produced, and that the messages are processed in EMR in the same order as arrival.

Which of the following options can satisfy the given requirement?

- Set up an Amazon SNS Topic to handle the messages.
- Create an Amazon Data Firehose to handle the messages.
- Set up an Amazon SQS standard queue and configure a dead-letter queue (DLQ) to handle failed messages.
- `Create an Amazon Kinesis Data Stream to collect the messages.`


Is question mein **Message Ingestion & Processing Order**, **Stream Processing (Kinesis vs SQS vs SNS)**, aur **Amazon EMR Integration** ka concept test ho raha hai.

Aayein requirements aur options ko Roman Urdu mein Step-by-Step analyze karte hain:

---

### 1. Requirement Breakdown

1. **Volume:** Thousands of messages per day.
2. **Target Consumer:** Amazon EMR Cluster (Big Data / AI training processing).
3. **Critical Conditions:**
* **No Message Loss:** Har message zaroor process hona chahiye.
* **No Duplicates:** duplicate records allow nahi hain.
* **Strict Ordering:** Messages EMR mein usi order mein process hone chahiye jis order mein receive hue (**First-In-First-Out / FIFO**).



---

### 2. Technical Evaluation

```
[ Incoming Messages ] ──► [ Amazon Kinesis Data Stream ] ──► [ Amazon EMR Cluster ]
                              (Strict In-Order Records)        (Processes Data for AI)

```

1. **Amazon Kinesis Data Streams:**
* High-throughput real-time streaming data collect aur process karne ke liye design kiya gaya hai.
* **Strict Ordering & Deduplication:** Partition Key ke zariye har shard ke andar messages ka **Strict Arrival Order** maintain rehta hai aur duplicate delivery prevent hoti hai.
* **EMR Native Integration:** Amazon EMR (Apache Spark / Flink) directly Kinesis Data Streams ke sath integration support karta hai.



---

### 3. Correct Option Explanation

#### ✅ **Create an Amazon Kinesis Data Stream to collect the messages.**

* **Why it works:** Kinesis Data Streams messages ki sequential ordering (per shard) guarantee karta hai, duplicates resist karta hai, zero message loss ensure karta hai, aur EMR real-time streaming processing ke sath natively integrate hota hai.

---

### 4. Incorrect Options Breakdown (Elimination Strategy)

| Option | Why It Fails |
| --- | --- |
| **Amazon SNS Topic...** | SNS (Simple Notification Service) ek Pub/Sub fan-out messaging tool hai. Is mein message ordering ki absolute guarantee nahi hoti aur duplicate messages ho sakte hain. |
| **Amazon Data Firehose...** | Amazon Data Firehose data ko S3, Redshift, ya OpenSearch mein auto-load karne ke liye hota hai; yeh real-time streaming ordering aur direct EMR consuming workflow ke liye design nahi hua. |
| **Amazon SQS Standard Queue...** | Standard SQS Queue **Best-Effort Ordering** allow karti hai aur **At-Least-Once Delivery** ki waja se **duplicates produce ho sakte hain**. Strict order aur no-duplicates ke liye SQS FIFO Queue required hoti hai (jo is option mein mentioned nahi hai). |

---

### 5. Cheat Sheet for AWS Messaging & Streaming (SAA-C03)

* **Real-Time Data Streaming for EMR / Analytics + Strict Order:** $\rightarrow$ **Amazon Kinesis Data Streams**
* **Decouple App Components with Ordering Guarantee:** $\rightarrow$ **Amazon SQS FIFO Queue**
* **Standard Asynchronous Queue (Order/Duplicates Allowed):** $\rightarrow$ **Amazon SQS Standard Queue**
* **Auto-Load Streaming Data into S3/Redshift:** $\rightarrow$ **Amazon Data Firehose**
