24. Question

Category: CSAA – Design Resilient Architectures

A solutions architect is tasked with designing a scalable infrastructure solution for a business that runs uses Amazon Elastic Kubernetes Service (Amazon EKS) to execute container applications. Since the company’s workload varies throughout the day, they want to make sure that its underlying infrastructure automatically scales in and out in response to demand.

Which of the following would meet the requirements with the LEAST amount of operational overhead?

- `Use a combination of Kubernetes Metrics and Kubernetes Cluster Autoscaler to manage the number of nodes.`
- Use Amazon EC2 Auto Scaling Groups with custom scaling policies to manage the scaling of EKS worker nodes.
- Set up CloudWatch alarms for CPU utilization or request count to monitor the relevant metrics of the container applications running on Amazon EKS.
- Integrate an edge-optimized API endpoint in Amazon API Gateway with Amazon EKS to manage and expose APIs for the containerized applications running on EKS.

Is question mein **Amazon EKS (Kubernetes) Cluster Scaling** aur **Least Operational Overhead** ka core architecture rule test ho raha hai.

Aayein requirements ko Roman Urdu mein analyze karte hain:

---

### 1. Requirement Breakdown

1. **Environment:** Application Amazon Elastic Kubernetes Service (Amazon EKS) par containerized environment mein chal rahi hai.
2. **Problem:** Workload din bhar vary karta rehta hai (traffic spiky hai).
3. **Goal:** Underlying infrastructure (EC2 worker nodes / pods) ko demand ke mutabiq **automatically scale in aur scale out** karna hai.
4. **Constraint:** Solution aisa hona chahiye jisme **LEAST operational overhead** ho (yani native Kubernetes cluster-native auto-scaling configuration use ki jaye).

---

### 2. Technical Evaluation

```
[ Pod Demand Increases / Pending Pods ]
                   │
                   ▼
     [ Kubernetes Metrics Server ]
                   │
                   ▼
     [ Kubernetes Cluster Autoscaler ]
                   │
                   ▼
 [ Automatically Adds / Removes EKS EC2 Worker Nodes ]

```

1. **Kubernetes Cluster Autoscaler + Metrics Server:**
* Kubernetes ecosystem mein **Metrics Server** pod CPU/Memory usage collect karta hai.
* **Cluster Autoscaler** (ya modern *Karpenter*) automatic component hota hai jo dekhta hai ke jab pods resource shortage ki waja se `Pending` state mein chale jayen, toh yeh EKS cluster mein naye EC2 worker nodes automatically add kar deta hai. Jab nodes idle hote hain, toh unhe scale in (remove) kar deta hai.
* Yeh native Kubernetes mechanism hai jo least operational effort ke sath EKS node management handle karta hai.



---

### 3. Correct Option Explanation

#### ✅ **Use a combination of Kubernetes Metrics and Kubernetes Cluster Autoscaler to manage the number of nodes.**

* **Why it works:** Kubernetes Cluster Autoscaler directly EKS control plane ke sath integrate ho kar pending pods ke metrics ke basis par EC2 worker nodes ki scaling ko automatically adjust karta hai.

---

### 4. Incorrect Options Breakdown (Elimination Strategy)

| Option | Why It Fails the Exam Requirement |
| --- | --- |
| **Integrate edge-optimized API endpoint...** | API Gateway API exposure ke liye hota hai; underlying EKS worker nodes ki auto-scaling manage nahi karta. |
| **EC2 Auto Scaling Groups with custom scaling policies...** | Direct EC2 ASG custom policies Kubernetes pod scheduling requirements (jaise pending pods) ko smartly handle nahi karti, jis se pods unscheduled reh sakte hain. |
| **CloudWatch alarms for CPU utilization...** | CloudWatch alarms sirf metrics monitor/alert kar sakte hain; yeh automatic Kubernetes cluster node provisioning aur scaling khud manage nahi karte. |

---

### 5. Exam Decision Matrix (EKS Auto Scaling Cheat Sheet)

* **Automatic EKS Worker Node Scaling (Kubernetes Native):** $\rightarrow$ **Kubernetes Cluster Autoscaler / Karpenter**
* **Automatic Pod Scaling based on CPU/Memory:** $\rightarrow$ **Horizontal Pod Autoscaler (HPA)**
* **Automatic Pod Scaling based on Request Count / Events:** $\rightarrow$ **Kubernetes Event-driven Autoscaling (KEDA)**
