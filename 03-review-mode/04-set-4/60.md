60. Question

Category: CSAA – Design Resilient Architectures

A newly hired Solutions Architect is checking all of the security groups and network access control list rules of the company’s AWS resources. For security purposes, the MS SQL connection via port 1433 of the database tier should be secured. Below is the security group configuration of their Microsoft SQL Server database:

The application tier hosted in an Auto Scaling group of EC2 instances is the only identified resource that needs to connect to the database. The Architect should ensure that the architecture complies with the best practice of granting least privilege.


Which of the following changes should be made to the security group configuration?


- For the MS SQL rule, change the Source to the Network ACL ID attached to the application tier.
- `For the MS SQL rule, change the Source to the security group ID attached to the application tier.`
- For the MS SQL rule, change the Source to the EC2 instance IDs of the underlying instances of the Auto Scaling group.
- For the MS SQL rule, change the Source to the static AnyCast IP address attached to the application tier.

Is question mein **Security Group Chaining / Referencing**, **Principle of Least Privilege**, aur **Dynamic Auto Scaling Security** ka concept test ho raha hai.

Aayein requirements aur options ko step-by-step analyze karte hain:

---

### 1. Requirement Breakdown

1. **Architecture:** Application Tier (Auto Scaling EC2 instances) $\rightarrow$ Microsoft SQL Server Database Tier (Port 1433).
2. **Goal:** Database ke Security Group mein Port 1433 par access dena hai.
3. **Constraint 1:** Sirf aur sirf **Application Tier** hi database se connect ho sakna chahiye (**Least Privilege** principle).
4. **Constraint 2:** Application Tier ek **Auto Scaling Group (ASG)** mein hai, jiska matlab hai ke EC2 instances constantly launch (scale-out) aur terminate (scale-in) hote rehte hain aur unke IP addresses change hote rehte hain.

---

### 2. Technical Evaluation

```
[ App Tier EC2 Instances ] ──► Associated with Security Group: sg-app123
           │
           │ (Allowed Rule: Inbound Port 1433 from Source: sg-app123)
           ▼
[ DB Tier MS SQL Server ] ──► Security Group: sg-db456

```

1. **Why IP Addresses or Instance IDs Fail in Auto Scaling:**
* Auto Scaling Groups mein **Instance IDs aur IP addresses dynamic hote hain**. Agar aap kisi specific IP ya Instance ID ko allow karein ge, toh jab bhi naya instance scale-out hoga, uski connection reject ho jayegi.


2. **Security Group Referencing (Chaining):**
* AWS Security Groups ki ek sab se powerful feature yeh hai ke aap Inbound Source mein IP Address/CIDR block ke bajaye **doosre Security Group ki ID** (e.g., `sg-app123`) add kar sakte hain.
* Iska matlab yeh hai: *"Har woh EC2 instance jiske paas `sg-app123` Security Group laga hua hai, woh DB se Port 1433 par connect kar sakta hai."*
* Yeh practice **Least Privilege** bhi enforce karti hai aur **Auto Scaling** ke sath 100% dynamically kaam karti hai.



---

### 3. Correct Option Explanation

#### ✅ **For the MS SQL rule, change the Source to the security group ID attached to the application tier.**

* **Why it works:** Database Security Group mein App Tier ka Security Group ID put karne se sirf authorised application instances ko access milta hai, chahay kitne hi naye instances ASG ke zariye add ya remove ho rahe hon.

---

### 4. Incorrect Options Breakdown (Elimination Strategy)

| Option | Why It Fails |
| --- | --- |
| **Source to Network ACL ID...** | Security Groups ke Inbound Rules mein **Network ACL ID reference nahi ho sakta** (sirf IP/CIDR ya Security Group IDs allow hoti hain). |
| **Source to EC2 instance IDs...** | Auto Scaling instances continuously create/destroy hote hain. Hardcoded Instance IDs naye scale-out instances par fail ho jayengi. |
| **Source to static AnyCast IP...** | AnyCast IP AWS Global Accelerator ke sath use hoti hai, standard internal EC2 Auto Scaling App Tiers ke liye nahi. |

---

### 5. Cheat Sheet for Security Group Best Practices (SAA-C03)

* **Multi-Tier App Access (App to DB / ALB to App):** $\rightarrow$ **Reference Source Security Group ID** (Security Group Chaining).
* **Dynamic Scaling (ASG) Security Rules:** $\rightarrow$ Always use **Security Group Rules**, never static IPs/Instance IDs.
* **Security Group vs Network ACL:** Security Group is **Stateful** (Instance Level); Network ACL is **Stateless** (Subnet Level).
