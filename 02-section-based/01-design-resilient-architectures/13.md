13. Question

Category: CSAA – Design Resilient Architectures

A manufacturing company has EC2 instances running in AWS. The EC2 instances are configured with Auto Scaling. There are a lot of requests being lost because of too much load on the servers. The Auto Scaling is launching new EC2 instances to take the load accordingly yet, there are still some requests that are being lost.

Which of the following is the MOST suitable solution that you should implement to avoid losing recently submitted requests?


- `Use an Amazon SQS queue to decouple the application components and scale-out the EC2 instances based upon the ApproximateNumberOfMessages metric in Amazon CloudWatch.`
- Replace the Auto Scaling group with a cluster placement group to achieve a low-latency network performance necessary for tightly-coupled node-to-node communication.
- Use larger instances for your application with an attached Elastic Fabric Adapter (EFA).
- Set up Amazon Aurora Serverless for on-demand, auto-scaling configuration of your EC2 Instances and also enable Amazon Aurora Parallel Query feature for faster analytical queries over your current data.



This is a **very important SAA pattern**. The key word is **"requests are being lost."** Auto Scaling alone does not guarantee that requests won't be lost.

# 13. Question — Easy Explanation

The current architecture is roughly:

```text
Users
  │
  ↓
EC2 instances
  │
  └── overloaded
       │
       ↓
   Requests lost ❌
```

The company already has Auto Scaling:

```text
High traffic
    ↓
ASG notices load
    ↓
Launch more EC2
```

But there is a problem:

> **It takes time to launch a new EC2 instance.**

Imagine suddenly 10,000 requests arrive.

```text
100 EC2 capacity
        ↓
10,000 requests arrive
        ↓
EC2 overloaded
        ↓
ASG starts launching instances
        ↓
⏳ takes time
        ↓
some requests are lost ❌
```

So we need somewhere to **temporarily hold the requests**.

That's where **Amazon SQS** comes in.

---

# ✅ Correct Answer

> **Use Amazon SQS to decouple the application components and scale out the EC2 instances based on the SQS queue backlog.**

The architecture becomes:

```text
                 Users
                   │
                   ↓
                  App
                   │
                   ↓
              ┌─────────┐
              │   SQS   │
              │  Queue  │
              └────┬────┘
                   │
          ┌────────┼────────┐
          ↓        ↓        ↓
        EC2-1    EC2-2    EC2-3
```

Now if 10,000 requests arrive but EC2 can process only 1,000 immediately:

```text
SQS
┌──────────────────────────────┐
│ 9,000 messages waiting       │
└──────────────────────────────┘
              ↓
        EC2 processes them
```

The requests aren't simply thrown away because the servers are temporarily busy.

---

# 🧠 What does "decouple" mean?

This is one of the most important words in AWS exams.

Without SQS:

```text
Application A
     │
     │ directly calls
     ↓
Application B
```

If B is overloaded:

```text
A → B ❌
```

The request can fail.

With SQS:

```text
Application A
     │
     ↓
    SQS
     │
     ↓
Application B
```

A can put the message into SQS even if B is temporarily busy.

Then B processes messages when it has capacity.

So:

> **SQS acts as a buffer between components.**

---

# 📦 Think of SQS like a waiting line

Imagine a restaurant.

Without a queue:

```text
Customers → Restaurant

Restaurant full → Customers rejected ❌
```

With a queue:

```text
Customers
   ↓
Waiting line
   ↓
Restaurant serves them one by one
```

SQS is basically the **waiting line for application messages**.

---

# 🔥 Why Auto Scaling + SQS?

This is the important architecture:

```text
                    Traffic
                       ↓
                      SQS
                       │
                Queue gets bigger
                       │
                       ↓
              CloudWatch metric
                       │
                       ↓
                  Auto Scaling
                       │
             ┌─────────┼─────────┐
             ↓         ↓         ↓
           EC2       EC2       EC2
```

As messages accumulate:

```text
SQS backlog ↑
     ↓
CloudWatch detects it
     ↓
ASG scales out
     ↓
More EC2 workers
     ↓
Queue gets processed
     ↓
Backlog ↓
```

This is a **very strong AWS architecture pattern**.

---

# ⚠️ Important detail: `ApproximateNumberOfMessages`

The answer says to scale based on:

> `ApproximateNumberOfMessages`

This tells you approximately how many messages are waiting in the SQS queue.

For example:

```text
ApproximateNumberOfMessages = 5,000
```

There is a large backlog.

You probably need more EC2 workers.

But there's an even better real-world metric:

> **Backlog per instance**

Because simply knowing "5,000 messages" doesn't tell you how many EC2 instances you need.

For example:

### Situation A

```text
5,000 messages
100 EC2
= 50 messages / instance
```

Maybe that's fine.

### Situation B

```text
5,000 messages
5 EC2
= 1,000 messages / instance
```

Much bigger problem.

That's why AWS recommends thinking about **backlog per instance** for target tracking.

For the exam, however, remember the core idea:

> **SQS queue depth/backlog can drive Auto Scaling.**

---

# ❌ Why the other options?

## 1. ❌ Cluster Placement Group

A cluster placement group puts EC2 instances physically close together to achieve:

> **Very low network latency / high network throughput**

Useful for tightly coupled workloads.

Example:

```text
EC2 ↔ EC2 ↔ EC2
very fast communication
```

But your problem isn't network latency.

Your problem is:

> **Requests are being lost during traffic spikes.**

A placement group doesn't provide a durable queue.

---

# 2. ❌ Larger EC2 + EFA

Larger EC2:

> More compute capacity.

EFA:

> High-performance network interface for tightly coupled HPC workloads.

Neither solves the fundamental problem:

```text
Traffic spike
     ↓
EC2 capacity temporarily insufficient
     ↓
Requests lost
```

SQS gives you a buffer.

---

# 3. ❌ Aurora Serverless

This is another exam trap.

Aurora Serverless scales:

> **The database**

It does NOT scale your EC2 instances.

```text
Aurora Serverless
       ↓
Database scaling
```

Not:

```text
Aurora Serverless
       ↓
EC2 scaling ❌
```

Also, Aurora Parallel Query is for database query processing, which has nothing to do with this request-buffering problem.

---

# 🎯 The SAA Pattern You Should Memorize

Whenever you see:

> **Traffic spikes + requests/messages must not be lost + processing can happen asynchronously**

Think:

# **SQS**

And when you see:

> **SQS + EC2 workers + increasing queue backlog**

Think:

# **CloudWatch + Auto Scaling**

Architecture:

```text
             Producers
                 │
                 ↓
              Amazon SQS
            ┌───────────┐
            │  Messages │
            │  Messages │
            │  Messages │
            └─────┬─────┘
                  │
                  ↓
             EC2 workers
             /    |    \
           EC2   EC2   EC2
                  ↑
                  │
          Auto Scaling Group
                  ↑
             CloudWatch
          Queue backlog metric
```

### One-line memory trick:

**SQS = buffer**

**CloudWatch = monitor**

**ASG = add/remove EC2**

Together:

> **Traffic spike → SQS stores the work → CloudWatch sees backlog → ASG launches workers → workers drain the queue.**

That's the core concept this question wants you to know.
