
10. Question

Category: CSAA – Design High-Performing Architectures

A global company has deployed numerous AWS Outposts servers in various remote locations worldwide. These servers frequently need to download software updates consisting of multiple files from an S3 bucket in the us-west-2 region. The company is experiencing significant delays in distributing these updates across all servers.
What solution would most effectively reduce the deployment latency while minimizing operational overhead?


- Set up an Amazon CloudFront distribution with the us-west-2 S3 bucket as the primary origin and create a secondary origin in another region, implementing a CachingDisabled cache policy. Use signed URLs for downloads.

- Set up AWS Global Accelerator to route traffic from Outposts servers to the nearest AWS edge location, then use private VIF connections to access the S3 bucket in us-west-2.

- `Create an Amazon CloudFront distribution with the us-west-2 S3 bucket as the origin. Use signed URLs for software downloads.`
- Use Amazon S3 Transfer Acceleration on the existing S3 bucket and have the Outposts servers use the Transfer Acceleration endpoint for downloads.

This is a **very useful CloudFront vs S3 Transfer Acceleration question**. The trick is recognizing that the same software files are being downloaded repeatedly by many locations.

# 10. Question — Easy Explanation

The company has:

```text
Outposts worldwide
      ↓
Need software updates
      ↓
S3 bucket in us-west-2
```

The problem is that every Outpost is far away from `us-west-2`, so downloading the same files directly from S3 can take a long time.

For example:

```text
Outpost Pakistan ───────────────→ S3 us-west-2
Outpost Europe  ────────────────→ S3 us-west-2
Outpost Japan   ────────────────→ S3 us-west-2
Outpost Australia ──────────────→ S3 us-west-2
```

The solution is to put **CloudFront in front of S3**.

---

# ✅ Correct Answer

> **Create an Amazon CloudFront distribution with the `us-west-2` S3 bucket as the origin. Use signed URLs for software downloads.**

Think of CloudFront as putting **copies of frequently requested files around the world**.

```text
                         S3
                     us-west-2
                         │
                         │
                  ┌──────▼──────┐
                  │  CloudFront │
                  └──────┬──────┘
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       Edge           Edge           Edge
      Europe          Asia         Australia
          ↓              ↓              ↓
      Outpost         Outpost        Outpost
```

The first time an Outpost requests:

```text
software-v10.zip
```

CloudFront retrieves it from S3 and caches it at an appropriate edge location.

The next Outpost near that edge location can receive the cached file instead of going all the way back to S3.

### That's the key:

> **CloudFront caches content close to users → repeated downloads become faster.**

---

# 🔐 Why Signed URLs?

The software updates might not be public.

You don't want:

```text
Anyone on Internet
       ↓
download software update
```

Instead:

```text
Authorized Outpost
       ↓
Signed URL
       ↓
CloudFront
       ↓
Software update
```

A **signed URL** gives controlled, time-limited access to the CloudFront content.

So the question combines two ideas:

**Performance → CloudFront**

**Private downloads → Signed URLs**

---

# 🧠 Why CloudFront is especially good here

Look at the wording:

> "multiple files"

> "servers worldwide"

> "frequently need to download"

> "reduce deployment latency"

Those are huge clues for **caching**.

CloudFront is designed exactly for this.

```text
Same file requested repeatedly
             ↓
        CloudFront cache
             ↓
     Serve from nearby edge
```

You don't need to manually copy the files to different AWS Regions.

That's also why it has **low operational overhead**.

---

# ❌ Option 1 — CloudFront + secondary origin + CachingDisabled

This is a classic distractor.

CloudFront is useful here **because of caching**.

But the option says:

> `CachingDisabled`

That's basically throwing away one of the biggest benefits we need.

```text
CloudFront
   ↓
Caching disabled ❌
   ↓
Keep going to origin
```

The requirement is to reduce repeated download latency.

So:

> **Don't disable caching when caching is the solution.**

The secondary origin also isn't necessary for this requirement.

---

# ❌ Option 2 — Global Accelerator

This sounds attractive because the question says:

> "global"

and

> "reduce latency"

But don't automatically choose Global Accelerator whenever you see "global + latency."

### Global Accelerator

Think:

> **Accelerate application traffic**

Especially:

* TCP
* UDP
* dynamic applications
* static IP requirements
* regional failover

### CloudFront

Think:

> **Deliver/cache content globally**

Especially:

* images
* videos
* static files
* software downloads
* web content

Here we're repeatedly downloading **files**.

Therefore:

# Files + caching + global users → CloudFront

---

# ❌ Option 4 — S3 Transfer Acceleration

This is the most dangerous distractor because **S3 Transfer Acceleration really can improve long-distance S3 transfers**.

So why isn't it the best answer?

Because the requirement isn't simply:

> "Transfer one large file from far away faster."

The scenario says servers **frequently download multiple files**.

CloudFront can **cache those files at edge locations**.

Transfer Acceleration doesn't provide the same CDN caching model.

Think:

### S3 Transfer Acceleration

```text
Client
   ↓
AWS edge/network
   ↓
S3
```

### CloudFront

```text
Client
   ↓
Nearby CloudFront Edge
   ↓
Cached file
```

For repeatedly requested software packages, caching is extremely valuable.

---

# 🧠 Very Important: CloudFront vs Transfer Acceleration

Remember this table for the exam:

| Requirement                                 | Best choice                      |
| ------------------------------------------- | -------------------------------- |
| Globally distribute static files            | **CloudFront**                   |
| Cache content close to users                | **CloudFront**                   |
| Images/videos/software downloads            | **CloudFront**                   |
| Repeated requests for same objects          | **CloudFront**                   |
| Speed up uploads to S3                      | **S3 Transfer Acceleration**     |
| Speed up long-distance transfers to/from S3 | **S3 Transfer Acceleration**     |
| Private CloudFront content                  | **Signed URLs / Signed Cookies** |

### Simple memory trick:

> **CloudFront = Cache and Deliver**

> **S3 Transfer Acceleration = Transfer faster**

---

# 🎯 Exam shortcut

When you see:

**"Global users + same files repeatedly downloaded + reduce latency"**

Immediately think:

# **CloudFront**

If you additionally see:

**"Only authorized users should download"**

Think:

# **CloudFront + Signed URLs/Signed Cookies**

And if the question says:

**"Upload files to S3 from geographically distant locations faster"**

Think:

# **S3 Transfer Acceleration**

---

## One-line README note

> **Use CloudFront when the same content is frequently accessed by users around the world because CloudFront caches objects at edge locations close to users, reducing latency and origin load. Use signed URLs or signed cookies when access to CloudFront content must be restricted. S3 Transfer Acceleration is instead designed to accelerate transfers to and from S3, particularly over long geographic distances, but does not provide CloudFront-style caching.**

### The mental model

```text
                    PERFORMANCE
                         │
          ┌──────────────┴──────────────┐
          │                             │
     Static content                 S3 transfer
     + repeated access              acceleration
          │                             │
          ↓                             ↓
     CloudFront                  S3 Transfer
        CDN                     Acceleration
          │
          ↓
   Edge caching
          │
          ↓
    Lower latency
```

This is another question where the **words in the scenario are more important than memorizing the service description**.
