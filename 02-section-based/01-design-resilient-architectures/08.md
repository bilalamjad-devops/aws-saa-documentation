
8. Question

Category: CSAA – Design Resilient Architectures
An online registration system hosted in an Amazon EKS cluster stores data to a db.t4g.medium Amazon Aurora DB cluster. The database performs well during regular hours but is unable to handle the traffic surge that occurs during flash sales. A solutions architect must move the database to Aurora Serverless while minimizing downtime and the impact on the operation of the application.

Which change should be taken to meet the objective?

- `Use AWS Database Migration Service (AWS DMS) to migrate to a new Aurora Serverless database.`
- Add an Aurora Replica to the cluster and set its instance class to Serverless. Failover to the read replica and promote it to primary.
- Change the Aurora Instance class to Serverless
- Take a snapshot of the DB cluster. Use the snapshot to create a new Aurora DB cluster.




Yes — this is an important **Aurora migration question**, and the key requirement is:

> **Move from provisioned Aurora → Aurora Serverless while minimizing downtime.**

Let's make it very simple.

# 8. Question — Easy Explanation

Currently:

```text
EKS application
      ↓
Aurora provisioned
db.t4g.medium
      ↓
Normal traffic → Fine
Flash sale → Traffic spike → Database struggles
```

The company wants:

```text
EKS application
      ↓
Aurora Serverless
      ↓
Automatically adjusts capacity
when traffic changes
```

But there is one important requirement:

> **Minimize downtime and application impact.**

So we need a migration method that allows the **old database to keep running while the new database is being populated.**

---

# ✅ Correct answer: AWS DMS

The best solution is:

> **Use AWS Database Migration Service (AWS DMS) to migrate the existing Aurora database to a new Aurora Serverless database.**

Think of DMS like a **moving truck that keeps copying changes while the original house is still being used.**

```text
                 ┌──────────────────────┐
                 │ Existing Aurora      │
                 │ Provisioned          │
                 └──────────┬───────────┘
                            │
                            │ AWS DMS
                            │ continuously
                            │ replicates changes
                            ↓
                 ┌──────────────────────┐
                 │ New Aurora           │
                 │ Serverless           │
                 └──────────────────────┘
```

The existing application can continue working while DMS copies the database.

When the migration is ready, you perform the final cutover.

Therefore:

### **DMS = minimal downtime migration**

---

# Why DMS is perfect here

AWS DMS supports **ongoing replication**.

Imagine:

### 10:00 AM

Old database:

```text
Users = 1,000
```

DMS copies the data to the new Aurora Serverless database.

### 10:05 AM

A customer places an order.

Old database:

```text
Users/orders/data
       ↓
new change
```

DMS also replicates that change to the target.

So the two databases stay synchronized.

```text
Source Aurora
     │
     │ initial data
     ↓
Target Aurora Serverless

Source Aurora
     │
     │ ongoing changes
     ↓
Target Aurora Serverless
```

Eventually the target is caught up.

Then:

```text
Application
     ↓
Aurora Serverless
```

with very little downtime during the final switch.

---

# ❌ Option 2: Add an Aurora Replica with Serverless

> Add an Aurora Replica and set its instance class to Serverless.

This sounds attractive, but the problem is that you **cannot simply change an Aurora replica's instance class from provisioned to Serverless** in this way.

More importantly, this isn't the migration mechanism the question is looking for.

The exam wants you to recognize:

> **Migration + minimal downtime → DMS**

---

# ❌ Option 3: Change the Aurora instance class to Serverless

This is the easiest distractor.

You might think:

> "It's already Aurora. Why don't we just change `db.t4g.medium` to Serverless?"

But you **can't simply convert the existing provisioned Aurora instance into Aurora Serverless by changing its instance class**.

It's not like:

```text
db.t4g.medium
       ↓
change setting
       ↓
Serverless
```

You need a migration approach to move to the new architecture.

---

# ❌ Option 4: Snapshot → New Aurora Cluster

This is also tempting.

You could:

```text
Existing Aurora
      ↓
Snapshot
      ↓
New Aurora cluster
```

But the question specifically says:

> **minimizing downtime and impact on the application**

A snapshot-based approach isn't the best choice for this requirement because the migration/cutover process doesn't provide the same continuous replication capability as DMS.

With DMS:

```text
Old DB ────────────────→ New DB
       continuous sync
```

With snapshot:

```text
Old DB
  ↓
Snapshot
  ↓
New DB
```

DMS is much better when **minimal downtime** is the key requirement.

# 🧠 The big exam concept

This question isn't really testing whether you know every Aurora feature.

It's testing whether you can recognize:

### **Database migration + minimal downtime**

→ **AWS DMS**

Memorize this pattern:

| Requirement                            | Think                                 |
| -------------------------------------- | ------------------------------------- |
| Migrate database with minimal downtime | **AWS DMS**                           |
| Continuously replicate changes         | **AWS DMS ongoing replication**       |
| Convert database engine/schema         | **AWS SCT**                           |
| Automatic Aurora capacity scaling      | **Aurora Serverless**                 |
| Aurora read scaling                    | **Aurora Replicas + Reader Endpoint** |
| Aurora HA/failover                     | **Multi-AZ / Aurora architecture**    |
