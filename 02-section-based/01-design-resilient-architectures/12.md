
12. Question

Category: CSAA – Design Resilient Architectures

A company hosts its web application on a set of Amazon EC2 instances in an Auto Scaling group behind an Application Load Balancer (ALB). The application has an embedded NoSQL database. As the application receives more traffic, the application becomes overloaded mainly due to database requests. The management wants to ensure that the database is eventually consistent and highly available.

Which of the following options can meet the company requirements with the least operational overhead?

- `Configure the Auto Scaling group to spread the EC2 instances across three Availability Zones. Use the AWS Database Migration Service (AWS DMS) with a replication server and an ongoing replication task to migrate the embedded NoSQL database to Amazon DynamoDB.`
- Change the ALB with a Network Load Balancer (NLB) to handle more traffic and integrate AWS Global Accelerator to ensure high availability. Configure replication of the NoSQL database on the set of EC2 instances to spread the database load.
- Configure the Auto Scaling group to spread the EC2 instances across three Availability Zones. Configure replication of the NoSQL database on the set of EC2 instances to spread the database load.
- Change the ALB with a Network Load Balancer (NLB) to handle more traffic. Use the AWS Glue DynamoDB export connector to export data from Amazon DynamoDB to Amazon S3 for analytics periodically, and continue running the application’s NoSQL database on the EC2 instances.

This is a **very important SAA pattern** because the question is really testing: **"Should I keep managing my database myself, or move it to a managed AWS database?"**

# 12. Question — Easy Explanation

The current architecture is:

```text
                    Users
                      ↓
                     ALB
                      ↓
               Auto Scaling Group
                /      |      \
              EC2     EC2      EC2
                \      |      /
                 Embedded
                NoSQL DB
```

The application is getting more traffic.

But the problem is **not mainly the EC2 servers**.

The problem is:

> **The embedded NoSQL database is becoming overloaded.**

Management wants:

1. **Eventually consistent database**
2. **Highly available**
3. **Least operational overhead**

Those three clues should immediately make you think:

# → Amazon DynamoDB

---

# ✅ Correct Answer

> **Configure the Auto Scaling group to spread the EC2 instances across three Availability Zones. Use AWS DMS with a replication server and an ongoing replication task to migrate the embedded NoSQL database to Amazon DynamoDB.**

There are actually **two parts** to this answer.

### Part 1 — EC2 application

Spread the EC2 instances across multiple AZs:

```text
                ALB
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
      AZ-A      AZ-B      AZ-C
       │         │         │
      EC2       EC2       EC2
```

This improves application availability.

### Part 2 — Database

Move the embedded NoSQL database to:

> **Amazon DynamoDB**

```text
EC2 application
      │
      ↓
 Amazon DynamoDB
```

DynamoDB is:

* Managed
* NoSQL
* Highly available
* Automatically scalable
* Designed for high request volumes
* Supports eventually consistent reads
* Low operational overhead

So you don't have to manually manage database servers.

---

# 🧠 Why DynamoDB?

The question gives you several clues:

### "NoSQL"

→ DynamoDB is a NoSQL database.

### "Eventually consistent"

→ DynamoDB supports eventually consistent reads.

### "Highly available"

→ DynamoDB is designed for high availability.

### "Least operational overhead"

→ DynamoDB is fully managed.

This is almost a direct invitation to choose DynamoDB.

---

# 🔥 The BIG Concept: Embedded Database vs Managed Database

This is probably the most important lesson from this question.

The company currently has:

```text
EC2
 └── Application
      └── Embedded NoSQL Database
```

That creates a problem.

Every time you scale your EC2 instances:

```text
EC2-1 → Database
EC2-2 → Database
EC2-3 → Database
```

Now you have to worry about:

* Database replication
* Synchronization
* Failover
* Scaling
* Patching
* Backups
* Recovery
* Data consistency

That's a lot of operational work.

Instead:

```text
                 ┌── EC2
                 ├── EC2
Application ─────┼── EC2
                 └── EC2
                      │
                      ↓
                 DynamoDB
```

AWS manages the database infrastructure.

### SAA rule:

> **If the question emphasizes "least operational overhead," strongly consider a managed AWS service.**

---

# 🔄 Why AWS DMS?

You might ask:

> "Why are we using DMS? Why not just create DynamoDB?"

Because the company already has **existing data** in the embedded database.

They need to migrate it.

AWS Database Migration Service can:

```text
Existing NoSQL database
          ↓
         DMS
          ↓
     DynamoDB
```

And with an **ongoing replication task**, changes can continue to be replicated while the application is still running.

This helps minimize disruption during migration.

Think of DMS as:

> **"Move my existing database/data to another database while keeping the source synchronized."**

---

# ❌ Option 2 — NLB + Global Accelerator + Database Replication

This is overengineering.

The problem is the database.

Changing:

```text
ALB → NLB
```

doesn't solve the embedded database problem.

And manually replicating the NoSQL database across EC2 instances means:

```text
You manage replication
You manage failures
You manage scaling
You manage synchronization
You manage maintenance
```

That's exactly the opposite of:

> **least operational overhead**

Global Accelerator is also unnecessary here because the scenario doesn't require global/regional traffic acceleration.

---

# ❌ Option 3 — Replicate the NoSQL database yourself

This sounds reasonable:

```text
EC2-1 → DB
EC2-2 → DB
EC2-3 → DB
```

But AWS expects you to recognize the operational burden.

You would have to manage the database yourself.

The question explicitly says:

> **least operational overhead**

Therefore:

**Managed DynamoDB > self-managed database on EC2**

---

# ❌ Option 4 — AWS Glue + DynamoDB Export

This one is a trap.

AWS Glue and DynamoDB export are useful for:

```text
DynamoDB
   ↓
Export
   ↓
S3
   ↓
Analytics
```

But the actual application database is **still the embedded NoSQL database on EC2**.

So the original problem remains.

You're solving an analytics problem that the question didn't ask about.

---

# 🎯 Exam Shortcut

When you see:

### Embedded NoSQL database + increasing traffic

Think:

> **Move it to DynamoDB**

When you see:

### Least operational overhead

Think:

> **Managed service**

When you see:

### Existing database needs migration

Think:

> **AWS DMS**

When you see:

### Eventually consistent + NoSQL

Think:

> **DynamoDB**

When you see:

### Application needs high availability

Think:

> **Multiple AZs + managed database**

# 🧠 One thing I want you to remember

Don't get distracted by all the services in the answer choices.

The question is essentially saying:

> **"My EC2 application is growing, but its embedded NoSQL database can't keep up. I want eventual consistency, high availability, and minimal management."**

Translate that in your head:

```text
Embedded NoSQL
       +
High traffic
       +
Highly available
       +
Eventually consistent
       +
Low management
       ↓
   DynamoDB
```

And because the database already exists:

```text
Existing database
       ↓
      DMS
       ↓
   DynamoDB
```

### Final mental model:

**ALB → EC2/ASG across AZs → DynamoDB**

That's the architecture this question wants you to recognize.
