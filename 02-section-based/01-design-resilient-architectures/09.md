9. Question

Category: CSAA – Design Resilient Architectures

A company is setting up a cloud architecture for an international money transfer service to be deployed in AWS which will have thousands of users around the globe. The service should be available 24/7 to avoid any business disruption and should be resilient enough to handle the outage of an entire AWS region. To meet this requirement, the Solutions Architect has deployed their AWS resources to multiple AWS Regions. He needs to use Route 53 and configure it to set all of the resources to be available all the time as much as possible. When a resource becomes unavailable, Route 53 should detect that it’s unhealthy and stop including it when responding to queries.

Which of the following is the most fault-tolerant routing configuration that the Solutions Architect should use in this scenario?

- Configure an Active-Active Failover with One Primary and One Secondary Resource.
- Configure an Active-Passive Failover with Multiple Primary and Secondary Resources.
- Configure an Active-Passive Failover with Weighted Records.
- `Configure an Active-Active Failover with Weighted routing policy.`

This is a **very important Route 53 question** because it tests the difference between **Active-Active vs Active-Passive**. Let's make it very easy.

# 9. Question — Easy Explanation

The company has a money-transfer application used worldwide.

Requirements:

* 🌍 Users are worldwide
* 🟢 Application should be available 24/7
* 🏢 Resources are deployed in **multiple AWS Regions**
* 💥 Even if an **entire Region goes down**, the application should continue working
* 🔍 Route 53 should detect unhealthy resources
* ❌ Route 53 should stop sending traffic to unhealthy resources
* ⭐ They want **all healthy resources working at the same time**

That last point is the key.

---

# ✅ Correct Answer

### **Configure an Active-Active Failover with Weighted routing policy.**

The important concept is:

> **Active-Active = all healthy resources are active and receiving traffic.**

For example:

```text
                  Route 53
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
    Region A      Region B      Region C
    🟢 Healthy    🟢 Healthy    🟢 Healthy
        ↑            ↑            ↑
        └──── All can receive traffic ────┘
```

If Region B fails:

```text
                  Route 53
                     │
        ┌────────────┼────────────┐
        ↓            X            ↓
    Region A      Region B      Region C
    🟢 Healthy    🔴 Failed      🟢 Healthy

                  ↓
        Route 53 removes B
        from DNS responses
```

Users continue reaching Regions A and C.

That is exactly what the question wants.

---

# 🧠 Why "Active-Active"?

Think about the words:

### Active-Active

**Both/all sides are ACTIVE.**

```text
Region A → ACTIVE 🟢
Region B → ACTIVE 🟢
Region C → ACTIVE 🟢
```

Traffic can go to any healthy resource.

If one becomes unhealthy:

```text
Region A → ACTIVE 🟢
Region B → UNHEALTHY 🔴
Region C → ACTIVE 🟢
```

Route 53 stops returning Region B.

---

# What does Weighted Routing mean?

Weighted routing lets Route 53 distribute traffic according to weights.

For example:

```text
Region A → weight 50
Region B → weight 30
Region C → weight 20
```

Approximately:

```text
50% → Region A
30% → Region B
20% → Region C
```

And importantly, you can associate **health checks** with the records.

If Region B becomes unhealthy:

```text
Region A → 🟢
Region B → 🔴
Region C → 🟢
```

Route 53 stops including the unhealthy record.

So:

> **Weighted + Health Checks = Active-Active capability**

---

# ⚠️ Very Important Exam Concept

Don't think:

> "Active-Active is a Route 53 routing policy."

It isn't.

Route 53 has routing policies such as:

* Simple
* Weighted
* Latency-based
* Failover
* Geolocation
* Geoproximity
* Multi-value answer

**Active-Active and Active-Passive describe architectures/configurations**, not separate routing policies.

According to the question's explanation:

### Active-Active

You can achieve it using routing policies such as:

> **Weighted or Latency-based routing + health checks**

### Active-Passive

You use:

> **Failover routing policy**

---

# ❌ Why Active-Passive is wrong

Active-Passive means:

```text
             Route 53
                │
                ↓
        ┌───────────────┐
        │ Primary       │
        │ 🟢 ACTIVE     │
        └───────┬───────┘
                │
          if it fails
                ↓
        ┌───────────────┐
        │ Secondary     │
        │ 🟡 STANDBY    │
        └───────────────┘
```

The secondary resource is basically waiting.

That's **not** what the question wants.

The question says:

> **"all of the resources to be available all the time as much as possible."**

That screams:

# **ACTIVE-ACTIVE**

---

# ❌ Option 1: Active-Active with One Primary and One Secondary

Wrong because **primary/secondary** is the concept of Active-Passive.

Active-Active doesn't have:

```text
Primary
Secondary
```

Instead:

```text
Resource A → active
Resource B → active
Resource C → active
```

---

# ❌ Option 2: Active-Passive with Multiple Primary and Secondary Resources

Still wrong because the requirement is to have **all resources available**, not keep secondary resources waiting.

---

# ❌ Option 3: Active-Passive with Weighted Records

This mixes two different concepts.

**Weighted routing** can be used for Active-Active.

**Failover routing** is used for Active-Passive.

Remember:

```text
Active-Active
      ↓
Weighted / Latency / other routing policies
      +
Health checks

Active-Passive
      ↓
Failover routing
```

---

# 🎯 The most important exam shortcut

When you see:

> **"All resources should be active."**

Think:

### 🟢 Active-Active

When you see:

> **"Primary is active, secondary is standby."**

Think:

### 🟡 Active-Passive

And when you see:

> **"When primary fails, send traffic to secondary."**

Think:

### **Route 53 Failover routing**

---

## One-line README note

> **Active-Active keeps multiple resources active simultaneously; Route 53 health checks remove unhealthy resources from DNS responses. Weighted or latency-based routing can be used to distribute traffic across healthy resources. Active-Passive uses Failover routing, where secondary resources remain on standby until primary resources become unhealthy.**

### 🧠 Exam memory

**All active → Active-Active**

**Primary + standby → Active-Passive**

**Failover routing → Active-Passive**

**Weighted + health checks → Active-Active**

This distinction is worth remembering because AWS SAA questions love to test it.
