21. Question

Category: CSAA – Design Resilient Architectures

Amazon Elastic Kubernetes Service (Amazon EKS) with IAM Role for Service Accounts (IRSA) is used by an e-commerce company to deploy and manage its containerized applications. The website experiences a surge in traffic around the holidays, which significantly adds to the effort. The goal is to ensure that its underlying infrastructure automatically scales in and out in response to demand.

Which of the following would meet the requirements with the LEAST amount of operational overhead? (Select TWO.)

- Use Amazon CloudWatch Alarms to trigger scaling for containerized applications.
- Install the Kubernetes Metrics Server on the EKS cluster and activate Vertical Pod Autoscaler.
- Install the Kubernetes Metrics Server on the EKS cluster and activate the Horizontal Pod Autoscaling.
- Set up Karpenter to automatically adjust the number of nodes in the EKS cluster when pods fail or are rescheduled onto other nodes.
- Enable the Cluster Autoscaler for EKS to automatically manage the number of nodes based on the resource needs of the pods.

## Question 21 — EKS Autoscaling made easy

This question looks complicated because it mentions **EKS, IRSA, Metrics Server, HPA, Karpenter, Cluster Autoscaler**.

But the core idea is actually very simple:

> **Traffic increases → need more Pods → need more EC2 worker nodes if existing nodes don't have enough capacity.**

So there are **two different things that need to scale**.

---

## 1. First understand Pod vs Node

Imagine your EKS cluster:

```text
EKS Cluster
│
├── Node 1 (EC2)
│    ├── Pod
│    ├── Pod
│    └── Pod
│
└── Node 2 (EC2)
     ├── Pod
     └── Pod
```

### Pod

A **Pod** runs your application container.

For example:

```text
E-commerce application
       ↓
     Pods
       ↓
  Containerized app
```

### Node

A **Node** is the machine that runs those Pods.

In the traditional EKS setup:

```text
Node = EC2 worker machine
Pod  = application workload running on that machine
```

---

# 2. Traffic increases

Suppose normally you have:

```text
100 users
   ↓
3 Pods
```

During Black Friday:

```text
10,000 users
      ↓
Need more Pods
      ↓
3 Pods → 10 Pods
```

Something needs to automatically increase the **number of Pods**.

That's where **HPA** comes in.

---

# 3. HPA = scales Pods

**Horizontal Pod Autoscaler (HPA)** means:

> Increase/decrease the **number of Pods**.

For example:

```text
Normal traffic

3 Pods
Pod Pod Pod


High traffic

8 Pods
Pod Pod Pod Pod Pod Pod Pod Pod
```

HPA can look at metrics such as CPU utilization and increase/decrease the number of replicas.

### But how does HPA know CPU usage?

That's where **Metrics Server** comes in.

```text
Metrics Server
      ↓
collects resource metrics
      ↓
HPA
      ↓
increases/decreases Pods
```

So remember:

> **Metrics Server + HPA = Pod scaling**

---

# 4. But here's the problem...

Suppose your EC2 nodes have no more capacity.

```text
Node 1
████████████ 100%

Node 2
████████████ 100%

HPA says:
"I need 5 more Pods!"

But...

❌ There isn't enough room.
```

Now we need to increase the number of **Nodes**.

That's where **Karpenter** comes in.

---

# 5. Karpenter = scales Nodes

Karpenter watches the Pods that cannot be scheduled because there isn't enough capacity.

It can provision appropriate EC2 capacity.

Think:

```text
Traffic increases
       ↓
HPA creates more Pods
       ↓
Not enough node capacity
       ↓
Karpenter
       ↓
Launches additional EC2 capacity
       ↓
New Pods get scheduled
```

So:

> **HPA → Pods**

> **Karpenter → Nodes/compute capacity**

---

# 6. This is why the answer has TWO components

The question says:

> "underlying infrastructure automatically scales in and out in response to demand."

We need both application scaling and infrastructure scaling.

### ✅ Correct #1

**Install Kubernetes Metrics Server and activate Horizontal Pod Autoscaling.**

Why?

```text
Metrics Server
      ↓
HPA
      ↓
Pods scale out/in
```

### ✅ Correct #2

**Set up Karpenter to automatically adjust the number of nodes.**

Why?

```text
Pods need more capacity
        ↓
Karpenter
        ↓
More EC2 compute capacity
```

Together:

```text
             Traffic
                ↓
              HPA
                ↓
        More / fewer Pods
                ↓
      Need more Node capacity?
                ↓
           Karpenter
                ↓
       More / fewer Nodes
```

That's the architecture you should remember.

---

# The important autoscaling distinction

This is **extremely important for SAA**:

| Technology             | What does it scale?        |
| ---------------------- | -------------------------- |
| **HPA**                | Pods                       |
| **Karpenter**          | Nodes / compute capacity   |
| **Cluster Autoscaler** | Nodes                      |
| **VPA**                | Pod resources (CPU/memory) |

### HPA

**Horizontal = more Pods**

```text
3 Pods → 10 Pods
```

### VPA

**Vertical = bigger Pods**

```text
Pod:
1 CPU → 2 CPU
512 MB → 2 GB
```

So when the question says:

> **"scale in and out"**

Think **horizontal**, not vertical.

---

# Karpenter vs Cluster Autoscaler

This question specifically prefers **Karpenter**.

Both can help with node scaling:

### Cluster Autoscaler

```text
Need more capacity
      ↓
Adjust node groups / ASGs
      ↓
More nodes
```

### Karpenter

```text
Need more capacity
      ↓
Karpenter evaluates workload requirements
      ↓
Provision appropriate EC2 capacity
```

Karpenter is generally more flexible because it can dynamically select suitable compute capacity rather than being tied to predefined node groups in the same way.

For **this particular question**, remember:

> **HPA + Karpenter**

---

# 🧠 Exam memory trick

Think of a restaurant:

```text
Customers increase
       ↓
Need more waiters
       ↓
HPA → more Pods

But restaurant needs more tables
       ↓
Karpenter → more Nodes
```

Or even simpler:

> **HPA = more workers**

> **Karpenter = more buildings to put workers in**

---

### One-line SAA rule

**EKS application needs to scale → HPA**

**EKS infrastructure/nodes need to scale → Karpenter or Cluster Autoscaler**

**Need to change the size of individual Pods → VPA**

For this question:

**HPA + Karpenter = ✅**
