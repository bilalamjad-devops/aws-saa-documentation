11. Question

Category: CSAA – Design Resilient Architectures

A start-up company has an EC2 instance that is hosting a web application. The volume of users is expected to grow in the coming months and hence, you need to add more elasticity and scalability in your AWS architecture to cope with the demand.

Which of the following options can satisfy the above requirement for the given scenario? (Select TWO.)

- `Set up two EC2 instances and use Route 53 to route traffic based on a Weighted Routing Policy.`
- `Set up two EC2 instances and then put them behind an Elastic Load balancer (ELB).`
- Set up two EC2 instances deployed using Launch Templates and integrated with AWS Glue.
- Set up an S3 Cache in front of the EC2 instance.
- Set up an AWS WAF behind your EC2 Instance.

Yes. This one is testing a **very important distinction: scalability/elasticity vs security vs routing**. Let's make it simple.

# 11. Question — Easy Explanation

The startup currently has:

```text
Internet
   ↓
EC2
   ↓
Web Application
```

Users are expected to increase.

So the problem is:

> **One EC2 instance may not be enough when traffic increases.**

We want to add more EC2 instances and distribute users between them.

For example:

```text
                    Users
                      │
              ┌───────┴───────┐
              ↓               ↓
            EC2-1           EC2-2
             🟢               🟢
```

Now the workload is distributed instead of being handled by one server.

---

# ✅ Correct Answers

### 1. Set up two EC2 instances and use Route 53 to route traffic based on a Weighted Routing Policy.

### 2. Set up two EC2 instances and then put them behind an Elastic Load Balancer (ELB).

Both can distribute traffic between multiple EC2 instances.

---

# 🥇 Answer 1: EC2 + Route 53 Weighted Routing

Route 53 is a **DNS service**.

With weighted routing, you can tell Route 53 approximately how much traffic should go to each resource.

For example:

```text
              Route 53
                  │
          Weighted Routing
             /          \
            /            \
         50%              50%
          ↓                ↓
       EC2-1             EC2-2
```

So instead of everyone going to one EC2:

```text
100% → EC2-1 ❌
```

you can distribute traffic:

```text
50% → EC2-1
50% → EC2-2
```

This gives you additional capacity.

---

# 🥈 Answer 2: EC2 + Elastic Load Balancer

This is the **more common architecture** for a web application.

```text
                    Users
                      │
                      ↓
              ┌──────────────┐
              │     ALB      │
              │ Load Balancer│
              └──────┬───────┘
                     │
             ┌───────┴───────┐
             ↓               ↓
          EC2-1            EC2-2
```

The Load Balancer receives requests and distributes them between the EC2 instances.

If EC2-1 becomes unhealthy:

```text
                    ALB
                     │
             ┌───────┴───────┐
             ↓               X
          EC2-1            EC2-2
          healthy          unhealthy
```

The load balancer can stop sending traffic to the unhealthy instance.

---

# 🧠 Elasticity vs Scalability

This is worth understanding because the question specifically says:

> "elasticity and scalability"

### Scalability

Ability to handle **more workload by adding capacity**.

Example:

```text
2 EC2 → 4 EC2
```

### Elasticity

Ability to **automatically increase or decrease capacity based on demand**.

Example:

```text
Normal traffic:
2 EC2

High traffic:
5 EC2

Traffic decreases:
2 EC2
```

The options in this question don't actually give you a complete **Auto Scaling Group**, but they are testing the idea of distributing traffic across multiple instances.

In a real production architecture, you'd usually go further:

```text
             Users
                ↓
              ALB
                ↓
         Auto Scaling Group
          /      |      \
       EC2      EC2      EC2
```

The **ALB distributes traffic**, while the **ASG automatically adjusts the number of EC2 instances**.

That's a very important architecture to remember.

---

# ❌ Why the other answers are wrong

## ❌ EC2 + Launch Template + AWS Glue

A Launch Template is useful for defining how EC2 instances should be launched.

But:

> **AWS Glue has nothing to do with EC2 scalability.**

Glue is an **ETL/data integration service**.

Think:

```text
AWS Glue
   ↓
ETL / Data Processing / Analytics
```

Not:

```text
AWS Glue
   ↓
EC2 scaling ❌
```

---

## ❌ S3 Cache

There is no general architecture called:

> "S3 Cache in front of EC2"

S3 is object storage.

It doesn't make your EC2 fleet scalable.

For caching web content, you would think about:

> **CloudFront**

For application/database caching, you might think about:

> **ElastiCache**

---

## ❌ AWS WAF

WAF is about **security**.

```text
AWS WAF
   ↓
Block malicious requests
SQL injection
XSS
Rate limiting
etc.
```

It doesn't add EC2 capacity.

So:

> **WAF = security**

not:

> **WAF = scalability**

---

# ⚠️ Important: Route 53 vs Load Balancer

You should understand why both options can distribute traffic, but they aren't the same.

### Route 53 Weighted Routing

Works at the **DNS level**:

```text
User
 ↓
Route 53
 ↓
EC2
```

It decides which DNS record/resource the user gets.

### Load Balancer

Works at the **application/network traffic level**:

```text
User
 ↓
ALB
 ↓
EC2
```

The ALB receives the actual request and distributes it among healthy targets.

For a normal web application, **ALB + ASG** is generally the architecture you'd prefer.

# 🎯 Exam Shortcut

When you see:

### "Distribute traffic across multiple EC2 instances"

Think:

> **Load Balancer**

### "Automatically increase/decrease EC2 capacity"

Think:

> **Auto Scaling Group**

### "Distribute DNS traffic according to percentages"

Think:

> **Route 53 Weighted Routing**

### "Protect web application from malicious requests"

Think:

> **AWS WAF**

### "Cache static content globally"

Think:

> **CloudFront**

### "Cache application/database data"

Think:

> **ElastiCache**

# 🧠 One important correction to your mental model

The question's answer says these two options satisfy the requirement, but **don't memorize "two EC2 + Route 53 = elasticity."**

A stronger real-world mental model is:

```text
                    Internet
                       │
                       ↓
                      ALB
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
          EC2-1                EC2-2
             ↑                   ↑
             └──── Auto Scaling ─┘
```

**ALB → distributes traffic**

**ASG → adds/removes EC2 instances**

Together they provide the scalability/elasticity you normally want for a growing web application.

And remember:

> **Route 53 Weighted Routing can distribute traffic between resources, but it is not a replacement for an Auto Scaling Group.**
