2. Question

Category: CSAA – Design Resilient Architectures

A tech startup is launching an on-demand food delivery platform using an Amazon ECS cluster with an AWS Fargate serverless compute engine and Amazon Aurora. It is expected that the database read queries will significantly increase in the coming weeks. A Solutions Architect recently launched two Read Replicas to the database cluster to improve the platform’s scalability. The team considered using lazy loading to cache results, but that does not balance read traffic across replicas.

Which of the following is the MOST suitable configuration that the Architect should implement to load balance all of the incoming read requests equally to the two Read Replicas?

- Create a new Network Load Balancer to evenly distribute the read queries to the Read Replicas of the Aurora database.
- `Use the built-in Reader endpoint of the Aurora database.`
- Use the built-in Cluster endpoint of the Aurora database.
- Enable Aurora Parallel Query.


Yes — this is another question where the **AWS terminology makes it look harder than it really is**. Let's reduce it to one simple idea.

## First: What is the question actually asking?

The startup has:

```text
ECS / Fargate
      ↓
   Aurora
      ↓
 ┌────┴────┐
 ↓         ↓
Replica 1  Replica 2
```

The database is getting lots of **read requests**, such as:

```sql
SELECT * FROM orders;
SELECT * FROM restaurants;
SELECT * FROM customers;
```

They have already created **2 Aurora Read Replicas**.

The problem is:

> **How do we automatically distribute the read requests across both replicas?**

We don't want:

```text
All reads
   ↓
Replica 1  ← overloaded
Replica 2  ← almost unused
```

We want:

```text
          Read requests
                ↓
        Aurora Reader Endpoint
             /        \
            ↓          ↓
       Replica 1   Replica 2
```

### ✅ Answer: **Use the built-in Reader endpoint of Aurora.**

---

# What is an Aurora Read Replica?

A Read Replica is basically a database instance whose main job is:

> **Handle read traffic.**

So if your application is doing lots of:

```sql
SELECT ...
```

you can have:

```text
             Aurora
                |
        ┌───────┴───────┐
        ↓               ↓
   Read Replica 1   Read Replica 2
```

This improves **read scalability**.

---

# Now the important part: Aurora endpoints

Aurora gives you different **endpoints**.

Think of an endpoint as a **door into the Aurora cluster**.

You don't have to tell your application:

> "Send this request to Replica 1, this one to Replica 2..."

Aurora provides an endpoint that handles this.

There are two especially important endpoints for the exam:

### 1. Writer / Cluster endpoint

Think:

> **"Take me to the primary/writer."**

```text
Application
     ↓
Cluster endpoint
     ↓
Primary DB
```

Used for **writes**.

---

### 2. Reader endpoint

Think:

> **"I want to read. Give me one of the Read Replicas."**

```text
Application
     ↓
Reader endpoint
     ↓
 ┌───┴────┐
 ↓        ↓
R1       R2
```

Aurora automatically distributes connections among the available Aurora Replicas.

That's exactly what this question is asking for.

---

# 🧠 Very important distinction

Remember this:

| Aurora component            | Main purpose                 |
| --------------------------- | ---------------------------- |
| **Writer/Cluster endpoint** | Write traffic → Primary      |
| **Reader endpoint**         | Read traffic → Read Replicas |
| **Read Replica**            | Handles read-only workload   |

So when the question says:

> "Load balance incoming **read requests** across Read Replicas"

Immediately think:

### **Reader Endpoint → Read Replicas**

---

# Why the other answers are wrong

### ❌ Aurora Parallel Query

Don't confuse **parallel query** with **load balancing**.

Parallel Query means:

> "Make ONE complicated query use more processing power."

It is roughly:

```text
ONE big query
      ↓
Aurora Parallel Query
      ↓
Multiple CPUs / storage layer
```

It does **not** mean:

```text
Many queries
     ↓
Replica 1
Replica 2
```

That's the job of the **Reader Endpoint**.

---

### ❌ Network Load Balancer

This sounds tempting because the question says **"load balance."**

But don't fall for the word.

An NLB is a load balancer for network traffic going to supported targets. You don't put an NLB in front of Aurora Read Replicas to solve normal Aurora read distribution.

Aurora already provides the appropriate mechanism:

> **Reader endpoint**

So don't build another load-balancing layer when Aurora already has one.

---

### ❌ Cluster endpoint

This is the opposite direction.

Think:

```text
Cluster/Writer endpoint
          ↓
       Primary
          ↓
       WRITE
```

Whereas:

```text
Reader endpoint
          ↓
   Aurora Replicas
          ↓
        READ
```

---

# The exam shortcut 🎯

Whenever you see:

> **Aurora + Read Replicas + distribute/load balance read requests**

Answer:

### ✅ Reader endpoint

Whenever you see:

> **Aurora + write requests**

Think:

### ✅ Writer/Cluster endpoint

And don't confuse:

> **Parallel Query = improving processing of a query**

with:

> **Reader Endpoint = distributing read connections across replicas**

---

## One-line memory trick

> **READ → READER endpoint → READ REPLICAS**

That's the entire question.
