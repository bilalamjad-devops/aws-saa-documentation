19. Question

Category: CSAA – Design High-Performing Architectures

An application is hosted in an Auto Scaling group of EC2 instances. To improve the monitoring process, you have to configure the current capacity to increase or decrease based on a set of scaling adjustments. This should be done by specifying the scaling metrics and threshold values for the CloudWatch alarms that trigger the scaling process.

Which of the following is the most suitable type of scaling policy that you should use?

- Scheduled Scaling
- `Step scaling`
- Target tracking scaling
- Simple scaling

Absolutely. This is an important SAA topic because AWS gives you several scaling policies, and the exam often tries to confuse **Step Scaling vs Target Tracking vs Simple vs Scheduled**.

## First: What is scaling?

Suppose your application currently has:

```text
EC2 Auto Scaling Group
        ↓
   2 instances
```

Traffic increases:

```text
2 instances → 5 instances
```

Traffic decreases:

```text
5 instances → 2 instances
```

The question is: **When and how should AWS change the number of EC2 instances?**

That's where scaling policies come in.

---

# 1. Target Tracking Scaling 🎯

Think:

> **"Keep this metric around this target."**

Example:

```text
Target CPU = 50%

CPU 70% → add instances
CPU 30% → remove instances
```

You don't tell AWS exactly how many instances to add at each threshold.

You simply say:

> "AWS, keep CPU around 50%."

AWS handles the scaling.

### Example

```text
ASG
Desired: 4 instances

CPU → 50% target

        ↓

AWS automatically adjusts capacity
        ↓
3 / 4 / 5 / 6 instances...
```

### Exam keyword

**"Maintain target"**

Examples:

* Keep CPU utilization at 50%
* Maintain average request count per instance
* Keep a metric around a target value

➡️ **Target Tracking**

---

# 2. Step Scaling 📈

This is the one in your question.

Think:

> **"The bigger the alarm breach, the bigger the scaling action."**

You define different steps.

For example:

```text
CPU < 40%       → remove 1 instance

CPU 40–60%      → do nothing

CPU 60–70%      → add 1 instance

CPU 70–80%      → add 2 instances

CPU > 80%       → add 4 instances
```

So:

```text
Small problem → small adjustment
Big problem   → big adjustment
```

That's **Step Scaling**.

### Your question

It says:

> "specifying the scaling metrics and threshold values for the CloudWatch alarms"

and

> "set of scaling adjustments"

That is the giveaway.

➡️ **Step Scaling**

---

# 3. Simple Scaling

Think:

> **"One alarm → one fixed scaling action."**

Example:

```text
CPU > 70%
     ↓
Add 2 instances
```

That's it.

You don't have multiple steps.

```text
CPU > 70% → +2
```

Compare:

**Simple:**

```text
CPU > 70% → +2
```

**Step:**

```text
CPU 60–70% → +1
CPU 70–80% → +2
CPU >80%   → +4
```

So if the question says:

> **single scaling adjustment**

➡️ Simple Scaling.

If it says:

> **multiple/set of scaling adjustments depending on breach**

➡️ Step Scaling.

---

# 4. Scheduled Scaling 🕐

This one doesn't primarily react to CloudWatch metrics.

You know the traffic pattern **in advance**.

For example, an e-commerce website gets huge traffic every day from:

```text
9 AM → traffic starts increasing
6 PM → traffic peaks
11 PM → traffic decreases
```

You can tell AWS:

```text
08:00 → minimum 5 instances
18:00 → minimum 10 instances
23:00 → minimum 3 instances
```

That's:

➡️ **Scheduled Scaling**

### Exam keyword

> **Predictable traffic / known schedule / specific time**

---

# The easiest way to remember all 4

| Scaling type          | Think                  | Example                          |
| --------------------- | ---------------------- | -------------------------------- |
| **Target Tracking**   | 🎯 Keep a target       | CPU ≈ 50%                        |
| **Step Scaling**      | 📊 Different steps     | CPU 70% +2, CPU 80% +4           |
| **Simple Scaling**    | ➕ One fixed adjustment | CPU >70% → +2                    |
| **Scheduled Scaling** | 🕐 Known time          | Every day at 6 PM → 10 instances |

---

# Very important SAA distinction

### Target Tracking

You say:

> **"Keep CPU at 50%."**

AWS decides **how much** to scale.

```text
CPU target = 50%
       ↓
AWS manages capacity
```

### Step Scaling

You say:

> **"If CPU breaches this much, make this specific adjustment."**

```text
CPU 60% → +1
CPU 70% → +2
CPU 80% → +4
```

You define the steps.

---

## 🧠 Exam cheat sheet

When you see:

**"target value"**

→ 🎯 **Target Tracking**

**"set of scaling adjustments"**

→ 📊 **Step Scaling**

**"single scaling adjustment"**

→ ➕ **Simple Scaling**

**"predictable traffic at specific times"**

→ 🕐 **Scheduled Scaling**

And one more important SAA idea:

> **Target Tracking is generally the preferred choice when you're trying to maintain a proportional utilization metric, such as CPU utilization, around a target.**

So don't automatically choose Step Scaling just because CloudWatch alarms are mentioned. Look for the **actual scaling behavior** described in the question.
