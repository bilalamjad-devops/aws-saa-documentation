18. Question

Category: CSAA – Design High-Performing Architectures

A popular social media website uses a Amazon CloudFront web distribution to serve static content to millions of users around the globe. Recently, the website has received a number of complaints about long login times. Additionally, there are instances where users encounter HTTP 504 errors. The manager has instructed the team to significantly reduce login time and further optimize the system.

Which of the following options should be used together to set up a cost-effective solution that improves the application’s performance? (Select TWO.)

- `Implement an origin failover by creating an origin group that includes two origins. Assign one as the primary origin and the other as secondary, which enables CloudFront to automatically switch to if the primary origin encounters specific HTTP status code failure responses.`
- Configure your origin to add a Cache-Control max-age directive to your objects, and specify the longest practical value for max-age to increase the cache hit ratio of your CloudFront distribution.
- `Customize the content that the CloudFront web distribution delivers to your users using Lambda@Edge, which allows your AWS Lambda functions to execute the authentication process in AWS locations closer to the users.`
- Deploy your application to multiple AWS regions to accommodate your users around the world. Set up a Route 53 record with latency routing policy to route incoming traffic to the region that provides the best latency to the user.
- Establish multiple Amazon VPCs in different AWS regions and configure a transit VPC to interconnect all of your resources. To handle the requests faster, set up AWS Lambda functions in each region with the AWS Serverless Application Model (SAM) service.

This question is testing **CloudFront optimization + resilience**, and there are two concepts you should separate.

## 1. Lambda@Edge → reduce login/authentication latency

Normally:

```text
User in Pakistan
      ↓
CloudFront Edge
      ↓
Origin in another region
      ↓
Authentication
```

The farther the authentication logic is from the user, the more latency can be introduced.

With **Lambda@Edge**:

```text
User
 ↓
Nearest CloudFront Edge
 ↓
Lambda@Edge
 ↓
Authentication logic
```

Lambda@Edge runs Lambda functions at AWS locations closer to CloudFront users.

So the keyword is:

> **Global users + authentication/customization close to users → Lambda@Edge**

---

## 2. CloudFront Origin Failover → deal with 504 errors

The question also says users sometimes receive:

> **HTTP 504**

You can configure:

```text
                 CloudFront
                     ↓
             Origin Group
              /          \
             ↓            ↓
       Primary Origin   Secondary
             │
          failure
             ↓
        automatically
        use secondary
```

So if the primary origin encounters certain configured failure responses, CloudFront can switch to the secondary origin.

This improves **availability/resilience**.

---

# Why not `Cache-Control max-age`?

This is a good trap.

`Cache-Control max-age` helps CloudFront keep objects cached longer:

```text
User → CloudFront Cache → Content
```

It can improve cache hit ratio.

But the problem specifically says:

> **long login times**

The bottleneck is authentication, not simply serving static content.

So:

**Caching static content ≠ fixing authentication latency.**

---

# Why not Multi-Region + Route 53?

This could improve latency:

```text
User Pakistan → Region A
User USA      → Region B
User Europe   → Region C
```

But now you have to deploy and maintain your application in multiple Regions.

The question specifically asks for a **cost-effective** solution.

So the exam prefers the lighter solution:

> **Lambda@Edge + CloudFront Origin Failover**

---

## 🧠 Exam pattern

Remember these three:

| Requirement                              | Think                                       |
| ---------------------------------------- | ------------------------------------------- |
| Execute logic closer to CloudFront users | **Lambda@Edge**                             |
| Serve cached content faster              | **CloudFront caching / Cache-Control**      |
| Origin failure / 504 resilience          | **CloudFront Origin Failover**              |
| Global application deployment            | **Multi-Region + Route 53 latency routing** |

### One subtle point

Don't think **Lambda@Edge is simply "Lambda in another region."**

It's specifically designed to execute functions in association with **CloudFront events at edge locations**, such as viewer request/response and origin request/response.

That's why it is particularly useful when the requirement says **"execute logic closer to global users."**
