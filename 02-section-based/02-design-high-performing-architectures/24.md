24. Question

Category: CSAA – Design High-Performing Architectures

A company has a cryptocurrency exchange portal that is hosted in an Auto Scaling group of EC2 instances behind an Application Load Balancer and is deployed across multiple AWS regions. The users can be found all around the globe, but the majority are from Japan and Sweden. Because of the compliance requirements in these two locations, you want the Japanese users to connect to the servers in the ap-northeast-1 Asia Pacific (Tokyo) region, while the Swedish users should be connected to the servers in the eu-west-1 EU (Ireland) region.

Which of the following services would allow you to easily fulfill this requirement?

- `Use Route 53 Geolocation Routing policy.`
- Use Route 53 Weighted Routing policy.
- Set up a new CloudFront web distribution with the geo-restriction feature enabled.
- Set up an Application Load Balancers that will automatically route the traffic to the proper AWS region.

Exactly — this question is testing **Route 53 routing policies**, especially **Geolocation vs Weighted**.

### The requirement

You have the same application in multiple AWS Regions:

```text
                    Users
                 /        \
            Japan          Sweden
              │               │
              ▼               ▼
       ap-northeast-1     eu-west-1
           Tokyo             Ireland
```

Requirement:

* 🇯🇵 Japan users → **Tokyo**
* 🇸🇪 Sweden users → **Ireland**

The keyword is **user geographic location**.

Therefore:

> ✅ **Route 53 Geolocation Routing**

---

## 1. Geolocation Routing = "Where is the user?"

Think:

> **Geo = Geography**

You tell Route 53:

```text
Japan  → Tokyo
Sweden → Ireland
Europe → Ireland
Asia   → Tokyo
```

It routes based on the **location from which the DNS query originates**.

### Exam shortcut

**"Users from different countries/continents should go to specific resources"**

→ **Geolocation**

---

## 2. Weighted Routing = "How much traffic?"

Weighted routing is completely different.

For example:

```text
Application
   │
   ├── Region A → 80%
   │
   └── Region B → 20%
```

This is useful for things like:

* 90/10 traffic split
* A/B testing
* Gradual migration
* Canary deployment

It does **not** mean:

> Japan → Tokyo, Sweden → Ireland

So:

**Country/location → Geolocation**

**Percentage → Weighted**

---

## 3. Geolocation vs Geoproximity

This is another distinction worth knowing for SAA.

### Geolocation

> "Users from Japan should go to Tokyo."

Based on **geographic location**.

### Geoproximity

> "Route users to resources based on geographic distance, and optionally bias the traffic toward one location."

So don't confuse them.

---

## 4. CloudFront Geo-restriction

This is another exam trap.

CloudFront geo-restriction answers:

> **"Who is allowed to access my content?"**

For example:

```text
Allow:
USA
Canada

Block:
Country X
Country Y
```

It is about **restricting access**, not selecting which AWS Region should serve a user.

So:

| Requirement                           | Service/policy                 |
| ------------------------------------- | ------------------------------ |
| Japan → Tokyo                         | **Route 53 Geolocation**       |
| 80% → Region A, 20% → Region B        | **Route 53 Weighted**          |
| Block users from certain countries    | **CloudFront Geo-restriction** |
| Route based on geographic distance    | **Route 53 Geoproximity**      |
| Route based on endpoint health        | **Route 53 Failover**          |
| Route based on lowest network latency | **Route 53 Latency-based**     |

### 🧠 SAA shortcut

Remember these questions:

**"Where are they?"** → Geolocation
**"How much traffic?"** → Weighted
**"Which endpoint is fastest?"** → Latency
**"Is the endpoint healthy?"** → Failover
**"How far away?"** → Geoproximity
**"Can this country access my content?"** → CloudFront Geo-restriction

For Q24, **"Japan users → Tokyo, Sweden users → Ireland" = Geolocation.**
