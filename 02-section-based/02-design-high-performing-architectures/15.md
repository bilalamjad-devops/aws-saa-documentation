15. Question

Category: CSAA – Design High-Performing Architectures

A game development company operates several virtual reality (VR) and augmented reality (AR) games that use various RESTful web APIs hosted in its on-premises data center, which currently sits behind a content delivery network (CDN) for faster global delivery. Due to the unprecedented growth of the company, the management decided to migrate its system to AWS Cloud to scale out its resources as well as to minimize costs.

Which of the following is the most cost-effective and scalable solution to meet the above requirement?

- `Use AWS Lambda and Amazon API Gateway.`
- Set up a micro-service architecture with Amazon ECS, Amazon ECR, and AWS Fargate.
- Host the APIs in a static Amazon S3 web hosting bucket behind a Amazon CloudFront web distribution.
- Use a Spot Fleet of Amazon EC2 instances, each with an Elastic Fabric Adapter (EFA) for more consistent latency and higher network throughput. Set up an Application Load Balancer to distribute traffic to the instances.

Yes. This question is mainly testing **serverless architecture**. And it connects directly to what we just discussed.

## The key idea

The application has:

* REST APIs
* unpredictable/growing global traffic
* wants scalability
* wants low cost
* doesn't want to keep servers running unnecessarily

So:

> **API Gateway + Lambda** ✅

Think:

```text
Users
  ↓
API Gateway
  ↓
Lambda
  ↓
Your application logic
```

### Why this is powerful

With traditional EC2:

```text
Users
  ↓
ALB
  ↓
EC2
EC2
EC2
```

You have servers running even when traffic is low.

With Lambda:

```text
Users
  ↓
API Gateway
  ↓
Lambda
```

AWS automatically runs more Lambda executions when requests increase.

```text
Low traffic:
   → Lambda
   → Lambda

High traffic:
   → Lambda Lambda Lambda Lambda Lambda...
```

You don't provision EC2 instances.

---

## Connect this to what you just learned

You now have three different ways to run applications:

### 1. ECS

```text
Docker containers
       ↓
      ECS
```

Use when you want to run/manage **containers** using AWS ECS.

### 2. EKS

```text
Containers
    ↓
Kubernetes
    ↓
   EKS
```

Use when you specifically need **Kubernetes**.

### 3. Lambda

```text
Code
 ↓
Lambda
```

Use when you want **serverless, event/API-driven compute** and don't want to manage servers or containers.

---

# Why not ECS + Fargate?

This is the interesting option.

ECS + Fargate **can absolutely be scalable**.

So don't memorize:

> "ECS/Fargate is not scalable."

That's not correct.

The better exam reasoning is:

> **Lambda + API Gateway provides the required API compute with less operational overhead and a pay-per-use model.**

If the application doesn't require containers or long-running processes, **Lambda is often the simpler choice**.

---

# Why not S3 + CloudFront?

This is another important SAA distinction.

S3 can host:

```text
HTML
CSS
JavaScript
Images
```

But S3 doesn't execute your backend API code.

So:

```text
Static website
→ S3 + CloudFront ✅
```

But:

```text
REST API / dynamic backend
→ S3 ❌
```

For REST APIs:

```text
API Gateway + Lambda ✅
```

---

# 🧠 Memorize this pattern

For your SAA exam:

> **REST API + serverless + no server management + unpredictable traffic → API Gateway + Lambda**

And:

> **Static website → S3 + CloudFront**

> **Docker containers → ECS**

> **Kubernetes → EKS**

> **Containers without managing servers → Fargate**

This is exactly how you should be studying these questions: **don't memorize the answer; identify the architecture pattern from the keywords.**
