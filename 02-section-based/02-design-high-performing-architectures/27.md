27. Question

Category: CSAA – Design High-Performing Architectures

A solutions architect is designing an infrastructure for a serverless application. The application is packaged as a Docker image stored in Amazon Elastic Container Registry (Amazon ECR) and must be deployed on a fully managed serverless compute service. Additionally, the application requires 5 GB of ephemeral storage for temporary data processing.

Which deployment option meets these requirements?

- Deploy the application Amazon ECS cluster with Amazon EC2 worker nodes and attach a 5 GB Amazon EBS volume.
- Deploy the application to an Amazon ECS cluster that uses AWS Fargate tasks.
- `Deploy the application in an AWS Lambda function with Container image support. Set the function’s storage to 5 GB.`
- Deploy the application in an AWS Lambda function with Container image support. Attach an Amazon Elastic File System (Amazon EFS) volume to the function.

Yes — **Q27 is testing a very useful distinction: Lambda container images vs ECS/Fargate.**

### First, identify the 3 clues

The question says:

1. Application is a **Docker image** in ECR
2. Must run on **fully managed serverless compute**
3. Needs **5 GB temporary/ephemeral storage**

That leads to:

> ✅ **Lambda + Container Image + 5 GB ephemeral storage**

---

### Why Lambda?

Lambda normally runs your function code, but it can also run a **Docker container image**.

```text
Docker Image
     │
     ▼
Amazon ECR
     │
     ▼
AWS Lambda
     │
     └── /tmp → up to 10 GB ephemeral storage
```

The important exam fact here is:

> **Lambda ephemeral storage = 512 MB by default, configurable up to 10 GB.**

So **5 GB** fits perfectly.

---

### What about EFS?

This is the important distinction:

**Ephemeral storage**

> Temporary → Lambda `/tmp`

**Persistent/shared storage**

> EFS

For example:

```text
Lambda
  │
  ├── /tmp → temporary data
  │
  └── EFS → persistent/shared files
```

So if the question says:

> "temporary processing data, 5 GB"

→ **Lambda ephemeral storage**

If it says:

> "persistent files shared across Lambda invocations"

→ **EFS**

---

### One correction to the explanation you pasted

The TutorialsDojo explanation says:

> ECS with Fargate is not a fully serverless solution.

That's a bit misleading.

**Fargate absolutely is serverless compute for containers** because you don't manage EC2 servers.

The better distinction is:

|                   | Lambda                           | ECS + Fargate                        |
| ----------------- | -------------------------------- | ------------------------------------ |
| Server management | None                             | None                                 |
| Container support | ✅ Container images               | ✅ Native                             |
| Best for          | Functions/event-driven workloads | Long-running/containerized workloads |
| Control           | Less                             | More                                 |
| Ephemeral storage | `/tmp`                           | Task ephemeral storage               |
| Orchestration     | Lambda manages execution         | ECS manages tasks/services           |

So don't memorize **"Fargate isn't serverless."**

Instead remember:

> **Lambda = serverless functions**
> **Fargate = serverless container compute**

And because this particular question specifically gives **5 GB ephemeral Lambda storage**, Lambda is the intended answer.

### 🧠 Your growing storage cheat sheet

You have now seen enough questions that I'd memorize this:

**S3** → objects
**EBS** → block storage for EC2
**EFS** → shared Linux/NFS filesystem
**FSx Windows** → Windows/SMB/AD
**FSx Lustre** → HPC/ML/high-performance parallel filesystem
**FSx ONTAP** → enterprise file + block/iSCSI
**Lambda `/tmp`** → temporary ephemeral storage

That's much more useful for SAA than memorizing isolated service definitions.
