23. Question

Category: CSAA – Design High-Performing Architectures

An Auto Scaling group (ASG) of Amazon EC2 Linux instances has an Amazon FSx for OpenZFS file system with basic monitoring enabled in Amazon CloudWatch. The Solutions Architect noticed that the legacy web application hosted in the ASG takes a long time to load. After checking the instances, the Architect noticed that the ASG is not launching more instances as it should be, even though the servers already have high memory usage.

Which of the following options should the Architect implement to solve this issue?

- `Install the CloudWatch unified agent to the EC2 instances. Set up a custom parameter in AWS Systems Manager Parameter Store with the CloudWatch agent configuration to create an aggregated metric on memory usage percentage. Scale the Auto Scaling group based on the aggregated metric.`
- Set up Amazon Rekognition to automatically identify and recognize the cause of the high memory usage. Use the AWS Well-Architected Tool to automatically trigger the scale-out event in the ASG based on the overall memory usage.
- Implement an AI solution that leverages Amazon Comprehend to track the near-real-time memory usage of each and every EC2 instance. Use Amazon SageMaker AI to automatically trigger the Auto Scaling event if there is high memory usage.
- Enable detailed monitoring on the EC2 instances of the Auto Scaling group. Use Auto Scaling with custom metrics to scale out the Auto Scaling group based on the aggregated memory usage of EC2 instances.

Yes. This question is basically testing **CloudWatch Agent + custom metrics + Auto Scaling**. It's closely related to Question 3 you just did.

## The core problem

The EC2 instances have:

> **High memory usage**

But the ASG isn't scaling out.

Why?

Because **EC2's standard CloudWatch metrics don't include memory utilization by default**.

Think:

```text
EC2
 │
 ├── CPU Utilization        ✅ CloudWatch default
 ├── Network                ✅ CloudWatch default
 ├── Disk read/write        ✅ CloudWatch default
 │
 └── Memory Utilization     ❌ Not default
```

So AWS doesn't know:

> "Hey, these servers are using 90% RAM. Launch another instance."

---

## Solution

Install the **CloudWatch Agent** on the EC2 instances.

```text
EC2 instances
     │
     │ CloudWatch Agent
     ▼
CloudWatch
     │
     │ MemoryUtilization
     ▼
CloudWatch Alarm
     │
     │ e.g. Memory > 80%
     ▼
Auto Scaling Group
     │
     ▼
Launch more EC2 instances
```

The CloudWatch Agent collects system-level metrics such as:

* Memory utilization
* Disk space utilization
* Swap utilization
* Processes
* Logs

Then you can use the custom memory metric for an ASG scaling policy.

### Important distinction

**Detailed Monitoring ≠ CloudWatch Agent**

This is an important SAA trap.

Detailed monitoring gives you **more frequent standard EC2 metrics**.

It does **not magically add memory utilization**.

So:

> "Enable detailed monitoring to get memory utilization"

❌ Wrong.

Instead:

> **Install CloudWatch Agent to collect memory utilization.**

---

## What is Systems Manager Parameter Store doing here?

The answer mentions:

> CloudWatch Agent configuration → Systems Manager Parameter Store

Don't let this distract you.

**Parameter Store is basically a place to centrally store configuration values.**

For example:

```text
Parameter Store
     │
     └── /prod/cloudwatch-agent-config
                  │
                  ▼
          CloudWatch Agent
                  │
                  ▼
          Memory metrics
```

It's useful for distributing/maintaining the agent configuration, but **the key concept being tested is CloudWatch Agent**.

# ⭐ Your SAA memory rule

When you see:

### "EC2 memory utilization"

Immediately think:

> **CloudWatch Agent → Custom Metric**

When you see:

### "ASG should scale based on memory"

Think:

> **CloudWatch Agent → Memory Metric → CloudWatch Alarm → ASG**

And when you see:

### "CPU utilization"

That's already available as a standard EC2 CloudWatch metric.

---

### One small thing about the question

The question's wording about an **"aggregated metric"** is a little more advanced. If you want the ASG to scale based on the **overall memory usage across instances**, you need a metric design that represents the group appropriately, rather than blindly using one instance's memory.

But for the exam, the fundamental pattern is:

**Memory isn't a default EC2 metric → install CloudWatch Agent → publish memory as a custom metric → use it for scaling.**
