
17. Question

Category: CSAA – Design Secure Architectures

A web application is hosted on an EC2 instance that processes sensitive financial information. The EC2 instance is launched in a private subnet, and all data is stored in an Amazon S3 bucket. Users access financial information over the Internet through pre-signed URLs generated by the web application. The company’s security team is concerned that internet connectivity to Amazon S3 poses a security risk.

In this scenario, what will you do to resolve this security vulnerability in the most cost-effective manner?

- Change the web architecture to access the financial data hosted in your S3 bucket by creating a custom VPC endpoint service.
- Change the web architecture to access the financial data in your S3 bucket through a VPN connection.
- `Change the web architecture to access the financial data through a Gateway VPC Endpoint.`
- Change the web architecture to access the financial data in S3 through an interface VPC endpoint, which is powered by AWS PrivateLink.

Yes bro — **you already know the concept, but there are two different things here: CloudFront Signed URLs and S3 Pre-Signed URLs.** This question is about **S3 pre-signed URLs**.

Let's first understand what the question is actually asking.

## 1. What is the architecture?

Currently:

```text
Internet
   │
   │ User requests financial file
   ▼
EC2 (Private Subnet)
   │
   │ S3 request
   ▼
Amazon S3
```

The web application generates an **S3 pre-signed URL** for the user.

A pre-signed URL basically says:

> "Here is a temporary URL that gives you permission to access this particular S3 object."

For example, conceptually:

```text
https://bucket.s3.amazonaws.com/report.pdf
   ?X-Amz-Algorithm=...
   &X-Amz-Expires=600
   &X-Amz-Signature=...
```

The user can use that URL temporarily without having AWS credentials.

---

# 2. What is the security team's concern?

The EC2 instance is private, but the S3 traffic is currently going through the **public path**.

The question says:

> Security team is concerned that internet connectivity to S3 poses a security risk.

They want:

```text
EC2 ───────► S3
```

without needing to go through the Internet.

And they specifically ask:

> **most cost-effective**

That's the big clue.

---

# 3. Answer: Gateway VPC Endpoint

For **Amazon S3**, use:

### ✅ Gateway VPC Endpoint

Architecture becomes:

```text
             AWS Network
                │
EC2            │
Private Subnet │
   │            │
   │            │
   ▼            │
Gateway VPC Endpoint
   │
   ▼
  S3
```

The traffic doesn't need:

❌ Internet Gateway
❌ NAT Gateway
❌ VPN
❌ Public IP

And importantly:

### Gateway Endpoint for S3 has no hourly/data-processing endpoint charge.

So it is the **most cost-effective** answer.

---

# 4. Gateway Endpoint vs Interface Endpoint

This is extremely important for SAA.

|                               | Gateway Endpoint       | Interface Endpoint |
| ----------------------------- | ---------------------- | ------------------ |
| Uses                          | **S3, DynamoDB**       | Many AWS services  |
| Technology                    | Route table target     | Private ENI        |
| Private connectivity          | ✅                      | ✅                  |
| Hourly endpoint charge        | **No**                 | Yes                |
| Data processing charge        | **No endpoint charge** | Yes                |
| Best for S3 when cost matters | ⭐ **Yes**              | Usually no         |

So when you see:

> **S3 + private connectivity + cost-effective**

your brain should immediately say:

### 🧠 S3 → Gateway VPC Endpoint

---

# 5. Now your question: "I knew signed URL, and this is pre-signed URL?"

Yes. But be careful because AWS has **two similar-sounding concepts**.

### S3 Pre-Signed URL

Used to temporarily give access to an **S3 object**.

```text
Application
     │
     │ generates
     ▼
S3 Pre-Signed URL
     │
     ▼
User → S3 object
```

Example use:

> "Allow this customer to download `invoice.pdf` for the next 10 minutes."

---

### CloudFront Signed URL

Used to control access to content being delivered **through CloudFront**.

```text
User
 │
 │ CloudFront Signed URL
 ▼
CloudFront
 │
 ▼
S3
```

Example:

> "Only paying customers can access this video through CloudFront."

---

## 🔥 Remember this distinction

### S3 Pre-Signed URL

**S3 directly**

> Temporary permission to access an S3 object.

### CloudFront Signed URL

**CloudFront**

> Control access to content delivered through CloudFront.

### CloudFront Signed Cookies

**CloudFront + multiple files**

> Give a user access to multiple private files **without changing URLs**.

---

# 6. One more important point

The **pre-signed URL is not the vulnerability** in this question.

The company is happy with the way users receive temporary access.

The concern is **how the EC2 application reaches S3**.

So we're changing:

```text
EC2 → Internet → S3
```

to:

```text
EC2 → Gateway VPC Endpoint → S3
```

The pre-signed URL concept can remain.

---

### 🧠 SAA exam shortcut

If you see:

> **EC2 private subnet → S3 → no Internet → cheapest**

Think:

**Gateway VPC Endpoint.**

If you see:

> **Private connectivity to an AWS service using a private ENI**

Think:

**Interface VPC Endpoint / PrivateLink.**

And if you see:

> **S3 + DynamoDB**

Think:

**Gateway Endpoint.**
