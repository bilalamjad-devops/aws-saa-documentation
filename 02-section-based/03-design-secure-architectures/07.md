7. Question

Category: CSAA – Design Secure Architectures

An On-Demand EC2 instance is launched into a VPC subnet with the Network ACL configured to allow all inbound traffic and deny all outbound traffic. The instance’s security group has an inbound rule to allow SSH from any IP address and does not have any outbound rules.

In this scenario, what are the changes needed to allow SSH connection to the instance?

- The outbound security group needs to be modified to allow outbound traffic.
- No action needed. It can already be accessed from any IP address using SSH.
- `The network ACL needs to be modified to allow outbound traffic.`
- Both the outbound security group and outbound network ACL need to be modified to allow outbound traffic.

Yes — this question is **mainly testing Stateful vs Stateless**, which is extremely important for SAA.

## First, understand the situation

You have:

```text
Your PC
   │
   │ SSH
   ↓
Internet
   │
   ↓
┌─────────────────────────┐
│        AWS VPC          │
│                         │
│   Network ACL           │
│   Inbound:  ALLOW       │
│   Outbound: DENY ❌     │
│          │              │
│          ↓              │
│   Security Group        │
│   Inbound SSH: ALLOW ✅ │
│   Outbound: NONE        │
│          │              │
│          ↓              │
│       EC2               │
└─────────────────────────┘
```

The question asks:

> **What needs to change so your computer can SSH into the EC2?**

---

# 🔑 The most important concept

There are two firewalls here:

### Security Group = STATEFUL

### Network ACL = STATELESS

Think of them differently.

---

## 1. Security Group = Stateful

Suppose your PC sends:

```text
PC ───── SSH request ─────> EC2
```

The Security Group says:

```text
Inbound SSH → ALLOW ✅
```

The EC2 sends the response:

```text
EC2 ───── SSH response ─────> PC
```

You **do NOT need an outbound SG rule** for that response.

Why?

Because Security Groups are **stateful**.

> If SG allows the incoming connection, the response traffic is automatically allowed.

So:

```text
SG:
Inbound SSH     ✅
Outbound        ❌/none

Result: Still works from SG perspective
```

---

# 2. Network ACL = Stateless

This is where the problem occurs.

The NACL says:

```text
Inbound → ALLOW ✅
Outbound → DENY ❌
```

Your SSH request comes in:

```text
PC ────────> EC2
       NACL
       ALLOW ✅
```

EC2 tries to respond:

```text
EC2 ────────> PC
       NACL
       DENY ❌
```

The SSH connection cannot be established properly.

Why?

Because NACLs are **stateless**.

They don't remember:

> "Hey, I already allowed this connection."

Every direction is evaluated independently.

Therefore you need:

```text
NACL

Inbound SSH     → ALLOW
Outbound        → ALLOW
```

---

# 🎯 Therefore, what is the answer?

The technically important answer is:

> **Modify the Network ACL to allow outbound traffic.**

The Security Group doesn't need an outbound rule specifically for the SSH response because it is **stateful**.

So the mental model is:

```text
                 Security Group
                 STATEFUL
                 ┌──────────────┐
SSH request ────>│ Inbound ALLOW │
SSH response <───│ Automatically │
                 │    allowed    │
                 └──────────────┘


                 Network ACL
                 STATELESS
                 ┌──────────────┐
SSH request ────>│ Inbound ALLOW │
SSH response <───│ Outbound must │
                 │ be ALLOWED    │
                 └──────────────┘
```

### 🧠 Exam rule

Memorize this:

> **Security Group → Stateful → allow inbound, response automatically allowed.**

> **NACL → Stateless → explicitly allow both inbound AND outbound.**

---

### One small nuance

The question's wording says the NACL **denies all outbound traffic**. In a real NACL configuration, you'd normally allow the appropriate return traffic rather than simply "allow everything outbound." But for the exam's simplified choices, the key answer is **modify the NACL outbound rules**.

This **SG vs NACL stateful/stateless** distinction is one of the things you should know extremely well for the Secure Architectures section.
