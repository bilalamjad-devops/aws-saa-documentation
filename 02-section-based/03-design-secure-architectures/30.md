30. Question

Category: CSAA – Design Secure Architectures

A tech company that you are working for has undertaken a Total Cost Of Ownership (TCO) analysis evaluating the use of Amazon S3 versus acquiring more storage hardware. The result was that all 1200 employees would be granted access to use Amazon S3 for the storage of their personal documents.

Which of the following will you need to consider so you can set up a solution that incorporates a single sign-on feature from your corporate AD or LDAP directory and also restricts access for each individual user to a designated user folder in an S3 bucket? (Select TWO.)

- `Set up a Federation proxy or an Identity provider, and use AWS Security Token Service to generate temporary tokens.`
- Use 3rd party Single Sign-On solutions such as Atlassian Crowd, OKTA, OneLogin and many others.
- `Configure an IAM role and an IAM Policy to access the bucket.`
- Set up a matching IAM user for each of the 1200 users in your corporate directory that needs access to a folder in the S3 bucket.
- Map each individual user to a designated user folder in S3 using Amazon WorkDocs to access their personal documents.

Yes bro. This question is mainly testing **Enterprise Federation + STS temporary credentials + IAM Roles**, and there is one extra requirement: **each employee should only access their own S3 folder**.

Let's simplify it.

# 1. What is the question actually asking?

Imagine the company has **1,200 employees**.

They already have:

```text
Corporate AD / LDAP
       │
       ├── Bilal
       ├── Ahmed
       ├── Ali
       ├── Sara
       └── ... 1,200 users
```

They don't want to create 1,200 separate AWS IAM users.

Instead, they want employees to use their **existing corporate username/password**.

That's the **Single Sign-On (SSO)** requirement.

Then they want an S3 bucket like:

```text
company-documents/
│
├── bilal/
│    ├── resume.pdf
│    └── notes.docx
│
├── ahmed/
│    ├── report.pdf
│    └── photo.jpg
│
├── ali/
│    └── document.pdf
│
└── sara/
     └── report.docx
```

And:

> Bilal should only access `bilal/`, Ahmed only `ahmed/`, etc.

So there are **two separate requirements**:

### Requirement 1 — Authentication

Use existing:

> **Corporate AD/LDAP**

instead of creating AWS IAM users.

### Requirement 2 — Authorization

Give each person access only to their own S3 folder.

---

# 2. How do we achieve SSO?

This is where **Federation** comes in.

The basic flow is:

```text
Employee
   │
   │ Corporate username/password
   ↓
Corporate AD / Identity Provider
   │
   │ Authentication
   ↓
Federation / STS
   │
   │ Temporary credentials
   ↓
AWS
   │
   ↓
S3
```

The employee doesn't need an IAM user.

Instead, AWS gives them **temporary credentials**.

---

# 3. What is AWS STS?

Remember this:

> **STS = Security Token Service**

Its job is to provide **temporary AWS credentials**.

Instead of giving someone permanent:

```text
Access Key
Secret Key
```

you can give them temporary credentials:

```text
Temporary Access Key
Temporary Secret Key
Session Token
Expiration
```

For example:

```text
Employee logs in
      ↓
AD authenticates employee
      ↓
AWS STS
      ↓
Temporary credentials
      ↓
S3
```

This is much better for federated users.

---

# 4. Why IAM Role?

The second correct answer is:

> **Configure an IAM role and an IAM policy to access the bucket.**

Think of an IAM Role as:

> **A permission package that a user can temporarily assume.**

For example:

```text
IAM Role
   │
   └── Policy
         │
         └── Allow access to S3
```

The role determines:

> **What can this federated user do?**

The identity provider determines:

> **Who is this user?**

STS provides:

> **Temporary credentials to use those permissions.**

---

# 5. But how does Bilal get only the Bilal folder?

This is the slightly more advanced part.

You can use IAM policies with the user's identity information to restrict access to a particular S3 prefix.

Conceptually:

```text
Bilal
  ↓
Federated login
  ↓
Temporary credentials
  ↓
IAM permissions
  ↓
company-bucket/bilal/*
```

While:

```text
Ahmed
  ↓
Federated login
  ↓
Temporary credentials
  ↓
IAM permissions
  ↓
company-bucket/ahmed/*
```

So you don't need:

```text
1,200 IAM Users ❌
```

You can use:

```text
Corporate identities
       ↓
Federation
       ↓
STS temporary credentials
       ↓
IAM Role
       ↓
S3 user-specific access
```

---

# 6. Why not create 1,200 IAM users?

This is a classic exam trap.

The option says:

> Set up a matching IAM user for each of the 1200 users.

❌ Wrong.

Why?

Because the requirement specifically says:

> **Single sign-on from corporate AD/LDAP.**

If you create:

```text
AD User → IAM User
AD User → IAM User
AD User → IAM User
...
```

you've created a second identity system.

That's exactly what federation is designed to avoid.

---

# 7. Why isn't a third-party SSO provider required?

The option mentions:

> Okta, OneLogin, Atlassian Crowd...

These can certainly be used in real-world environments.

But the question asks what you need to implement this requirement.

You don't **have to** introduce another third-party SSO solution.

AWS supports federation using standards such as:

> **SAML 2.0**

and services such as:

> **AWS STS**

So this option isn't the best answer.

---

# 8. Where does AD FS fit?

You asked about this in the previous question.

A common AWS architecture is:

```text
Corporate AD
     ↓
   AD FS
     ↓
 SAML 2.0
     ↓
   AWS STS
     ↓
 IAM Role
     ↓
    S3
```

AD FS acts as the **Identity Provider (IdP)**.

It says:

> "I have authenticated this employee. This is Bilal, and here are the claims/attributes associated with him."

AWS trusts that identity provider.

Then AWS can issue temporary credentials through STS.

---

# 9. The two answers

### ✅ Answer 1

> **Set up a Federation proxy or an Identity Provider, and use AWS STS to generate temporary tokens.**

Because you need:

**Corporate AD/LDAP → AWS SSO**

---

### ✅ Answer 2

> **Configure an IAM role and an IAM policy to access the bucket.**

Because after authentication you need to determine:

> **What is this employee allowed to access?**

---

# 🧠 Memorize this architecture

For these SAA questions, remember:

```text
                 AUTHENTICATION
                      ↓
             Corporate AD / LDAP
                      ↓
               IdP / AD FS
                      ↓
                  SAML 2.0
                      ↓
                 AWS STS
                      ↓
              Temporary Credentials
                      ↓
                  IAM ROLE
                      ↓
                IAM POLICY
                      ↓
                     S3
                      ↓
            User's own folder
```

### The keywords are:

| Question keyword             | Think                                            |
| ---------------------------- | ------------------------------------------------ |
| Existing corporate AD        | Federation                                       |
| SSO                          | Federation                                       |
| SAML 2.0                     | AD FS / IdP                                      |
| Temporary credentials        | **STS**                                          |
| Permissions                  | **IAM Role + Policy**                            |
| Don't create IAM users       | Federation                                       |
| 1,200 employees              | Definitely don't manually create 1,200 IAM users |
| Each user gets own S3 folder | IAM policy / S3 prefix restriction               |

### 🔥 One-line memory trick

> **AD tells AWS WHO you are → STS gives temporary credentials → IAM Role tells you WHAT you can do → S3 policy restricts WHERE you can go.**

This question is essentially the same **federation concept** as Question 20, but Q30 adds the **S3 per-user folder restriction** on top.
