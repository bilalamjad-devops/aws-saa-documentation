
10. Question

Category: CSAA – Design Secure Architectures

A company has clients all across the globe that access product files stored in several Amazon S3 buckets, which are behind each of the respective Amazon CloudFront web distributions. The company currently wants to deliver content to a specific client, ensuring that only that client can access the data. At present, all clients can access the S3 buckets directly using an S3 URL or through the CloudFront distribution. The Solutions Architect must serve the private content via CloudFront only, to secure the distribution of files.

Which combination of actions should the Architect implement to meet the above requirements? (Select TWO.)

- Create a custom CloudFront function to check and ensure that only their clients can access the files.
- Generate an S3 presigned URL to ensure that only the client can access the files. Remove permission to use S3 URLs to read the files for anyone else.
- `Restrict access to files in the origin by creating an origin access control (OAC) and giving it permission to read the files in the bucket.`
- Enable the Origin Shield feature of the CloudFront distribution to protect the files from unauthorized access.
- `Require the users to access the private content by using special CloudFront signed URLs or signed cookies.`

Yes bro — this question is really testing **two layers of security for private S3 content behind CloudFront**.

## First: What is the question asking?

Currently, clients can access files in **two ways**:

```text
                 ┌── S3 URL ───────────────► S3
Client ──────────┤
                 └── CloudFront URL ────────► CloudFront ──► S3
```

The company wants to change this to:

```text
Client
   │
   │ ONLY CloudFront
   ▼
CloudFront
   │
   │ authorized access
   ▼
S3
```

And specifically:

> **Only the intended client should be able to access the private content.**

So there are actually **two separate problems**:

### Problem 1 — Stop people bypassing CloudFront

Someone shouldn't be able to say:

> "I'll just use the S3 URL directly."

That's what **Origin Access Control (OAC)** solves.

### Problem 2 — Stop unauthorized people using CloudFront

Even if they must use CloudFront, you still need to determine:

> "Is this client allowed to access this private content?"

That's what **CloudFront Signed URLs / Signed Cookies** solve.

Therefore:

> ✅ **OAC + Signed URLs/Signed Cookies**

---

# 1. OAC = Protect the S3 origin

Think of OAC as:

> **"S3, only trust CloudFront."**

Without OAC:

```text
Attacker ─────────────► S3 URL
                         ✅ potentially accessible
```

With OAC properly configured:

```text
Attacker ─────────────► S3 URL
                         ❌ denied

CloudFront ───────────► S3
                         ✅ allowed
```

OAC gives CloudFront permission to retrieve objects from the S3 bucket, while you remove direct public access.

So the first answer is:

> ✅ **Restrict access to files in the origin by creating an Origin Access Control (OAC) and giving it permission to read the files in the bucket.**

### Easy memory:

**OAC = CloudFront → S3 protection**

---

# 2. Signed URL / Signed Cookie = Protect the viewer

Now suppose the client uses CloudFront:

```text
Client ──► CloudFront ──► S3
```

How does CloudFront know whether this client is authorized?

Use:

* **Signed URL**
* **Signed Cookie**

These contain authorization information that CloudFront validates.

Think:

```text
Authorized client
       │
       │ Signed URL/Cookie
       ▼
   CloudFront
       │
       │ valid?
       ▼
      S3
```

If the signature is invalid or expired:

```text
Client ──► CloudFront
             │
             └── ❌ Access denied
```

So the second answer is:

> ✅ **Require users to access private content using CloudFront signed URLs or signed cookies.**

---

# 3. Signed URL vs Signed Cookie

This connects directly to your **Question 1** from earlier.

### Signed URL

Best when you want access to **individual files**.

Example:

```text
CloudFront/file1.pdf?signature=...
```

You give the user authorization for that particular resource.

Think:

> **Signed URL = individual file**

---

### Signed Cookie

Best when the user needs access to **multiple files**.

For example, a subscriber logs in and should be able to access:

```text
video1.mp4
video1-part1.ts
video1-part2.ts
video1-part3.ts
thumbnail.jpg
subtitle.vtt
```

Instead of generating a signed URL for every file, use a signed cookie.

Think:

> **Signed Cookie = multiple files**

And remember Question 1:

> **"Don't change current URLs" + "multiple private files" → Signed Cookies**

---

# 4. Why not S3 Presigned URL?

This is an important distinction.

### S3 presigned URL

This is essentially:

> "Here's temporary permission to access this specific S3 object."

Example:

```text
Client ──► Presigned S3 URL ──► S3
```

But the question specifically says:

> **"The Architect must serve the private content via CloudFront only."**

So we want:

```text
Client ──► CloudFront ──► S3
```

not:

```text
Client ──► S3
```

Therefore, **CloudFront signed URL/cookie + OAC** is the intended architecture.

---

# 5. Why not CloudFront Function?

CloudFront Functions are useful for things like lightweight request manipulation:

```text
Viewer request
      ↓
CloudFront Function
      ↓
modify/check request
```

But the question is specifically testing the established CloudFront private-content mechanisms:

**OAC + Signed URL/Cookie.**

Don't think:

> "CloudFront Function = security mechanism for private S3 objects."

---

# 6. Why not Origin Shield?

This one is easy.

**Origin Shield is about improving origin performance**, not controlling who is authorized to download your private content.

Think:

| Service/Feature          | Main purpose                                    |
| ------------------------ | ----------------------------------------------- |
| **OAC**                  | Protect S3 origin from direct access            |
| **Signed URL**           | Authorize access to individual CloudFront files |
| **Signed Cookie**        | Authorize access to multiple CloudFront files   |
| **Origin Shield**        | Improve caching/origin performance              |
| **CloudFront Functions** | Lightweight request/response customization      |

---

# 🧠 The architecture to remember

This is the important picture for the exam:

```text
                    ┌───────────────┐
                    │ Authorized    │
                    │ Client        │
                    └───────┬───────┘
                            │
                  Signed URL / Cookie
                            │
                            ▼
                    ┌───────────────┐
                    │  CloudFront   │
                    └───────┬───────┘
                            │
                       OAC authentication
                            │
                            ▼
                    ┌───────────────┐
                    │      S3       │
                    │ Private       │
                    │ Bucket        │
                    └───────────────┘
```

### Remember it as:

> **Signed URL/Cookie protects the VIEWER side.**
> **OAC protects the S3 ORIGIN side.**

That's the key idea behind this question.
