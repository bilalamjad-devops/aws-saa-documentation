26. Question

Category: CSAA – Design Secure Architectures

A Solutions Architect is unable to connect to the newly deployed EC2 instance via SSH using a home computer. However, the Architect was able to successfully access other existing instances in the VPC without any issues.

Which of the following should the Architect check and possibly correct to restore connectivity?

- Use Amazon Data Lifecycle Manager.
- Configure the Security Group of the EC2 instance to permit ingress traffic over port 3389 from your IP.
- `Configure the Security Group of the EC2 instance to permit ingress traffic over port 22 from your IP.`
- Configure the Network Access Control List of your VPC to permit ingress traffic over port 22 from your IP.


Exactly bro. **Question 26 is very similar to Question 25**, but the clue is slightly different.

## What is the question asking?

You have:

```text
Home computer
     ↓ SSH
   EC2 #1 ❌
```

You cannot SSH into the **new EC2 instance**.

But:

```text
Home computer
     ↓ SSH
   EC2 #2 ✅
   EC2 #3 ✅
```

You can already connect to other EC2 instances **in the same VPC**.

The question asks:

> **What should you check to fix SSH connectivity to this particular new EC2 instance?**

### ✅ Correct answer

> **Configure the Security Group of the EC2 instance to permit ingress traffic over port 22 from your IP.**

---

## Why Security Group?

SSH uses:

```text
SSH → TCP → Port 22
```

So the new EC2's Security Group needs something like:

```text
Inbound Rule

Type: SSH
Protocol: TCP
Port: 22
Source: YOUR-IP/32
```

For example:

```text
203.0.113.50/32
```

means:

> Only this specific IP address can SSH.

---

# 🔥 Why does the question tell us other instances work?

This is the **big clue**.

Suppose:

```text
Same VPC
│
├── EC2-A → SSH ✅
├── EC2-B → SSH ✅
└── EC2-C → SSH ❌
```

If the VPC's general networking were broken, you'd expect the other instances to have problems too.

Therefore, focus on something **specific to EC2-C**.

And the Security Group is attached to the individual EC2 instance.

So:

> **New instance → check its Security Group.**

---

## Why not Network ACL?

A Network ACL applies at the **subnet level**, not to one particular EC2 instance.

Imagine:

```text
Subnet
│
├── EC2-A ✅
├── EC2-B ✅
└── EC2-C ❌
```

If you changed the NACL, you'd potentially affect **all three instances** in that subnet.

The question specifically says the other instances work.

Therefore, **Security Group is the more appropriate place to investigate first.**

---

## Why port 3389?

❌ 3389 is **RDP**.

RDP is normally used for:

> Windows remote desktop.

SSH uses:

> **TCP 22**

So memorize:

| Protocol | Common port | Used for               |
| -------- | ----------: | ---------------------- |
| SSH      |      **22** | Linux remote access    |
| HTTP     |      **80** | Web                    |
| HTTPS    |     **443** | Secure web             |
| RDP      |    **3389** | Windows remote desktop |
| FTP      |   **20/21** | File transfer          |

---

# Question 25 vs Question 26

These two are worth connecting in your head.

### Q25

> SSH works, website doesn't.

Think:

**HTTP port 80 missing from Security Group.**

```text
SSH 22 ✅
HTTP 80 ❌
```

### Q26

> New EC2 can't SSH, but other EC2s can.

Think:

**New EC2's Security Group → check SSH port 22.**

```text
Old EC2 → SSH 22 ✅
New EC2 → SSH 22 ❌
             ↑
       check Security Group
```

### 🧠 SAA rule

> **Security Group = instance/resource-level firewall**

> **NACL = subnet-level firewall**

So if **one EC2 has a problem while others in the same network work**, strongly suspect its **Security Group** first.
