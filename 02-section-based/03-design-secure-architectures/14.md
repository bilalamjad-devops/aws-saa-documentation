14. Question

Category: CSAA – Design Secure Architectures

A company is designing a banking portal that uses Amazon ElastiCache for Redis as its distributed session management component. To secure session data and ensure that Cloud Engineers must authenticate before executing Redis commands, specifically MULTI EXEC commands, the system should enforce strong authentication by requiring users to enter a password. Additionally, access should be managed with long-lived credentials while supporting robust security practices.

Which of the following actions should be taken to meet the above requirement?


- Set up a Redis replication group and enable the AtRestEncryptionEnabled parameter.
- Enable the in-transit encryption for Redis replication groups.
- Generate an IAM authentication token using AWS credentials and provide this token as a password.
- `Authenticate the users using Redis AUTH by creating a new Redis Cluster with both the --transit-encryption-enabled and --auth-token parameters enabled.`

Yes bro. This question is mainly testing **Redis authentication vs encryption**. The wording is unnecessarily complicated.

## 1. First understand the scenario

The company has:

```text
Banking Portal
      │
      ▼
ElastiCache for Redis
      │
      └── Stores user session data
```

Redis is being used as a **session store**.

For example, when you log in:

```text
User logs in
   ↓
Application creates session
   ↓
Session stored in Redis
   ↓
Redis: session_id → user information
```

The company now has a security requirement:

> **Before a Cloud Engineer can execute Redis commands, they must authenticate with a password.**

The question specifically mentions `MULTI EXEC`, but don't let that distract you.

The key requirement is:

> **"Require a password before Redis commands can be executed."**

That points directly to **Redis AUTH**.

---

# 2. What is Redis AUTH?

Redis supports an authentication mechanism called **AUTH**.

Think of it like logging into Redis:

```text
Cloud Engineer
      │
      │ password
      ▼
   Redis AUTH
      │
      ▼
Authenticated ✅
      │
      ▼
Can execute Redis commands
```

Without authentication:

```text
Engineer
   │
   │ MULTI / EXEC
   ▼
Redis
   ❌ Access denied
```

With authentication:

```text
Engineer
   │
   │ AUTH password
   ▼
Redis
   ✅ Authenticated
   │
   ▼
MULTI / EXEC
```

That's what the question wants.

---

# 3. How do we enable Redis AUTH in ElastiCache?

The important parameter is:

```text
--auth-token
```

You create the Redis cluster/replication group with an authentication token:

```text
--auth-token "YourPassword"
```

Then users must authenticate using that password.

The answer also includes:

```text
--transit-encryption-enabled
```

So the correct option is:

> **Authenticate users using Redis AUTH by creating a new Redis Cluster with both `--transit-encryption-enabled` and `--auth-token` enabled.** ✅

---

# 4. Why does it also mention transit encryption?

This is another concept you should separate in your head.

There are **two different security problems**:

### Authentication

**Who are you?**

```text
AUTH password
      ↓
"Prove who you are"
```

### Encryption in transit

**Can someone read the data while it travels?**

```text
Application
     │
     │ 🔒 encrypted
     ▼
Redis
```

So:

| Feature            | Protects                                 |
| ------------------ | ---------------------------------------- |
| Redis AUTH         | **Who can execute Redis commands**       |
| Transit encryption | **Data moving between client and Redis** |
| At-rest encryption | **Data stored in Redis**                 |

The question's primary requirement is **authentication**, so `AUTH` is the critical part.

---

# 5. Why the other answers are wrong

### ❌ Enable in-transit encryption

This:

```text
--transit-encryption-enabled
```

protects communication:

```text
Client 🔒──── Redis
```

But it doesn't by itself mean:

> "You must provide a password before executing Redis commands."

So it isn't enough.

---

### ❌ Enable `AtRestEncryptionEnabled`

This protects data **while stored**.

Think:

```text
Redis memory/storage
      🔒
   session data
```

But it doesn't authenticate the engineer.

Therefore:

**At-rest encryption ≠ authentication**

---

### ❌ IAM authentication token

This is the tricky distractor.

AWS IAM authentication can be used with some ElastiCache authentication scenarios, but the question specifically requires **long-lived credentials** and Redis command authentication.

IAM authentication tokens are temporary and expire, so they don't fit this requirement.

Also remember:

> **IAM authentication and Redis AUTH are different mechanisms.**

---

# 🧠 The exam shortcut

When you see:

> **"Require users to enter a password before executing Redis commands."**

Immediately think:

### **Redis AUTH → `--auth-token`**

And if the question also mentions protecting communication:

### **Redis AUTH + TLS/in-transit encryption**

So memorize:

```text
Redis Security
│
├── AUTH → Authentication/password
│
├── Transit Encryption → Data moving 🔒
│
└── At-Rest Encryption → Stored data 🔒
```

### For this question:

**Requirement:** Password before Redis commands
**Answer:** ✅ **Redis AUTH + `--auth-token`**

The `MULTI EXEC` wording is mostly there to make the question look more complicated. The real clue is **"authenticate before executing Redis commands"**.
