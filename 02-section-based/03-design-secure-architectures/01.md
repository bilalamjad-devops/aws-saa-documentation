A company has a web application that uses Amazon CloudFront to distribute its images, videos, and other static content stored in its Amazon S3 bucket to users around the world. The company has recently introduced a new member-only access feature for some of its high-quality media files. There is a requirement to provide access to multiple private media files only to paying subscribers without having to change the current URLs.

Which of the following is the most suitable solution to implement to satisfy this requirement?

- Configure your CloudFront distribution to use Match Viewer as its Origin Protocol Policy which will automatically match the user request. This will allow access to the private content if the request is a paying member and deny it if it is not a member.
- Configure your CloudFront distribution to use Field-Level Encryption to protect your private data and only allow access to members.
- `Use Signed Cookies to control who can access the private files in your CloudFront distribution by modifying your application to determine whether a user should have access to your content. For members, send the required Set-Cookie headers to the viewer which will unlock the content only to them.`
- Create a Signed URL with a custom policy which only allows the members to see the private files.

Yes. We’ve finished **High-Performing Architectures** and now you’re starting **Secure Architectures**. For this question, the key concept is **CloudFront private content**.

### Question 1 — The important concept

There are two ways to restrict CloudFront content:

|             | **Signed URL**             | **Signed Cookie**            |
| ----------- | -------------------------- | ---------------------------- |
| Best for    | Individual/specific file   | Multiple files               |
| Change URL? | Yes                        | **No**                       |
| Example     | `/movie.mp4?signature=...` | Normal URL remains unchanged |
| Typical use | Download one private file  | Subscriber/member area       |

### Your question

The requirements are:

* Private media
* **Multiple files**
* Only paying subscribers
* **Don't change the existing URLs**

That combination screams:

> **Signed Cookies**

### Simple example

Suppose your existing URLs are:

```text
https://example.com/videos/movie.mp4
https://example.com/videos/trailer.mp4
https://example.com/images/premium.jpg
```

A customer logs in and your application verifies:

> "This user is a paying subscriber."

Your application then gives the browser a **CloudFront signed cookie**.

The user can continue requesting:

```text
/videos/movie.mp4
/videos/trailer.mp4
/images/premium.jpg
```

**without changing those URLs.**

CloudFront checks the cookie and says:

```text
Valid signed cookie?
       ↓
      YES → Serve private content
       ↓
       NO → Deny
```

### Exam shortcut 🧠

Remember:

> **One file → Signed URL**
> **Many files → Signed Cookie**
> **Don't change existing URLs → Signed Cookie**

So the answer is:

✅ **Use Signed Cookies to control access to the private files in CloudFront.**

---

### One important distinction

Don't confuse **Field-Level Encryption** with access control.

**Field-Level Encryption** protects sensitive information that users **submit to your application**, such as:

```text
Credit card number
SSN
Personal information
```

It isn't used to decide whether someone can download private CloudFront content.

And **Match Viewer** is about whether CloudFront communicates with the origin using HTTP or HTTPS. It has nothing to do with subscriber authorization.

Bro, no problem 😄. Let's forget the answer for a moment and **understand what the question is actually asking**.

## 1. First understand the problem

Imagine a website:

```text
mywebsite.com
```

It has videos stored in S3:

```text
S3
 ├── movie1.mp4
 ├── movie2.mp4
 ├── movie3.mp4
 └── movie4.mp4
```

CloudFront sits in front:

```text
User → CloudFront → S3
```

Normally, if the S3 objects are publicly accessible, anyone could request:

```text
https://mywebsite.com/movie1.mp4
```

and get the video.

But now the company says:

> "These are **premium videos**. Only users who have paid for membership should see them."

So we need **private content**.

---

# 2. What does "signed" mean?

Think of a **signature as proof of permission**.

Your application checks:

```text
Is Bilal a paying customer?
        ↓
      YES
        ↓
Give Bilal proof/permission
        ↓
CloudFront accepts the request
```

The proof is cryptographically signed.

So:

### Without permission

```text
User → CloudFront → ❌ Access denied
```

### With permission

```text
User → CloudFront
          ↓
    Valid signature?
          ↓
         YES
          ↓
       S3 content
```

That's the basic idea behind **signed URLs and signed cookies**.

---

# 3. So what's the difference?

This is the part you need to remember for the exam.

### Signed URL

The **permission is attached to the URL itself**.

For example, conceptually:

```text
https://example.com/movie.mp4
        + permission/signature
```

So you're basically saying:

> "This particular URL/file can be accessed by this person."

### Signed Cookie

The permission is stored in a **cookie in the user's browser**.

The URL can remain exactly the same:

```text
https://example.com/movie1.mp4
https://example.com/movie2.mp4
https://example.com/movie3.mp4
```

The browser sends the cookie with each request.

So CloudFront sees:

```text
Request
   +
Signed Cookie
   ↓
CloudFront
   ↓
"Okay, this user is authorized."
```

---

# 4. Now look at the question again

The **two extremely important phrases** are:

> **"multiple private media files"**

and

> **"without having to change the current URLs."**

Those two phrases basically give you the answer.

Imagine a subscriber has access to:

```text
/movie1.mp4
/movie2.mp4
/movie3.mp4
/movie4.mp4
/movie5.mp4
```

You don't want to create a special signed URL for every single file.

And you don't want to change the URLs.

So:

### Signed URL ❌

You'd be dealing with URLs containing authorization information.

### Signed Cookie ✅

Give the subscriber a signed cookie once.

Then they can access the multiple authorized files using the **existing URLs**.

---

# 5. Think of it like a cinema 🎬

This analogy makes it easy.

### Signed URL = individual movie ticket

You give someone a ticket specifically for:

> Movie #1

They can enter Movie #1.

---

### Signed Cookie = membership wristband

You give someone a wristband:

> **Premium Member**

Now they can enter:

```text
Movie 1
Movie 2
Movie 3
Movie 4
```

without getting a new ticket/URL every time.

That's why:

> **Multiple files + don't change URLs → Signed Cookies**

---

## 6. What does "unsigned" mean?

You may remember **signed vs unsigned URLs**.

An ordinary/unsigned URL is simply:

```text
https://example.com/movie.mp4
```

There is no CloudFront signature proving that the requester is authorized.

A signed URL is conceptually:

```text
https://example.com/movie.mp4
        + signature
        + expiration
        + policy
```

The exact format isn't important for your SAA exam right now.

The important concept is:

> **Signed = CloudFront can verify that access was authorized.**
