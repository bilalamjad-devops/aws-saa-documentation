6. Question

Category: CSAA – Design Secure Architectures

An online events registration system is hosted in AWS and uses ECS to host its front-end tier and an RDS configured with Multi-AZ for its database tier. What are the events that will make Amazon RDS automatically perform a failover to the standby replica? (Select TWO.)

- `Loss of availability in primary Availability Zone`
- Storage failure on secondary DB instance
- Compute unit failure on secondary DB instance
- `Storage failure on primary`
- In the event of Read Replica failure

Yes bro — this one is actually testing a **very important RDS Multi-AZ concept**.

## 1. First understand the architecture

With RDS **Multi-AZ**, AWS creates:

```text
                RDS Multi-AZ
                     
        AZ-1                    AZ-2
     ┌─────────┐              ┌─────────┐
     │ PRIMARY │──synchronous─│ STANDBY │
     │   DB    │  replication │   DB    │
     └─────────┘              └─────────┘
          ↑
       Application
```

The **primary** handles your application's database traffic.

The **standby** is there mainly for **high availability/failover**.

Important:

> **Standby ≠ Read Replica**

The standby does **not** serve normal read traffic.

---

# 2. What happens when Primary fails?

Suppose:

```text
Primary 💥
   ↓
RDS detects failure
   ↓
Standby becomes Primary
   ↓
Application reconnects
```

AWS automatically performs the failover.

Your application continues using the **same RDS endpoint**. You don't manually change the database hostname.

---

# 3. What does the question ask?

It asks:

> Which failures cause RDS Multi-AZ to automatically fail over to the standby?

The key idea is:

### **Problems with PRIMARY → failover**

### **Problems with STANDBY → normally NO failover**

So remember:

```text
PRIMARY problem
      ↓
FAILOVER
      ↓
STANDBY becomes PRIMARY
```

---

# 4. Let's examine each option

### ✅ Loss of availability in primary AZ

Suppose:

```text
AZ-1
Primary 💥
```

The standby is in another AZ:

```text
AZ-2
Standby ✅
```

RDS automatically fails over.

✅ **Correct**

---

### ❌ Storage failure on secondary DB instance

Secondary = standby.

If the standby has a problem:

```text
Primary ✅
Standby 💥
```

The primary is still working.

There's no reason to switch your production database to a broken standby.

❌ **Incorrect**

---

### ❌ Compute unit failure on secondary

Same logic.

```text
Primary ✅
Standby 💥
```

The primary hasn't failed.

❌ **Incorrect**

---

### ✅ Storage failure on primary

This is a primary database failure:

```text
Primary 💥
   ↓
Failover
   ↓
Standby → Primary
```

✅ **Correct**

---

### ❌ Read Replica failure

This is another important distinction.

A **Read Replica** is different from the Multi-AZ standby.

Read Replica:

```text
Primary
   │
   ├── Read Replica 1
   ├── Read Replica 2
   └── Read Replica 3
```

Its purpose is primarily **read scaling**.

Multi-AZ:

```text
Primary
   │ synchronous replication
   ↓
Standby
```

Its purpose is **high availability/failover**.

So a Read Replica failure doesn't cause the Multi-AZ primary to automatically fail over.

❌ **Incorrect**

---

# 🧠 Very important exam distinction

Memorize this:

| Feature                 | Multi-AZ Standby      | Read Replica                                                     |
| ----------------------- | --------------------- | ---------------------------------------------------------------- |
| Main purpose            | **High availability** | **Read scaling**                                                 |
| Replication             | Synchronous           | Asynchronous                                                     |
| Can serve normal reads? | ❌ No                  | ✅ Yes                                                            |
| Automatic failover?     | ✅ Yes                 | Generally no automatic promotion in the basic read-replica model |
| Different AZ?           | Usually yes           | Can be                                                           |
| Application writes      | Primary               | ❌                                                                |

### Easy memory trick:

> **Multi-AZ = "What if my DB dies?"**

> **Read Replica = "What if I have too many reads?"**

---

# 🎯 For this question

The two answers are:

✅ **Loss of availability in primary Availability Zone**

✅ **Storage failure on primary**

Because both are **primary-side failures** that can trigger automatic Multi-AZ failover.

---

### One more thing for your SAA preparation

Don't memorize the five options individually. Learn this rule:

**RDS Multi-AZ automatically fails over when the PRIMARY becomes unavailable**, such as:

* Primary AZ failure
* Primary network connectivity failure
* Primary compute failure
* Primary storage failure

That rule will help you answer many variations of this question.
