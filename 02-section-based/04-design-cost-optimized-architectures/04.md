4. Question

Category: CSAA – Design Cost-Optimized Architectures

Both historical records and frequently accessed data are stored on an on-premises storage system. The amount of current data is growing at an exponential rate. As the storage’s capacity is nearing its limit, the company’s Solutions Architect has decided to move the historical records to AWS to free up space for the active data.

Which of the following architectures deliver the best solution in terms of cost and operational management?

- Use AWS Storage Gateway to move the historical records from on-premises to AWS. Choose Amazon S3 Glacier Deep Archive to be the destination for the data.
- `Use AWS DataSync to move the historical records from on-premises to AWS. Choose Amazon S3 Glacier Deep Archive to be the destination for the data.`
- Use AWS DataSync to move the historical records from on-premises to AWS. Choose Amazon S3 Standard to be the destination for the data. Modify the S3 lifecycle configuration to move the data from the Standard tier to Amazon S3 Glacier Deep Archive after 30 days.
- Use AWS Storage Gateway to move the historical records from on-premises to AWS. Choose Amazon S3 Glacier to be the destination for the data. Modify the S3 lifecycle configuration to move the data from the Standard tier to Amazon S3 Glacier Deep Archive after 30 days.

Yes — this question is mainly testing **DataSync vs Storage Gateway**, plus choosing the right S3 storage class.

## What is the question asking?

The company has:

```text
On-premises storage
├── Historical data ❄️  ← rarely needed
└── Active data 🔥      ← frequently accessed
```

The on-premises storage is almost full.

They want to:

> **Move the historical/cold data to AWS so that on-premises space becomes available.**

And they want the solution with the **lowest cost and operational management**.

---

# ✅ Correct answer

> **AWS DataSync → S3 Glacier Deep Archive**

The flow is:

```text
On-premises storage
       │
       │ AWS DataSync
       ↓
S3 Glacier Deep Archive
```

### Why?

**DataSync** is designed for moving large amounts of data between:

* On-premises → AWS
* AWS → AWS

It's particularly useful for **migration and bulk data transfer**.

And **Glacier Deep Archive** is designed for:

> Long-term, very rarely accessed data at very low storage cost.

That's exactly what **historical records** represent here.

---

# 🧠 The most important concept: DataSync vs Storage Gateway

This is a common SAA distinction.

### AWS DataSync

Think:

> **"I need to MOVE data."**

```text
ON-PREM
   ↓
DataSync
   ↓
AWS
```

Typical use cases:

* Data migration
* Moving archives to AWS
* Large-scale transfers
* Replication
* Moving file data to S3/EFS/FSx

---

### AWS Storage Gateway

Think:

> **"I want my on-premises applications to KEEP USING cloud storage."**

It provides a bridge between on-premises environments and AWS storage.

For example:

```text
On-prem application
       ↓
Storage Gateway
       ↓
AWS storage
```

It is useful for **hybrid storage** and continued access from on-premises.

---

## 🚨 Exam shortcut

If the question says:

> **"Move/migrate a large amount of existing data from on-premises to AWS"**

Think:

### **DataSync**

If it says:

> **"Maintain on-premises access to cloud-backed storage"**

Think:

### **Storage Gateway**

---

# Why not S3 Standard → Glacier after 30 days?

This option sounds reasonable:

```text
On-prem
 ↓
DataSync
 ↓
S3 Standard
 ↓ 30 days
Glacier Deep Archive
```

But it's unnecessarily complicated.

DataSync can transfer the historical data directly to an appropriate AWS storage destination, so you don't need to:

1. Put it into Standard first
2. Pay Standard storage
3. Wait 30 days
4. Transition it

Instead:

```text
On-prem
   ↓
DataSync
   ↓
Glacier Deep Archive
```

Much simpler.

---

# Why Glacier Deep Archive?

Think about the access frequency:

| Data               | Access pattern        | Storage                  |
| ------------------ | --------------------- | ------------------------ |
| Active data        | Frequently accessed   | S3 Standard              |
| Older data         | Occasionally accessed | IA classes               |
| Historical/archive | Very rarely accessed  | **Glacier Deep Archive** |

The question specifically says **historical records** and the objective is **cost optimization**.

So Deep Archive is the natural choice.

---

# 🎯 Memorize this pair

This is probably the most useful takeaway from Q4:

> **Data migration → DataSync**

> **Hybrid on-prem + AWS storage → Storage Gateway**

And:

> **Long-term archive + extremely rare access + lowest storage cost → S3 Glacier Deep Archive**

So when you see **"move historical data from on-premises to cheap AWS archival storage"**, your answer should almost instantly be:

### **AWS DataSync → S3 Glacier Deep Archive**.

## 🪣 S3 Storage Classes — SAA Cheat Sheet

| Storage class                     | Best use                           | Access frequency | Key idea                            |
| --------------------------------- | ---------------------------------- | ---------------- | ----------------------------------- |
| **S3 Standard**                   | Active/frequently accessed data    | Frequent         | 🟢 Default choice                   |
| **S3 Intelligent-Tiering**        | Access pattern is unknown/changing | Unknown          | 🤖 Automatically optimizes cost     |
| **S3 Standard-IA**                | Backups, older data                | Infrequent       | 💰 Cheaper storage, rapid access    |
| **S3 One Zone-IA**                | Re-creatable/infrequent data       | Infrequent       | 💰 Cheaper, **one AZ**              |
| **S3 Glacier Instant Retrieval**  | Archive but needs immediate access | Rare             | ⚡ Millisecond access                |
| **S3 Glacier Flexible Retrieval** | Archives accessed occasionally     | Rare             | 🐢 Retrieval can take minutes–hours |
| **S3 Glacier Deep Archive**       | Long-term archives                 | Very rare        | 💰 Cheapest S3 storage              |
| **S3 Express One Zone**           | Very high-performance workloads    | Frequent         | 🚀 Single-AZ, very low latency      |

---

## 1. S3 Standard 🟢

Think:

> **"I use this data frequently."**

Examples:

* Website assets
* Active application data
* Frequently accessed documents
* Images/videos being served regularly

```text
Frequently accessed
        ↓
   S3 Standard
```

---

## 2. S3 Intelligent-Tiering 🤖

Think:

> **"I don't know when users will access this data."**

S3 automatically moves objects between access tiers based on access patterns.

Example:

```text
Don't know access pattern
          ↓
 Intelligent-Tiering
          ↓
AWS automatically optimizes
```

### Exam clue:

**"Unknown or unpredictable access pattern"**

➡️ **S3 Intelligent-Tiering**

---

## 3. S3 Standard-IA 💰

IA = **Infrequent Access**

Think:

> **"I don't access it often, but when I do, I need it quickly."**

Examples:

* Backups
* Older documents
* Disaster recovery data

```text
Rarely accessed
      +
Need quick retrieval
      ↓
S3 Standard-IA
```

---

## 4. S3 One Zone-IA ⚠️

Similar to Standard-IA, but data is stored in **one Availability Zone**.

Think:

> **"Infrequently accessed + I can recreate the data if that AZ is lost."**

Examples:

* Secondary backup copies
* Re-creatable data
* Thumbnails
* Temporary data

### Key exam clue:

**"Can be recreated" / "doesn't need multi-AZ resilience"**

➡️ **One Zone-IA**

---

## 5. S3 Glacier Instant Retrieval ⚡

Think:

> **"Archive data, but I need immediate access when required."**

Example:

A medical company archives old medical images but might need to retrieve them immediately.

```text
Rarely accessed
       +
Immediate retrieval
       ↓
Glacier Instant Retrieval
```

---

## 6. S3 Glacier Flexible Retrieval 🧊

Think:

> **"Archive data; I don't need immediate retrieval."**

Retrieval can take **minutes to hours**, depending on the retrieval option.

Examples:

* Long-term backups
* Archives
* Historical data

```text
Rarely accessed
       +
Can wait
       ↓
Glacier Flexible Retrieval
```

---

## 7. S3 Glacier Deep Archive 🥶

Think:

> **"I almost never access this data."**

This is for **very long-term, low-cost archival**.

Examples:

* Regulatory records
* Financial records
* Compliance archives
* 7–10 year backups
* Historical records

```text
Very rarely accessed
          +
Long-term retention
          +
Lowest storage cost
          ↓
Glacier Deep Archive
```

Your Q3 and Q4 are classic examples.

---

# 8. S3 Express One Zone 🚀

This is the one you should recognize separately.

Think:

> **"I need extremely high performance and very low latency."**

It's designed for workloads such as:

* High-performance computing
* Machine learning
* Data analytics
* AI workloads
* Latency-sensitive applications

And **One Zone** is important.

---

# 🧠 The SAA decision tree

When you see an S3 storage question, ask:

### 1️⃣ Is data accessed frequently?

➡️ **S3 Standard**

### 2️⃣ Access pattern is unpredictable?

➡️ **Intelligent-Tiering**

### 3️⃣ Rarely accessed but needs rapid access?

➡️ **Standard-IA**

### 4️⃣ Rarely accessed + data can be recreated?

➡️ **One Zone-IA**

### 5️⃣ Archive + immediate retrieval?

➡️ **Glacier Instant Retrieval**

### 6️⃣ Archive + can wait minutes/hours?

➡️ **Glacier Flexible Retrieval**

### 7️⃣ Long-term archive + almost never accessed + lowest cost?

➡️ **Glacier Deep Archive**

### 8️⃣ Extremely high-performance / low-latency?

➡️ **S3 Express One Zone**

## 🔥 Super-short exam memory trick

```text
ACTIVE
  ↓
S3 Standard
  ↓
UNKNOWN
  ↓
Intelligent-Tiering
  ↓
INFREQUENT
  ↓
Standard-IA
  ↓
INFREQUENT + RECREATABLE
  ↓
One Zone-IA
  ↓
ARCHIVE
  ├── Immediate → Glacier Instant Retrieval
  ├── Can wait   → Glacier Flexible Retrieval
  └── Almost never → Glacier Deep Archive
```

### One more important SAA concept

**Storage class ≠ backup/immutability.**

For example:

> "Keep data for 7 years and nobody can delete it."

Don't automatically answer **Deep Archive**.

You may need:

**S3 Object Lock + Compliance Mode + appropriate storage class/lifecycle.**

That's exactly the distinction you saw in **Question 3**.
