26. Question

Category: CSAA – Design Cost-Optimized Architectures

An e-commerce company plans to optimize its disaster recovery configuration using AWS Cloud to minimize operational disruptions during outages or major system maintenance for its on-premises Microsoft SQL Server-based application. The objective is to achieve a recovery point objective (RPO) of 60 seconds or less and a recovery time objective (RTO) of 1 hour.

Which of the following is the MOST cost-effective solution for this scenario?

- Back up SQL Server to AWS Storage Gateway for hybrid storage and fast disaster recovery. Enable fast snapshot restore in Amazon Elastic Block Store (Amazon EBS).
- On AWS, implement a warm standby using Amazon RDS for SQL Server database and configure AWS Database Migration Service (AWS DMS) with change data capture (CDC) to sync the data from the on-premises application.
- Use Microsoft SQL Server Enterprise with Always On availability groups and set up a multi-site active/active setup between the corporate on-premises application and AWS.
- `Set up a pilot light strategy using AWS Elastic Disaster Recovery (AWS DRS) to replicate the changes of the on-premises application to AWS`

Absolutely. This question is mainly testing **Disaster Recovery (DR) strategies + RPO/RTO + cost**.

### 1. First understand what the company wants

They currently have:

**On-premises**
→ Microsoft SQL Server application

They want AWS to be their **disaster recovery site**.

The requirements are:

* **RPO ≤ 60 seconds** → they can tolerate losing at most about 60 seconds of data.
* **RTO ≤ 1 hour** → after a disaster, the application must be running again within 1 hour.
* **Most cost-effective** → don't keep expensive infrastructure running unnecessarily.

So the real question is:

> **"How can we continuously replicate the on-premises application to AWS, recover it within 1 hour, and keep the DR cost low?"**

---

## 2. RPO vs RTO — very important

Think of a disaster at **10:00 AM**.

### RPO = How much data can I lose?

If:

**RPO = 60 seconds**

and the disaster happens at 10:00:

```text
09:59:00 ───────────── 10:00:00
                         💥 Disaster
```

You should be able to recover data from approximately **9:59 onward**.

So:

> **RPO = acceptable data loss**

---

### RTO = How quickly must I recover?

If:

**RTO = 1 hour**

and disaster happens at 10:00:

```text
10:00 💥 Disaster
       ↓
       ↓ Recovery
       ↓
11:00 ⏰ Application must be running
```

So:

> **RTO = acceptable downtime**

### Easy memory:

**RPO → data**
**RTO → time**

---

# 3. Now look at the four answers

### A. Storage Gateway + EBS snapshot

This is basically:

```text
On-premises SQL
       ↓
Storage Gateway
       ↓
AWS storage
       ↓
Restore
```

The problem is that this is more like **backup/restore**.

You don't have continuous application replication and automated recovery suitable for the requirements.

So ❌.

---

### B. Warm standby with RDS + DMS CDC

This would look like:

```text
On-prem SQL Server
       │
       │ continuous changes
       ↓
     DMS CDC
       │
       ↓
RDS for SQL Server
       │
       │ already running
       ↓
    Failover
```

This can achieve the RPO/RTO.

**But there is a cost problem.**

You must keep the RDS database running as a standby even when there is no disaster.

So you're continuously paying for:

> **running standby infrastructure**

For a company specifically asking for **cost-effective DR**, this isn't the best choice.

❌

---

### C. SQL Server Always On active/active

This would basically keep two environments actively running:

```text
ON-PREMISES          AWS
SQL Server  ←────→  SQL Server
    ACTIVE             ACTIVE
```

Excellent availability.

But expensive.

You're maintaining substantial infrastructure on both sides continuously.

So:

**Technically good → Yes**
**Cost-effective → No**

❌

---

# 4. D. AWS Elastic Disaster Recovery — correct

This is the important one.

AWS Elastic Disaster Recovery (DRS) continuously replicates your on-premises servers to AWS.

Conceptually:

```text
             CONTINUOUS REPLICATION
                    ↓↓↓↓↓
┌────────────────┐       ┌──────────────────────┐
│ On-Premises    │       │ AWS                  │
│                │       │                      │
│ SQL Server     │ ────→ │ DRS staging area     │
│ Application    │       │ Replicated data      │
└────────────────┘       └──────────────────────┘
                                  │
                                  │ Disaster
                                  ↓
                         Launch recovery servers
                                  │
                                  ↓
                              Application
```

The key idea is:

### Normal situation

You **don't need a fully running copy of your application in AWS**.

DRS continuously replicates the server data into AWS using a relatively inexpensive staging architecture.

Therefore:

**Normal operation = relatively low DR cost**

---

### Disaster happens

For example:

```text
On-premises
    💥 DOWN
       ↓
AWS DRS
       ↓
Launch recovery instances
       ↓
Application running
```

That's why it can satisfy the RTO requirement while avoiding the cost of keeping a full warm standby running all the time.

---

# 5. Why DRS is particularly good here

Look at the requirements:

| Requirement                                | DRS |
| ------------------------------------------ | --- |
| On-premises application                    | ✅   |
| Continuous replication                     | ✅   |
| RPO of ≤60 sec                             | ✅   |
| RTO of ≤1 hour                             | ✅   |
| Don't keep full AWS infrastructure running | ✅   |
| Cost-effective DR                          | ✅   |

Therefore:

> **AWS Elastic Disaster Recovery (DRS) is the best answer.**

---

# 6. Very important DR strategy comparison

For SAA/CSAA, memorize this progression:

```text
Cheapest
   ↓
Backup & Restore
   ↓
Pilot Light
   ↓
Warm Standby
   ↓
Active/Active
   ↓
Most expensive
```

### Backup & Restore

```text
Normal:
On-prem ──────── AWS backups

Disaster:
                 Restore everything
```

💰 Cheapest
🐌 Slowest recovery

---

### Pilot Light

```text
Normal:

On-prem
   │
   │ replication
   ↓
AWS
(minimal infrastructure)
```

During disaster:

```text
AWS
 ↓
Scale / launch resources
 ↓
Application
```

💰 Low cost
⚡ Faster than backup/restore

**This question's answer uses this concept with DRS.**

---

### Warm Standby

```text
On-prem
   │
   ↓
AWS
(running smaller version)
```

AWS is already running, but at reduced capacity.

💰 More expensive
⚡ Faster recovery

---

### Active/Active

```text
        ┌── On-prem ACTIVE
Users ──┤
        └── AWS ACTIVE
```

Both environments are fully operational.

💰💰💰 Most expensive
⚡ Very fast recovery

---

# 7. One correction to the question's wording

The question says:

> "Set up a **pilot light strategy** using AWS Elastic Disaster Recovery..."

That's the key clue.

Don't think:

> "DRS = backup"

Instead think:

> **DRS = continuously replicate servers to AWS + launch them when disaster occurs.**

And because the recovery infrastructure isn't fully running all the time, it can be much cheaper than a warm standby.

---

## 🧠 Exam shortcut

When you see:

**On-premises → AWS DR**

and requirements like:

* **RPO seconds/minutes**
* **RTO minutes/hour**
* **cost-effective**
* don't want fully running duplicate infrastructure

Think:

> **AWS Elastic Disaster Recovery (DRS)**

When you see:

**"already running AWS copy"**

think:

> **Warm Standby**

When you see:

**"fully operational copies in both locations"**

think:

> **Active/Active**

When you see:

**"backup and restore is acceptable"**

think:

> **Backup & Restore**

And remember:

**RPO = how much data can I lose?**
**RTO = how long can I be down?**
