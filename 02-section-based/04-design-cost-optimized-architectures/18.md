18. Question

Category: CSAA – Design Cost-Optimized Architectures

A company hosted a web application in an Auto Scaling group of EC2 instances. The IT manager is concerned about the over-provisioning of the resources that can cause higher operating costs. A Solutions Architect has been instructed to create a cost-effective solution without affecting the performance of the application.

Which dynamic scaling policy should be used to satisfy this requirement?

- Use simple scaling.
- Use scheduled scaling.
- `Use target tracking scaling.`
- Use suspend and resume scaling.

Exactly. This question is testing **which Auto Scaling policy should react automatically to changing demand**.

## The answer: Target Tracking Scaling ✅

The problem says:

* Current resources may be **over-provisioned**
* This increases cost
* But performance must not suffer
* Traffic/load can change

So you want:

> **Automatically add/remove EC2 instances based on actual demand.**

Target tracking is designed exactly for this.

### Simple example

Suppose you want average CPU utilization around **50%**:

```text
ASG
Target CPU = 50%

CPU rises to 70%
      ↓
Add EC2 instances
      ↓
CPU moves toward 50%

CPU falls to 20%
      ↓
Remove EC2 instances
      ↓
CPU moves toward 50%
```

So instead of permanently running 10 instances:

```text
Low traffic → 4 instances
Medium traffic → 6 instances
High traffic → 10 instances
```

This helps reduce **over-provisioning** while maintaining performance.

# Know the scaling policies for SAA

This is the part I'd memorize:

| Policy                 | Think about it as                                     | Best use                           |
| ---------------------- | ----------------------------------------------------- | ---------------------------------- |
| **Target Tracking**    | "Keep metric around X"                                | ⭐ General dynamic scaling          |
| **Step Scaling**       | "Scale differently depending on how bad the alarm is" | More granular reaction             |
| **Simple Scaling**     | "Alarm → add/remove fixed amount"                     | Older/simple approach              |
| **Scheduled Scaling**  | "I know when traffic will happen"                     | Predictable traffic                |
| **Predictive Scaling** | "AWS predicts future demand"                          | Predictable recurring patterns     |
| **Suspend/Resume**     | "Pause scaling"                                       | Temporarily stop scaling processes |

---

## 1. Target Tracking ⭐

Think:

> **Maintain a target.**

Example:

> Keep average CPU at 50%.

```text
CPU > target → scale OUT
CPU < target → scale IN
```

This is usually your **first choice** when the question says:

* dynamic demand
* automatically scale
* maintain performance
* avoid over-provisioning
* cost optimization

### Exam clue:

> "Keep CPU utilization at 50%"

→ **Target Tracking**

---

# 2. Step Scaling

Step scaling is more granular.

Imagine:

```text
CPU 50–60% → +1 instance
CPU 60–70% → +2 instances
CPU 70–80% → +3 instances
CPU >80%   → +4 instances
```

The bigger the alarm breach, the bigger the scaling action.

### Exam clue:

> "Scale by different amounts depending on how much the CloudWatch alarm is breached."

→ **Step Scaling**

---

# 3. Simple Scaling

Simple scaling is older and less responsive.

Example:

```text
CPU > 70%
     ↓
CloudWatch alarm
     ↓
Add 2 instances
     ↓
Cooldown
     ↓
Wait before another scaling action
```

The cooldown behavior is the important distinction in questions like this.

---

# 4. Scheduled Scaling

This is when **you already know the traffic pattern**.

Example:

A website gets heavy traffic every day:

```text
08:00 → 10 instances
18:00 → 4 instances
```

You can schedule the scaling actions.

### Exam clue:

> "Traffic predictably increases every weekday at 9 AM."

→ **Scheduled Scaling**

---

# 5. Suspend/Resume

Don't confuse this with scaling up/down.

It's basically:

> **Temporarily pause one or more Auto Scaling processes.**

For example, during maintenance, you might temporarily suspend scaling.

---

# 🧠 The easiest way to distinguish them

Ask:

### "I need to maintain a metric around a target."

→ **Target Tracking** ⭐

### "I need different scaling amounts depending on how severe the problem is."

→ **Step Scaling**

### "I know traffic will increase at a specific time."

→ **Scheduled Scaling**

### "I want to temporarily stop scaling."

→ **Suspend/Resume**

---

### For Q18:

> **Over-provisioning + changing demand + don't affect performance**

= **Target Tracking Scaling** ✅

This is one of those questions where the wording **"cost-effective without affecting performance"** is basically telling you:

**Don't keep unnecessary EC2 capacity running; let Auto Scaling continuously adjust capacity to demand.**
