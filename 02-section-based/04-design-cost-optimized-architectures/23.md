23. Question

Category: CSAA – Design Cost-Optimized Architectures

A company is building an internal application that allows users to upload images. Each upload request must be sent to Amazon Kinesis Data Streams for processing before the pictures are stored in an Amazon S3 bucket.

The application should immediately return a success message to the user after the upload, while the downstream processing is handled asynchronously. The processing typically takes about 5 minutes to complete.

Which solution will enable asynchronous processing from Kinesis to S3 in the most cost-effective way?

- Use a combination of Amazon SQS to queue the requests and then asynchronously process them using On-Demand Amazon EC2 Instances.
- Send data from Kinesis Data Streams to Amazon Data Firehose and configure it to deliver directly to S3.
- Use a combination of AWS Lambda and Step Functions to orchestrate service components and asynchronously process the requests.
- `Use Kinesis Data Streams with AWS Lambda consumers to asynchronously process records and write them to S3.`

Q23 is mainly testing **Kinesis Data Streams + Lambda** and the idea of **asynchronous processing**.

## The requirement

The application should do this:

```text
User uploads image
       ↓
Kinesis Data Streams
       ↓
Return SUCCESS immediately
       ↓
       │
       └─────── asynchronous
                 ↓
              Lambda
                 ↓
                S3
```

The user **doesn't wait 5 minutes**.

Kinesis accepts the record, and the application can immediately respond:

> "Upload successful."

Then Lambda processes the record in the background.

---

## Why Kinesis + Lambda? ⭐

AWS Lambda can consume records from **Kinesis Data Streams** using an event source mapping.

Lambda essentially does:

```text
Kinesis
   ↓
Lambda polls stream
   ↓
Batch records
   ↓
Process
   ↓
Write to S3
```

AWS handles much of the polling, batching, checkpointing, and retry behavior.

And you don't need to manage EC2 servers.

So:

> **Kinesis Data Streams + Lambda = serverless stream processing** ✅

---

# Don't confuse Kinesis Data Streams and Firehose

This is particularly important for SAA.

### Kinesis Data Streams

Think:

> **"I need to process streaming data using my own application logic."**

```text
Producer
   ↓
Kinesis Data Streams
   ↓
Lambda / EC2 / other consumers
   ↓
Processing
```

You have more control over how the data is consumed.

---

### Kinesis Data Firehose

Think:

> **"I want to deliver streaming data into a destination."**

```text
Producer
   ↓
Firehose
   ↓
S3 / Redshift / OpenSearch / etc.
```

Firehose is primarily a **delivery mechanism**.

It handles buffering and delivery for you.

---

# Why not Step Functions?

Step Functions is excellent when you have a **workflow**.

For example:

```text
Lambda
 ↓
Check payment
 ↓
If approved
 ↓
Process order
 ↓
Send notification
 ↓
Update database
```

But Q23 doesn't need a complicated workflow.

It is simply:

```text
Kinesis → process → S3
```

Adding Step Functions would add unnecessary complexity and cost.

---

# Why not EC2 + SQS?

Apart from being more operationally expensive, it violates an important requirement:

> **Every upload must be sent to Kinesis Data Streams.**

So don't replace Kinesis with SQS.

---

# 🧠 Exam shortcut

When you see:

> **Kinesis Data Streams + serverless processing**

Think:

### **Lambda consumer** ⭐

When you see:

> **Streaming data → reliably deliver to S3**

Think:

### **Kinesis Data Firehose**

When you see:

> **Complex workflow / branching / sequencing / approvals**

Think:

### **Step Functions**

And for Q23:

**Kinesis Data Streams → Lambda → S3** ✅
