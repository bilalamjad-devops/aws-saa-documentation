
5. Question

Category: CSAA – Design Cost-Optimized Architectures

A company has established a dedicated network connection from its on-premises data center to AWS Cloud using AWS Direct Connect (DX). The core network services, such as the Domain Name System (DNS) service and Active Directory services, are all hosted on-premises. The company has new AWS accounts that will also require consistent and dedicated access to these network services.

Which of the following can satisfy this requirement with the LEAST amount of operational overhead and in a cost-effective manner?

- Set up a new Direct Connect gateway and integrate it with the existing Direct Connect connection. Configure a VPC peering connection between AWS accounts and associate it with Direct Connect gateway.
- `Create a new Direct Connect gateway and integrate it with the existing Direct Connect connection. Set up a Transit Gateway between AWS accounts and associate it with the Direct Connect gateway.`
- Set up another Direct Connect connection for each and every new AWS account that will be added.
- Create a new AWS VPN CloudHub. Set up a Virtual Private Network (VPN) connection for additional AWS accounts.

Yes, this one is a little more advanced. The key is understanding **Direct Connect Gateway + Transit Gateway**.

## What is the question asking?

The company already has:

```text
On-Premises
   │
   │ Direct Connect
   │
AWS
```

Their important network services are **on-premises**:

* DNS
* Active Directory
* etc.

Now they are creating **multiple new AWS accounts**, and every account needs to access those same on-premises services.

The architect wants:

* dedicated/private connectivity
* consistent access
* low cost
* **least operational overhead**

So the question is basically asking:

> **"How can I connect many AWS VPCs/accounts to the same on-premises network without creating a separate Direct Connect connection for every account?"**

---

# 🧠 The answer: Transit Gateway

The architecture becomes:

```text
                     ┌─── AWS Account A / VPC
                     │
On-Premises ── DX ── DX Gateway ── Transit Gateway ─── AWS Account B / VPC
                     │
                     └─── AWS Account C / VPC
```

So instead of:

```text
On-Prem ── DX ── Account A
On-Prem ── DX ── Account B
On-Prem ── DX ── Account C
On-Prem ── DX ── Account D
```

you have a centralized network:

```text
                    Account A
                       │
                    Account B
                       │
On-Prem ── DX ── DX Gateway ── Transit Gateway
                       │
                    Account C
                       │
                    Account D
```

That's the important idea.

---

# What does Transit Gateway do?

Think of **Transit Gateway (TGW)** as a **central router/hub**.

Instead of connecting every VPC directly to every other network:

```text
VPC A ───── VPC B
  │ \         │
  │  \        │
  │   ───── VPC C
  │
On-Prem
```

you use:

```text
             VPC A
               │
             VPC B
               │
               ▼
        ┌──────────────┐
        │    Transit   │
        │    Gateway   │
        └──────────────┘
          │          │
       VPC C      On-Prem
```

This is called a **hub-and-spoke architecture**.

* **Transit Gateway = hub**
* **VPCs/networks = spokes**

---

# Why Direct Connect Gateway?

You already have a Direct Connect connection to on-premises.

A **Direct Connect Gateway (DXGW)** allows you to connect your Direct Connect connection to multiple VPC/networking resources across AWS.

In this question, the architecture is essentially:

**Direct Connect → Direct Connect Gateway → Transit Gateway → multiple VPCs**

This lets the new AWS accounts reach the on-premises DNS/AD services through the existing dedicated connectivity.

---

# Why not create a new Direct Connect for every account?

Because that's expensive and operationally painful.

Imagine 20 AWS accounts:

```text
20 accounts
   ↓
20 DX connections
```

You would have to manage all those connections.

Instead:

```text
                    ┌── Account 1
                    ├── Account 2
On-Prem ── DX ── TGW├── Account 3
                    ├── Account 4
                    └── Account 5
```

Much easier to manage.

---

# Why not VPC Peering?

This is an important exam trap.

VPC Peering is:

> **VPC-to-VPC connectivity**

It is not the centralized solution you want for connecting many VPCs to on-premises through Direct Connect.

Also remember:

### VPC Peering is NOT transitive.

For example:

```text
VPC A ←→ VPC B
VPC B ←→ VPC C
```

does **not** mean:

```text
VPC A ←→ VPC C
```

You would need another peering connection.

That becomes messy as the number of VPCs grows.

Transit Gateway solves this with a central hub.

---

# What about VPN CloudHub?

VPN uses VPN connectivity over the Internet.

But the question specifically has an existing **dedicated Direct Connect connection** and asks for consistent/dedicated access.

So VPN CloudHub isn't the best fit.

---

# 🎯 SAA memory trick

Whenever you see something like:

> **Many VPCs/accounts + on-premises + centralized connectivity**

Think:

### **Transit Gateway**

And when you see:

> **Existing Direct Connect + multiple VPCs**

Think:

### **Direct Connect Gateway + Transit Gateway**

---

## One important distinction

Don't confuse these three:

| Service                    | Think                                                    |
| -------------------------- | -------------------------------------------------------- |
| **Direct Connect**         | Dedicated private connection between on-premises and AWS |
| **Direct Connect Gateway** | Extend/manage DX connectivity across AWS networks        |
| **Transit Gateway**        | Central hub connecting multiple VPCs and networks        |

So for this question:

**Existing dedicated connection** → Direct Connect
**Multiple AWS accounts/VPCs** → Transit Gateway
**Connect DX to the TGW** → Direct Connect Gateway

### Final answer

> **Create a Direct Connect Gateway and integrate it with the existing Direct Connect connection, then use a Transit Gateway for the AWS accounts and associate it with the Direct Connect Gateway.**

Absolutely. These networking services are confusing because they all sound like **"connect AWS networks together."** The trick is to understand **what each one connects and why you'd choose it**.

# 1. First understand the big picture

Imagine a company has:

```text
                 AWS
        ┌─────────────────────┐
        │ VPC A    VPC B      │
        │   │        │        │
        │ VPC C    VPC D      │
        └─────────────────────┘
                  │
               On-Prem
```

There are several ways to connect these networks:

* **VPC Peering**
* **Transit Gateway**
* **Site-to-Site VPN**
* **VPN CloudHub**
* **Direct Connect**
* **Direct Connect Gateway**

They solve different problems.

---

# 2. VPC Peering

### Simple definition

**VPC Peering = direct private connection between TWO VPCs.**

Think:

> **VPC A ↔ VPC B**

```text
┌──────────┐         ┌──────────┐
│  VPC A   │◄───────►│  VPC B   │
└──────────┘ Peering └──────────┘
```

The traffic stays on the AWS network rather than going over the public Internet.

### Example

You have:

```text
Production VPC
      ↕
   Peering
      ↕
Database VPC
```

You want resources in Production to privately communicate with resources in Database VPC.

Perfect use case.

---

## 🚨 Biggest VPC Peering limitation: NO TRANSITIVE ROUTING

Suppose:

```text
A ↔ B
B ↔ C
```

You might think:

```text
A → B → C
```

should work.

It doesn't.

A cannot automatically communicate with C through B.

Therefore:

```text
A ↔ B
B ↔ C

A ❌ C
```

You would need:

```text
A ↔ B
B ↔ C
A ↔ C
```

This becomes difficult with many VPCs.

### SAA clue

> "Many VPCs need to communicate"

Think **Transit Gateway**, not dozens of peering connections.

---

# 3. Transit Gateway 🚦

Now imagine you have:

```text
VPC A
VPC B
VPC C
VPC D
On-Premises
VPN
Direct Connect
```

Instead of connecting everything individually, create a central hub.

```text
                 VPC A
                   │
                 VPC B
                   │
             ┌────────────┐
             │  Transit   │
             │  Gateway   │
             └────────────┘
               │    │
             VPC C  VPC D
               │
          On-Premises
```

### Simple definition

> **Transit Gateway is a centralized network hub/router for connecting multiple VPCs and on-premises networks.**

It's basically:

**"One central place where my networks connect."**

---

# 4. Why TGW is better than VPC Peering for many VPCs

Imagine 50 VPCs.

With peering, you could end up managing a huge number of connections.

With Transit Gateway:

```text
VPC 1 ──┐
VPC 2 ──┤
VPC 3 ──┤
VPC 4 ──┼── Transit Gateway
VPC 5 ──┤
VPC 6 ──┤
VPC 7 ──┘
```

Each VPC connects to the hub.

This is called:

### Hub-and-spoke architecture

```text
              Spoke
                │
Spoke ─── Hub ─── Spoke
                │
              Spoke
```

**Hub = Transit Gateway**

**Spokes = VPCs/networks**

---

# 5. Transit Gateway can connect more than VPCs

This is important for SAA.

TGW can connect:

* VPCs
* VPN connections
* Direct Connect through Direct Connect Gateway
* Other Transit Gateways in some architectures

So you might have:

```text
                 VPC A
                   │
                 VPC B
                   │
On-Prem ── DX ── DXGW ── TGW
                   │
                 VPC C
                   │
                 VPN
```

This is where Question 5 came from.

---

# 6. Direct Connect

Now let's forget VPC-to-VPC for a moment.

Suppose your company has:

```text
Company Data Center
        │
        │
        │ Direct Connect
        │
        ▼
       AWS
```

### What is Direct Connect?

**AWS Direct Connect = dedicated network connection from your on-premises network to AWS.**

Instead of relying on an Internet-based connection:

```text
On-Prem → Internet → AWS
```

you establish dedicated connectivity:

```text
On-Prem ───────────── AWS
          Direct
          Connect
```

### Why use it?

* predictable network performance
* private connectivity
* consistent bandwidth
* hybrid cloud architecture
* large amounts of data
* enterprise networking

---

# 7. Direct Connect Gateway

This is where people often get confused.

Direct Connect itself gives you connectivity from:

```text
On-Prem → AWS
```

But what if you have **multiple VPCs / AWS Regions / accounts**?

That's where **Direct Connect Gateway (DXGW)** becomes useful.

Think:

> **DXGW = centralized gateway for Direct Connect connectivity to multiple AWS networks.**

Conceptually:

```text
                  VPC A
                    │
On-Prem ── Direct Connect ── DX Gateway
                    │
                  VPC B
                    │
                  VPC C
```

And in the architecture from your previous question:

```text
On-Prem
   │
Direct Connect
   │
Direct Connect Gateway
   │
Transit Gateway
   ├── VPC A
   ├── VPC B
   └── VPC C
```

### Memory trick

**DX = the dedicated connection**

**DXGW = gateway for that DX connectivity**

**TGW = central hub for multiple networks**

---

# 8. Site-to-Site VPN

Now imagine you don't want a dedicated physical connection.

You can create an encrypted VPN tunnel:

```text
On-Prem
   │
   │ encrypted VPN tunnel
   │
 Internet
   │
   ▼
 AWS VPC
```

AWS Site-to-Site VPN creates encrypted IPsec tunnels between your on-premises network and AWS.

### Important:

VPN **uses the Internet as its underlying transport**.

But the traffic is encrypted.

So:

```text
VPN ≠ Direct Connect
```

Direct Connect:

```text
Dedicated connectivity
```

VPN:

```text
Encrypted tunnel over Internet
```

---

# 9. VPN CloudHub

This is a special VPN architecture.

Suppose you have multiple remote offices:

```text
Office A
   │
   VPN
   │
   ├──────── AWS / VPN CloudHub
   │
   VPN
   │
Office B
   │
   VPN
   │
Office C
```

The idea is to connect **multiple geographically distributed networks using VPN connections through a central AWS hub**.

### Think:

> **VPN CloudHub = hub-and-spoke VPN architecture for multiple sites.**

For example:

```text
             Office A
                │
                VPN
                │
Office B ─── VPN CloudHub ─── Office C
                │
                VPN
                │
             AWS VPC
```

# 10. VPC Peering vs Transit Gateway

This is VERY important for SAA.

| Feature             | VPC Peering          | Transit Gateway       |
| ------------------- | -------------------- | --------------------- |
| Connection          | VPC ↔ VPC            | Central hub           |
| Best for            | Small number of VPCs | Many VPCs             |
| Architecture        | Point-to-point       | Hub-and-spoke         |
| Transitive routing  | ❌ No                 | ✅ Through TGW routing |
| Centralized routing | Limited              | ✅                     |
| Complexity at scale | High                 | Lower                 |

### Easy rule

**2 VPCs → VPC Peering can be excellent**

**Many VPCs → Transit Gateway**

---

# 11. Direct Connect vs VPN

Another SAA favorite.

|                | Direct Connect                 | Site-to-Site VPN                 |
| -------------- | ------------------------------ | -------------------------------- |
| Connectivity   | Dedicated                      | Internet-based                   |
| Encryption     | Not automatically encrypted    | Encrypted                        |
| Predictability | High                           | Depends on Internet              |
| Setup          | More involved                  | Faster                           |
| Cost           | Generally higher               | Generally lower                  |
| Common use     | Enterprise hybrid connectivity | Secure/quick hybrid connectivity |

### Exam clue

> "Dedicated connection"

➡️ **Direct Connect**

> "Encrypted connection over the Internet"

➡️ **VPN**

---

# 12. Direct Connect vs Direct Connect Gateway

Don't confuse them.

### Direct Connect

Answers:

> **"How do I connect my on-premises data center to AWS?"**

### Direct Connect Gateway

Answers:

> **"How do I centrally manage/extend my Direct Connect connectivity to supported AWS networks?"**

# 13. Transit Gateway vs Direct Connect Gateway

This is probably the most important distinction from your Q5.

### Direct Connect Gateway

Focus:

> **Direct Connect connectivity**

```text
On-Prem
   │
  DX
   │
 DXGW
```

### Transit Gateway

Focus:

> **Connecting multiple VPCs/networks**

```text
 VPC A
   │
 VPC B ── TGW ── VPC C
   │
 VPC D
```

They can work **together**:

```text
                    VPC A
                      │
                    VPC B
                      │
On-Prem ── DX ── DXGW ── TGW
                      │
                    VPC C
                      │
                    VPC D
```

That's exactly the architecture your Question 5 was testing.

# 🔥 One final architecture to remember

If a company says:

> "We have an on-premises data center, one Direct Connect connection, and 30 AWS VPCs across multiple accounts. We want centralized connectivity with minimal management."

Your brain should immediately produce:

```text
                         AWS Account 1
                              VPC
                               │
                         AWS Account 2
                              VPC
                               │
                         AWS Account 3
                              VPC
                               │
                              TGW
                               │
                              DXGW
                               │
                         Direct Connect
                               │
                         On-Premises
                       ┌───────┴───────┐
                      DNS             AD
```

**DX → dedicated on-prem connection**

**DXGW → Direct Connect gateway**

**TGW → centralized AWS network hub**

**VPC Peering → direct VPC-to-VPC**

**VPN → encrypted Internet-based connection**

**VPN CloudHub → hub-and-spoke VPN for multiple sites**

If you remember just those six relationships, a large portion of the networking questions in this **Design Cost-Optimized Architectures** section becomes much easier.
