27. Question

Category: CSAA – Design Cost-Optimized Architectures

A multinational corporate and investment bank regularly processes steady workloads of accruals, loan interests, and other critical financial calculations every night from 10 PM to 3 AM on their on-premises data center for their corporate clients. Once the process is done, the results are then uploaded to the Oracle General Ledger which means that the processing should not be delayed or interrupted. The CTO has decided to move its IT infrastructure to AWS to save costs. The company needs to reserve compute capacity in a specific Availability Zone to properly run their workloads.

As the Senior Solutions Architect, how can you implement a cost-effective architecture in AWS for their financial system?

- Use Regional Reserved Instances to reserve capacity on a specific Availability Zone and lower the operating cost through its billing discounts.
- Use On-Demand EC2 instances which allows you to pay for the instances that you launch and use by the second. Reserve compute capacity in a specific Availability Zone to avoid any interruption.
- `Use On-Demand Capacity Reservations, which provide compute capacity that is always available on the specified recurring schedule.`
- Use Dedicated Hosts, which provide a physical host that is fully dedicated to running your instances, and bring your existing per-socket, per-core, or per-VM software licenses to reduce costs.

Yes — **this question is a good signal that you should strengthen your EC2 purchasing/capacity concepts**, especially the difference between **On-Demand, Spot, Reserved Instances, Savings Plans, and Capacity Reservations**.

But don't worry: the concepts are actually quite logical once you separate **“How do I pay?”** from **“How do I guarantee capacity?”**

## First: the big picture

Think of EC2 decisions as answering **two different questions**:

### Question 1: How do I get a lower price?

| Option                | Main purpose                           |    Commitment? | Can be interrupted? |
| --------------------- | -------------------------------------- | -------------: | ------------------: |
| **On-Demand**         | Flexible, pay as you use               |              ❌ |                   ❌ |
| **Spot**              | Cheapest spare capacity                |              ❌ |                   ✅ |
| **Reserved Instance** | Discount for predictable usage         | Usually 1/3 yr |                   ❌ |
| **Savings Plans**     | Discount for predictable compute spend |         1/3 yr |                   ❌ |

### Question 2: Do I need guaranteed EC2 capacity?

| Option                   | Guarantees capacity in specific AZ? |
| ------------------------ | ----------------------------------: |
| **On-Demand**            |                                   ❌ |
| **Spot**                 |                                   ❌ |
| **Regional RI**          |                                   ❌ |
| **Zonal RI**             |                                   ✅ |
| **Capacity Reservation** |                                   ✅ |

**This distinction is the key to Question 27.**

---

# 1. On-Demand

Think:

> **“I need an EC2 instance now, but I don't want a commitment.”**

You launch it → use it → pay for usage.

Good for:

* unpredictable workloads
* short-term workloads
* testing
* applications where you don't know future capacity requirements

Example:

> I need 3 EC2 instances today, but I don't know whether I'll need them next month.

Use **On-Demand**.

### Important exam point

On-Demand **does NOT reserve capacity**.

So this statement is wrong:

> "Use On-Demand and reserve compute capacity in an AZ."

On-Demand itself doesn't provide that capacity reservation mechanism.

---

# 2. Spot Instances

Think:

> **“I want the cheapest EC2 possible, and I can tolerate interruption.”**

Spot uses AWS's **unused EC2 capacity**.

You can save substantially compared with On-Demand, but AWS can interrupt the instance.

Your Question 20 was a perfect Spot example.

The video transcoding workload:

* huge backlog
* need extra workers temporarily
* workload can tolerate interruption
* another EC2 can process the video

Therefore:

**Spot = excellent.**

### Spot mental shortcut

> **Interruptible workload → Spot**

Examples:

* batch processing
* video transcoding
* scientific calculations
* CI jobs
* rendering
* temporary workers

Avoid Spot for:

* critical database
* primary production server
* workload that cannot tolerate interruption

---

# 3. Reserved Instances

Think:

> **“I know I will continuously use EC2 for a long time, so give me a discount.”**

Typical commitment:

**1 year or 3 years**

You receive a discount in exchange for committing to usage.

Example:

You know:

> "This application will run 24/7 for the next 3 years."

Then Reserved Instances may make sense.

### Very important

Reserved Instance is primarily a **billing discount mechanism**.

Don't think:

> RI = capacity reservation

That's the trap.

There are different RI scopes:

### Regional RI

Provides discount across the Region, with more flexibility.

### Zonal RI

Provides discount **and capacity reservation in a specific AZ**.

So:

> **Regional RI → discount/flexibility**

> **Zonal RI → discount + capacity reservation**

---

# 4. Capacity Reservation

This is where Question 27 becomes easy.

Think:

> **“I don't want a discount. I want AWS to guarantee that EC2 capacity will be available in this AZ when I need it.”**

That's **Capacity Reservation**.

You specify things such as:

* AZ
* instance type
* number of instances
* platform/OS
* tenancy

AWS reserves that EC2 capacity for you.

### But here's the catch

You pay for the reservation while it is active, even if you aren't actually running instances against it.

So Capacity Reservation is **not automatically a cost-saving mechanism**.

Its primary purpose is:

> **Capacity guarantee**

---

# 5. Question 27

Let's translate the question into simple English.

The bank has a workload:

**Every night:**

```text
10 PM ─────────────── 3 AM
       COMPUTE
```

Only **5 hours per day**.

And they say:

> "We need compute capacity in a specific Availability Zone."

And the processing **cannot be interrupted**.

So identify the requirements:

### Requirement 1

Specific AZ.

➡️ We need **capacity reservation**.

### Requirement 2

Cannot be interrupted.

➡️ **Not Spot**.

### Requirement 3

Only needed during 10 PM–3 AM.

➡️ Don't commit to running EC2 24/7 unnecessarily.

### Requirement 4

Need guaranteed capacity.

➡️ **On-Demand Capacity Reservation**.

Therefore:

**Correct answer = On-Demand Capacity Reservation.**

---

# 6. Why not Spot?

Because Spot can be interrupted.

The question explicitly says:

> processing should not be delayed or interrupted.

So:

```text
Spot
 ↓
Cheap
 ↓
Can be interrupted
 ↓
❌
```

---

# 7. Why not Reserved Instance?

This is a very important distinction.

A Reserved Instance is mainly about getting a **billing discount** for predictable usage.

But the question specifically says:

> reserve compute capacity in a specific Availability Zone.

A **Regional RI** doesn't provide that AZ-specific capacity reservation.

A **Zonal RI** can provide capacity reservation, but the answer specifically proposes **Regional Reserved Instances**, so that option is wrong.

Also, this workload only runs 5 hours/day, making a long-term commitment less attractive.

---

# 8. Why not Dedicated Host?

Dedicated Host means:

> "Give me an entire physical server dedicated to my account."

Useful for things like:

* licensing requirements
* compliance
* dedicated physical hardware requirements

But here?

The bank simply needs EC2 capacity for 5 hours every night.

A Dedicated Host would be massive overkill.

---

# The most important distinction for your SAA exam

Memorize this:

### **Spot**

**Cheap + interruptible**

### **On-Demand**

**Flexible + no long-term commitment**

### **Reserved Instance**

**Long-term predictable usage + discount**

### **Capacity Reservation**

**Guarantee EC2 capacity in an AZ**

### **Savings Plans**

**Long-term predictable compute usage + discount**

---

# One more thing: Capacity Reservation + RI can work together

This is a slightly advanced but important SAA concept.

You can have:

```text
Capacity Reservation
        +
Reserved Instance / Savings Plan
```

Meaning:

**Capacity Reservation** gives you:

> "I have capacity."

And:

**RI/Savings Plan** gives you:

> "I have a billing discount."

So don't think they're mutually exclusive.

# Your EC2 decision tree

When you see an exam question, mentally ask:

```text
Can workload tolerate interruption?
        │
       YES
        ↓
      SPOT
```

If **NO**:

```text
Do I need guaranteed capacity
in a particular AZ?
        │
       YES
        ↓
CAPACITY RESERVATION
```

If **NO**:

```text
Is workload predictable for 1–3 years?
        │
       YES
        ↓
RI / SAVINGS PLAN
```

If **NO**:

```text
ON-DEMAND
```

That's the core logic.
