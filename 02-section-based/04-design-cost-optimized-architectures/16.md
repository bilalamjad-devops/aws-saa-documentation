16. Question

Category: CSAA – Design Cost-Optimized Architectures

A media company is using Amazon EC2, ELB, and S3 for its video-sharing portal for filmmakers. They are using a standard S3 storage class to store all high-quality videos that are frequently accessed only during the first three months of posting.

As a Solutions Architect, what should you do if the company needs to automatically transfer or archive media data from an S3 bucket to Glacier?

- Use a custom shell script that transfers data from the S3 bucket to Glacier
- Use Amazon SQS
- Use Amazon SWF
- `Use Lifecycle Policies`

Yes — **Question 16 is straightforward**, but it's reinforcing a very important S3 concept that will appear repeatedly in SAA.

## What is the question asking?

The videos are:

* Stored in **S3 Standard**
* Frequently accessed only for the **first 3 months**
* After that, they should be moved/archived to **Glacier**
* The transfer should happen **automatically**

The keyword is:

> **automatically**

Therefore:

### ✅ S3 Lifecycle Policy

```text id="z2pjh0"
Video uploaded
      ↓
S3 Standard
      ↓
First 3 months
Frequently accessed
      ↓
Lifecycle Rule
      ↓
Glacier
      ↓
Long-term archive
```

You don't need an EC2 server or custom script.

---

# S3 Lifecycle has two major actions

This is worth memorizing.

### 1. Transition

Move objects to another storage class.

Example:

```text id="f3b8h1"
Day 0
S3 Standard
      ↓
Day 30
S3 Standard-IA
      ↓
Day 90
Glacier
```

This is called a **Transition Action**.

---

### 2. Expiration

Delete objects after a specified period.

Example:

```text id="h1d2r4"
Day 0
S3 Standard
      ↓
Day 30
S3 Standard-IA
      ↓
Day 365
DELETE
```

This is an **Expiration Action**.

---

# 🧠 Very important SAA distinction

When you see:

### "Automatically move S3 objects after X days"

Think:

> **Lifecycle Transition**

When you see:

### "Automatically delete S3 objects after X days"

Think:

> **Lifecycle Expiration**

---

## Why not a shell script?

You could technically write:

```text
EC2/Cron
   ↓
Shell script
   ↓
Move S3 data
```

But that's unnecessary infrastructure.

AWS already provides the managed feature:

> **S3 Lifecycle**

Less:

* code
* maintenance
* infrastructure
* operational overhead

And therefore generally the better architectural answer.

---

## Why not SQS?

SQS is a **message queue**.

```text
Producer → SQS → Consumer
```

It is used to decouple applications.

It isn't an S3 archival mechanism.

---

## Why not SWF?

AWS SWF is a workflow/orchestration service and is not the appropriate tool for a simple S3 storage-class transition.

For this requirement:

> **S3 itself already knows how to do it.**

---

# 🔥 Connect Questions 1, 9 and 16

You've now seen the same underlying concept several times:

### Q1

"Move obsolete S3 data to cheaper storage."

→ **Lifecycle Transition**

### Q9

"Delete logs after one month."

→ **Lifecycle Expiration**

### Q16

"Move videos to Glacier after 3 months."

→ **Lifecycle Transition**

So remember:

> **S3 Lifecycle = automatic aging rules for objects.**

**Move → Transition**
**Delete → Expiration**
