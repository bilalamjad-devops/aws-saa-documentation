6. Question

Category: CSAA – Design Cost-Optimized Architectures

A company has several EC2 Reserved Instances in their account that need to be decommissioned and shut down since they are no longer used by the development team. However, the data is still required by the audit team for compliance purposes.

Which of the following steps can be taken in this scenario? (Select TWO.)

- `You can opt to sell these EC2 instances on the AWS Reserved Instance Marketplace`
- Convert the EC2 instance to On-Demand instances
- Stop all the running EC2 instances.
- Convert the EC2 instances to Spot instances with a persistent Spot request type.
- `Take snapshots of the EBS volumes and terminate the EC2 instances.`

Yes. This question is mainly testing **Reserved Instances + EBS snapshots + what to do when compute is no longer needed but data must be retained**.

## 1. What is the question saying?

The company has some **EC2 Reserved Instances (RIs)** that the development team no longer needs.

So:

> **We don't need these EC2 servers anymore.**

But:

> **The audit team still needs the data for compliance.**

So we have two separate things:

```text
EC2 compute → No longer needed ❌
Data        → Still needed ✅
```

The solution should therefore:

1. Get rid of unnecessary compute costs.
2. Preserve the data for the audit team.

---

# 2. Why take an EBS snapshot?

An EC2 instance normally has EBS volumes attached:

```text
EC2
 │
 ├── EBS volume
 │      └── Application/data
 │
 └── EBS volume
```

Before terminating the instance, you can create a snapshot:

```text
EBS Volume
     │
     ▼
EBS Snapshot
     │
     ▼
EC2 terminated
```

The snapshot preserves the data.

Later, if the audit team needs it, you can use the snapshot to create a new EBS volume.

### Important distinction

**Snapshot ≠ EC2 instance**

The snapshot is a backup/copy of the EBS volume.

So you can safely terminate the compute while preserving the data.

---

# 3. Why sell the Reserved Instance?

This is the other correct answer.

A **Reserved Instance isn't really a physical EC2 server that you sell**.

It's essentially a **billing/discount commitment** associated with eligible EC2 usage.

If the company purchased a **Standard Reserved Instance** and no longer needs it, AWS provides the **Reserved Instance Marketplace**, where eligible unused Standard RIs can potentially be sold.

Conceptually:

```text
Company
   │
   │ no longer needs RI
   ▼
Reserved Instance Marketplace
   │
   ▼
Another AWS customer
```

So instead of simply letting an unused RI commitment go to waste, the company may be able to sell it.

---

# 4. Why "Stop the instance" is wrong

This is an important exam distinction.

If you stop an EC2 instance:

```text
Running
   ↓
Stopped
```

You stop paying for the **instance compute**, but you still pay for things such as the attached EBS storage.

And the question says the instances need to be **decommissioned and shut down**.

So the better approach is:

```text
Snapshot EBS
     ↓
Terminate EC2
```

Now the compute resource is gone, while the data remains in the snapshot.

---

# 5. Why not convert to On-Demand?

That makes no sense here.

The development team doesn't need the instance anymore.

Converting:

```text
Reserved → On-Demand
```

still leaves the EC2 instance running and generating compute charges.

The requirement is essentially:

> **"We don't need the server anymore."**

So don't change the pricing model. **Remove the server.**

---

# 6. Why not Spot?

Same basic reason.

Spot is cheaper compute, but the question doesn't say:

> "We still need these servers but want cheaper compute."

It says:

> **"We don't need these servers anymore."**

So switching to Spot doesn't solve the problem.

---

# 🧠 The important pattern

Whenever you see:

> **EC2 no longer needed + data still required**

Think:

```text
              EC2
               │
        ┌──────┴──────┐
        │             │
     Compute         Data
        │             │
   No longer       Still needed
     needed
        │             │
   Terminate       Snapshot
```

And because this question specifically mentions **Reserved Instances**:

```text
Unused Standard RI
       ↓
Reserved Instance Marketplace
       ↓
Potentially sell it
```

Therefore the two answers are:

✅ **Sell the eligible Reserved Instance through the Reserved Instance Marketplace**

✅ **Take EBS snapshots and terminate the EC2 instances**

---

### One correction to keep in mind for your SAA studies

The question's wording says **"sell these EC2 instances on the AWS Reserved Instance Marketplace."** Technically, you are selling the **Reserved Instance commitment**, not the actual EC2 instance.

That distinction is useful because AWS has several different concepts:

* **EC2 instance** → the compute resource
* **EBS volume** → persistent block storage
* **EBS snapshot** → backup of an EBS volume
* **Reserved Instance** → pricing/usage commitment
* **Reserved Instance Marketplace** → place where eligible Standard RIs can be sold

That vocabulary will help you avoid traps in the Cost-Optimized section.

# EC2 Purchasing Options — Quick Revision

| Option                    | Price | Commitment              | Best for                                       |
| ------------------------- | ----- | ----------------------- | ---------------------------------------------- |
| **On-Demand**             | $$$   | None                    | Short/unpredictable workloads                  |
| **Reserved Instances**    | $$    | 1 or 3 years            | Steady, predictable workloads                  |
| **Savings Plans**         | $$    | 1 or 3 years            | Predictable compute spending, more flexibility |
| **Spot Instances**        | $     | No long-term commitment | Fault-tolerant / interruptible workloads       |
| **Dedicated Hosts**       | $$$$  | Optional                | Dedicated physical server / licensing          |
| **Dedicated Instances**   | $$$   | None                    | Hardware isolation from other customers        |
| **Capacity Reservations** | $$$   | No term                 | Guarantee EC2 capacity in an AZ                |

# 1. On-Demand Instances

### Think:

> **Pay as you go.**

```text
Start EC2 → Pay
Stop/terminate → Stop compute charges
```

No 1-year or 3-year commitment.

### Best when:

* Workload is unpredictable
* Short-term application
* You don't know how long you'll need it
* Cannot tolerate interruption

### SAA clue:

> "No commitment"

➡️ **On-Demand**

---

# 2. Reserved Instances (RI)

### Think:

> **I know I'll need this EC2 capacity for a long time.**

Typically:

**1 year or 3 years**

You get a significant discount compared with On-Demand.

Example:

```text
Company knows:
"We will run this workload continuously for 3 years."

        ↓

Reserved Instance
```

### Best for:

* Stable workloads
* Predictable usage
* Long-term applications
* Databases that run continuously

---

## Important RI types

### Standard RI

* Largest discount
* Less flexible
* Can potentially be sold through **Reserved Instance Marketplace**

### Convertible RI

* Lower discount than Standard
* More flexible
* Can exchange for another configuration

### Memory trick

> **Standard = more savings, less flexibility**

> **Convertible = more flexibility, less savings**

---

# 3. Savings Plans

This is another important SAA topic.

Think:

> **"I commit to spending a certain amount on compute, but I want more flexibility than an RI."**

For example:

```text
Commit to:
$10/hour of compute usage
for 1 or 3 years
```

In return, you get discounted rates.

### Why Savings Plans?

Suppose today you use:

```text
m6i
```

Later you move to:

```text
c7i
```

A Savings Plan can provide more flexibility than a traditional Standard RI.

---

## Two major types

### Compute Savings Plans

Most flexible.

Can apply across:

* EC2
* Fargate
* Lambda

### EC2 Instance Savings Plans

Less flexible but potentially better discount.

Applies to a specific EC2 instance family in a Region.

### Exam shortcut

**Need maximum flexibility → Compute Savings Plan**

---

# 4. Spot Instances ⭐

This one is VERY important.

Think:

> **AWS has unused EC2 capacity → you use it cheaply → AWS can take it back.**

```text
AWS unused capacity
       ↓
   Spot Instance
       ↓
Huge discount
       ↓
AWS needs capacity
       ↓
Instance can be interrupted
```

You can get very large discounts compared with On-Demand.

### Best for:

Workloads that can tolerate interruption:

* Batch processing
* Big data
* CI/CD workers
* Stateless applications
* Flexible workloads
* Distributed processing

### NOT ideal for:

❌ Critical database

❌ Single important server

❌ Workload that cannot tolerate interruption

---

# 5. Dedicated Hosts

This is about **physical hardware**.

You get an entire physical server dedicated to you.

Think:

```text
Physical AWS server
┌──────────────────────┐
│ YOUR organization    │
│                      │
│ EC2 instances        │
└──────────────────────┘
```

Useful when you have:

* Certain licensing requirements
* Compliance requirements
* Need visibility/control over physical server

### SAA clue:

> "Existing server-bound software license"

➡️ **Dedicated Hosts**

---

# 6. Dedicated Instances

These also provide hardware-level isolation from other AWS customers.

But there is an important distinction:

### Dedicated Instance

You get instances running on hardware dedicated to your AWS account.

### Dedicated Host

You get an entire physical server and have visibility/control over the physical host.

For SAA:

> **Need control over physical host → Dedicated Host**

---

# 7. Capacity Reservations

This one is commonly confused with Reserved Instances.

### Capacity Reservation

Means:

> **"I need AWS to guarantee EC2 capacity for me in this Availability Zone."**

Example:

```text
AZ-A

I need:
10 × EC2 instances

       ↓

Capacity Reservation
       ↓
Capacity guaranteed
```

It is about **capacity**, not primarily getting a discount.

---

# 🚨 Reserved Instance vs Capacity Reservation

Very important:

### Reserved Instance

Think:

> 💰 **Discount**

### Capacity Reservation

Think:

> 🏠 **Guaranteed capacity**

You can even use them together in appropriate scenarios.
